## 1. 业务承诺

会话组织历史；执行负责一次启动、运行和结束；客户端连接观察执行。
归档 round 可以跨越多次执行，不能充当停止某次执行的身份。

| 承诺 | 可验证的结果 |
| --- | --- |
| 接受明确 | 从占用会话开始就有可取消的执行责任；启动失败或被停止后不会留下稍后重新占用会话的任务。送达结果未知时不自动重发给 CLI。 |
| 归属明确 | 只有当前执行及其适配器实例能提交当前执行的事件；过期启动、停止、终态不会改写下一次执行的状态、正文或台账。 |
| 停止明确 | 停止请求与停止完成分开；启动阶段也能停止。结束前处理所属任务与进程，无法确认关闭时保留可操作错误及执行责任。 |
| 观察可恢复 | 同一 Client 经断线或 daemon 重启后，以新快照和对应游标恢复；重同步失败会再次尝试；旧订阅回调不能改写新订阅。 |
| 内容可恢复 | 正常退出保存已接收正文；进行中输出即使随后静默也有定时检查点；完成记录持久化成功后才删除检查点，恢复不得重复追加同一条正文。 |

现有 `session.send` 回复继续表示其既有交接结果。本轮不增加自动重试、自动续跑或外部工具副作用
的 exactly-once 承诺。明确重试是一条新的用户命令；结果未知时应先读取会话当前事实。

## 2. 基线上的具体缺口

1. `send` 的超时只结束等待；启动期间未安装到 `Live.agent` 的资源尚无统一取消入口。
   ACP 初始化前启动的后台任务可持有进程，`interrupt` 此时又找不到 agent。
2. 停止升级在外部等待后继续修改当前会话；围栏用 round 身份，覆盖不到同一 round 内的下一次执行。
3. 泵先 apply 终态，之后才在 `settle_round` 核验 turn；拒绝台账结算并没有拒绝状态变更与发布。
4. Client 对 reset 快照没有同步重置游标；重同步失败还会提前清掉待恢复标记。
5. 进行中保存依靠下一条事件触发，最后一批输出可能长期不落盘；chat 追加只 flush，随后就删除
   已 fsync 的检查点；写入失败时也会先取走待保存条目。

这些是代码边界上的待验证缺口。只有失败 run 或能检查的生命周期不变量支撑对应结论；
既有压力用例通过、没有复现某个猜测，均不扩大解释为所有交错安全。

## 3. 最小职责调整

### 3.1 一处管理执行归属

在每个 Live 内集中管理当前执行身份、启动/运行/停止阶段及取消责任。新请求与授权后的继续执行
使用同一套领取和结束规则。状态转换在同一串行边界内完成检查与改写；CLI 等待在边界外进行，
返回后重新按原执行身份提交结果。旧 round 台账继续承担归档职责。

终态、事件通道关闭、启动失败、停止升级和关闭会话共享结束入口。该入口负责一次性的状态、
台账、正文提交及发布；过期事件在进入这些副作用之前拒绝。逐步删除各路径独立写 Idle/Failed
和自行 flush 的分支。与会话执行无关的标题、选项和历史查询继续使用原有接口。

取消责任覆盖尚未完成 initialize 的启动任务。适配器持有其后台任务与进程的清理责任，原生
及 WASI 路径都需成立。停止使用执行身份，保留同一逻辑 round 继续运行的产品能力。

### 3.2 快照与游标共同恢复

初次订阅、缺口恢复和重新连接共用快照接纳规则：接纳快照时同步接纳它的 seq，reset 允许游标
降低；服务端识别超出当前序列范围的旧游标。客户端串行处理恢复结果，保留失败后的恢复需求，
以订阅及连接身份拒绝已失效的异步回复。快照应用后，旧 replay 状态不能覆盖快照中的较新状态。

优先复用已有 snapshot/seq/reset 契约。只有现有字段无法消除歧义时才扩展协议，并补混合版本
验证。快照描述当前事实，事件负责递送变化；连接退出不会取消执行。

### 3.3 明确保存的提交顺序

保留现有 chat/trunk 格式和 open-turn 检查点。用受执行生命周期管理的定时触发保存最后一批
输出；终态和退出先停止相关写入并等待完成，再做最终保存。chat 记录达到持久性边界后才清理
检查点。失败时保留待保存数据并给出错误，下一次执行不能覆盖尚未恢复的检查点。

进程崩溃恢复与机器掉电的保证分开记录。SIGKILL 测试不作为掉电持久性证据；文件提交顺序另做
代码和文件系统边界审查。恢复已有历史沿用当前语义，未完成执行不会自动重跑外部工具。

## 5. 范围与方案门

实现模式为 guest-only：daemon/adapter 与公共 Client；使用已有 host 进程能力，不扩展 WIT 或安装
协议。若实际复现证明必须改 host，先更新此声明并增加相应原生验证。

资产与执行留在资源机器；本机和远程 Client 使用同一协议。内核不按 agent 名称分支。第二种
执行形状为内置 stdio Agent 与 OpenCode HTTP/SSE；共享规则必须支持现有适配器差异。

外来事件仍经适配器归一化，受已有协议形状与体积限制；执行身份在内核入口核验。日志记录执行
关联、取消阶段、过期结果及保存错误，不记录模型凭证或完整提示词。

本轮范围不含静默判死、分布式工作流平台、通用事件溯源日志、自动重放工具副作用、跨升级无缝
续跑、诊断容量策略重做或无关测试迁移。

## 6. 本轮落地与判定

本轮把执行领取收敛到 `claim_execution`，终态提交收敛到 `finish_execution`，进程退役经过
`retire_execution`。启动阶段即持有取消责任；适配器拥有其读写后台任务；泵通过停止信号排空
原始详情和 blob 写入后退出。归档 round 与一次执行的身份分开，CLI 的等待不占用执行状态锁。
正文保存失败保留待提交条目，下一次发送先重试保存。Client 接纳快照时接纳其游标，每次重新
连接要求完整快照，以覆盖新旧 daemon 序号范围重叠的情形。

这些改动保留已有协议和存储布局，也保留正常完成后的适配器复用。取消、失败后的实例被退役，
之后按已有会话恢复能力启动新的实例。已有全局启动串行门保留：它针对实际存在的 CLI 共享
初始化资源冲突，与按静默时长判断任务死亡是不同的需求。

源码行数并未减少。复杂度的减少体现在结束职责合并：生产代码中的五处 `flush_turn` 调用收敛
到两个职责（三个调用点：领取前重试、结束提交）。本轮没有把全部 Live 字段重写成另一套框架，
不能据此宣称所有状态的组合都已形式化或穷举。

### 6.1 为什么原来反复迭代

业务对象可以简化为会话、执行、连接，但它们的结束时间不同。原实现让 round、适配器实例、
后台任务、前端状态和磁盘提交各自判断结束，修一处并不自动修复其他边界。典型例子是停止命令
返回不代表进程退出，进程退出不代表详情写完，事件发布有序不代表快照游标一致。

原提案在可复现不变量尚不明确时，先组织了 M1–M6 的整套架构与“不可拆”论证；之后用新增故障
点推动局部补丁。有效的进程树清理、原子事件发布、轮次围栏和进行中检查点应保留；按静默判死、
未证实需求的强制架构捆绑、为本地会话引入通用工作流引擎没有对应收益。本轮从已合入主干的新
分支推进，是为了分清基线与新证据，不是撤销已经有效的修复。

测试数量也不是完备性的近似值。两条旧控制面用例把“已有停止请求卡住”作为前提，全部请求
正常返回时反而 blocked；另一个旧用例把取消后复用原进程当作要求。这些前提已改成外部 CLI
不再读取 stdin、下一次执行确实活着等独立事实。首次 382 条全部通过之后，审查仍发现泵被
abort 会丢原始推理尾部；新增公开用例先复现，再以排空并等待写入完成修复。

### 6.2 行业内可借鉴的做法

Tokio 将正常关闭分为决定关闭、通知任务、等待任务结束；任务收到取消后仍可先完成文件写入。
本轮泵的停止与排空采用这个原则。[Tokio graceful shutdown](https://tokio.rs/tokio/topics/shutdown)

Erlang/OTP 的 supervisor 负责子任务的启动、停止与退出顺序，也明确指出父任务提前终止可能
留下子任务、相互等待可能死锁。本轮采用资源归属和明确退出顺序；不照搬它的自动重启语义。
[Erlang supervisor](https://www.erlang.org/doc/system/sup_princ.html)

AWS 的幂等 API 实践讨论通过请求身份避免重试造成重复副作用。第三方 CLI 的 send 未提供统一的
副作用去重契约，因此本轮对送达未知保留错误，不自动重放提示词或工具调用。
[AWS Builders' Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

产品候选提交为 `eeceacb7cf08c428fd07caa93198228d85b0643f`，测试提交为 `b7295b058b64d32d0ae95e2943f860b4972cdef8`；
两者分别经修改审查封印。Cloud 无源文件修改，候选仍为基线 SHA。

### 6.4 验收边界

本候选验证了声明的 Linux 真实 host/guest、公开 Client 和受控外部 CLI 场景，交付形态是独立
分支上的验证候选。主干合并、dev 体验部署及发布不属于本轮交付。

- Windows 进程树、WASI 在 Windows 上的文件系统语义，以及真实 `child.wait()` 长期不返回的
  内核故障未获得本轮实机证据；保留清理责任和超时错误不是“进程必已消失”的证明。
- SIGKILL 与正常退出覆盖进程重启。文件内容要求 fsync 成功，目录同步沿用现有尽力而为策略，
  没有进行机器掉电实验，不能声明所有平台掉电零丢失。
- 本轮写入故障针对正文 chat 追加和检查点交接。blob/trunk 的全面写失败恢复仍沿用既有机制，
  其中 trunk 写失败后丢弃内存工作项的旧策略仍需独立处理；强制停止排空测试不覆盖磁盘损坏。
- 九条新增契约及完整 change 门禁不等于穷举所有事件交错，也不替代 merge gate、真实第三方
  服务 canary 或 Windows E2E 的执行结果。没有运行的项目仍是未验证。

本轮完成的是可追溯、已验证的生命周期修复候选，旧提案“系统性解决”的全量验收不因此自动通过。
