## 先回答三个问题

1. **现在的影响是什么。** 判断团队工作质量只能靠人读会话。今天上午那次三队核查用了 61 次工具调用，结论里仍写着"首次采用率、返工率及完整分工成本缺事件覆盖，不能可靠计算"。三队里只有 XWorld 两队有自己写的评分脚本，tikistar 没有任何过程记录，各队口径不同，无法比较。发布之后也答不出"这次发布有没有让团队工作更顺"。
2. **怎么解决。** 评估做进团队工作流样板，由团队定时自评，反思岗位据此改进本队。以"一张支持单的一生"为统一模型，定义 5 条红线和 6 项主指标，全部由脚本从账本和会话历史计算，不调用模型。主指标按固定锚点换算成基础分，再按触发的红线每类扣 50 分，得到 0 至 100 的综合分。评估器以公开基类实现，项目可以继承扩展自己的红线和指标，升级样板时不冲突。每一分失分标明是本队能改的，还是要上报平台（样板脚本或平台接口）的。平台开发侧读取多个团队的分数卡和上报，改进平台。
   - **已完成**：只读的事实原型和评分原型已在三队真实账本上跑通，首批数字和分数见第 3.5 节。三队今天都有红线触发：XWorld 和 5a 综合分为 0，tikistar 不超过 50。
   - **待实施**：样板增加过程事件日志、评估器基类和每小时自评，反思岗位读分数卡；平台补三项通用事实；平台开发侧的观察者 Skill（见配套提案）。
   - **今天算不出**：采用与返工、成本归集、失败归因。对应的记录还不存在，本文说明各自需要补什么。
3. **怎么防止问题复发。** 近三周主干修过的每一类协作缺陷，都对应一项会变差的指标（第 3.4 节）。每类缺陷配一个固定的账本夹具，指标必须能检出。发布验收增加"三队分数卡前后对比"，触发的红线类数或实例数上升即记为回归。

## 1. 摘要与建议

**团队工作质量的定义**：团队把一个目标变成被采用的结果的过程中，接力是否不丢、不等、不重做，是否少占用人，花费是否值得。它评的是过程；画面好不好、玩法过不过关属于成果质量，两者并列汇报，互不替代。

主要建议有五条：

1. **以支持单为统计单位**，量它从派出到被采用的每一步，而不是量会话数、并行路数或工具次数。
2. **收束为一个综合分**（第 5.8 节）。综合分 = 基础分 − 50 × 触发的红线类数，最低为 0。基础分由 6 项主指标按固定锚点插值后加权得到：值达到及格线得 60，达到预期得 80，部分超出得 90，全面超出得 100。XWorld 的加权分之所以失效，是因为维度靠主观判定、缺数据时自动重分权重、不区分噪声（第 3.2 节）。新模型只用脚本算出的事实，锚点按版本固定，缺数据就标为暂定分，变化必须超过噪声区间才算数。
3. **评估归团队**（第 5.10 节）。评估器是样板脚本的一部分，以 `genet_builtin.api` 的公开基类实现，与现有的工作流、资源、反思策略类同一套扩展方式。团队定时出分，反思岗位读分数卡改进本队。项目在自己的业务包里继承扩展，可以增加红线和指标、调整样板默认值；样板升级只替换内置包，项目扩展不需要三方合并。
4. **平台做两件事**。一是提供任何多会话用法都需要的通用事实，例如回合错误码和轮次用量，daemon 仍然不解释团队状态。二是平台开发侧作为观察者，读取多个团队的分数卡和上报：接口不足或摩擦大就改平台，样板脚本有公共问题就改样板脚本，团队自己的问题没被团队发现或改好，就改内置 Skill 和反思流程，让团队能自己改（见配套提案）。失分账单的归属（第 5.9 节）就是这两条通道的分界。
5. **Agent 不填表**。事件由脚本在它本来就执行动作的位置写入。新增的 Agent 输入只有两个可选参数：派重做单时的 `--follows`，和标记常驻支持的 `--standing`。

需要评审决定的事项在第 9 节，其中 D1 至 D3 决定 P1 和 P2 能否开工，D5 至 D7 决定评分模型的初版，D8、D9 决定评估器在样板里的结构。

## 2. 背景与用户场景

### 2.1 必要概念

| 名称 | 含义 |
| --- | --- |

### 3.2 三支团队已有的尝试

| 团队 | 现有手段 | 状态 |
| --- | --- | --- |
| XWorld、XWorld-5a | `tools/health/team_score.py`（627 行，11-05 至 11-09 迭代三版）；团队自己给工作流打的过程事件补丁；11-09 的五项核心指标讨论稿 | 评分脚本在用但"不作团队排名"；讨论稿明确"尚未实现" |
| tikistar | 无事件日志、无评分。11-10 靠独立 QA 人工读原生轮次，证明"原负责人确实读了结果并发起了下一步" | 一次性人工取证 |

XWorld 的尝试方向正确，下面六点说明它为什么还是初步的。

1. **加权总分区分不出真实差异。** 实验 3 中三个副本同一需求同一预算，修正后的过程分为 7.2、7.3、7.1。实际进度却是：一个 87 分钟接进成品，一个到截止仍未合入。同配置两次运行的首次派单时间相差 15 分钟以上，噪声大于变量带来的差异。问题不在"有总分"，而在总分的构成：八个维度里速度、并行这类量更多反映任务难度和调度偏好，而不是接力是否可靠；断档没有一票否决，被其他维度的高分平均掉了；缺数据的维度自动重分权重；分数没有噪声区间。第 5.8 节的模型逐条针对这四点。
2. **"采用"用的是代理。** 脚本把"Owner 下一轮开始"当作采用，它自己的说明写着"不能证明已实际采用结果"。
3. **事件不能可靠关联。** 事件不带 `operationId`；事件种类中途改过名；盘上 `result-delivered` 有 2979 条，而 `result-ready` 只有约 450 条。
4. **读取成本高、常不完整。** 脚本逐会话调用 CLI，45 秒预算用完即标未知。11-10 07:41 的评分卡因 13 张创建回执待核，过程分为空。
5. **指标被当成了调度目标。** "10 路并行"写进了巡检，每分钟催办。原型测算显示，XWorld 24 小时内 104 次容量唤醒中，只有 58 次（55.8%）在 10 分钟内带来新派单。
6. **只在本队成立。** XWorld 把结果回传从"同批合并"改成了"每单独立"，与官方样板不同，交接时间无法与其他团队直接比较。

讨论稿提出的五项指标（转化与返工、流转延迟、并行与空档、分工序成本、自主闭环）与本提案的主指标基本一致。本提案补的是三件事：数据放在哪一层、最少要新增哪些记录、怎样验证指标本身可信。

### 3.3 平台今天记录了什么

以下结论来自对主干 `2beda9ed` 和已安装团队的对照，关键位置已抽查。

| 数据 | 写入方 | 今天能提供 | 缺什么 |
| --- | --- | --- | --- |
| 任务账本 `.genethub/team/tasks/` | 官方样板脚本 | Owner、协作者列表、状态、结论及其时间 | 覆盖写快照，没有状态变化历史；没有预算或期限字段 |
| 派单意图 `task-dispatch/` | 官方样板脚本 | 岗位、请求方、创建时间、是否已有会话回执 | 只有一个时间戳 |
| 在途与已结回执 `pending/`、`done/` | 官方样板脚本 | 成员的明确结论及时间、对账观察到的状态 | 没有"结果就绪""已送达"的时间；同一会话再次被续接时会覆盖 |
| 会话轮次 `genet session rounds` | 平台 daemon | 每轮起止时间、结果、由哪条消息开启 | 不含用量和错误码 |
| 回合统计 `turnSummary` | 平台 daemon | 每回合的模型轮次、输入输出 token、模型、工具次数 | 只能逐会话翻页读取；错误码不落盘 |
| 协作摘要 `session-coordination.json` | 样板写、daemon 只读 | 每个会话当前的在途、就绪、未知数量 | 只有当前快照 |
| 过程事件 `events/<taskId>.jsonl` | **XWorld 本地补丁** | 派出、结论、送达、追加输入、唤醒的时刻 | 官方样板和 tikistar 都没有 |

今天完全不存在的结构化记录有六项：处置（采用、返工、废弃）、重做单与原单的关联、结果送达时间、等待原因、失败归因、人工输入的类别。

两处值得注意的事实：

- **用量其实已经在记。** 抽查 XWorld 600 个会话的 2131 个回合，97.1% 有 token 用量，58.4% 有金额。成本算不出来的原因是没有按支持单归集的读取路径。
- **错误码有枚举却没落盘。** 平台有 `TurnErrorCode`（缺凭据、限流、上游、超时、Agent 崩溃、取消、内部），失败时只写进文本日志和内存缓冲，事后无法统计。

| 远程与凭据 | 几分钟耗尽 Hub 票据（429）；临时失败被报成凭据撤销 | 是 | M6 按错误类别 |
| 会话失败后的恢复 | Owner 约 90 秒零工具失败 3 次；六条线同一分钟失败后约 2 小时无人接力 | 是 | M6 异常→续工时长 |

这张表也是验收清单：每一类至少要有一个固定夹具，证明对应指标能检出它。

1. **三队都有账本上挂着、实际没人在做的义务。** 最老的 66 至 83 小时。这类记录会让"在途数"虚高，XWorld 自己的统计里也提到"仅被账本标 active 的事项"。它是今天就能算、也最该先清的红线。
2. **XWorld 当天的过程事实在变好，成果分却在回落。** 前 12 小时与后 12 小时相比，"送达后 30 分钟无新派单"从 30.4% 降到 5.3%，容量唤醒带来派单的比例从 37.0% 升到 70.7%。而它最近几轮成果评审的均分从 7.50（R28）降到 7.25（R33）。过程和成果不一定同向变化，必须分两张卡。
3. **5a 的请求方接续明显更快。** 送达到下一次派单的 P90 是 8.7 分钟，XWorld 是 26.6 分钟。这与 5a 成果分连续上升的观察方向一致，但这只是代理，不能据此断言因果。
4. **tikistar 的工作形态不同。** 它有挂着常驻服务的长期支持，派出到结论最长约 59 小时。有限工作和常驻服务混在一起算分位数没有意义，指标必须能区分二者。

原型的限制：没有读会话历史，所以没有执行时长、token 和成本；"送达→下一次派单"不等于采用；重做和失败原因只能靠文字关键词粗分，文中没有把它们当结论使用。

**按第 5.8 节模型试算的分数。** 评分原型只用上表能算的三个指标：结论→送达 P90、送达→请求方下一次派单 P90（代替送达→读入），以及容量唤醒后 10 分钟内无派单的比例（代替被唤醒却无动作）。后两项是代理量。主指标权重只覆盖 30%，R4、R5 尚无数据，所以下面的分数全部是暂定分，不定级。

读法：

1. **综合分为 0 是真实状态，不是模型过严。** 三队都有成员已空闲、却在账本上挂了几十小时的义务，XWorld 两队还有派单悬空和结果迟到。按平台"结果自动回到发起方"的承诺，这些都是接力断档。
2. **基础分保留了改进的梯度。** 在红线清零之前，团队和平台看基础分和红线实例数的下降来判断方向。XWorld 后 12 小时的基础分比前 12 小时高 27 分，主要来自空转比例从 63.0% 降到 29.3%，以及送达后接续的 P90 从 49.5 分钟降到 16.2 分钟。
3. **最快的提分路径是清 R2。** 三队 R2 实例大多超过 6 小时，属于结算机制没有收口的旧义务，而不是新工作的失败。只清 R2，5a 后 12 小时的综合分就能从 0 变为 33.7；R3 也清零后为 83.7，但仍是暂定分，因为另外 70% 的权重尚无数据。
4. **tikistar 只能给区间。** 它没有事件和送达时间，基础分无从计算；R2 已触发，所以上限是 50。这本身就是样板脚本的一个覆盖缺口：官方样板没有提供可评估的记录。

## 4. 目标与范围

| 目标 | 成功的样子 |
| --- | --- |
| G1 可复现 | 同一份账本快照运行两次，输出逐字节相同；不调用模型。 |
| G2 能检出已知缺陷 | 第 3.4 节每一类缺陷的夹具，都让对应指标发生预期变化。 |
| G3 能用于比较 | 同配置重复运行的指标差异，小于改变一个变量后的差异；达不到的指标标为"仅诊断"。 |
| G4 不增加 Agent 负担 | Agent 新增的必填输入为 0，可选输入不超过 2 个。 |
| G5 不干扰业务 | 事件写入失败不影响派单；评估器只读；事件日志不被任何调度逻辑读取。 |
| G6 综合分可信 | 同一快照算两次分数相同；同配置重复运行的分差落在公布的噪声区间内；第 3.4 节每类缺陷夹具都让分数下降，且失分账单指向正确的层。 |
| G7 失分可行动 | 每个失分项都带归属层、证据位置和对应的指标或红线，能直接成为平台或团队的改进项。 |

**本期不做**：

- 不评成果质量，不替代各项目的质量门禁；工作质量分和成果分并列汇报，不相互折算。
- 不做模型排名。跨团队的综合分只在第 5.5 节的可比条件下比较。
- 不在 daemon 里增加团队调度、团队数据库或新的状态机。
- 不以模型阅读全部会话作为默认评估方式。
- 不处理 XWorld 已指出但主干未改的样板问题（例如完成检查的证据体积），它们另行跟踪。

## 5. 具体方案

### 5.1 统一模型：一张支持单的一生

```text
派出 ──► 确认创建 ──► 开工 ──► 明确结论 ──► 送达请求方 ──► 读入 ──► 处置 ──► 下游
 │          │          │          │             │           │        ├ 采用
 悬空      创建未知    排队       无结论结束     未达/错投    未读     ├ 返工（重做单 --follows 原单）
                                                 /重复                └ 废弃
```

每个箭头有三种可量的东西：这一步丢了多少、花了多久、还有多少停在这一步及其最老年龄。第 3.4 节的每类缺陷都落在其中一个箭头上。

### 5.2 指标体系

**红线：完整性计数，目标为 0。** 它们表示接力断了，不随业务难度变化，可以直接作为门槛。每类触发扣 50 分（第 5.8 节）。阈值为初拟值，需按实际定时周期校准。

| 编号 | 红线 | 判定 | 数据来源 | 今天能算 |
| --- | --- | --- | --- | --- |
| R1 | 派单悬空 | 派出超过 10 分钟仍无会话回执 | 派单意图 | 能 |
| R2 | 未结算义务 | 成员已空闲、无明确结论超过 60 分钟，且未标记为常驻 | 在途回执 | 能（常驻标记尚无） |
| R3 | 结果未达、错投或重复 | 有结论超过 10 分钟未送达；送达对象不是原请求方；同一结果送达超过一次 | 事件 | 仅 XWorld |
| R4 | 无因停摆 | 任务进行中，Owner 空闲、无在途单、无待用户问题、未暂停、未结算，持续超过 15 分钟 | 账本与事件 | 不能 |
| R5 | 资源未归还 | 已有结论的支持单仍持有写锁、租约或进程超过 10 分钟 | 派单意图的释放记录 | 部分 |

R4 的条件就是样板看门狗现有的唤醒条件，不需要新的判断逻辑，只需把它已经算出的结果记下来。

**主指标：带分母的事实。** 按第 5.8 节的锚点换算为基础分，同时看各队自身趋势。

| 编号 | 指标 | 计算 | 数据来源 | 今天能算 |
| --- | --- | --- | --- | --- |
| M1 | 首次采用率与返工率 | 首次处置为采用（或返工）的工作项数 ÷ 已处置的工作项数。待处置、未读入的数量和最老年龄并列显示 | 事件、`--follows`、请求方轮次 | 不能 |
| M2 | 关键流转时间 | 派出→开工、派出→结论、结论→送达、送达→读入、读入→下游，各报中位、P90 和未闭环的最老年龄；有限工作与常驻支持分开。派出→结论只作诊断，不入分 | 账本、事件、请求方轮次 | 前两段部分可算 |
| M3 | 人的占用 | 每任务日：未经询问的人工输入数、人工中断数、提问到应答的等待时长；外部救援次数 | 前台轮次、事件 | 不能 |
| M4 | 单位采用成本 | 一个工作项全部尝试的模型轮次、输出 token、执行时长之和 ÷ 被采用的工作项数；另报协调开销占比 | 回合统计、M1 | 不能 |
| M5 | 空转 | 被唤醒却没有任何账本增量的轮次数、重复触发的反思次数、团队空闲时的模型调用次数，及其占总用量的比例 | 事件、轮次、回合统计 | 不能 |
| M6 | 失败与恢复 | 按错误类别的失败轮次率；从异常到业务续工的时长；由谁恢复；同类是否复发 | 回合错误码、事件 | 不能 |

几点口径说明：

- **M1 的"采用"分三档。** 未读入：请求方没有任何一轮由这条结果开启。暂定采用：已读入，且观察期内没有重做单指向它。返工：有重做单用 `--follows` 指向它。这三档不需要 Agent 表态。Agent 明确表态的处置作为可选记录，标为自报。
- **正确的阻塞不扣分。** 成员如实报告 `blocked`，或 QA 正确判定不通过，都是可用的结果。结论构成只陈列，不折算。
- **M3 不靠语义分类。** 人工消息之前前台有未答的提问，算应答。否则看这条消息开启的那一轮里发生了什么：新建了任务算新目标，不计入；向已有任务追加算追加或纠正；什么都没发生算询问或催促。外部人员替团队修环境属于救援，按平台验证计划的口径"原自主场景应判失败"，需人工登记。
- **M4 不用金额。** 金额覆盖只有约六成。token 里的输入量含缓存读取，累计值不能当账单，所以用模型轮次、输出 token 和非缓存输入分别报告。
- **M5 只数"被唤醒却无动作"。** 由结果开启的轮次可能合理地什么都不做，例如还在等其他结果，这类不计。

**仅作诊断、不评级的量**：并行路数、工具时间占比、每单调用次数、首次派单时间。它们用来解释主指标为什么变差，不能单独说明质量高低。并行尤其如此：XWorld 把它当目标后，四成多的催办没有带来派单。

**下钻项**（按需展开）：派单后的补充输入比例（说明派单时信息不全）、同一写入目录的并发、定时任务单次耗时与连续失败数、远端状态未知占比。

### 5.3 数据：沿用、调整和新增

**沿用**：任务账本、派单意图、在途与已结回执、会话轮次、回合统计。评估器直接读，不改变它们。

**内置样板新增（L1）**。现有账本是覆盖写的快照，没有时间序列，也没有送达时间，所以量不出流转和停摆。新增四项：

1. **过程事件日志** `.genethub/team/events/<taskId>.jsonl`。只追加，由样板脚本在已有动作点写入。它吸收 XWorld 补丁的做法并修正其问题：每条事件带 `operationId`；同一送达只记一次并带消息编号；种类固定。

   ```jsonl
   {"atMs":1794279587761,"kind":"dispatch","operationId":"taskop.830a…","requester":"s_6a03…","role":"map-props","follows":null,"standing":false}
   {"atMs":1794279588102,"kind":"dispatch-confirmed","operationId":"taskop.830a…","sessionId":"s_eacd…"}
   {"atMs":1794280363812,"kind":"conclusion","operationId":"taskop.78d3…","outcome":"success"}
   {"atMs":1794280373378,"kind":"result-delivered","operationId":"taskop.78d3…","to":"s_6a03…","messageId":"x.4e29…"}
   {"atMs":1794280403048,"kind":"wake","target":"s_6a03…","reason":"stall","count":1}
   ```

   完整种类：`task-start`、`dispatch`、`dispatch-confirmed`、`dispatch-rejected`（带原因码）、`conclusion`、`result-delivered`、`input`（带发送方类别）、`tell-user`（是否提问）、`wake`（原因：停摆、反思提醒）、`control`（暂停、恢复、取消、换 Owner）、`reflect-run`（触发原因与处理的留言集合）、`remote-error`（CLI 返回的错误码）、`resource-released`。

2. **`task support --follows <operationId>`**（可选）。Owner 派重做单时指明它接续哪一张。Owner 今天已经在描述里写"重派""再修"，这只是把它变成可关联的字段。一张原始单和所有接续它的单构成一个工作项，不需要另发编号。

3. **`task support --standing`**（可选）。标记常驻服务类支持，使它不计入 R2，也不进入有限工作的分位数。

4. **`tools/run.py quality`**。只读出卡命令，见第 5.4 节；评估器本身的结构见第 5.10 节。

**平台内核新增（L0）**。这三项对任何多会话用法都成立，换掉样板仍然需要，所以属于平台。它们也是路线图里"用量统计页"的前置。

1. **回合统计带错误码。** 把现有 `TurnErrorCode` 写进 `turnSummary`。今天失败后只能读错误文案。
2. **`session rounds` 每行带该轮用量和等待时长。** 用量已在回合统计里，等待时长已在盘上但未输出。
3. **一次读取多个会话的轮次摘要。** XWorld 的脚本逐会话读取，单次查询曾超过 154 秒；团队工具逐会话轮询还触发过 Hub 限流。接口形态留待原型确认。

**团队定义中的项目扩展（L2）**：红线阈值、观察期长度、岗位到工作类型的映射，以及项目自己的红线和指标，按第 5.10 节在项目业务包里扩展。不配置时用样板默认值，映射缺失时只按岗位分组。

### 5.4 评估器的行为（拟议合同）

```bash
python3 tools/run.py quality card [<taskId>] --since <ISO> --until <ISO> [--json] [--save]
python3 tools/run.py quality history [--last N]      # 读本队已保存的分数卡
python3 tools/run.py quality describe               # 实际生效的模型类、红线与指标清单、来源和版本
```

- 输入只有账本、事件日志和会话历史。不调用模型，不写团队状态。`--save` 只向 `datas/quality/cards.jsonl` 追加一行历史。样板的定时任务默认每小时以 `--save` 运行一次。
- 每个数字带分母和样本数。样本少于 20 时不给 P90，只列中位、最大值和样本数。
- 读不到的保持未知，不当作零。分数只能按已知权重计算时，必须标为暂定分并给出可能区间（第 5.8 节）。输出里有覆盖率：

  ```json
  {
    "schema": "team-facts/1",
    "coverage": {"events": "none", "sessionsRead": 0, "sessionsRequested": 163, "usage": "unknown"},
    "redLines": {"danglingDispatch": {"n": 15, "of": 178, "oldestAgeMin": 1164}},
    "conversion": {"firstPassAdopted": null, "reason": "no follows or consumption records in window"}
  }
  ```

- 跨机：派单账本在发起方，所以在团队所在机器运行。远端岗位的会话用量读不到时，该岗位成本记未知并在覆盖率里列出。
- 窗口内已结束的工作和仍未闭环的等待分开报告。未闭环的报当前年龄，不混进已完成的时长样本，也不从卡上消失。

### 5.5 怎样解读和比较

- **先看自身趋势。** 同一团队相邻窗口对比。变化要超过该指标的噪声带才算变化，噪声带由同配置重复运行得出。
- **跨团队只在可比时比较。** 同一目标、同一时间预算、至少三次重复，比较综合分的同时逐项并列主指标。工作形态不同的团队（例如有常驻服务的 tikistar）只比较红线和不依赖工作形态的指标，不比较流转分位数。
- **始终与成果卡并列。** 实验 3 表明过程指标单独判断不了团队好坏。第 3.5 节 XWorld 的例子表明两者可以反向变化。
- **用于发布验收。** 每次 dev 或 Beta 版本被团队机器采用后，取发布前后各 24 小时的分数卡。触发的红线类数不得增加，各类红线实例数不得上升，基础分下降不得超过噪声区间。结果写进发布记录，与"专项测试通过"分开陈述。

### 5.6 防止指标被刷

1. **指标和分数不写进派单约束。** 红线是正确性，可以由脚本提示。流转、转化、成本和综合分只给反思岗位、前台和人看，不变成 Owner 每轮要满足的数字。
2. **核心分口径固定，项目分可以扩展。** 每张卡同时给出两个分数：核心分只用样板的红线、指标和锚点，项目改不了，用于跨团队观察和发布比较；项目分在核心分基础上叠加项目自己的红线、指标和调整，用于本队目标（第 5.10 节）。模型改版时新旧两版并行算一个周期，历史分数不被静默改写。
3. **成对解读。** 流转变快要同时看返工是否上升；并行变高要同时看单位采用成本；向用户提问减少要同时看被用户催问是否增加。
4. **分母和未知必须显示。** 待处置数量与最老年龄和采用率并列，防止只审容易的结果抬高比例。
5. **事件由脚本写，自报单独标记。** Agent 说"已采用""平台原因"是待核事实，不直接进入主指标。
6. **评估不参与调度。** 事件日志不被定时对账读取，避免它变成第二套状态来源。

### 5.7 第二层：由异常触发的抽样审查

拆解是否合理、QA 裁定是否可靠、汇报是否如实，这些判断脚本做不了。它们由反思岗位按现有职责处理，但只审第一层标出的异常，例如返工链超过两次的工作项、被唤醒却无动作的轮次、裁定被后续复评推翻的 QA 单。审查结论按现有留言机制记录，按派单量归一化后报告，不进入第一层的任何数字。

### 5.8 综合评分模型（tq/1，初版待评审）

```text
综合分 = max(0, 基础分 − 50 × K)
基础分 = Σ 权重(Mi) × 指标分(Mi) ÷ Σ 已知指标的权重
K      = 本窗口触发的红线类数，0 至 5
```

| 分数 | 档位 | 在团队工作里意味着什么 |
| --- | --- | --- |
| 低于 60 | 不及格 | 有接力断档，或多数指标低于"人不用盯着也能往前走"的底线。 |
| 60 至 79 | 及格 | 没有红线；工作能自己往前走，但等待、返工或打扰人明显偏多。 |
| 80 至 89 | 比较符合预期 | 达到平台的承诺：结果自动回到发起方，卡住有人接手，只有需要人判断时才找人。 |
| 90 至 99 | 部分超出预期 | 在符合预期的基础上，部分指标明显更好，例如更少返工、更快接续或更低的单位成本。 |
| 100 | 全面超出预期 | 无红线，所有指示量都达到最高锚点。 |

一个直接推论：**触发任何一类红线，综合分最高 50，必然不及格；触发两类即为 0。** 及格的前提是接力不断。

**红线怎么计。**

- **按类扣分，不按实例。** 某类红线在窗口内有至少一个已确认实例即触发，扣 50 分。实例包括窗口内新发生的，以及窗口结束时仍未消除的旧实例；旧债在每个窗口都计，直到清掉。实例数和最老年龄并列显示，用来看红线清理的进展。按实例扣分会让分数长期停在 0，失去梯度，所以不采用。
- **有记录的豁免。** 用户暂停、等待用户决定、标为常驻、被用户取消的工作不计入红线，依据是对应事件。豁免数量单独显示，防止被滥用。
- **判定不了的红线不扣分**，但这时的分数只能是暂定分。

**指标分怎么算。** 每项主指标由 1 至 3 个指示量组成。指示量的值在五个锚点之间线性插值：到达下限为 0，及格线 60，预期 80，部分超出 90，全面超出 100；比下限更差记 0，比最高锚点更好记 100。主指标分取其指示量分数的平均。样本少于 20 的指示量记未知。

| 主指标（权重） | 指示量 | 0 | 60 | 80 | 90 | 100 |
| --- | --- | --- | --- | --- | --- | --- |
| M1 转化（25） | 首次采用率 | 30% | 60% | 75% | 85% | 92% |
| | 返工率 | 50% | 30% | 20% | 12% | 6% |
| M2 流转（20） | 派出→开工 P90 | 60 分 | 20 分 | 10 分 | 5 分 | 2 分 |
| | 结论→送达 P90 | 60 分 | 10 分 | 3 分 | 1.5 分 | 0.5 分 |
| | 送达→读入 P90 | 120 分 | 30 分 | 10 分 | 5 分 | 2 分 |
| M3 人的占用（20） | 每任务日未经询问的人工纠正与催促 | 10 次 | 4 次 | 2 次 | 1 次 | 0 次 |
| M4 成本（15） | 单位采用成本 ÷ 本队同类工作基线 | 2.0 | 1.2 | 1.0 | 0.85 | 0.7 |
| | 协调开销占比 | 60% | 40% | 30% | 22% | 15% |
| M5 空转（10） | 被唤醒却无账本增量的轮次比例 | 50% | 25% | 12% | 6% | 2% |
| M6 失败与恢复（10） | 失败回合率（不含用户取消） | 10% | 4% | 2% | 1% | 0.3% |
| | 异常→业务续工 P90 | 240 分 | 60 分 | 20 分 | 10 分 | 5 分 |

权重和锚点的依据：

- **权重**：M1 对应"不重做"，是把工作变成结果的核心，权重最高。M2 和 M3 分别对应平台承诺里的"接力不等"和"只有需要人判断时才找人"。M5、M6 与成本和红线有部分重叠，权重较低。
- **锚点**：60 取三队当前水平中可以接受的一档，80 取平台文档承诺的行为，90 和 100 取三队目前最好的表现或明确的目标。例如结论→送达 P90，红线是 10 分钟，预期是 3 分钟，5a 今天的 1.0 分钟落在 90 至 100 之间。全部初值都要在 P3 用真实数据校准。
- **派出→结论不入分。** 它主要反映工作本身的大小和难度，接近成果属性，只作诊断。入分的是派出→开工的排队等待。
- **人工救援封顶。** 窗口内发生外部人员替团队修环境或搬运成果的救援时，M3 最高 60，并按平台验证计划的口径记为"原自主场景失败"。

**什么时候能定级。** 同时满足三条：已知指标的权重不少于 80%；五类红线都能判定；窗口内已闭环的工作项不少于 20 个。不满足时输出暂定分和可能区间：未知指标分别按 0 和 100 计，未知红线分别按触发和未触发计，得到下界和上界。暂定分可以看趋势，不能用于定级，也不能在发布验收里作为"变好了"的依据。

**噪声区间。** 对窗口内的工作项有放回地重抽 1000 次，报告 80% 区间。两个分数之差小于 5 分，或小于两个区间半宽之和时，视为没有变化。P3 用同配置重复运行做 A/A 检验：同配置的分差超出区间的指示量降为仅诊断，不再入分，直到口径修正。

**对照 XWorld 加权分失效的四个原因：**

| XWorld 第 1 至第 3 版的问题 | 本模型的做法 |
| --- | --- |
| 速度、并行等维度反映任务难度和调度偏好 | 只用接力事实入分；派出→结论、并行路数只作诊断 |
| 断档被其他维度的高分平均掉 | 红线每类扣 50 分，任何断档都不可能及格 |
| 缺数据时自动重分权重，分数看起来完整 | 允许按已知权重计算，但必须标为暂定分并给出可能区间 |
| 没有噪声区间，7.2 与 7.3 被当作差异 | 报告 80% 区间，A/A 不稳的指示量不入分 |

### 5.9 失分账单与归属

综合分只说明"好不好"，失分账单说明"该谁改什么"。评估在团队里运行，所以账单首先回答团队自己的问题：这一分是本队能改的，还是要上报给平台的。

**失分怎么记。** 每类触发的红线计 50 分。每个指示量的失分 = 该指示量占总分的权重 × (100 − 指示量分数) ÷ 100；暂定分按已知指标的权重换算占比。账单合计等于 100 减去综合分（红线扣分超过基础分时，超出的部分照记，用来显示离及格还有多远）。按"离 80 分的差距 × 权重"排序给出改进优先级。

**每条失分的去向**（字段 `route`）：

| 去向 | 含义 | 谁处理 |
| --- | --- | --- |
| `team` | 本队的岗位、Skill、业务脚本或项目扩展造成的 | 本队反思岗位直接改定义源 |
| `report:template-script` | 发生在样板脚本负责的步骤，且本队没改过这部分 | 反思岗位以留言上报，汇总进反思报告；平台开发侧读取 |
| `report:platform-interface` | 平台接口出错、能力不足或调用摩擦大，例如原因码指向 daemon、CLI 返回平台错误码 | 同上 |
| `external` | 上游模型或网络故障 | 只记录 |
| `pending` | 规则判不了 | 反思岗位按第 5.7 节抽查后改判 |

**团队内的判定规则**（按顺序，能判定就停）：

1. **按原因码。** 上游模型或网络故障记 `external`；daemon 内部错误、Agent 崩溃、协作会话创建结果未知、`dispatch-rejected` 带平台错误码，记 `report:platform-interface`。
2. **按机制位置。** 失分发生在样板脚本负责的步骤（确认创建、结算、送达、释放、看门狗唤醒），用 `run.py drift` 确认本队没改过这部分，记 `report:template-script`；改过，记 `team`。
3. **项目自己的红线和指标**，一律记 `team`。
4. **都判不了**，记 `pending`。`pending` 超过 30% 时，账单只能用于排查。

团队只看得见自己，判断不了"多支团队都有"。跨团队的比较、上报是否属实、团队自己的问题为什么没有被团队发现，由平台开发侧的观察者判断，见[配套提案](team-quality-iteration-skill-proposal-20261110.md)。

**覆盖缺口也有去向。** 算不出的指标不扣分，但列为覆盖缺口：没有过程事件记 `report:template-script`，轮次上没有用量和错误码记 `report:platform-interface`，项目未配置工作类型记 `team`。

**用今天的数据试判**（候选，未经审查）：

| 失分 | 涉及队伍 | 团队卡上的去向 | 观察者的进一步判断 |
| --- | --- | --- | --- |
| R2 未结算义务 | 三队 | `report:template-script`（XWorld 需先用 `drift` 核对结算路径） | 三队同类，像样板结算没有收口的公共问题 |
| R1 派单悬空 | XWorld、5a | 原因码缺失，暂为 `pending` | 与订阅静默丢弃、查询异常当空目录两项主干修复同类，需原因码区分平台创建未知还是样板未确认 |
| R3 结果迟到 | XWorld、5a | `team`：两队用的是 XWorld 本地的逐单回传补丁 | 项目改了公共机制，说明样板的回传语义不够用，或团队不知道应该通过扩展类定制；属于内置 Skill 的引导问题 |

### 5.10 评估器的结构：放在样板里，按公开基类扩展

**为什么放在样板里。** 平台的定位是"换掉样板之后它还成立吗"：红线、指标和分数都以团队的任务账本为对象，换一套团队机制就要换一套量法，所以属于样板，而不是 daemon。样板已经用公开基类让项目定制工作流、资源、反思和看板（`team-core/references/extensions.md`），评估沿用同一套机制，不另起配置文件或插件系统。

**新增的公开基类**（拟议，加入 `genet_builtin.api`）：

| 基类 | 重写点 | 调用边界 |
| --- | --- | --- |
| `QualityModel` | `red_lines()`、`indicators()`、`weights()`、`route(loss, facts)`、`collect(context, facts)` | 定时自评和 `quality` 命令调用；只读，返回分数卡 |
| `RedLine` | `detect(context, facts)` 返回实例列表；`exempt(instance, facts)` | 每类一个子类，带稳定 `id` 和 `version` |
| `Indicator` | `measure(context, facts)` 返回值、样本数和覆盖情况；类属性 `metric`、`anchors`、`lower_is_better`、`min_samples` | 每个指示量一个子类，带稳定 `id` 和 `version` |
| `QualityFacts` | 不重写 | 平台包构造的只读事实快照：账本、事件、轮次和用量摘要；字段是公开合同，内部结构不暴露 |

`TeamMode` 增加 `quality_class` 槽位；根描述的 `team` 对象增加 `"quality_class"`，`settings` 增加 `quality` 分组。不指定时使用样板默认的 `QualityModel`，即第 5.8 节的 tq/1。

**项目怎样扩展**（代码放在项目自己的业务包里，例如 `tools/xworld/quality.py`）：

```python
from genet_builtin.api import QualityModel, RedLine, Indicator

class SceneBuildBroken(RedLine):
    id, version, title = "x.R1", 1, "集成构建坏了超过 30 分钟没人认领"
    def detect(self, context, facts):
        return [i for i in facts.extra("build-status") if i["brokenMin"] > 30 and not i["claimed"]]

class QaVerdictOverturned(Indicator):
    id, version, metric = "x.qaOverturnedPct", 1, "M1"
    anchors, lower_is_better, min_samples = (40, 20, 10, 5, 2), True, 20
    def measure(self, context, facts):
        ...

class XWorldQuality(QualityModel):
    def red_lines(self):
        return super().red_lines() + [SceneBuildBroken()]
    def indicators(self):
        return super().indicators() + [QaVerdictOverturned()]
    def collect(self, context, facts):
        facts.put_extra("build-status", read_build_status(context.team_root))
```

```json
{"team": {"quality_class": "xworld.quality:XWorldQuality",
          "settings": {"quality": {"thresholds": {"R2": {"idleMin": 90}},
                                   "anchors": {"M2.deliveryToConsumeP90Min": [180, 45, 15, 8, 3]},
                                   "disable": ["M5.idleWakePct"]}}}}
```

规则：

- **加东西用继承**：在 `super()` 的结果上追加红线和指标，不复制样板的列表。样板以后增加内置项时，项目自动得到，不需要合并。
- **改默认值用设置**：阈值、锚点、权重、停用某项都写在 `settings.quality`，按稳定 `id` 引用，不改样板代码。样板修改同一项的实现时，项目的设置仍然有效；样板改了该项的 `version` 时，`quality describe` 提示项目设置是针对旧版本的，由反思岗位确认。
- **核心分不受项目影响**：项目分 = 样板项 + 项目项，叠加项目设置后计算。核心分只用样板项和样板默认值，忽略项目设置。两分同时上卡，项目的红线触发只扣项目分。这样项目可以按自己的标准要求自己，平台观察者看到的仍是可比较的分数。
- **确需修改样板评估代码时**：允许，但按 `extensions.md` 的规则记录补丁与原因；`drift` 会显示出来，观察者把它当作"样板评估不够用"的信号。
- **`quality describe`** 列出实际生效的模型类、每个红线和指标的 `id`、`version`、来源（样板或项目）、项目设置和被停用的项。不存在或不兼容的类明确报错，不静默回退到默认模型；报错本身作为覆盖缺口上卡。

**升级时为什么冲突少。** 样板升级只替换 `tools/genet_builtin/` 和内置 Skill。项目的扩展类只依赖公开基类和 `QualityFacts` 的公开字段，项目设置只按 `id` 引用。破坏这些公开合同时，样板必须升 API 版本并给迁移说明，与现有扩展合同一致。今天三队都需要三方合并样板脚本，原因正是它们改的是内部实现；评估器从第一版起就走扩展层，可以避免重复这个问题。

**XWorld 现有脚本的迁移。** XWorld 的 `team_score.py` 和事件补丁里有价值的部分（例如成果评审之外的本队指标）可以迁成 `XWorldQuality` 的子类和项目指标，由 XWorld 的反思岗位决定何时迁移。迁移前，两套分数并存，核心分以样板评估器为准。

## 6. 取舍与替代方案

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 维持现状，各队自己打分 | 不采用 | tikistar 没有任何记录；XWorld 的口径只在本队成立；发布后无法比较前后。 |
| XWorld 式多维加权总分 | 不采用 | 实验 3 的三个副本得分 7.2、7.3、7.1，与实际进度无关；断档被平均掉，缺数据时自动重分权重。 |
| 只给红线和指标，不合成分数（本提案第 1 版） | 不采用 | 无法收束成一个判断，难以驱动团队反思和平台改进，也无法做发布门禁的单一结论。事实卡保留为分数的解释。 |
| 红线一票否决 + 锚点插值的综合分 | 采用 | 断档不可能及格；锚点固定可跨版本比较；缺数据时显式标暂定；每条失分有明确去向。 |
| 红线按实例扣分 | 不采用 | 三队今天的实例数都在 3 至 17 张，按实例扣分会长期停在 0，看不出清理进展。实例数在卡上并列显示。 |
| 未知指标按 0 分或 60 分计 | 不采用 | 按 0 会把样板和平台缺记录的问题算到团队头上；按 60 会让不可评估的团队显得及格。改为给出可能区间。 |
| 用模型评审全部会话 | 仅作第二层抽样 | 不可复现，成本随会话量线性增长，且评审本身需要被评审。 |
| 由平台开发侧在团队外部打分 | 不采用 | 团队不能自评就不能自我改进，外部分数只能驱动平台，驱动不了团队反思。平台开发侧读团队自己的分数卡，做跨团队观察。 |
| 项目复制样板评估器后各自修改 | 不采用 | 这正是今天三队升级都要三方合并的原因。改为公开基类加按 `id` 引用的设置。 |
| 项目设置直接改写唯一的分数 | 不采用 | 跨团队和跨版本就无法比较。改为核心分与项目分并列。 |
| 在 daemon 里做团队遥测 | 不采用 | 违反"daemon 不解释团队状态"。平台只补对所有用法都成立的三项通用事实。 |
| 要求 Owner 对每个结果明确表态采用或返工 | 作为可选 | 更准确，但每单多一步操作。平台已有"LLM 操作复杂度偏高"的记录，所以默认用读入加重做关联推出三档。 |
| 只做第 3.5 节的账本测算，不加事件 | 作为 P0 | 立刻可用，但量不出送达、停摆、采用和成本，只能覆盖两条红线和一段流转。 |

主要成本与风险：

- **样板升级不会自动覆盖已有团队。** 三支团队都改过自己的脚本，需要各自三方合并。合并前它们只能出账本可得的项。
- **事件日志会增长。** XWorld 两个长任务的事件文件各有约 2200 和 2700 行。需要按任务归档的规则，但不需要新的存储。
- **指标可能被当成目标。** 第 5.6 节是对策，但需要在样板 Skill 里明确写出"不作为派单约束"。
- **分数会被简化理解。** 三队起步都是 0 分，只看综合分会看不出进展。卡上必须同时显示基础分、红线实例数和失分账单，周报按这三项讲变化。
- **锚点初值可能偏。** 锚点是凭三队一天的数据和平台承诺定的，P3 校准前不用于跨团队排名，也不用于发布的硬门禁，只用于记录和预警。
- **读入不等于采用。** 多条输入合并进一轮时只能看到开启该轮的那条，会低估读入。这一点要在卡上标注覆盖率。

## 8. 兼容、迁移和恢复

- **没有事件的旧团队**：只出账本可得的项，其余显示未知并注明原因。不回填、不从旧日志猜测。
- **XWorld 已有的本地事件**：评估器按种类映射读取，标注来源为团队本地。它的回传语义与样板不同，卡上注明，不与其他团队比较交接时间。
- **混合版本**：事件日志带版本号。窗口跨越升级时刻时，升级前的部分按旧覆盖率报告。
- **事件写入失败**：不影响业务，但计数并显示在覆盖率里。不能静默丢失后让指标看起来完整。
- **回滚**：删除事件写入点和 `quality` 命令即可；项目扩展类随之不再被加载，`quality describe` 会如实报告。事件日志不被调度读取，回滚不影响派单、对账和结算。
- **平台字段**：新增字段都是可选的。旧 CLI 读不到时，对应指标为未知。

## 9. 未决问题与需要的决定

**需要评审决定**（影响 P1、P2 是否开工）：

- **D1** 是否把过程事件日志收进官方样板。不同意则止步于 P0。
- **D2** 是否接受 `--follows` 作为推断返工的唯一依据（另有可选的 `--standing` 标记常驻支持），明确表态的处置只作可选。
- **D3** 平台是否持久化回合错误码并在轮次上输出用量。
- **D4** 红线阈值的初值（10、60、10、15、10 分钟）是否可作为起点。
- **D5** 红线是否按类扣 50 分、最低 0 分（本提案建议），而不是按实例扣分。
- **D6** 第 5.8 节的权重（25、20、20、15、10、10）和锚点初值是否可作为 tq/1 草案，P3 校准后再定稿。
- **D7** 定级条件（已知权重不少于 80%、红线全部可判、已闭环工作项不少于 20）是否合适；在此之前对外只报暂定分和区间。
- **D8** 评估器作为样板脚本的一部分，以 `QualityModel`、`RedLine`、`Indicator` 公开基类和 `quality_class` 槽位实现，沿用现有扩展合同（第 5.10 节）。
- **D9** 每张卡同时给核心分和项目分：核心分只用样板口径，供跨团队观察；项目分叠加项目扩展，供本队目标。

| --- | --- | --- |
