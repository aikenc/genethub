# 平台开发侧的团队观察与改进 Skill 提案

- **主题**：新增 Skill `genethub-team-observer`。在一个 dev 槽位里驱动若干团队完成各自的远期目标，在预算时间内持续观察它们的工作质量和平台运行情况，把发现的问题归到平台接口、样板脚本或内置 Skill 与反思流程，及时修复并发布 dev 版本，再看团队是否因此工作得更好。
- **状态**：待评审。本文只是提案，没有创建 Skill、没有修改任何 PipeSpace 配置、产品代码、样板或团队。
- **日期**：2026-11-10（北京时间）
- **适用范围**：GeneHub 开发管线（`genethub-spaces`）的 dev 槽位 Space，例如 `spaces/dev-2`。
- **分层**：角色层与制品层的定义、写权限和问题归属见 [分层模型](team-platform-layer-model-20261110.md)；dev-2 的落地前提与对 Beta/Stable 的影响见 [dev-2 落地准备提案](team-observer-dev2-readiness-proposal-20261110.md)。
- **依赖**：团队自评的分数卡、失分去向和评估器扩展结构见[团队工作质量的可量化评估提案](team-work-quality-evaluation-proposal-20261110.md)第 3 版（下称"评估提案"）。
- **事实基线**：产品仓 `genethub` 主干 `2beda9ed`；`dev-2` 槽位以 parity 车道运行，安装与当前构建一致，尚无 Live 版本；`dev-2` 挂载 12 个 Skill，其中没有任何一个负责观察团队。
- **来源**：用户要求 `u_e7291d8619ce425091c42581097aeba5` 与 `u_dca64c712c30436092a8f2ecaaae8677`。
- **修订**：第 2 版（11-10 12:12）整体取代第 1 版。第 1 版把迭代循环放在 `release-beta`，让平台流程替团队打分、给团队派改进单，混淆了团队与平台开发的职责。本版按用户的划分重写：团队自己评估、自己反思改进；平台开发侧是多个团队的观察者，只改平台。

## 先回答三个问题

1. **现在的影响是什么。** 用户希望这样下达任务："在槽位 dev-2 驱动团队 A 完成目标 X，团队 B 完成目标 Y，你不断跟进和改进团队工作质量，预算 2 天。"今天没有 Skill 能接住这个请求。接手的 Agent 不知道开工前要核对什么，也不知道怎样在 2 天里持续跟进而不中断；发现问题后，分不清该改平台接口、样板脚本，还是该让团队自己改。结果要么去直接修团队项目，替团队干活；要么只报告问题、不修平台。XWorld 的历史就是例子：团队为了评估和结果回传，直接改了样板的内部脚本，每次升级都要三方合并；平台则没有任何流程把这些补丁识别为"样板不够用"。
2. **怎么解决。** 新增 `genethub-team-observer`，按八个环节工作：解析输入、准备核对、以用户身份下达目标、按心跳持续观察、给问题分类、在本槽位修复并发布 dev 版本、确认采用后复验、按事件和到期汇报。分类遵循用户给出的三条路线：
   - 平台接口不足或摩擦大，改平台接口或流程。
   - 样板工作流脚本有公共问题，改内置工作流脚本。
   - 团队工作流有项目自己的问题，不去改项目，而是改内置 Skill、工作流 Skill 或反思岗位的流程，让团队能自己发现、自己改。

   进度：
   - **已完成**：本提案；评估提案里的评分原型和失分去向试判。
   - **待实施**：本 Skill，以及评估提案 P1 中团队自评的样板能力。
   - **待验证**：观察者会话怎样定时唤醒，是否需要平台补一个会话级定时原语；dev 版本能否让远端机器自动采用。
3. **怎么防止问题复发。** 每个修复都附账本夹具或回归测试，并且要在团队实际采用新版本后，在团队自己的分数卡上确认对应红线或指标好转，才能关闭。同类问题再出现时重开原项、记为复发。观察者还单独跟踪团队的自愈表现：问题是团队自己先发现的，还是观察者发现的；团队自己修好用了多久；修完是否复发。团队发现不了、修不好的问题类型，会成为内置 Skill 和反思流程的改进项。

## 1. 摘要与建议

**职责划分**：按[分层模型](team-platform-layer-model-20261110.md)，分两条轴。角色层回答谁做事：团队执行层、团队自管理层、平台开发层。制品层回答改哪里：平台内核、内置样板、团队定义、业务产物。每个制品层只有一个角色层能写。本 Skill 属于平台开发层。

| 角色层 | 做什么 | 能写的制品层 | 不做什么 |
| --- | --- | --- | --- |
| 团队执行层（前台、Owner、成员） | 推进目标，产出业务成果 | 业务产物 | 不改团队定义；改进意见以留言交给反思岗位 |
| 团队自管理层（反思岗位、定时自评） | 定时自评出分；读分数卡改进本队；把平台问题以留言上报；决定何时采用样板升级 | 团队定义（岗位、Skill、脚本、项目扩展与设置） | 不给内置样板打补丁冒充修复；确需临时补丁时登记 |
| 平台开发层（本 Skill） | 在 dev 槽位驱动多个团队，观察多个团队和平台运行，发布 dev 版本并复验 | 平台内核、内置样板（含内置 Skill 与反思流程） | 不写团队定义和业务产物，不替团队派单或结算，不给团队会话透露内部信息 |

**建议**：

1. **一个 Skill 承接整段预算。** 从解析"槽位、团队、目标、预算"开始，到预算结束的汇报为止。运行状态保存在任务目录，换会话也能接着跟进。
2. **准备不齐就问人。** 团队和远端机器由准备阶段负责。开工前逐项核对，缺什么就一次列清楚问用户，不自己去建团队或配对机器。
3. **以用户身份下达目标和跟进。** 沿用 dev 生命周期 Skill 的真实用户视角规则，不向团队会话透露日志、路径或内部编号。
4. **只改平台，三条路线分流。** 团队自己的问题先等团队自己的反思处理；超过时限或团队没发现，才判为内置 Skill 或反思流程的缺口，改平台而不改项目。
5. **问题修复以 dev 版本交付。** 在本槽位双仓里开发、审查、测试，按改动所在的制品选 Live 或重新构建安装，确认本机和远端机器都已切到新版本、团队已升级样板之后，才开始复验。
6. **观察者有自己的指标。** 包括每队的核心分趋势、团队自愈表现、平台摩擦，以及每个 dev 版本的修复成效。团队的分数由团队自己算，观察者不另算一套。

需要评审决定的事项在第 9 节，其中 E1 至 E3 决定 Skill 能否开始编写。

## 2. 背景与用户场景

### 2.1 必要概念

| 名称 | 含义 |
| --- | --- |
| 槽位 | `worktrees/<slot>/` 下的一对产品仓检出，加上该槽自己的 dev 配置与运行数据；由同名 `spaces/<slot>` 操作。 |
| dev 版本 | 槽位构建并发布的版本。只换 guest 时用 `devctl.sh live`，版本号为 `0.0.1-dev.N`；改了宿主或 CLI 时重新 `build` 并重启 `serve`，安装后生效。 |
| 远端岗位 | 团队里 `TEAM_MACHINE` 指向另一台机器的岗位。那台机器要接入同一个槽位的 Hub，才能跑到这些岗位。 |
| 分数卡 | 团队用样板评估器给自己算的卡，含核心分、项目分、红线、失分账单和每条失分的去向（评估提案第 5.8 至 5.10 节）。 |
| 失分去向 | 团队卡上每条失分的 `route`：`team` 本队改，`report:template-script` 上报样板脚本，`report:platform-interface` 上报平台接口，`external` 外部，`pending` 待判。 |
| 心跳 | 观察者按固定间隔做一次只读巡检，不依赖会话记忆。 |
| 自愈 | 团队自己发现问题、自己修好，而且修完不复发。 |

### 2.2 场景：驱动两支团队 2 天

用户输入："在槽位 dev-2 驱动团队 A 完成修仙游戏的地图切片，团队 B 在叙事方面做到产品级表现，你不断跟进和改进团队工作质量，预算 2 天。"

**改前**：接手的 Agent 直接给两队前台发目标，然后时有时无地查看。发现 A 队账本上挂着成员已空闲、却没有结论的义务，就去 A 队目录里手工结算；发现 B 队的巡检规则在空转，就去改 B 队的脚本。2 天后的汇报只能说"修了这些"，说不清平台变好了没有。下一支团队还会撞上同样的问题，因为平台什么都没改。

**改后（拟议）**：

1. **开工前核对。** dev-2 正在运行当前构建；A、B 两队在槽位里，前台会话可达；两队的样板版本与槽位内置版本一致，自评能出卡；两队的远端岗位指向的两台机器已接入 dev-2 的 Hub、在线、版本一致。假如其中一台没接入，观察者列出缺口问用户，在此之前不下达目标。
2. **下达目标。** 以用户身份分别向两队前台发送目标，记录消息编号，以后不重发。
3. **心跳观察。** 每 30 分钟读一次两队最新的分数卡、反思报告、上报留言、看板进展和会话健康，同时检查槽位 daemon 和远端机器的错误、定时任务失败、CLI 错误码。
4. **发现问题。** 第 3 小时，A 队卡上出现 R2 未结算义务，去向为 `report:template-script`。观察者核对 B 队，B 队有同样的模式，只是实例未到阈值。两队都没改过样板的结算路径，于是判为样板公共脚本问题。
5. **修复发布。** 在 dev-2 的产品仓里修改样板结算逻辑，先写一个让 R2 出现的账本夹具，确认修复前失败、修复后通过；经审查与测试后构建发布 dev 版本。本机和两台远端机器都确认切到新版本；两队反思岗位按升级提醒合入新样板，观察者用 `run.py describe` 和 `drift` 确认采用。
6. **复验。** 采用之后，两队连续的分数卡上 R2 实例为 0，其他红线没有增加，这一项关闭，夹具进入回归。
7. **另一类问题。** 第 20 小时，B 队的 M5 空转失分持续偏高，去向为 `team`，B 队反思岗位跑了两次都没有处理。观察者不改 B 队的巡检规则，而是判为反思流程的缺口：反思岗位没有读分数卡里的空转项，也没有"诊断量不当目标"的引导。于是修改样板 `team-reflect` 的流程和 `team-work` 的引导，发布 dev 版本，再看 B 队的反思岗位能否自己发现并改掉。
8. **到期汇报。** 第 48 小时，按三问汇报：两队目标进展（成果）、核心分趋势、发布的 dev 版本和每项修复的成效、团队自愈表现、仍开放的问题，以及建议提 MR 的提交。合入主干等待人授权。

## 3. 现状与证据

### 3.1 今天的混淆从哪里来

- **团队只能改内部实现。** XWorld 为了记录过程事件，在样板的 `tools/genet_builtin/tasks.py` 里加了补丁，注释写着"XWorld patch 2026-11-05: append-only process events for team work-quality scoring"；结果回传也改成了逐单。样板的升级说明明确要求这类修改"三方核对，不是零成本覆盖"。样板已有工作流、资源、反思和看板的公开扩展点，但没有评估的扩展点。
- **平台没有观察团队的流程。** `genethub-beta-quality-loop` 和 `genethub-beta-user-journeys` 驱动真实使用，看的是产品体验，不看团队过程。`genethub-dev-development` 能构建发布 dev 版本，也规定了真实用户视角，但没有"持续跟进多个团队"的环节。
- **本提案第 1 版也犯了同样的错。** 它让平台流程给团队打分、给团队写改进简报，把团队的自我改进当成了平台的任务。

### 3.2 可以直接沿用的能力

| 能力 | 位置 | 本 Skill 怎么用 |
| --- | --- | --- |
| 槽位构建、安装、Live 发布与身份核对 | `genethub-dev-development`（`devctl.sh check/status/build/serve/live/identity`） | 修复后的 dev 版本发布与身份证明 |
| 真机加入槽位 | 同上 `references/dev-real-machines.md` | 核对远端机器接入；远端更新的已知做法 |
| 真实用户视角 | 同上，"严禁开启上帝视角剧透""严禁越俎代庖" | 下达目标和跟进的约束 |
| 开发、审查、测试门禁 | `genethub-role-development`、`genethub-modify-review`、测试 Skill | 平台改动的实施路径 |
| 样板扩展合同 | `team-core/references/extensions.md` | 判断团队是否绕过扩展点改了内部实现 |
| 团队工具 | `run.py describe`、`drift`、`notes`；样板升级提醒 | 确认样板采用、读取团队上报、识别补丁 |
| 团队自评 | 评估提案 P1 的 `run.py quality card/history/describe` | 观察的主要输入 |
| 会话读取与输入 | `genet session send/get/rounds/narrative` | 下达目标、读健康状况 |
| 管线问题登记 | `genethub-pipeline-issues` | 观察者自身工具链或 Skill 的问题 |

### 3.3 缺什么

1. **开工前的准备核对**：没有一份清单说明驱动团队之前要确认什么。
2. **持续跟进的唤醒方式**：CLI 的公开命令里没有会话级定时器。团队的定时 hook 是 Space 级原语，由 SpaceBuilder 从 Skill 的 `hooks/` 编译生成；平台开发侧会话没有对应的唤醒机制。
3. **问题分流的规则**：没有规则区分平台接口、样板脚本和项目问题，也没有"先等团队自己修"的时限。
4. **采用的确认**：dev 版本发布后，远端机器是否会自动取到新 guest 没有验证过。`dev-real-machines.md` 记录的做法是手工下载 guest 再启动。
5. **观察者自己的指标**：没有记录团队自愈表现和平台摩擦的口径。

## 4. 目标与范围

| 目标 | 成功的样子 |
| --- | --- |
| G1 准备核对 | 开工前清单全部通过，或者带着精确缺项问用户；准备不齐时不下达目标。 |
| G2 预算内持续跟进 | 从开工到预算结束，心跳间隔不超过设定值的两倍；错过的心跳有记录；换会话后能从运行记录接着跟进，不重发已发出的消息。 |
| G3 问题有证据地分流 | 每个问题有路线、证据位置和判断理由；"团队自己的问题"都先给团队自愈时限。 |
| G4 修复以 dev 版本交付并被采用 | 每个修复有提交、制品身份和版本号；本机、远端机器和团队样板的采用分别确认后才复验。 |
| G5 不越界 | 观察者没有修改团队定义源和业务目录，没有替团队派单或结算，发给团队的消息不含内部信息。 |
| G6 能说清变好了多少 | 到期汇报给出每队核心分和红线的趋势、每项修复的成效、团队自愈表现和平台摩擦的变化。 |

**本期不做**：

- 不发布 Beta 或 Stable，不合入主干。提 MR 需要人授权，与 `genethub-dev-development` 一致。
- 不负责团队准备：建团队、配置岗位、配对远端机器都属于准备阶段。观察者只核对，缺了就问。
- 不评判成果质量，只把团队目标进展作为背景并列汇报。
- 不替团队计算分数。团队自评是样板能力；在评估提案 P1 交付之前，观察者用只读原型算出的分数只作参考，标明来源。

## 5. 具体方案

### 5.1 位置和组成

拟议放在 `genethub-spaces/skills/lifecycle/genethub-team-observer/`，挂载到需要驱动团队的 dev Space，首批为 `dev-2`。与 `genethub-dev-development` 同属槽位生命周期，同一 Agent 沿用同一任务状态完成观察、开发和发布。

```text
genethub-team-observer/
  SKILL.md                    输入、八个环节、护栏、完成与恢复
  references/
    readiness.md              准备核对清单与问用户的格式
    routing.md                问题分流规则、自愈时限、典型案例
    observation.md            心跳巡检项、观察者指标的口径
    acceptance.md             触发自检、每个环节的验收和反例
  scripts/
    observer.py               ready / tick / issue / report 子命令
    test_observer.py          用固定团队快照测试准备核对、巡检和分流
```

**描述草案**（决定 Skill 何时被选用）：

> 在 dev 槽位驱动一个或多个团队完成远期目标，并在预算时间内持续观察团队工作质量和平台运行情况：核对槽位、团队和远端机器是否就绪，以用户身份下达目标，按心跳读取团队自评分数卡与上报，把问题分流到平台接口、样板脚本或内置 Skill 与反思流程，在本槽位修复并发布 dev 版本，确认采用后复验。用于"在槽位 dev-N 驱动团队完成目标、跟进和改进团队工作质量、预算 N 天"。不修改团队项目；不用于 Beta 或 Stable 发布、单条反馈修复或只读的团队现状查询。

### 5.2 输入和运行记录

从用户输入解析出槽位、团队与目标、预算，以及可选的质量期望。缺项时只问缺的部分；槽位必须等于当前 Space 绑定的槽位。

运行记录放在同一任务目录的 `team-observer.json`。生命周期仍由 `workflowctl.py` 管理，这个文件只是索引：

```json
{
  "schema": "team-observer/1",
```

### 5.3 准备核对（开工门槛）

| 项目 | 怎么核对 | 不满足时 |
| --- | --- | --- |
| 槽位身份与运行 | `dev-context.py`、`devctl.sh status` 与 `identity`：槽位、双仓路径、运行中的构建与当前源码一致 | 槽位本身的故障按 `genethub-dev-development` 在同槽恢复；其他情况报告 |
| 团队存在、前台可达 | 槽位 daemon 的工作区里有这些团队；前台会话可读 | 问用户 |
| 样板版本 | 每队 `run.py describe` 的样板版本与槽位内置版本一致；记录 `drift` 基线 | 不一致时问用户是否先由团队升级 |

### 5.4 下达目标与跟进

- 用槽位的 CLI 向每队前台发送目标，消息编号固定为 `obs-<任务>-goal-<团队>`。恢复时先查原消息，不重发。
- 消息只写用户会说的话：目标、期望和对可见成果的反馈。不写日志、文件路径、函数名、CLI 参数或会话编号，也不教团队怎么做。
- 远期目标不要求观察者拆解。团队来问时，只按用户的意图回答；需要用户判断的问题转给用户，不替用户拍板。
- 跟进时，观察者可以像用户一样询问进展或反馈体验，但次数计入团队的 M3"人的占用"，并在汇报里列出。

### 5.5 心跳巡检

默认每 30 分钟一次，全部只读：

| 巡检对象 | 读什么 |
| --- | --- |
| 团队自评 | 每队最新的分数卡：核心分、项目分、红线实例、失分去向、覆盖缺口 |
| 团队反思 | 反思报告、`route` 为 `report:*` 的上报、`drift` 相对基线的变化 |
| 目标进展 | 看板、Owner 的任务状态、可见成果 |
| 会话健康 | 失败、长时间无进展、等待用户、暂停 |
| 平台运行 | 槽位 daemon 和 Hub 的错误日志、定时任务连续失败、CLI 错误码分布、远端机器在线与版本、资源占用 |

每次巡检生成一条心跳记录，编号按截止时间倒推，保证重放时不重复。错过的心跳照实记录，不补造。

**唤醒方式是待验证项。** 平台目前没有面向这类会话的定时原语。候选做法有三种：

- 槽位里由 supervisor 托管的小调度器，按心跳编号向观察者会话发送 `genet session send`（稳定消息编号，重复投递会被去重）。
- 观察者在一轮里等待。这种做法不可靠，只适合短预算。
- 平台补一个会话级的定时唤醒。

S0 采用第一种做法，同时把"没有会话级定时原语"作为一条平台接口问题登记，按第 5.6 节的规则评估。

### 5.6 问题分流

**问题来源**：团队卡上的红线和失分、团队的上报、观察者巡检发现而团队没有发现的问题、平台运行错误。

| 路线 | 判定依据 | 改哪里 | 不做什么 |
| --- | --- | --- | --- |
| **平台接口或流程** | 去向为 `report:platform-interface` 且证据属实；CLI 或 daemon 错误码；团队为绕开平台限制写了补丁；完成一件常见事需要过长的命令序列或反复重试；跨机未知占比高 | 产品仓的 daemon、CLI、协议、定时 hook；必要时 `genethub-cloud` | 不为团队的偶发误用改接口 |
| **样板公共脚本** | 去向为 `report:template-script`，且两支以上团队出现同类问题，或这段脚本在团队里未被改过；评估器的误报或漏报也归此类 | `apps/daemon/builtin-skills/genehub/references/team-template/tools/genet_builtin/` | 不在某支团队的副本里修 |
| **内置 Skill、工作流 Skill 或反思流程** | 去向为 `team`，但超过自愈时限团队仍未发现或未修好；或者团队绕过扩展点改了样板内部实现；或者团队把诊断量当成了目标 | 样板 `skills/genet_builtin/team-*`（含 `team-reflect` 的流程）、工作流 Skill、扩展合同文档 | 不改团队的岗位、Skill、脚本或业务目录 |
| **外部** | 上游模型或网络故障 | 只记录；平台对外部故障处理不当时另判为平台接口问题 | 不追 |
| **观察者自身** | 观察者的脚本、本 Skill、槽位工具或网关出问题 | 本 Skill 源码经 PipeBuilder；管线问题按 `genethub-pipeline-issues` | 不算作团队失分 |

**自愈时限**：去向为 `team` 的问题，默认先给团队两次反思周期或 4 小时，以先到者为准。时限内团队自己修好，记为一次成功自愈；没修好，才进入"内置 Skill 或反思流程"路线。红线已经阻断目标进展时可以提前判定，但记录理由。

**确认后才动手**：每个问题至少有一份原始证据（账本记录、会话片段或日志行），以及一次复核，确认不是评估器误报。只有团队卡上的分数、没有原始证据的，记为待核。

### 5.7 修复和发布 dev 版本

1. **开发**：在本槽位的成对产品仓里，按 `genethub-role-development` 实施。样板脚本和平台接口的修复先写夹具或测试，确认修复前失败、修复后通过；内置 Skill 和反思流程的修复，写一个触发场景说明期望团队怎么做。
2. **门禁**：按 `genethub-modify-review` 形成候选，按影响范围运行测试。
3. **发布**：按改动所在的制品选择方式，由 `genethub-dev-development` 判断。只换 guest 时用 `devctl.sh live`，不重启；改了宿主、CLI 或随安装包分发的内容时，重新 `build` 并重启 `serve`。重启会打断团队会话，所以选在没有在途关键操作的时刻，事先记录，事后检查团队能否自己恢复。这本身也是一次自愈测试。
4. **成批发布**：多个修复合成一个 dev 版本。除非红线阻断目标，两次发布之间至少间隔一次心跳复验，避免改动叠加后无法判断效果。
5. **采用**：分别确认三件事。
   - 槽位 daemon 的版本等于新版本。
   - 每台远端机器的版本等于新版本；远端不能自动更新时，按 `dev-real-machines.md` 在已授权的隔离目录中更新。
   - 涉及样板的改动，每队反思岗位已按升级提醒合入，用 `run.py describe` 和 `drift` 确认。

   团队合入样板由团队自己完成，观察者不代为合并。

### 5.8 复验和关闭

- 复验从采用全部确认的时刻开始。红线类问题要求之后至少两张连续的团队分数卡上该类实例为 0。指标类问题要求变化超过评估提案第 5.8 节的噪声区间。
- 同时检查其他红线没有新增，成对指标没有变差（评估提案第 5.6 节）。
- 结论分为有效、无效、变差回退、不可判定。变差时先恢复到上一个 dev 版本，再查原因。
- 关闭后，同类问题再次出现时重开原项，记为复发。
- 内置 Skill 和反思流程类的修复，判定标准是团队自己发现并修好同类问题，而不是观察者看到分数变好。

### 5.9 观察者自己的指标

团队的分数由团队自己算。观察者只汇总、比较，并补上团队看不到的跨队和平台视角：

| 类别 | 指标 | 说明 |
| --- | --- | --- |
| 团队工作质量 | 每队核心分、红线实例数、基础分的趋势 | 来自团队卡的核心分，跨队可比 |
| 团队自愈 | 自检出率：问题由团队自己先标出的比例 | 观察者先发现的说明团队的评估或反思有缺口 |
| | 自修时长：从团队标出到团队修好 | |
| | 自修后复发率 | |
| | 上报属实率：团队上报给平台的问题经核实属实的比例 | 太低说明团队在推卸，太高而平台未修说明平台跟进慢 |
| | 样板内部补丁数的变化 | 增加说明扩展点不够用 |
| 平台摩擦 | 按错误码的 CLI 与 daemon 错误率；定时任务连续失败次数；跨机未知占比；完成一次派单或结算平均需要的命令数 | |
| 修复成效 | 每个 dev 版本的修复项数、有效项数、回退次数 | |
| 目标进展 | 每队目标的可见进展 | 只作背景，不折算进工作质量 |

### 5.10 汇报

- **事件驱动**：发布 dev 版本、需要用户决定、红线阻断目标进展时，立即汇报。
- **定时**：每 12 小时一份简报。
- **到期**：预算结束时给出最终报告。内容是每队目标进展、核心分与红线趋势、发布的 dev 版本和每项修复的成效、团队自愈表现、平台摩擦变化、仍开放的问题，以及建议提交 MR 的候选。
- 所有汇报遵循核心工作流的三问规则；没有证据的不写成已解决。

### 5.11 护栏

- **不改团队项目。** 团队定义源和业务目录只读；需要团队改的，由团队自己改。到期时用 `drift` 和团队定义源的提交记录证明观察者没有写入。
- **不替团队干活。** 不派单、不结算、不手工清理红线实例、不搬运成果。
- **不透露内部信息。** 发给团队的消息只含用户视角的内容。
- **不制造分数。** 不改团队的评估设置，不改样板锚点来让分数变好。评分模型的修改是独立的评估提案修订。
- **授权不扩张。** 只发布 dev 版本；合入主干、Beta 发布、远端机器上非 dev 的安装都不在本 Skill 范围内。远端机器只在准备阶段已授权的隔离目录中操作。
- **预算到期即停。** 到期停止新的修复和发布，正在进行的发布按原 job 收尾，然后汇报。不以"还差一点"为由自行延长预算。

## 6. 取舍与替代方案

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 观察者直接修团队项目 | 不采用 | 团队得不到自愈的锻炼，下一支团队仍会撞上同样的问题，平台也没有改进。 |
| 平台流程替团队打分（本提案第 1 版） | 不采用 | 团队不能自评就不能自我改进；两套分数会互相矛盾。 |
| 扩展 `genethub-beta-quality-loop` | 不采用 | 它面向 Beta 真实用户体验与发布，本 Skill 面向 dev 槽位里的团队与平台改进，触发条件、发布范围和验收都不同。共用的做法（运行索引、采用后复验）直接沿用。 |
| 每发现一个问题就发一个 dev 版本 | 不采用 | 改动重叠后无法判断哪项有效；远端机器和团队样板的采用也跟不上。 |
| 团队问题立即判为内置 Skill 缺口 | 不采用 | 会把团队本来能自愈的问题变成平台工作，也测不出团队的自愈能力。 |
| 心跳由观察者在一轮里等待 | 仅短预算可用 | 2 天预算下会话中断就会丢失跟进。 |

主要成本与风险：

- **跟进有成本。** 每 30 分钟一次巡检，2 天约 96 次。巡检本身只读、不调用模型，但观察者会话每次被唤醒都有一次模型调用。巡检没有新事实时，应当只记录、不展开分析，这一点需要在 S0 实测。
- **宿主重启会打断团队。** 需要重启的修复尽量合批，并选在团队空闲的时刻。
- **自愈时限可能拖慢修复。** 红线阻断目标时允许提前判定，但要记录理由，事后看提前判定是否必要。
- **团队采用样板升级可能失败。** 采用逐队记录，没采用的队不进入复验，不计为修复无效。

## 7. 分期、验收与交付

| 阶段 | 依赖 | 交付 | 验收 |
| --- | --- | --- | --- |
| **S0** 准备核对与只读跟进 | 无 | SKILL.md、准备核对、目标下达、心跳巡检、问题登记与分流、汇报；`observer.py` 的 ready、tick、issue、report | 缺一台远端机器时，开工前问用户且不下达目标；24 小时以上的跟进里心跳无静默缺口；换会话恢复后不重发目标；发给团队的消息不含内部信息 |

| **S2** 内置 Skill 与反思流程修复、自愈指标 | S0；评估提案 P1 | 自愈时限、自愈指标、引导类修复的判定 | 至少一项团队问题按时限转为引导类修复，修复后由团队自己发现并改掉同类问题 |
| **S3** 平台摩擦与多团队比较 | 评估提案 P2 | 错误码驱动的平台接口分流、跨队核心分比较 | 一次 2 天预算的完整运行，到期报告覆盖第 5.10 节全部内容 |

各期可以独立交付。没有测量依据，这里不给工期。

**Skill 自身的验收**：

- **触发**：说"在槽位 dev-N 驱动团队完成目标、跟进改进工作质量、预算 N 天"时选用。只问"团队现在怎么样"时不进入驱动和修复，只读汇总团队卡。Beta 发布、单条反馈和团队成果评审不选用。
- **反例**：
  - 观察者修改了团队定义源。
  - 观察者替团队结算了义务。
  - 采用未确认就宣布修复有效。
  - 预算到期后继续发布。
  - 团队问题没给自愈时限就改了内置 Skill，又没有记录理由。

  出现任何一条，都判为 Skill 验收失败。

## 8. 兼容、迁移和恢复

- **评估提案 P1 之前**：团队还没有自评能力。观察者用评估提案的只读原型读团队账本，标明"原型代算"，不写入团队目录。P1 之后改为只读团队自己的卡。
- **已有本地评估的团队**（XWorld 两队）：观察者读它们的样板核心分；它们的本地 `team_score.py` 只作背景，由团队自己决定何时迁移到项目扩展类。
- **中断恢复**：所有外部动作都有原回执：目标消息编号、开发候选、dev 版本号与身份、远端更新记录。恢复时先查回执，不重做已完成的动作。
- **回滚**：dev 版本可回到上一个版本，按 `genethub-dev-development` 的恢复路径；Skill 本身删除即可，不留运行状态在团队里。
