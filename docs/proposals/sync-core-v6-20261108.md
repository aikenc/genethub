## 摘要

**体验影响。** 今天只有平台自身的状态需要同步，而且每一族各做一套。将来还有：
- 团队项目进展这类预览页面，需要实时数据。
- Agent 为用户编写的自定义 Web 系统，以及这些系统的后端脚本。
- 网络游戏。

如果每个场景各自解决同步，平台会长出很多套缓存、推送和重连逻辑，每套都要单独修性能问题。这正是平台族今天已经出现的问题。

**怎么解决（待实施）。** 所有信息系统的同步是同一件事，由五个要素构成：权威、基线、兴趣、差异、意图（第 2 节）。据此分为两层：
- **核心层（同步内核）：** 只实现五个要素的调度。键、令牌和数据对它都是不透明的。它不存数据、不消费数据，也不认识任何节点格式。
- **提供与消费层：**
  - 数据源提供方：存储型、计算型、观察型、进程型、副本型。
  - 节点定义工具：值节点与追加节点的约定、编码与 hash、视图、schema。
  - 消费方接口：TS SDK、CLI、Python、预览桥。

平台自身是第一个应用，预览进展页是第二个应用，用来证明抽象成立。

**怎么防止复发。**
- 编译期检查：核心层不依赖任何存储、编码、schema 或业务类型。
- 核心层的测试只用"令牌是整数、数据是随机字节"的假数据源也能全部通过。
- 第二个应用验收期间不允许修改核心层。
- 第 11 节验收（均未执行）。

## 2. 统一原理

### 2.1 五个要素

| 要素 | 含义 |
| --- | --- |
| **状态** | 权威持有的数据，由一组键标识 |
| **基线** | 副本当前持有的版本，用权威给出的令牌记录 |
| **兴趣** | 副本需要哪部分状态（范围） |
| **差异** | 把基线推进到当前状态所需的操作 |
| **意图** | 副本想改变状态，发给权威；副本可以先预测，以权威的结果为准 |

### 2.2 已知系统都是这五个要素的参数组合

| 系统 | 状态 | 基线 | 兴趣 | 差异 | 意图 |
| --- | --- | --- | --- | --- | --- |
| Git | 对象树 | 对方已有的提交 | 分支、路径 | 缺失的对象 | 推送（可能被拒） |
| rsync | 文件树 | 目标端文件的大小和 mtime | 指定目录 | 变了的文件、文件内的块 | 无 |
| HTTP ETag | 资源 | 客户端缓存的 ETag | 单个 URL | 304 或整份 | POST/PUT |
| Firestore、JMAP | 文档集合 | resume token、state 字符串 | 查询 | 增、改、删 | 写入 |
| Replicache、Zero | 行 | 服务端为每个客户端记录的已发送版本 | 查询 | 行差异 | 具名 mutator，客户端预测后以服务端为准 |
| Quake 3 快照同步 | 世界实体 | 客户端**已确认**的那一帧快照 | 视野内（PVS） | 相对已确认快照的增量 | 输入命令，客户端预测、服务端校正 |
| RTS 帧同步 | 各方的输入序列 | 已收到的帧号 | 全部 | 新的输入 | 输入；状态由各端确定性计算 |
| CRDT 协同编辑 | 可合并的文档 | 状态向量 | 文档 | 对方缺的更新 | 本地直接改，各方合并 |
| Cassandra 反熵 | key 区间 | Merkle 树 | 区间 | 不一致的叶子 | 写入 |

差别只在参数上。所以同步只需要实现一次，场景差异都表达为参数。

### 2.3 参数轴，以及每条轴归哪一层

| 轴 | 取值 | 归属 |
| --- | --- | --- |
| 基线确认 | 可靠传输下"已发送即基线"；不可靠传输下"已确认才是基线" | 核心层 |
| 节奏 | 变化驱动（连接可写时发送并自动合并）；固定节拍 | 核心层 |
| 背压与预算 | 只积累脏键，不排队；帧大小、订阅规模上限 | 核心层 |
| 权威位置 | daemon、Hub、进程型后端、游戏服务 | 提供方（核心层只需要一个实现了 `Source` 的对象） |
| 节点形态 | 整份替换（值节点）、只追加（追加节点）；将来可合并 | 节点定义工具 |
| 令牌算法 | 内容 hash、文件元数据、`(epoch, 长度)` | 提供方 |
| 兴趣的语义 | 路径子树、视图窗口、空间范围 | 提供方（核心层只把范围交给提供方解析） |
| 写入策略 | 具名意图、带 `ifToken` 的条件写 | 提供方 |
| 持久性 | 持久、派生、瞬态 | 提供方 |
| 数据编码 | JSON、二进制 | 节点定义工具 |
| 副本存储、预表现、插值 | IndexedDB、内存；预测与校正 | 消费方 |

## 3. 两层结构

```text
应用：平台 schema、Agent 应用、预览页面、团队与 PM 脚本、（将来）游戏
  │
提供与消费层
  ├ 数据源提供方：存储型 · 计算型 · 观察型 · 进程型 · 副本型
  ├ 节点定义工具：值节点 / 追加节点约定 · 规范编码与 hash · 视图索引 · schema 与类型生成
  └ 消费方接口：TS SDK（前端）· CLI（JSONL）· Python（包装 CLI）· 预览桥 · 库形式（暂缓）
  │ 只通过 Source / Sink 两个接口
核心层（同步内核）：会话与范围登记 · 基线表 · 脏集合 · 调度与背压 · 意图路由 · 回执 · 未知语义 · 预算 · 协议信封
  │
传输：WebSocket · Fabric · /cli 回环 · postMessage · 进程内
```

### 3.1 核心层：只管同步，不管数据

**核心层认识的东西只有：**
- **键：** 有序字节串。授权按键前缀限定，这是核心层对键的唯一假设。
- **令牌：** 不透明字节串，只做相等比较。
- **操作：** `{key, token?, body}`。`token` 为空表示删除；`body` 是不透明字节，是整份数据还是一段追加内容，由提供方和消费方约定。
- **范围：** 不透明值，交给提供方解析成键集合。

**核心层不做：** 存数据、读写文件或数据库、算 hash、解析节点内容、定义视图、渲染、保存副本。

**两个接口：**

```rust
/// 提供方实现：核心层通过它取得状态
pub trait Source {
    /// 把一个范围解析成键（可以分批返回）
    fn resolve(&self, scope: &Scope, budget: &mut Budget) -> Result<Resolved>;
    /// 给定副本的基线令牌，返回把它推进到当前状态的操作；None 表示没有变化
    fn diff(&self, key: &Key, baseline: Option<&Token>) -> Result<Option<Op>>;
    /// 处理写入意图，回执里带上它造成的操作
    async fn call(&self, intent: Intent) -> Result<Receipt>;
}

/// 消费方实现：核心层把操作交给它
pub trait Sink {
    /// 应用一批操作（写入副本、刷新界面、输出 JSONL……由实现决定）
    fn apply(&mut self, ops: &[Op]);
    /// 重连时报告自己持有的令牌，核心层据此发 get
    fn known(&self, scope: &Scope) -> Vec<(Key, Token)>;
}

// 提供方通知核心层的入口
kernel.dirty(keys);            // 这些键可能变了
kernel.unknown(keys, reason);  // 暂时无法提供（离线、超预算、出错）
```

**核心层的全部算法：**
- **`get`：** 用 `resolve` 得到键，对每个键调用 `diff(键, 副本声明的已知令牌)`，按预算分帧回复。同时把副本的基线表设为它声明的已知令牌。
- **推送：** 收到 `dirty` 后标脏。连接可写（或节拍到达）时，对订阅范围内的脏键调用 `diff(键, 基线令牌)`，发出操作并推进基线。
- **背压：** 写不动时只积累脏键，恢复后调用一次 `diff`，多次变化自然合并。
- **不可靠传输：** 收到 `ack` 才推进基线；丢失的操作不重发，下一次 `diff` 自然补上。
- **意图：** 按键前缀路由给对应的提供方，回执里的操作同时推进发起方的基线。
- **消费方一侧：** 核心层维护范围登记和重连。重连时调用 `Sink::known` 取得已知令牌，发出 `get`，再把收到的操作交给 `Sink::apply`。

比较逻辑（值节点比令牌、追加节点从断点续接）不在核心层，由提供方的 `diff` 实现。节点定义工具为常见形态提供现成实现（第 3.2 节）。

### 3.2 提供与消费层

**数据源提供方（实现 `Source`）：**

| 类型 | 是什么 | 例子 |
| --- | --- | --- |
| 存储型 | 数据存放在持久介质里，提供方负责读写和令牌 | 会话文件（daemon Store）、Agent 应用的文件存储、Hub 的 SQLite |
| 计算型 | 由其他数据算出来，按依赖重算 | 会话摘要、视图窗口、项目状态卡、机器总览 |
| 观察型 | 观察外部状态的变化 | 进程与 Agent 运行状态、文件与 Git（元数据令牌、文件监听） |
| 进程型 | 一个外部进程通过 CLI 或 Python 发布数据、处理意图 | Agent 应用的后端脚本、团队与 PM 脚本、导入工具 |
| 副本型 | 把上游权威的副本再提供给下游（链式） | 本地 daemon 为 CLI `--machine` 提供的远端节点缓存 |

存储只是其中一种。核心层不区分数据来自文件、数据库、计算还是另一个进程。

**节点定义工具（供提供方和消费方复用，核心层不依赖）：**
- **值节点：** 令牌为规范编码的 SHA-256 截取 128 位；`diff` 在令牌不同时返回整份数据。
- **追加节点：** 令牌为 `(epoch, 长度)`；`diff` 返回从基线长度起的尾部；epoch 变了或超出保留窗口时返回快照。
- **元数据令牌：** 文件型数据用 inode、大小、mtime、ctime 作为令牌，零内容 IO（v5 第 3.2 节）。
- **视图索引：** 有序索引加窗口计算，带 `limit/after` 参数（v4 第 3.4 节）。
- **schema：** 声明键模式、数据类型、视图、可写规则、意图签名和限额，由此生成 Rust、TS、Python 的带类型句柄。

**消费方接口（实现 `Sink`，或包装它）：**

| 接口 | 适用 | 形态 |
| --- | --- | --- |
| **TS SDK** | 前端：工作台、Console、预览页面、Agent 应用页面 | 副本存储（IndexedDB 或内存）、预表现层、`useNode`/`useView`/`call` hooks；预览页面经预览桥使用同一 SDK |
| **CLI** | 实时性要求低的后端、脚本、诊断 | `genet sync get/view/watch` 输出 JSON 或 JSONL；`genet sync put/del/call` 写入；`genet sync serve` 作为进程型提供方 |
| **Python** | 实时性要求低的后端（Agent 写的业务脚本、数据处理、团队脚本） | 薄包装 CLI 的子进程和 JSONL，不重新实现协议（G03）；提供 `watch`、`put`、`call` 和意图处理装饰器 |
| **库形式**（Rust/TS 内嵌内核） | 实时性要求高的场景，如游戏服务 | **前期不做**，模型和协议中预留了不可靠传输与节拍参数 |

**CLI 和 Python 既能消费，也能提供：**

```python
from genehub_sync import Client

c = Client()                                    # 经 genet CLI 连接本机 daemon
for ops in c.watch(view="sessions.recent", ws="w_1", limit=100):
    ...                                         # 只收到变化
c.put("app/todo/task/t1", {"title": "写周报"}, if_token=tok)

@c.handle("app/todo", "task.assign")            # 进程型提供方：处理这个前缀下的意图
def assign(args, cx):
    cx.put(f"app/todo/task/{args['id']}", {"owner": args["owner"]})
    return {"ok": True}

c.serve()
```

进程型提供方有两种模式：
- **写入存储型命名空间：** 例如 `app/todo/`。数据由 daemon 的存储型提供方持久化，进程退出后数据仍在。
- **作为瞬态命名空间的权威：** 进程退出后，这部分键变为未知。

### 3.3 存储型提供方的位置约定

这一节只约束存储型提供方，与核心层无关。依据 [storage-layout.md](../../docs/storage-layout.md) 第 1–4 节：

| 数据 | 位置 | 理由 |
| --- | --- | --- |
| 平台业务状态（会话等） | Space 根下的 `.genethub/`（现状不变） | 跟着项目走，各 channel 共用 |
| Agent 应用数据 | `.genethub/apps/<应用>/`，先登记到 storage-layout 第 2 节 | 属于业务状态（律法 L13） |
| 计算型提供方的缓存快照 | `<data>/cache/sync/`，按项目根路径分开 | 规范把缓存划给 `<data>`；每个 channel 一份，可随时删除 |
| Agent 与脚本的临时材料 | `.genethub/temp/`（现有规范） | 普通可编辑目录，不放 daemon 私有缓存 |

## 4. 场景总览

| 场景 | 提供方 | 消费方接口 | 参数 | 阶段 |
| --- | --- | --- | --- | --- |
| 平台状态 | daemon：存储型（会话文件）、计算型（摘要、视图）、观察型（运行状态、文件、Git） | TS SDK（工作台）、CLI、Python | 可靠、变化驱动 | 首批 |
| Hub | Cloud 服务端：存储型（SQLite） | TS SDK、daemon | 可靠、变化驱动 | 后续 |
| 跨机副本 | 本地 daemon：副本型 | CLI `--machine`、团队远端 | 可靠 | 后续 |
| 团队项目进展预览页 | daemon 平台节点的只读子集 | TS SDK 经预览桥 | 可靠、只读授权 | 首批（第二个应用） |
| Agent 数据应用（看板、跟踪表、表单） | daemon：存储型（`.genethub/apps/`） | 页面用 TS SDK | 可靠、带 `ifToken` 的条件写 | 第二批 |
| Agent 应用的后端逻辑 | 进程型（Python 或任意语言经 CLI） | 同上 | 可靠、低实时 | 第二批 |
| 团队与 PM 脚本 | 消费，必要时作为进程型提供方 | CLI、Python | 可靠、变化驱动 | 第二批 |
| 网络游戏 | 游戏服务（库形式内嵌内核） | TS SDK 或库 | 不可靠、节拍、空间视图 | **前期不做** |
| 协同编辑 | 可合并节点 | 编辑器 | 可靠 | **前期不做** |

**团队项目进展页：** Agent 写一个普通静态 HTML，调用注入的 `genehub.sync.view(...)`。页面不轮询，也不需要知道机器和连接；授权只允许读这个项目的节点。本地双击打开时没有桥接，降级为静态内容。

**Agent 数据应用：** Agent 声明 schema（集合、字段、视图、可写规则），页面用 TS SDK 读写。需要业务逻辑时，Agent 写一个 Python 脚本作为进程型提供方处理意图，不需要在 daemon 里运行沙箱代码。

## 5. 协议：信封归核心层，内容归提供方

| 帧 | 方向 | 作用 | 核心层读取的字段 |
| --- | --- | --- | --- |
| `open` | 副本 → 权威 | 协商命名空间、schema 版本和参数 | `namespace`、`profile`；`schema` 与 `schemaHash` 原样交给提供方 |
| `get` | 副本 → 权威 | 读取、恢复、订阅 | `known` 的键和令牌、`watch`；`scope` 原样交给提供方 |
| `drop` | 副本 → 权威 | 取消订阅 | `scope` 的标识 |
| `call` | 副本 → 权威 | 写入意图 | `opId`、`key` 前缀（用于路由和授权）；其余原样交给提供方 |
| `ops` | 权威 → 副本 | 回复、推送、回执 | `key`、`token`、`seq`、`done`、`opId`、`outcome`；`body` 不透明 |
| `ack` | 副本 → 权威 | 只用于不可靠传输 | `seq` |

可靠传输只用前五个帧；`ack` 和 `tick` 为前期不做的游戏场景预留。

```json
{"type":"open","namespace":"genehub.platform","schema":"genehub.platform","schemaHash":"7c…","profile":{"delivery":"reliable","cadence":"change"}}
```

```json
{"type":"get","scope":{"view":"sessions.recent","ws":"w_1","limit":100,"include":"summary"},"known":[["sessions.recent?limit=100&ws=w_1","9f…"],["session/s_9/summary","c2…"]],"watch":true}
```

```json
{"type":"ops","ops":[{"key":"session/s_9/summary","token":"d4…","body":{"title":"…"}},{"key":"session/s_3/summary","token":null,"body":null}],"done":true}
```

```json
{"type":"call","opId":"op_7f2","key":"app/todo/task/t1","name":"task.assign","args":{"owner":"alice"}}
```

示例中 `scope` 和 `body` 用 JSON 书写只是为了可读；对核心层来说它们是不透明值，其格式由节点定义工具和 schema 决定。

## 6. 安全：不可信代码接入（引导 G08）

| 接入方 | 来源标记 | 形状约束 | 限额 |
| --- | --- | --- | --- |
| 预览页面 | 预览桥按 iframe 颁发授权；页面写入的内容若进入 Agent 上下文，标注为不可信 | 默认只读；可调用的意图由授权名单列明；帧按 schema 校验 | 每秒请求数、订阅规模、单帧字节数；超限返回明确错误（律法 L05） |
| Agent 应用页面 | 键前缀 `app/<应用>/`；不能读平台节点，除非授权列出 | 写入按应用 schema 校验类型和大小 | 存储配额、写入速率 |
| 进程型提供方（Python/CLI 后端） | 以该 OS 用户身份运行，只能注册授权中列出的命名空间 | 发布的数据按 schema 校验 | 发布速率、单条大小、命名空间配额 |

授权模型遵循 product-authority：已认证的完整连接拥有该 OS 账号的全部权限；受限授权只用于展示分享、预览和应用，形态是"键前缀 + 意图名单"，不引入按项目或按 Agent 的 ACL。

## 7. 平台作为第一个应用

- **平台 schema `genehub.platform`：** 会话、Space、Agent、进程、文件、Git、日志、机器总览，内容见 v5 第 3–10 节和 v4 第 7 节的族映射。
- **平台各族是提供方：**
  - 会话族 = 存储型（会话文件）+ 计算型（摘要、视图）+ 观察型（运行状态）。
  - 文件与 Git = 观察型。
- **工作台用 TS SDK，CLI 和 Python 用 CLI 接口**，都是同一个核心层的消费方。
- v5 中"同步内核"的职责按两层重新划分：
  - 归核心层：基线表、背压、调度。
  - 归提供方和节点定义工具：比较逻辑、视图、令牌、内存读模型、缓存快照。
  - 归 TS SDK：预表现。

## 8. 性能性质由核心层保证

无论数据来自哪里、消费方是谁，以下性质都成立：
- **G1 读取与范围成正比。**
- **G2 同步与变化成正比。**
- **G3 内存有上界：** 核心层只存基线令牌和脏键，数据在提供方和消费方。
- **G4 不排队。**
- **G5 与权威数线性相关。**

提供方要配合两条义务：`diff` 的代价与返回的数据量成正比；`resolve` 支持按预算分批。这两条写进提供方合同，由合同测试检查。

节拍模式的 G6（节拍预算）和 G7（丢包自愈）随游戏场景一起，前期不做。

## 9. 覆盖边界与取舍

| 事物 | 为什么不在核心层 | 处理 |
| --- | --- | --- |
| 数据存储 | 存储只是数据源的一种提供方式 | 存储型提供方 |
| 节点格式、视图、hash | 属于数据的定义 | 节点定义工具与 schema |
| 副本存储、预表现、界面 | 属于数据的消费 | TS SDK、CLI、Python |
| 音视频媒体流 | 是连续信号，不是可比较的状态 | 现有媒体通道；核心层只同步它的元数据 |
| 交互输入（按键、PTY 输入） | 是有顺序的命令流 | 意图，或现有输入通道 |
| 游戏的确定性模拟、物理、延迟补偿 | 游戏领域逻辑 | 游戏逻辑；前期不做 |
| 多人实时协同编辑 | 需要可合并类型 | 将来作为节点定义工具中的可合并节点；前期不做 |
| 大文件内容 | 不适合放进帧 | 提供方只发元数据和令牌，内容走现有传输数据面 |

**取舍原则：**
- 核心层只做五个要素的调度，越薄越稳定。
- 一切与"数据是什么、放在哪、给谁看"有关的，都在提供与消费层。
- 新场景只增加提供方、节点定义或消费方，不改核心层。
