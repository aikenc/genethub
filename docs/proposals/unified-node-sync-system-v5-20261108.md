## 摘要

**体验影响。** 一个用户要管理十几台机器、几百上千个 Space、上万个会话。现在的问题是：
- 打开和重连慢，手机恢复慢。
- 列表之间互相放大开销。
- 文件和 Git 面板不会自动更新。
- 团队脚本靠轮询，`--machine` 每次都重新连接。
- 机器越多、会话越多越慢。

这些问题出在不同地方，但根源相同：每类信息自己发明读取、缓存和推送，性能问题出现一次就在那一族打一次补丁。

**怎么解决（待实施）。**
- **三层：** 持久层是唯一的源；缓存层可以丢失、可以重算；应用端有副本，也有自己的瞬态数据。
- **一种对象：** 节点。所有同步都是对节点的写入、删除和追加；流式输出只是"追加"这一种写法。
- **一个比较函数：** 读取、断线恢复、推送、背压都用它。
- **令牌取自源头：** 文件的令牌直接由文件系统元数据（inode、大小、修改时间、状态变更时间）算出，不读内容，也不建中心化元数据库。
- **三层软件结构：** 协议层（帧与编码）、框架层（与业务无关的同步引擎，Rust 和 TS 各一份）、接口层（发布者 API、页面 hooks、CLI）。
- **性能是体系的性质：** 代价只与"变了多少"和"看了多少"成正比，与机器数、会话总量无关。新增业务族只写发布者，自动获得缓存、恢复、推送、CLI 和多机能力。

**怎么防止复发。**
- 一份发布者合同，明确禁止族内自建缓存、自建推送帧、轮询和翻页循环。
- 防回流测试。
- 第 14 节的规模验收（均未执行）。

## 1. 根因：为什么过去总在打补丁

v4 第 2 节和第 8.1 节的源码证据显示，现在每一族都有自己的一套读取、缓存和推送：

| 族 | 读取 | 缓存 | 推送 | 为性能打过的补丁 |
| --- | --- | --- | --- | --- |
| 会话目录 | `session.list`、`session.page` | `PageCatalog`、`CatalogProjection`、浏览器 IndexedDB 目录缓存、`store.ts` 第二份目录 | `Catalog` 帧 | `catalog.sync` 已知清单（最多 12,000 项）、`summary_etag`、页面翻页循环 |
| 会话正文 | `inspect/narrative/rounds/context` | `Live` | `Event` 帧 + `subscribe` 重放 | `Desync`、`read_view` 全量构造 |
| Agent、进程、PTY | 各自的 list | 无 | `AgentsChanged`、`BackgroundProcesses`、`PtyOutput` | 无 |
| 文件、Git | `file.tree`、`git.status` | 无 | 无 | 手动刷新 |
| CLI | 复用上面各 RPC | 无 | 无 | `session list` 循环翻页，`--machine` 每次重新连接 |

规模一上来，每一族都会再遇到同样的问题，再各打一次补丁。所以要换的是同步体系本身，而不是继续优化某一族。

**设计目标：** 性能必须是体系的性质，而不是某一族的实现细节。

## 2. 规模目标与性能性质

**规模（每个用户）：** 15 台机器，1,000 个 Space，合计 20,000 个会话，单台最多 12,000 个；同时在线 3 个客户端（桌面、手机、浏览器）和若干 CLI `--watch`。

**五条性能性质，由内核保证，任何一族都不需要单独实现：**

| 编号 | 性质 | 含义 |
| --- | --- | --- |
| G1 | 读取与范围成正比 | 一次读取的代价只与订阅范围（看了多少）有关，与会话总量、Space 总量无关 |
| G2 | 同步与变化成正比 | 重连和推送的代价只与"上次核对以来变了多少"有关；内容不变时，每台机器一次往返、几百字节 |
| G3 | 内存有上界 | daemon 内存 = 常驻目录（与会话数线性，约 600 B/条）+ 各订阅范围之和，有总预算 |
| G4 | 不排队 | 慢消费者只积累"脏路径"，不积压消息；流也一样 |
| G5 | 机器数线性 | 15 台机器的总览开销是 15 份小节点，不随机器内容增长 |

## 3. 三层模型

| 层 | 是什么 | 能否丢失 | 丢了怎么恢复 | 例子 |
| --- | --- | --- | --- | --- |
| **a 持久层**（唯一源） | 拥有方机器上的持久事实 | 不能 | — | 会话 `meta.json`、`chat.jsonl`、轮次与 blob，工作区 registry，配置，Hub SQLite |
| **b 缓存层** | 从持久层和其他状态计算出来的数据，以及尚未持久化的瞬态数据；放在内存或临时文件里 | 可以 | 从 a 重算；运行状态重新观察；瞬态数据丢失后，已落盘的部分仍在，未落盘的明确标为"中断" | 摘要、排序索引、视图、项目状态卡；进程和 Agent 运行状态；流式 token；远端机器节点的副本；缓存层快照文件 |
| **c 应用端** | 节点副本，加上应用端自己的瞬态数据 | 可以 | 副本用 `get` 重新核对；瞬态数据随操作回执消失 | IndexedDB 中的节点副本；操作预表现（例如消息先显示为"发送中"）；滚动位置等界面状态 |

**每个节点声明持久性：**
- `persistent`：持久层的投影，重启后相同的源得到相同的令牌。
- `derived`：由其他节点或运行观察计算得出，可以重算。
- `transient`：可以丢失，例如流式 token。

应用端据此决定怎么展示：`transient` 丢失时显示"中断"，不显示"已删除"。

**现有代码已经有缓存层临时文件的雏形。** 流式输出中的半成品会定期写入 `open-turn.jsonl`，轮次落盘后清除（`store.rs` 第 2483–2535 行，`manager.rs` 的 `persist_open_trunk` 与 `flush_turn`）。这正是"可丢失、可重算的缓存层数据"。v5 把它纳入统一的 `transient` 节点。

### 3.1 易变不等于不能缓存

会话列表是易变的，但这不意味着每次都要从磁盘重新读。这里有三样东西被缓存，"易变"只影响第三样的令牌变化频率：

| 缓存什么 | 在哪一层 | 如何保持最新 | 是否读磁盘 |
| --- | --- | --- | --- |
| 实体（每条会话的摘要） | b 和 c | 持久层每次写入后，增量更新这一条 | 不读：写入点直接更新 |
| 排序索引（按 `updatedAt` 排好的全部会话） | b | 摘要更新时，在有序索引里移动这一条，`O(log n)` | 不读：现有 `PageCatalog.order` 就是这样的 `BTreeMap` |
| 视图窗口（例如最近 100 条的有序 id） | b 现算，c 保存上次结果 | 在内存索引上取前 100 条，代价与窗口大小成正比，微秒级 | 不读 |

**只有两种情况读磁盘：**
- **冷启动：** 构建缓存层，要逐个读取 12,000 个 `meta.json`。为避免每次重启都全量读取，在 daemon 数据目录 `<data>/cache/sync/` 下为每个项目放一份**缓存快照**（摘要、令牌、源文件的文件戳）。启动时只对源文件做元数据检查，只重读文件戳变了的；快照损坏就丢弃，按全量读取重建。具体见 3.2。
- **外部改动对账：** 只对有订阅的 B 类数据做。

**其他易变数据是同一个模式，按同样的方式处理：**

| 数据 | 易变在哪里 | 缓存层维护什么 | 视图或节点 |
| --- | --- | --- | --- |
| 项目（Space）列表 | 按最近活动排序，1,000 个 Space | 每个 Space 的状态卡，按活动时间的有序索引 | `spaces.recent` 视图，按窗口分页 |
| Agent 与运行状态 | 运行、等待、请求权限，随轮次跳变 | 运行观察（`derived`，重启后重新观察） | `agents/<id>`，`sessions.active`、`sessions.attention` 视图 |
| 进程列表 | 启动、退出 | 进程注册表 | `processes` 视图、`processes/<id>` |
| Git 状态、文件树 | 外部编辑、构建产物 | 有订阅时由 watcher 增量维护 | `git/<ws>/status`、`files/<ws>/<path>` |
| 机器在线、版本 | 心跳 | 只保留状态跳变，心跳时间不进入令牌 | `machine/overview` |
| 流式 token、PTY、日志 | 每秒很多次 | 追加缓冲区，按 `(epoch, 长度)` 定位 | 追加节点 |

所以，没有哪一类数据"无法缓存"。区别只在于令牌变化得快还是慢；变得快的，核对时更常需要重传，但永远只重传变了的那部分。

### 3.2 源头：文件系统能提供什么样的"免内容 IO"信号

**结论：** 文件系统不提供可移植、免读取的内容 hash。Btrfs、ZFS 的校验和是块级的内部数据，没有按文件取用的通用接口。但它提供两类**不读文件内容**的变化信号，足够作为令牌的源头。

| 信号 | 内容 | 代价 | 平台 |
| --- | --- | --- | --- |
| 文件元数据（stat） | 大小、修改时间（mtime，纳秒）、状态变更时间（ctime）、inode 或文件 ID、设备号 | 一次元数据 IO，不读内容 | 全平台；Windows 的状态变更时间要用 `GetFileInformationByHandleEx` 取 `ChangeTime` |
| 目录元数据 | 目录的 mtime 在其中增删、改名条目时变化；文件内容变化不影响 | 一次元数据 IO | 全平台 |
| 持久变化日志 | 可以查询"某个位置以来变了什么"，重启后也能续查 | 读日志 | macOS FSEvents（事件 ID）；Windows NTFS USN 日志 |
| 实时变化通知 | 只在进程运行期间有效 | 内核推送 | Linux inotify/fanotify、macOS FSEvents、Windows `ReadDirectoryChangesW` |

**业界的做法相同：先看元数据，元数据变了才读内容。**
- **Git：** 索引里为每个文件缓存大小、mtime、ctime、inode。`git status` 只做 stat，stat 变了才重新算 hash。mtime 落在写索引的同一时间粒度内时视为"可疑"并重读（racy-git 规则）。需要时用 fsmonitor 免去全量 stat。
- **rsync：** 默认用"大小 + mtime"做快速判断。
- **Bazel：** 按 stat 缓存文件摘要。
- **Spotlight、Windows Search：** 分别依靠 FSEvents 和 USN 日志做增量索引。

**本方案的做法：令牌直接取自源头的元数据。**
- **文件型节点：** `token = H(设备号, inode, 大小, mtime_ns, ctime_ns)`，零内容 IO。只有令牌变了，才读内容重新投影；派生节点（例如摘要）的令牌再由投影结果算出。
- **目录清单节点：** 数据只含名字和类型，令牌取自目录本身的元数据，一次 stat 就知道条目有没有变。文件大小和内容变化由各自的文件节点表示，不放进目录清单。
- **我们自己写的文件，根本不需要检测：** daemon 就是写者，在写入点直接更新节点（3.1）。文件元数据只在两种时候用：冷启动校验，以及别的程序改了这些文件。
  - 会话元数据每次都写临时文件再改名替换（`config.rs` 第 722–736 行），每写一次 inode 都会变，所以元数据令牌一定能察觉。
- **现状要补的一处：** `MetadataStamp` 只记了修改时间和大小（`store.rs` 第 1003–1010 行）。`cp -p`、`rsync -t`、解压等工具会保留 mtime，大小又恰好不变时就会漏检，需要补上 inode 和 ctime。

**陷阱与防护：**

| 陷阱 | 防护 |
| --- | --- |
| 工具保留 mtime（`cp -p`、`rsync -t`、`tar`） | 令牌包含 ctime 和 inode：Unix 上 ctime 无法由用户态程序随意设置，原子替换一定换 inode |
| 时间粒度粗（FAT 2 秒、HFS+ 1 秒）导致同一粒度内的两次写入看起来一样 | 采用 racy-git 规则：mtime 与上次检查落在同一粒度内的文件标为可疑，下次检查时重读内容 |
| 时钟回拨 | 令牌只比较相等，不比较先后 |
| 网络文件系统（NFS、SMB）没有可靠的变化通知，stat 也慢 | 只对有订阅的部分按预算定期做 stat 对账，节点附带观察时间 |
| Linux 没有持久变化日志，重启期间的外部改动无从查询 | 冷启动时对缓存快照涉及的文件做一遍 stat 对账；macOS、Windows 可以选用持久日志免去这一步，作为可选优化 |
| inotify 有监听数量上限 | 只监听有订阅的目录，超限时退回定期 stat，并标为"未完整" |

**不建中心化元数据库。**
- 缓存快照放在 `<data>/cache/sync/`，按项目根路径分开存放。storage-layout 规定缓存属于 `<data>`，每个 channel 一份，可以随时删除（v6 第 0 节）。
- daemon 内存只是缓存层，令牌全部能从文件系统重新算出。
- 冷启动的代价分三档（数字均需测量）：
  - 有快照：只 stat 12,000 个文件，然后只重读变了的。
  - 有快照，且平台有持久日志：只读日志。
  - 没有快照：全量读取。
- **项目文件与 Git：** 只对有订阅的目录启用 watcher，并用 stat 对账兜底。Git 状态在 `.git/index`、`.git/HEAD` 和引用变化时重算。Git 自己也是用 stat 缓存来加速，与本方案原则一致。现在代码里还没有文件监听依赖（Cargo 只有 `ignore`；Git 通过 `git.rs` 调用命令行），由框架层的监听源统一引入。

## 4. 节点与操作：一切同步都是节点的增删改查

### 4.1 节点

| 字段 | 含义 |
| --- | --- |
| `path` | 唯一身份，例如 `session/s_1/summary`。视图的身份是视图名加按键排序的参数，例如 `sessions.recent?ws=w_1&limit=100` |
| `kind` | `value`（整份替换）或 `append`（只在尾部追加） |
| `durability` | `persistent`、`derived` 或 `transient`（第 3 节） |
| `token` | 校验令牌，只用于判断"要不要更新"，不是版本号，也不保存历史 |
| `data` | 规范编码的数据 |

**令牌规则：**
- `value` 节点：`token = SHA-256(规范编码)` 截取 128 位。容器节点的数据就是子节点的 `[(名字, token)]`，所以子节点一变，容器的令牌也跟着变。
- `append` 节点：`token = (epoch, 长度)`。拥有方保证同一个 epoch 内只追加不改写，所以长度相同就代表内容相同。持久的追加节点（例如时间线）用会话 id 和格式版本作为 epoch，重启后不变；瞬态的追加节点用拥有方实例 id，重启后就变了。

**视图也是 `value` 节点：** 数据是有序的 `[(id, 排序键)]`，由缓存层在有序索引上现算，不存放。它和普通节点一样有令牌，可以被比较和推送。

### 4.2 三种写操作，一个比较函数

所有变化都表示成三种操作：

| 操作 | 含义 | 是否幂等 |
| --- | --- | --- |
| `put(path, token, data)` | 新建或整份替换 | 是：按路径覆盖 |
| `del(path)` | 删除 | 是 |
| `append(path, from, token, data)` | 从长度 `from` 起追加 | 是：`from` 不连续时拒收，再按比较函数补齐 |

流式推送就是连续的 `append`，没有单独的帧，也没有单独的语义。

**比较函数 `D(已知令牌, 当前节点)`** 是整个体系唯一的同步算法：

| 情况 | 产生的操作 |
| --- | --- |
| 令牌相同 | 无 |
| 对方没有这个节点 | `put` |
| `value` 节点，令牌不同 | `put`；如果是容器，就对范围内的子节点递归 |
| `append` 节点，epoch 相同，已知长度仍在保留窗口内 | `append` 从已知长度起的尾部 |
| `append` 节点，epoch 不同，或已知长度已经超出保留窗口 | `put` 一份快照（已封存部分用容器引用，尾部内联） |
| 节点已不存在 | `del` |

读取、断线恢复、推送和背压都只调用 `D`：
- **读取与恢复：** 客户端在 `get` 中带上已知令牌，拥有方对范围内的每个节点运行 `D`，一次返回全部操作。
- **推送：** 拥有方为每个连接记一张"已告知令牌表"。节点变化只标脏；连接可写时，对脏节点运行 `D(已告知令牌, 当前节点)`。
- **背压：** 连接写不动时只积累脏路径。恢复后运行一次 `D`，自动把多次变化合并成一个操作；流也一样，合并成一段从已告知长度开始的 `append`。不需要队列，也不需要 `reset`。

### 4.3 写入：意图在上，效果是节点操作

客户端的写入有两种：
- **可直接写的节点：** 草稿、标签、界面设置这类没有副作用的节点，节点声明为 `writable`，客户端直接发 `put/del`，拥有方校验后提交。`put` 可以带 `ifToken`：拥有方当前的令牌与之不同就拒绝，两台设备同时改同一份草稿时，后到的一方会收到冲突，不会悄悄覆盖。
- **有副作用的意图：** 发送消息、批准权限、启动进程、改名这类要触发运行或维护不变量的操作，用具名操作 `call(name, args, opId)`。

两种写入的回执都一样：`{opId, outcome: committed | rejected | unknown, ops}`。`ops` 就是这次写入对节点造成的效果，与推送的格式相同。

为什么不把一切写入都做成裸的 `put`：发送消息会启动 Agent，批准权限会恢复执行。这些不变量属于持久层的拥有方，不能交给客户端去拼数据。业界同样如此：Replicache 和 Zero 用具名 mutator，而不是让客户端直接改行。

所以准确的说法是：**同步就是节点的增删改查；写入是意图，它的效果也是节点的增删改查。**

## 5. 协议层：四个帧

| 方向 | 帧 | 作用 |
| --- | --- | --- |
| 客户端 → 拥有方 | `get` | `{scope, known, watch}`：读取、恢复、订阅都用它；不带 `watch` 就是一次查询 |
| 客户端 → 拥有方 | `drop` | `{scope}`：取消订阅 |
| 客户端 → 拥有方 | `call` | `{opId, name 或 put/del, args}`：写入 |
| 拥有方 → 客户端 | `ops` | `{ops, unknown, done, opId?, outcome?}`：读取回复、推送、流、写入回执，全部是它 |

```json
{"type":"get","scope":[{"view":"sessions.recent","ws":"w_1","limit":100,"include":"summary"},{"path":"session/s_1","depth":2}],"known":{"sessions.recent?limit=100&ws=w_1":"9f…","session/s_9/summary":"c2…","session/s_1/timeline":["s_1.v10",8812]},"watch":true}
```

```json
{"type":"ops","ops":[
  {"op":"put","path":"sessions.recent?limit=100&ws=w_1","token":"a1…","data":[["s_9",1762571000000],["s_3",1762570400000]]},
  {"op":"put","path":"session/s_9/summary","token":"d4…","data":{"title":"…"}},
  {"op":"append","path":"session/s_1/timeline","from":8812,"token":["s_1.v10",8813],"data":"…"}],
 "unknown":[],"done":true}
```

```json
{"type":"call","opId":"op_7f2","name":"session.rename","args":{"sessionId":"s_9","title":"B"}}
```

```json
{"type":"ops","opId":"op_7f2","outcome":"committed","ops":[{"op":"put","path":"session/s_9/summary","token":"e5…","data":{"title":"B"}}],"unknown":[],"done":true}
```

**范围语言：**
- `{path, depth}`：实体及其下几层。
- `{view, 参数, limit, after, include}`：视图窗口；`include` 表示把视图里列出的实体子节点一起纳入范围，列表和它显示的摘要一次拿齐；`after` 是键集游标，页面向下翻页和 CLI `--cursor` 用同一个参数。

**共享合同（Rust 和 TS 逐字节一致，最先冻结）：**
- 路径与视图身份的语法。
- 规范编码：键排序的 JSON，不含浮点数，不含多余空白。
- 令牌算法与共享测试向量。
- 预算：单帧 256 KiB、512 个操作；视图 `limit` 最大 1,000；每连接已告知令牌表最多 20,000 项。
- `unknown` 原因：`offline`、`scope`、`budget`、`warming`、`error`。

协议类型由 ts-rs 从 Rust 生成到 `packages/proto/bindings/index.ts`。连接与控制（`hello`、认证、配对、Hub 票据）以及实时媒体（RTC、语音、PTY 与 shell 输入）不在这四个帧里，保持现状。

## 6. 软件结构：协议层、框架层、接口层

```text
业务：各族发布者、页面组件、CLI 命令
  │ 只使用
接口层：发布者 API（Rust）、消费者 API 与 hooks（TS）、通用 CLI 命令、节点 schema
  │ 只使用
框架层：与业务无关的同步引擎（拥有方引擎、消费方引擎），Rust 与 TS 各一份
  │ 只使用
协议层：四个帧、范围语言、规范编码、令牌、预算与错误码、测试向量
  │
传输：WebSocket、Fabric、/cli 回环、进程内调用
```

**依赖规则（由编译期依赖和防回流测试保证）：**
- 业务代码看不到帧、令牌和传输。
- 框架层看不到业务类型：数据对它来说只是"规范编码的字节 + schema id"。
- 新增一个业务族，不改协议层，也不改框架层。

### 6.1 协议层

| 内容 | 位置 |
| --- | --- |
| 四个帧、范围语言、操作类型、回执 | `packages/proto/src/sync/`，由 ts-rs 生成 TS 类型 |
| 规范编码、令牌算法 | 同上 |
| 共享测试向量（编码、令牌、比较函数的输入输出） | `packages/proto/fixtures/sync/`，Rust 和 TS 的测试都读它 |
| 版本 | `hello` 中的 `sync.v1` 能力位；只增字段，未知字段忽略；不兼容的改动升为 `sync.v2` |

传输只负责搬运帧：WebSocket、Fabric 对等链路、`/cli` 回环使用同一套帧。本地 CLI 走进程内调用，直接传协议层的 Rust 类型，省掉序列化。

### 6.2 框架层

**拥有方引擎**（daemon 用 Rust；Hub 所在的 Cloud 服务端是 TypeScript，所以 TS 也要有一份精简实现）：

| 组件 | 职责 |
| --- | --- |
| 节点表 | 路径 → `{kind, durability, token, data?}`；数据可以按预算淘汰，需要时通过发布者从持久层重新加载 |
| 令牌 | 规范编码 hash；文件元数据令牌（3.2）；追加节点的 `(epoch, 长度)` |
| 来源 | 写入点钩子、元数据对账、文件监听（inotify/FSEvents/ReadDirectoryChangesW）、运行观察，统一转换成"某路径变脏" |
| 派生调度 | 依赖图，脏传播，按 `WorkBudget` 分片让出 |
| 视图 | 有序索引、视图计算、跨视图参数校验 |
| 订阅 | 每个连接的范围、已告知令牌表、脏集合、比较函数 `D`、背压 |
| 写入 | `opId` 去重表、`ifToken` 校验、具名操作分发、回执 |
| 快照 | 缓存快照的写入、加载、按文件戳校验、损坏时丢弃 |
| 预算 | 内存总预算、每连接上限、淘汰顺序 |

**消费方引擎**（TS 供页面和 Console 使用；Rust 版供 daemon 的远端副本和 CLI `--machine` 使用）：

| 组件 | 职责 |
| --- | --- |
| 副本 | 内存加 IndexedDB（Rust 版只用内存），以路径为键保存 `{token, data}` |
| 预表现 | 按 `opId` 叠加预测效果，由回执消除 |
| 链路 | 每个拥有方一条连接；重连时带已知令牌发 `get` |
| 范围合并 | 把各个界面组件声明的需求做引用计数后合并成范围，再转成 `get` 和 `drop` |
| 归并 | 跨机器的视图 k 路归并 |
| 状态 | 已核对、上次状态、未知、未确认 |

**实现位置：**
- `packages/sync/`：新的 Rust crate，包含两个引擎。
- `packages/sync-ts/`：新的 TS 包，包含消费方引擎和精简的拥有方引擎，供 workbench 和 Cloud 共用。
- 两份实现的一致性由共享测试向量保证。

另一种选择是把 Rust 引擎编译成 WASM 给浏览器用，只维护一份实现。代价是包体积、IndexedDB 要经过 JS 胶水层、调试更困难；而且 Cloud 服务端仍然需要 TS 版。所以暂不采用，S1 测量两份实现的差异成本后再定。

### 6.3 接口层

**发布者 API（Rust，供 daemon 中的各族使用）：**

```rust
pub trait Publisher {
    fn schema(&self) -> Schema;                      // 节点模式、kind、durability、视图、writable、calls
    fn load(&self, path: &Path) -> Result<Bytes>;    // 从持久层重新加载被淘汰的数据
    fn validate_put(&self, path: &Path, data: &Bytes) -> Result<()>;
    async fn call(&self, name: &str, args: Value, cx: &mut Effects) -> Result<Value>;
}

// 框架交给发布者的句柄：只能在持久层提交之后调用
cx.put(path, data); cx.del(path); cx.append(path, bytes); cx.seal(path);
cx.observe_file(path);   // 以文件元数据作为令牌源头
```

**消费者 API（TS，供页面使用）：**

```ts
const summary = useNode(machine, nodes.sessionSummary(id));      // {data, status}
const recent = useView(machine, views.sessionsRecent({ ws, limit: 100, include: "summary" }));
const all = useMergedView(machines, views.sessionsRecent({ limit: 100 }));
await sync.call(machine, calls.sessionRename({ sessionId, title }), {
  predict: (o) => o.put(nodes.sessionSummary(sessionId), { title }),
});
```

**节点 schema：** 每个节点模式的数据类型只在 Rust 里定义一次，例如 `session/{id}/summary` 对应 `SessionSummary`，由 ts-rs 生成 TS 类型。`nodes.*`、`views.*`、`calls.*` 是由 schema 生成的带类型构造器，页面不手写路径字符串。

**CLI：**
- **通用命令**，供脚本和诊断使用：
  - `genet sync get <path> [--depth N]`
  - `genet sync view <name> [--ws ..] [--limit N] [--cursor C]`
  - 两者都可以加 `--watch` 和 `--machine X`
- **现有产品命令**（`session list/get` 等）的命令面保持不变，内部改为调用同一个接口层。

## 7. 多机与规模

**拓扑：**
- 每台机器的 daemon 拥有自己的节点。
- Hub 拥有机器目录、placement 和在线状态，也作为拥有方发布节点。
- 页面直接连每台机器：15 台就是 15 条连接，各自独立核对，一台离线只把它标为未知。
- CLI 经本地 daemon 访问远端：本地 daemon 维护链路池，远端节点的副本属于本地缓存层。

**每台机器固定发布三个小节点，供总览使用：**
- `machine/overview`：会话数、活动数、待处理数、Space 数、daemon 版本、健康状态。约 300 B。
- `sessions.attention`：需要用户处理的会话，例如请求权限、出错、收件箱有新内容。通常不到 20 条。
- `sessions.active`：正在运行的会话。

**跨机器的"全部最近会话"不需要全局节点。** 应用端订阅每台机器 `sessions.recent` 的前 N 条，再按排序键做归并。全局前 N 一定包含在各机器前 N 的并集里，所以归并结果是精确的，不是近似。

**规模下的成本（设计目标，未测量）：**

| 旅程 | 传输与处理 | 与总量的关系 |
| --- | --- | --- |
| 打开工作台，15 台机器 | 每台一次 `get`：总览、待处理、头部视图（含摘要）。冷启动约 15 × 60 KB；有缓存且没有变化时约 15 × 300 B | 只与机器数和窗口大小有关 |
| 管理 1,000 个 Space | `spaces.recent` 视图按窗口加载，每次 100 个 | 与窗口大小有关 |
| 某台机器上一个 Agent 完成一轮 | 看着这台机器的连接收到：1 条摘要、1 个视图的 id 列表、总览，约 4 KB | 与变化有关 |
| 手机断线 10 分钟后恢复 | 每台机器一次 `get`，只回变了的节点 | 与变化有关 |
| 打开 3,000 轮的会话 | 摘要、`state`、时间线最后几个已封存分段、尾部 | 与可见范围有关 |
| PM 脚本 `--watch` 全队状态 | 空闲时零流量；有变化时每次一个 JSONL 行 | 与变化有关 |
| 跨 15 台机器搜索 | 每台机器执行一次查询视图，应用端归并 | 与结果大小有关 |

## 8. 应用端：副本与预表现

- **副本：** IndexedDB 以路径为键，保存与拥有方逐字节相同的 `{token, data}`，按账号范围和机器隔离，总预算 64 MiB，超出时淘汰最久未用的。副本可以随时删除，删除后只是下一次 `get` 变成冷启动。
- **预表现层：** 每个待确认的写入按 `opId` 在副本之上叠加预测的效果，例如消息先显示为"发送中"，标题先显示为新值。预表现层从不写进副本。
- **回执对账：**
  - `committed`：回执里的 `ops` 已经写进副本，删除这一层预表现。
  - `rejected`：删除这一层预表现，提示失败原因。
  - `unknown`：保留并标为"未确认"，按 `opId` 查询结果，不自动换 id 重发。
- **界面看到的 = 副本 ⊕ 预表现。** 每个节点处于下列状态之一：已核对、上次状态、未知（附原因）、未确认（有待确认的写入）。

## 9. 三层一致性不变量

| 编号 | 不变量 | 怎么保证 |
| --- | --- | --- |
| I1 单一来源 | 每个节点只有一个拥有方能写；`persistent` 节点只来自持久层 | 内核拒绝非拥有方写入；发布者合同 |
| I2 先落盘再发布 | 持久层原子提交 → 缓存层更新 → 标脏推送；缓存层不得先于持久层改变 | 发布者只能在提交点调用 `put`；故障注入测试 |
| I3 缓存层可重算 | `persistent` 和 `derived` 节点是持久层与运行观察的纯函数：相同输入得到相同令牌，重启后不变 | 令牌确定性测试；重启后令牌对比 |
| I4 副本逐字节 | 应用端副本与缓存层的数据和令牌逐字节相同，可以校验 `H(data) == token`；应用端不自行派生节点数据 | 共享测试向量；应用端校验 |
| I5 预表现不污染副本 | 预测效果只在预表现层，由回执消除 | 应用端合同测试 |
| I6 未知不等于空 | 拥有方离线、超预算、出错时标为未知并保留上次内容；不在视图窗口里不等于被删除，只有 `del` 才是删除 | 内核与应用端合同测试 |

## 10. 防补丁：新增一个业务族只需要什么

**发布者合同：**

```text
publisher <族名>:
  nodes:     路径模式、kind(value|append)、durability(persistent|derived|transient)
  sources:   持久层的写入点；运行观察；外部观察（watcher + 对账）
  derive:    依赖表：哪个输入变了，重算哪些节点
  views:     视图名、排序键、可选过滤参数
  writable:  允许客户端直接 put/del 的节点及校验规则
  calls:     具名写操作，以及它们产生的节点效果
```

写完这份声明，这一族自动获得：
- 缓存层维护与预算。
- 一次往返的恢复。
- 比较式推送与背压。
- 应用端副本与预表现。
- CLI 读取、`--watch` 与 `--machine`。
- 多机总览。

**明确禁止（由防回流测试检查）：**
- 族内自建缓存或第二份目录。
- 新增族专用的推送帧或读 RPC。
- 轮询，或在客户端循环翻页。
- 应用端自行拼装本应由拥有方发布的数据。
- 把心跳时间、相对时间、token 计数放进令牌。

遇到性能问题时，只允许两种改法：调整范围（看得更少），或改进内核（所有族同时受益）。不允许在某一族里打补丁。

## 11. 覆盖度：能高效覆盖什么，不能覆盖什么

v4 第 7 节的 27 个方法族都能映射到节点。下面按"效率"再分三档，并说明每个取舍。

**高效覆盖：** 天然符合"单一拥有方、按 id 寻址、变化频率不高于每轮"的模型。
- 会话目录、摘要、状态、时间线（追加节点加已封存分段）。
- Space 与项目列表、项目状态卡。
- Agent、Provider（凭证不进入节点）、设置。
- 进程列表、设备、更新状态、日志（追加节点）。
- 机器总览、待处理、运行中，以及 Hub 的机器目录与 placement。
- 团队协调投影、预览批注与制品清单。
- CLI 读取、`--watch`、`--machine`。

**可以覆盖，但有代价：**

| 场景 | 代价在哪里 | 取舍 |
| --- | --- | --- |
| PTY 输出、流式 token | 追加节点在语义上完全吻合，但对延迟敏感；JSON 帧有额外开销 | 连接可写时立即发送，不等合并窗口；S3 测回显延迟，劣化就为追加数据启用二进制编码。PTY 输入不进入节点（见下一张表） |
| 大型项目的文件树（如 `node_modules`、十万级文件） | 不能对整棵树维护令牌；Linux 监听数量有上限 | 只维护有订阅的目录，按层展开；超出预算时标为"未完整"，不追求整棵树一致 |
| 网络文件系统上的项目 | 没有可靠的变化通知，stat 也慢 | 按预算定期 stat 对账，节点附带观察时间；界面显示"可能滞后" |
| 大文件与二进制内容（视频、大资源、下载） | 单帧上限 256 KiB；整份 `put` 不合理 | 节点只放元数据和令牌；内容走现有的传输与预览数据面（分块、断点续传），用令牌判断是否需要重新下载 |
| 全文搜索（会话、文件内容） | 无法增量维护，也不适合订阅 | 搜索是一次性的查询视图，代价与扫描的数据量成正比，结果不实时更新；需要时再把索引做成独立的派生节点 |
| 长任务进度（更新下载、文件传输） | 进度变化频繁，令牌会持续变化 | 用瞬态节点表示，进度按 1% 一档进入令牌，细粒度进度不进入令牌 |
| 跨机器操作（fork 到另一台、跨机传输） | 没有分布式事务 | 拆成两台机器上各自独立的意图，用 `machineId + id` 关联；中间状态显示为"进行中"或"未知" |
| 两台设备同时修改同一个可写节点 | 单一拥有方，不做合并 | `put` 带 `ifToken`，后到的一方收到冲突，由用户决定；不做自动合并 |
| 手机同时连 15 台机器 | 连接数、电量和流量 | 只为有关注内容的机器保持完整订阅，其余只订阅总览；需要实测（第 15 节） |

**不覆盖（刻意排除）：**

| 场景 | 为什么不覆盖 | 用什么 |
| --- | --- | --- |
| 实时媒体（RTC、语音音频、远程桌面画面） | 允许丢包、要求时序，与"按令牌补齐"的语义相反 | 现有媒体通道 |
| 交互输入（PTY 和 shell 的标准输入、远程桌面输入） | 每次按键都是有顺序的命令，不是状态 | 现有输入通道；输出部分仍是追加节点 |
| 多人实时协同编辑同一份文档 | 需要 CRDT 或 OT 做并发合并；本方案是单一拥有方加意图 | 当前产品没有这个场景；将来需要时作为独立的节点类型引入，不改现有模型 |
| 长时间离线编辑后再合并 | 拥有方不在线就无法提交 | 短时断线时，未确认的写入可以用同一个 `opId` 安全重发；长时间离线编辑不支持 |
| 历史回看（"昨天这个列表长什么样"） | 不保存版本，令牌只用来判断要不要更新 | 历史存放在持久数据里（时间线、Git） |
| 跨拥有方的一致快照或事务 | 每个拥有方各自独立，没有全局时钟 | 应用端按 id 现场组合，缺失的来源标为"缺源" |
| 细粒度访问控制 | 产品约定：认证后的完整连接拥有该 OS 账号的全部权限（见 product-authority） | 只读展示分享按路径前缀限定范围 |
| 连接控制面（配对、认证、Hub 票据） | 建立连接之前就要用到 | 控制协议；daemon 重启、安装更新等动作仍是 `call` |

**取舍原则：**
- 不为少数场景让核心模型变复杂。
- 能用"缩小范围"解决的，就不引入新机制。
- 语义本身不同的（媒体、输入、协同编辑），留在各自的专用通道，不硬塞进节点模型。

## 12. 与 v4 的差异

| 方面 | v4 | v5 |
| --- | --- | --- |
| 分层 | L0–L4 五层，按模块划分 | 持久、缓存、应用三层，按"是否唯一源、能否丢失"划分；每个节点声明持久性 |
| 对象 | 实体、视图、流三种节点 | 一种节点，两种 `kind`；视图是现算的 `value` 节点 |
| 变化 | 变化通知加单独的流帧 | `put`、`del`、`append` 三种操作；流就是连续的 `append` |
| 帧 | `sync.check`、`sync.nodes`、`sync.append`，加各族的动作 RPC | `get`、`drop`、`call`、`ops` 四个帧；写入回执也是 `ops` |
| 校验值 | 所有节点都用内容 hash | `value` 用内容 hash，`append` 用 `(epoch, 长度)`，流可以从断点续接 |
| 应用端瞬态 | 未定义 | 预表现层，按 `opId` 对账 |
| 规模 | 单机为主 | 15 台机器的总览、待处理视图、精确的跨机归并 |
| 防补丁 | 发布者检查清单 | 合同加禁止清单加防回流测试，性能问题只允许改范围或改内核 |
| 令牌源头 | 文件戳只用修改时间和大小，hash 都在投影后计算 | 文件型节点直接用元数据令牌（inode、大小、mtime、ctime），零内容 IO；缓存快照放在 `<data>/cache/sync/` |
| 软件结构 | 内核 API 和发布者合同 | 协议层、框架层、接口层，依赖单向；Rust 与 TS 各一份引擎，由共享测试向量保证一致 |

## 14. 验收（均未执行）

| 场景 | 通过条件 |
| --- | --- |
| 令牌确定性 | 相同输入得到相同令牌；内容不变时重启 daemon，全部 `persistent`、`derived` 节点的令牌不变 |
| 冷启动 | 12,000 条会话，有快照时只重读变了的 `meta.json`；快照损坏时自动全量重建，结果一致 |
| 15 台机器打开工作台 | 有缓存且没有变化：总传输小于 10 KB，每台一次往返；一台离线不影响其他 |
| 跨机归并 | 15 台机器的"全部最近 100 条"与全量排序的结果完全一致 |
| 一轮对话完成 | 看着该机器的连接收到不超过 4 个操作、小于 8 KB；没订阅这台机器的连接收到 0 个 |
| 断线恢复 | 5 个 Agent 工作期间断线 10 分钟，传输量不超过不用缓存时的 30%；时间线从断点 `append` 续接，不重不漏 |
| 背压 | 暂停读取 60 秒后恢复：同一节点只收到 1 次；流合并为 1 段 `append`；拥有方内存不随暂停时长增长 |
| 瞬态丢失 | 流式输出中途重启 daemon：已落盘部分保留，未落盘部分显示"中断"，不显示"已删除" |
| 预表现 | 改名后界面立即显示新值；被拒绝时回滚并提示；`unknown` 时显示"未确认"，不自动重发 |
| 三层一致性 | 应用端对全部节点校验 `H(data) == token` 均通过；在持久层提交前注入崩溃，客户端看不到未提交的状态 |
| CLI | 列出 12,000 条会话只扫描一次内存索引；同一远端机器连续 10 次读取只建 1 条链路 |
| 内存 | 12,000 条会话、20 个打开的会话、10 个连接时，缓存层不超过预算（初值 64 MiB，S1 实测后定） |
| 防回流 | 代码中不存在已迁移族的旧读 RPC、旧推送帧、轮询和客户端翻页循环 |
| 元数据令牌 | 用 `cp -p` 或 `rsync -t` 替换一个 `meta.json`，大小和 mtime 都不变，仍能被察觉；有快照时冷启动只读取变了的文件 |
| Linux 重启期间的外部改动 | daemon 停止期间改动 10 个会话文件，启动后的对账找出全部 10 个，且不读取其余文件的内容 |
| 分层依赖 | 编译期检查：业务 crate 不依赖协议层的帧类型；框架层不依赖任何业务类型 |

所有数字都是设计目标，需要在真实的 daemon、浏览器和 WASM Host 上测量确认。

## 15. 实施前必须测清楚的问题

1. **WASM Host 单线程下的令牌计算与视图计算开销。** 冷启动 12,000 条摘要算令牌要按 `WorkBudget` 分片让出；S1 测前台 p95。
2. **快照临时文件的收益。** 先测冷启动全量扫描 12,000 个 `meta.json` 要多久，再决定快照的格式和写入频率。
3. **追加节点的保留窗口。** 时间线尾部和 PTY 各保留多少字节，才能让常见的断线都能续接、不必退回快照。
4. **15 条连接的移动端成本。** 手机同时保持 15 条连接时的电量和流量；是否需要只连"有关注内容"的机器，其余只订阅总览。
5. **元数据检查的实际代价。** 在本地 SSD、机械盘、网络文件系统上分别测 12,000 次 stat 的耗时，据此决定是否在 macOS、Windows 上启用持久变化日志。
6. **缓存快照的位置（已解决）。** 按 storage-layout 放在 `<data>/cache/sync/`，不放进项目文件夹（v6 第 0 节）。
7. **草稿保存刷新排序。** `replace_drafts` 刷新 `updatedAt`，打字时会话会被顶到最前，需要产品确认。
8. **发布窗口。** 设备 daemon 版本混杂期间，"需要更新"的提示必须可以直接操作，需要与 release-beta 确认。
