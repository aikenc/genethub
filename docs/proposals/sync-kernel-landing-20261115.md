## 摘要

**体验影响。** v9 要解决的问题：
- 十几台机器看不全；
- 跨机协作靠轮询，所以慢；
- 每一族状态各做一套机制，越来越复杂。

如果落地方式不对，会出现两种坏结果：
- **只加不删：** 新内核加上了，旧路径一直留着，复杂度反而上升。dev-2 团队模板四天内从 7,988 行涨到 13,020 行，就是这个循环在"红线快修"下出现过的现象。
- **迁移中断业务：** 迁移过程打断团队业务，比如结果没送达、派单重复，用户看到的是工作卡住。

**怎么解决（全部待实施）：**
1. **两种推进方式。**
   - P0 规范和 P1 内核用设计评审、属性测试和预算门槛推进，在 dev-3 完成后合入主干。
   - P2 起进入 dev-2 的 Harness 循环，以真实团队为负载打磨，同时跑 testctl 规模用例。
2. **补上同步专属的信号：** 4 条红线、6 条警告线，接进 `observer.py check`（第 5.2 节）。
3. **两条处置规则：**
   - 同步红线先把这一族回退到旧路径止血，再修新路径；
   - 任何修复都不得新增状态机制，由静态门禁检查。
4. **试点方式：** 一次只切一个团队或一个远程岗位，另一方留在旧路径作为对照。
5. **双记分：** 团队质量卡和同步指标都达标，一步才算完成。

**怎么防止复发：**
- 状态面盘点脚本同时供 CI 门禁和 Harness 使用，口径只有一份（第 6.2 节）；
- 每一步的完成定义都包含删除项和机制数（第 4 节）；
- 发布记录同时写质量分和机制数。

**本次需要评审：**
1. 第 0 节文档关系与冲突时的优先级；
2. 第 2 节的槽位分工，尤其是 dev-2 领先主干 266 个提交带来的前置条件；
3. 第 3 节的协议目标形态；
4. 第 5 节的同步红线、警告线和处置规则；
5. 第 6 节的 Harness 扩展。

## 3. 协议结构的目标形态（补充 v9）

### 3.1 现状（主干 `158d7351`）

```text
业务层     exchange 方法 8 个：protocol.identity / rpc / events / asset.preview /
             shell.run / rtc.negotiate / service.preview / file.read
           rpc 内：Request 129 种变体与 Reply 枚举
           events 内：11 种 ServerFrame，用 seq 重放，Desync 处理失步
           协商：WEB_PROTOCOL_VERSION=4、DATA_PLANE_VERSION=4、protocol.identity 和
             connection.identity、21 个特性字符串（router.rs:497），工作台在 48 处判断其中 15 个
           CLI：argv 经 loopback /cli 进入 daemon，在 cli_front 里解析成 Request；输出 schema 手写
DataEndpoint  有界帧、逻辑流、credit、公平发送、取消
E2EE          PSK 双向证明、AES-256-GCM record
Carrier       loopback WS / Fabric / RTC
```

底下三层已经是"一种帧、一种流、一种加密"，**不改**。复杂度集中在业务层：
- 一个大 RPC 枚举承载所有语义；
- 读接口的形状每变一次就加一个特性开关；
- 推送共用一条事件流，PTY 洪泛事故就是这个原因；
- CLI 和工作台是两套入口。

### 3.2 目标形态

```text
hello   连接时交换：数据面版本 + 每族的 schema 描述（schema 哈希、节点种类、意图名单）
sync    一条长流：get/watch/ops/unknown（v7 第 10.2 节的帧）
call    一种信封：{key, name, args, ifToken, opId} → 结果或错误
        错误码只有 conflict/budget/tooLarge/unknownKey/handler/forbidden
字节流  pty（每个终端一条流）· asset.preview · file.read · shell.run · service.preview
连接    rtc.negotiate
```

| 维度 | 现在 | 目标 |
| --- | --- | --- |
| 业务入口 | `rpc` 129 种变体，加 `events` 11 种帧 | `sync` 加 `call`；77 种写操作变成各族 schema 里声明的意图名 |
| 能力协商 | 2 个版本号、2 次身份确认、21 个特性字符串 | 数据面版本，加每族的 schema 描述；特性字符串全部删除 |
| 推送 | 共用一条事件流 | 状态走 `sync`；每个终端一条独立的流 |
| 类型来源 | Rust 枚举生成 TS，CLI schema 手写 | 一份 schema 同时生成 Rust、TS 和 CLI 的输入输出 |
| 逻辑连接续传 | 约 60 秒内接回流表和订阅 | 订阅靠令牌续接，写入靠 `opId`。是否还需要续传层，在 P5 之后评估：只剩字节流需要它时，改为按流续接 |

### 3.3 每个阶段的协议删除项

| 阶段 | 新增 | 删除或进入兼容窗口 |
| --- | --- | --- |

| P1 | `sync`、`call` 方法（只用于假端口和 CLI） | — |

## 4. 每个阶段的门槛与打磨方式

### 4.1 P0：规范

- **评审清单：**
  1. 五族覆盖检查：会话目录的分页、排序、搜索，会话正文的日志，进程观察者，远端不可达，团队互斥。逐族写出键、节点种类、视图和意图。
  2. 第 3.2 节的帧示例都能解析。
  3. 跨渠道共用同一个 home 时谁是权威，已定稿（v9 第 13 节第 2 条）。
  4. 应用子树的配额、schema 和节点大小上限已经给出数字。
- **退出条件：** 清单全部关闭；architecture.md 修订合入；盘点脚本在主干上给出基线（第 6.2 节）；静态门禁在 CI 上生效。

### 4.2 P1：内核

- **测试：**
  - 只用假端口跑完全部测试；
  - 对"随机交错写入、断线、续接"做属性测试，最终状态必须等于快照；
  - Rust 和 TS 之间的互通测试向量。
- **门槛：** v9 第 9.4 节的预算；单次 `put` 的独占时间上界；在 20,000 个会话的规模下，实测每条连接的内存。
- **不进 Harness 的原因：** 这一步没有用户能感知的行为。团队质量分反映不出内核是否正确，用它来驱动只会噪声大于信号。

### 4.3 P2：团队跨机协作（进入 Harness）

1. **试点顺序：** 先选一个团队的一个远程岗位走新路径。同队的其他岗位，以及另一个团队，留在旧路径作为对照。两队使用的模型不同，结论中要注明这一点。
2. **观察窗口：** 试点路径连续 24 小时没有同步红线、同步警告线收敛，并且同期质量卡不低于对照方，才扩展到该队全部岗位，再扩展到另一队。
3. **内核冻结：** P2 期间只允许修内核的缺陷，每个修复都要附带回归测试。需要改内核接口或语义，就触发 v9 第 9.5 节的失败条件，暂停 P2，回到设计评审。
4. **完成定义：**
   - `_sync_*` 已删除；
   - `reconcile` 和 watchdog 中的远端轮询读取已删除；
   - 团队流程不再调用 `shell` 接单，旧路径只在兼容窗口内对未升级的目标机器生效；
   - 两队空闲时零请求、零 hook 运行；
   - 跨机派单端到端 P95 达到 v9 第 3.2 节的目标；
   - 两队的质量卡没有因为迁移出现新的红线；
   - 盘点脚本显示机制数下降，并写进发布记录。

### 4.4 P3：会话目录与汇聚

- **规模：** testctl 多机规模用例覆盖 15 台机器、20,000 个会话，满足 v9 第 11.2 节的条件。
- **真实使用：** dev-2 两队的前台和看板改为订阅之后，Human 用手机只连一台机器查看全部会话。
- **完成定义：** 第 3.3 节的 P3 删除项已进入兼容窗口；工作台里 `summary-directory*`、30 秒刷新、连接池的目录保留规则已删除。

### 4.5 P4、P5 与收尾

- 每迁一族，都按"迁移模板"走：schema、数据源、合同测试、删除清单、门禁，落在发布记录里。
- 收尾按 v7 第 12 节：新路径进入 Stable 之后的下一个 Stable 版本，统计旧路径的调用次数，确认没有当前版本的客户端仍在使用，再删除旧路径。

## 5. 迭代打磨循环

### 5.1 循环

沿用 dev-2 的循环：团队干活 → 出卡 → 归因分流 → 发 dev → 确认采用 → 看卡。P2 起在每个检查点同时看两组信号：
- 质量卡：沿用，不新增评分口径；
- 同步信号：第 5.2 节，作为单独的一组记录。

### 5.2 同步信号（拟议阈值，P2 开始前校准）

**红线（最高优先，立即处置）：**

| 编号 | 含义 | 判定 | 数据来源 |
| --- | --- | --- | --- |
| S1 | 已承诺的写入丢失，或重复执行 | 意图返回成功，但权威端最终没有这个值；同一个 `opId` 或派单编号产生了两次副作用 | 意图回执与权威端节点核对；派单账本 |
| S2 | 监听漏掉了变化 | `source.drift` 大于 0 | daemon 诊断（v8 第 10 节） |
| S3 | 错误地显示"未知" | 权威端可达，但它的子树连续 5 分钟显示 `unknown` | 链路状态与订阅状态核对 |
| S4 | 迁移导致结果没送达 | 试点路径上出现团队红线 R3（结果未送达） | 现有质量卡 |

**警告线（本候选结束后处理）：**

| 编号 | 含义 | 判定 |
| --- | --- | --- |
| SW1 | 空闲时仍有轮询 | 团队空闲 10 分钟的窗口内，对 daemon 的请求数大于 0 |
| SW2 | 跨机太慢 | 跨机派单端到端 P95 超过 2 秒，或状态变化到达订阅方超过 1 秒 |
| SW3 | 机制没有减少 | 某一步合入后，盘点脚本显示机制数没有下降 |
| SW4 | 预算超出 | 新增代码超过 v9 第 9.4 节的任一预算 |
| SW5 | 旧路径仍在被使用 | 某一族进入兼容窗口 24 小时后，旧路径的调用次数没有下降 |
| SW6 | 修复增加了机制 | 某个候选新增了 `Request` 变体、`ServerFrame` 变体、特性字符串或状态轮询（盘点脚本的差异） |

### 5.3 处置规则

1. **先回退，再修复。** 出现 S1–S4 时，平台开发先把这一族切回兼容窗口里的旧路径，按族或按团队切换，并发出说明。用户只看到"已回退到兼容路径"，工作照常进行。之后在槽位里复现、修复、测试，重新试点。回退本身不算修复完成。
2. **修复不得新增机制。** 违反 SW6 的候选不得发布。如果确实需要新机制，说明 v9 的抽象有缺口，按失败条件回到设计评审，不在循环里打补丁。
3. **发版节奏。** 同步相关的改动单独成版，版本说明里写清对应的阶段、族、红线或警告线编号，以及机制数的变化。红线修复随时发；其他改动沿用每 2 小时 3–4 版的节奏。
4. **团队原因的问题交给反思。** 比如团队脚本绕过意图直接写锁文件。按现有分层，由团队反思层处理，平台只负责让警告可见。

### 5.4 双记分

每一步在发布记录里同时写：
- 质量卡：各队的正式分、红线、连续达标张数（沿用观察 Skill 的 `report` 首行）；
- 同步：S1–S4 的当前状态、SW1–SW6、机制数的增减、旧路径调用次数。

**一步完成的条件：** 两组都达标，并且第 4 节的完成定义全部满足。只有质量分达标、机制数没降，不算完成；只有机制数降了、质量卡出现迁移引起的红线，也不算完成。

### 5.5 何时退出循环

- **正常退出：** P5 完成、兼容窗口关闭之后，同步信号并入常规的 CI 门禁和发布检查，不再需要 Harness 的专门观察。
- **异常退出：** 出现 v9 第 9.5 节的任一失败条件，就暂停循环，回到设计评审。

## 6. Harness 扩展（拟议，由 Harness 开发在观察 Skill 中实施）

本节是对 Spaces 仓 `skills/lifecycle/genethub-team-observer` 的修改建议。本文不修改它；是否采纳、如何实现，由 Harness 开发决定，并按它自己的规则验收。

### 6.1 `observer.py check` 的新输入

- **同步指标：** 通过会话绑定的 CLI 读取各机器 daemon 的诊断，包括 `source.drift`、`source.relist`、链路状态、`unknown` 持续时间、派单端到端延迟。机器不可达时记为 unknown，不当作健康。
- **机制数和预算：** 运行产品仓中的状态面盘点脚本（第 6.2 节），和上一次发布的结果比较。
- **旧路径调用次数：** 读取 daemon 诊断中兼容窗口路径的计数。

拟议输出（在现有输出上增加 `sync` 字段）：

```json
{"action":"preempt",
 "sync":{"redLines":[{"rule":"S3","machine":"mac-mini","prefix":"m/mac-mini/app/xworld-hy/team/","minutes":7}],
         "warnings":[{"rule":"SW3","release":"0.0.1-dev.120","mechanisms":{"before":{"readRpc":32,"frames":11,"features":21},"after":{"readRpc":32,"frames":11,"features":21}}}],
         "phase":"P2","pilot":{"team":"XWorld-hy","role":"qa","path":"sync"}}}
```

`sync.redLines` 不为空时 `action` 取 `preempt`，只有 `warnings` 时取 `warn`，和现有语义一致。

### 6.2 状态面盘点脚本（P0 的交付物，放在产品仓）

- **统计口径：**
  - `Request` 变体数，按读、写、流、连接分类；
  - `ServerFrame` 变体数；
  - 特性字符串数；
  - 版本概念数；
  - 已迁移族中的周期性轮询（`setInterval`、固定周期 sweep）；
  - 新增组件的非测试行数。
- **用途：**
  - CI 的静态门禁：已迁移的族和新增的族出现增量就失败；
  - Harness 的 SW3、SW4、SW6；
  - 发布记录中的机制数。
- **一份口径三处使用**，避免 CI、Harness 和提案各算各的。

### 6.3 Skill 文字的修改

- 在"红线插队与警告线"一节增加 S1–S4、SW1–SW6，并引用本文第 5.3 节的"先回退，再修复"和"修复不得新增机制"。
- 在"量化迭代循环"一节增加双记分（第 5.4 节）。
- 观察 Skill 的现行规则"按离 80 分的差距乘以权重排序"，只适用于质量卡的失分。同步警告线另按第 5.3 节处理，不进入这个排序。

### 6.4 扩展的验收（回放）

1. 注入一次 `source.drift` 加 1，`check` 返回 `preempt` 和 S2；修正之后，下一次 `check` 不再出现 S2。
2. 构造一个新增了 `ServerFrame` 变体的候选，`check` 返回 SW6，平台开发不发布这个候选。
3. 拿掉试点机器的网络 6 分钟，权威端不可达时不报 S3；网络恢复后子树仍显示未知超过 5 分钟，才报 S3。
4. 在没有任何同步改动的发布上，`sync` 字段为空，现有的质量卡流程不受影响。

## 7. 风险与回退

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| dev-2 与主干分叉太大 | P2 的基础不确定，估计不准 | 第 2.2 节：先确定基础，再重新测量 |
| 团队升级需要合并代码 | 每一步都打扰两队，反思层负担加重 | 优先落地平台包不可变的方案；改动限制在 `genet_builtin`；升级前做只读预检 |
| 质量分噪声掩盖同步回归 | 有问题看不出来，或者优先级被带偏 | 同步信号单独记录、单独处置（第 5.2、5.3 节） |
| 循环诱导打补丁 | 复杂度上升，背离 v9 | SW6 门禁，加"修复不得新增机制" |
| 规模覆盖不足 | 真实团队只证明语义正确 | 每个阶段同时跑 testctl 规模用例 |
| 回退路径本身有缺陷 | 止血失败 | 兼容窗口内旧路径只修缺陷、不加功能；回退演练作为 P2 的进入条件之一（第 8 节） |
| Human 的注意力消耗 | dev-2 记录里已有 22 次 Human 介入 | 同步信号自动进入 `check`，不需要 Human 转达；汇报首行加入同步状态 |
