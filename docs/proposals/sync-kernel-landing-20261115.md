## 摘要

**体验影响。**
- v9 要解决的问题：十几台机器看不全、跨机协作靠轮询所以慢、每一族状态各做一套机制导致越来越复杂。
- 落地过程不能影响 dev-2：dev-2 正在用真实团队跑长期迭代，它的代码、环境、团队、Harness 规则、机器资源和发版节奏都不能被打扰。
- 落地方式不对时还会出现两种坏结果：
  - 只加不删，复杂度反而上升。dev-2 团队模板四天内从 7,988 行涨到 13,020 行，就是"红线快修"循环出现过的现象，dev-3 的循环要避免重蹈覆辙；
  - 迁移过程打断业务。

**怎么解决（全部待实施）：**
1. **隔离合同（第 1 节）。** 代码分支、主干合入、门禁作用范围、环境和端口、真机实例、测试团队、观察脚本、CPU 和磁盘资源，逐项和 dev-2 分开，并为每一项给出核验方法。
2. **两种推进方式。**
   - P0 规范、P1 内核：设计评审、属性测试、预算门槛。
   - P2 起：在 dev-3 自建的测试团队和多机环境里进入打磨循环，同时跑 testctl 规模用例。
3. **打磨循环（第 6 节）。**
   - 4 条同步红线、6 条警告线；
   - "先回退，再修复"和"修复不得新增机制"两条处置规则；
   - 试点和对照两组都在 dev-3 内部；
   - 双记分。

**怎么防止复发：**
- 第 1.3 节的隔离核验在每个阶段开始和结束时各跑一次，任何一项不通过就暂停；
- 状态面盘点脚本同时供 CI 门禁和 dev-3 的观察脚本使用，口径只有一份；
- 每一步的完成定义都包含删除项和机制数。

## 1. 隔离合同

**目标：** 从 P0 开始到兼容窗口关闭，dev-2 的代码、环境、团队、规则、资源和发版节奏都不因本方案而改变；dev-2 也不需要为本方案做任何事。

### 1.1 代码与主干

1. **只在 dev-3 的分支上开发。** 文档在 `docs/dev3-proposals-20261115` 分支，代码在 dev-3 自己的开发分支。不向 dev-2 的分支提交，不 cherry-pick 到 dev-2，不给 dev-2 开 PR。
2. **主干只单向流入 dev-3。** dev-3 定期合并主干（包括 dev-2 自己合入主干的内容），冲突由 dev-3 解决。
3. **迁移全程不向主干合入同步代码**，包括规范、文档修订和独立的新增包。原因有两个：
   - 任何主干变化都会触发 dev-2 观察脚本的"落后主干"警告，让 dev-2 在下一个候选边界合并主干；
   - "只新增、不改行为"的合入，也会带来一次合并、一次构建和一次发版。
4. **最终合入（收尾阶段之前）一次完成，满足以下条件：**
   - P0–P5 在 dev-3 全部验收通过；
   - dev-3 已经基于最新主干重新验证；
   - 旧路径全部保留在兼容窗口内，按族协商，旧客户端和旧 daemon 照常工作；
   - 静态门禁只作用于第 1.2 节的范围；
   - 用 dev-2 合入主干的全部现有测试和 dev-3 的规模用例验证：已有的调用方和团队模板不需要改动就能照常运行。

   合入之后，dev-2 何时合并主干由 dev-2 自己决定。不合并，它照常运行；合并之后，旧路径照常工作，行为不变。
5. **如果不得不提前合入。** 比如主干和 dev-3 的分叉太大。提前合入属于本合同的例外，需要 Human 单独批准，并在批准记录里写明对 dev-2 的影响。

### 1.2 门禁的作用范围

- 静态门禁（禁止新增 `Request` 变体、`ServerFrame` 变体、特性字符串、状态轮询）**只作用于已迁移的族**，以及 dev-3 新增的模块。
- 其他族的新增照常允许，包括 dev-2 现有的 `team.quality-integrity.v1` 和它新增的 RPC，以及将来的类似改动。
- 门禁规则以"族的清单"为准，不扫描全仓，不会因为别的槽位的改动而失败。

### 1.3 运行环境

### 1.4 团队与负载

- 不使用 dev-2 的团队（XWorld-hy、XWorld-ds 等），不向 dev-2 的任何会话发消息，不读取它们的质量卡和运行记录。
- dev-3 在自己的 daemon 上建立测试团队（第 5 节），使用的模型额度和 dev-2 分开记账。

### 1.5 观察脚本与 Skill

- 不修改 Spaces 仓的共享观察 Skill（`skills/lifecycle/genethub-team-observer`）。dev-2 选用了它，改动会直接影响 dev-2。
- dev-3 新建一个只有 dev-3 选用的 Skill，包含规则文字和观察脚本（第 6.6 节）。PipeBuilder 只为选用它的 Space 生成产物；新增后要核对 dev-2 的生成文件没有变化（第 1.7 节）。

### 1.6 机器资源

开发服务器是共享的：诊断记录里出现过遗留浏览器打满 CPU 配额、拖慢所有槽位的情况。dev-3 的规模用例和测试团队都有可能挤占 dev-2。

- **CPU 和内存：** 规模用例和测试团队的 daemon 放在带配额的 systemd scope 里运行（`systemd-run --user --scope -p CPUQuota=… -p MemoryMax=…`，具体数字在 P0 按机器实测给出），同时降低优先级，限制 testctl 的并发。
- **浏览器：** 每次运行结束必须回收截图和测试用的浏览器，结束后核对没有残留进程。
- **磁盘：** dev-3 的产物和日志设上限并定期清理。在 dev-2 监视的真机上，保持可用空间高于 dev-2 的 20 GiB 告警阈值，并为它留出余量。
- **时段：** 高负载的规模用例放在独立的时间窗口内运行，并记录开始、结束时间和资源峰值。

### 1.7 隔离核验（每个阶段的开始和结束各跑一次）

| 检查 | 通过条件 |
| --- | --- |
| dev-2 代码 | dev-2 两仓的 HEAD 和工作区状态，与阶段开始时的记录相同，或者只有 dev-2 自己的提交（按提交来源核对） |
| dev-2 生成物 | `spaces/dev-2` 下 PipeBuilder 生成的文件，与阶段开始时的摘要一致 |
| 主干 | 没有来自 dev-3 的同步相关合入（第 1.1 节例外除外） |
| 端口与进程 | dev-3 的进程只监听自己的端口；没有 dev-3 进程访问 dev-2 的端口或数据目录 |
| 真机 | dev-2 的服务、目录和 TLS 桥未被修改（按 plist、unit 和目录摘要核对） |
| 资源 | 规模运行期间，CPU 和内存不超过 scope 配额；没有残留的浏览器；真机可用空间高于阈值 |
| 消息 | dev-3 没有向 dev-2 的任何会话、团队发送过消息 |

任何一项不通过就暂停当前阶段，先恢复隔离，再继续。

## 3. 打磨阶段的完成定义

### 3.1 P2：团队跨机协作

1. **试点：** 先让测试团队 A 的一个远程岗位走新路径；同队其他岗位和团队 B 留在旧路径作为对照。两队使用相同的模型和任务，排除模型差异（第 5 节）。
2. **扩大：** 试点路径连续 24 小时没有同步红线、同步警告线收敛、同期质量卡不低于对照方，才扩展到 A 的全部岗位，再扩展到 B。
3. **内核冻结：** P2 期间只允许修内核的缺陷，每个修复都要附带回归测试。需要改内核接口或语义，就触发 v9 第 9.5 节的失败条件，暂停 P2，回到设计评审。
4. **完成定义：**
   - `_sync_*` 已删除；`reconcile` 和 watchdog 中的远端轮询读取已删除；
   - 团队流程不再调用 `shell` 接单，旧路径保留在兼容窗口内；
   - 两队空闲时零请求、零 hook 运行；
   - 跨机派单端到端 P95 达到 v9 第 3.2 节的目标；
   - 两队的质量卡没有因为迁移出现新的红线；
   - 盘点脚本显示机制数下降，写进 dev-3 的发布记录；
   - 隔离核验通过。

### 3.2 P3：会话目录与汇聚

- **规模：** testctl 多机规模用例覆盖 15 台机器、20,000 个会话（多数机器是模拟的），满足 v9 第 11.2 节的条件，并且在第 1.6 节的资源配额内运行。
- **真实使用：** 用手机只连 dev-3 的一台机器，查看全部 dev-3 机器的会话。
- **完成定义：** 第 4.3 节的 P3 删除项已进入兼容窗口；工作台里 `summary-directory*`、30 秒刷新、连接池的目录保留规则已删除。

### 3.3 P4、P5

每迁一族都按"迁移模板"走：schema、数据源、合同测试、删除清单、门禁，落在 dev-3 的发布记录里。

## 4. 协议结构的目标形态（补充 v9）

### 4.1 现状（主干 `158d7351`）

```text
业务层     exchange 方法 8 个：protocol.identity / rpc / events / asset.preview /
             shell.run / rtc.negotiate / service.preview / file.read
           rpc 内：Request 129 种变体与 Reply 枚举
           events 内：11 种 ServerFrame，用 seq 重放，Desync 处理失步
           协商：WEB_PROTOCOL_VERSION=4、DATA_PLANE_VERSION=4、protocol.identity 和
             connection.identity、21 个特性字符串（router.rs:497），工作台在 48 处判断其中 15 个
           CLI：argv 经 loopback /cli 进入 daemon，在 cli_front 里解析成 Request；输出 schema 手写
DataEndpoint  有界帧、逻辑流、credit、公平发送、取消
E2EE          PSK 双向证明、AES-256-GCM record
Carrier       loopback WS / Fabric / RTC
```

底下三层已经是"一种帧、一种流、一种加密"，**不改**。复杂度集中在业务层：
- 一个大 RPC 枚举承载所有语义；
- 读接口的形状每变一次就加一个特性开关；
- 推送共用一条事件流；
- CLI 和工作台是两套入口。

### 4.2 目标形态

```text
hello   连接时交换：数据面版本 + 每族的 schema 描述（schema 哈希、节点种类、意图名单）
sync    一条长流：get/watch/ops/unknown（v7 第 10.2 节的帧）
call    一种信封：{key, name, args, ifToken, opId} → 结果或错误
        错误码只有 conflict/budget/tooLarge/unknownKey/handler/forbidden
字节流  pty（每个终端一条流）· asset.preview · file.read · shell.run · service.preview
连接    rtc.negotiate
```

| 维度 | 现在 | 目标 |
| --- | --- | --- |
| 业务入口 | `rpc` 129 种变体，加 `events` 11 种帧 | `sync` 加 `call`；77 种写操作变成各族 schema 里声明的意图名 |
| 能力协商 | 2 个版本号、2 次身份确认、21 个特性字符串 | 数据面版本加每族的 schema 描述；已迁移族的特性字符串删除 |
| 推送 | 共用一条事件流 | 状态走 `sync`；每个终端一条独立的流 |
| 类型来源 | Rust 枚举生成 TS，CLI schema 手写 | 一份 schema 同时生成 Rust、TS 和 CLI 的输入输出 |
| 逻辑连接续传 | 约 60 秒内接回流表和订阅 | 订阅靠令牌续接，写入靠 `opId`。P5 之后评估：只剩字节流需要它时，改为按流续接 |

新旧形态在兼容窗口内并存：旧客户端继续用 `rpc` 和 `events`，新客户端按族协商。所以最终合入之后，没有升级的调用方不受影响（第 1.1 节）。

### 4.3 每个阶段的协议删除项

| 阶段 | 新增 | 删除或进入兼容窗口 |
| --- | --- | --- |
| P0 | `hello` 中的 schema 描述；`sync`、`call` 的帧定义 | 门禁只对清单内的族生效（第 1.2 节） |
| P1 | `sync`、`call` 方法（只用于假端口和 CLI） | — |
| P2 | 应用子树的 schema 描述 | 团队流程不再依赖 `shell.run` 接单（进入兼容窗口） |
| P3 | 会话目录族的 schema | `catalog.sync`、`session.page`、`session.changes`、`session.list` 的 `since`；特性字符串 `catalog.sync.v1`、`session.page.v1`、`session.active-page.v1`、`session.changes.v1`、`session.summary.v1` |
| P4 | 低频族的 schema | 6 种推送帧；对应的读取 RPC；`access.status.v1`、`process.services.v1` 等读形状开关 |
| P5 | 每个终端独立的 `pty` 流；正文日志节点 | `events` 中的 `Event`、`Desync`、`PtyOutput`、`PtyClosed` |
| 收尾 | — | `rpc` 和 `events` 两个方法本身；`protocol.identity` 并入 `hello`（兼容窗口关闭之后） |

### 4.4 需要更正的文档

- `docs/e2ee-data-plane.md`：
  - 版本号写成了 3，代码里两个版本号都是 4（`packages/identity/src/lib.rs:26,32`）；
  - 写着"删除 `file.read`"，但它作为跨机下载又回来了（`apps/daemon/src/dataplane/file_read.rs`）。

## 5. dev-3 的测试团队与负载

### 5.1 为什么自建

真实团队的负载能暴露派单丢失、重复、结果没送达这类语义问题，这是合成用例做不到的。dev-2 的团队不能用（第 1.4 节），所以在 dev-3 自建。

### 5.2 组成（拟议）

- **两个测试团队 A、B：** 用同一份团队模板、同一个模型、同一组固定任务。两队都至少有一个绑定在另一台 dev-3 机器上的远程岗位（`TEAM_MACHINE`），保证跨机派单真的发生。
- **固定任务：** 为可重复而设计。例如在 fixture 仓库中实现若干小功能，再交给远程 QA 岗位验证并回传结果。每轮任务包含跨机派单、并行岗位、结果回传和接手。任务内容不变，迁移前后的数据才能直接比较。
- **合成负载：** 另外用不调用模型的脚本，在应用子树上制造高频的请求、认领和释放，覆盖真实团队频率达不到的并发和冲突。

### 5.3 基线（E1）

在旧路径上运行至少 24 小时，记录：
- 质量卡；
- 跨机派单的端到端延迟和结果回传延迟；
- 空闲时对 daemon 的请求数；
- hook 运行次数；
- 盘点脚本输出的机制数。

P2 之后的数据都和这份基线比较。

### 5.4 预算

测试团队的模型调用量、运行时长和机器占用，在 E1 之前由 Human 确认上限，和 dev-2 分开记账。超出上限就暂停测试团队，只保留合成负载和 testctl 用例。

## 6. 打磨循环

### 6.1 循环

测试团队干活 → 出卡，同时出同步指标 → 归因：平台还是团队用法 → dev-3 发 dev 版本 → 测试团队采用 → 再看卡和指标。

检查点和 dev-2 的做法一样：每个候选边界（定向测试后、构建后、发布后），以及每次等待返回之后。

### 6.2 同步信号（拟议阈值，E1 用基线数据校准）

**红线（最高优先，立即处置）：**

| 编号 | 含义 | 判定 | 数据来源 |
| --- | --- | --- | --- |
| S1 | 已承诺的写入丢失，或重复执行 | 意图返回成功，但权威端最终没有这个值；同一个 `opId` 或派单编号产生了两次副作用 | 意图回执与权威端节点核对；派单账本 |
| S2 | 监听漏掉了变化 | `source.drift` 大于 0 | dev-3 daemon 诊断（v8 第 10 节） |
| S3 | 错误地显示"未知" | 权威端可达，但它的子树连续 5 分钟显示 `unknown` | 链路状态与订阅状态核对 |
| S4 | 迁移导致结果没送达 | 试点路径上，结论超过 10 分钟没有送达请求方，或者出现错投、重复投递（沿用团队质量模型 R3 的判定） | 测试团队的质量卡 |

**警告线（本候选结束后处理）：**

| 编号 | 含义 | 判定 |
| --- | --- | --- |
| SW1 | 空闲时仍有轮询 | 团队空闲 10 分钟的窗口内，对 daemon 的请求数大于 0 |
| SW2 | 跨机太慢 | 跨机派单端到端 P95 超过 2 秒，或状态变化到达订阅方超过 1 秒 |
| SW3 | 机制没有减少 | 某一步合入 dev-3 分支后，盘点脚本显示机制数没有下降 |
| SW4 | 预算超出 | 新增代码超过 v9 第 9.4 节的任一预算 |
| SW5 | 旧路径仍在被使用 | 某一族进入兼容窗口 24 小时后，dev-3 内旧路径的调用次数没有下降 |
| SW6 | 修复增加了机制 | 某个候选在已迁移的族里新增了 `Request` 变体、`ServerFrame` 变体、特性字符串或状态轮询 |
| SW7 | 隔离受损 | 第 1.7 节任一项不通过（这一条按红线优先级处理） |

### 6.3 处置规则

1. **先回退，再修复。** 出现 S1–S4 时，先把这一族切回兼容窗口里的旧路径，按族或按团队切换。之后在 dev-3 里复现、修复、测试，重新试点。回退本身不算修复完成。
2. **修复不得新增机制。** 违反 SW6 的候选不得发布。如果确实需要新机制，说明 v9 的抽象有缺口，按失败条件回到设计评审。
3. **SW7 立即处理：** 停下当前工作，先恢复隔离。
4. **发版节奏：** 同步改动单独成版，版本说明里写清阶段、族、对应的信号编号，以及机制数的变化。红线修复随时发；其他改动攒批发布。
5. **团队原因的问题交给反思。** 比如团队脚本绕过意图直接写锁文件，由测试团队的反思层处理，平台只负责让警告可见。

### 6.4 双记分

每一步在 dev-3 的发布记录里同时写：
- 质量卡：各队的正式分、红线、连续达标张数；
- 同步：S1–S4、SW1–SW7、机制数的增减、旧路径调用次数、和第 5.3 节基线的对比。

一步完成的条件：两组都达标，并且第 3 节的完成定义全部满足。

### 6.5 何时退出循环

- **正常退出：** P5 完成、最终合入之后，同步信号并入常规的 CI 门禁和发布检查；测试团队按第 1.6 节清理。
- **异常退出：** 出现 v9 第 9.5 节的任一失败条件，暂停循环，回到设计评审。

### 6.6 dev-3 的观察 Skill（拟议）

- **位置：** Spaces 仓新建 `skills/lifecycle/genethub-sync-landing`，只有 dev-3 选用。新增后运行 `pipebuilder build` 和 `pipebuilder verify`，并按第 1.7 节核对 dev-2 的生成物没有变化。
- **内容：**
  - 第 6.2、6.3 节的规则文字；
  - 一个观察脚本，提供 `check`、`wait`、`report` 和隔离核验 `isolation`。

  借鉴 dev-2 观察脚本的做法：检查点、等待唤醒、汇报首行；但不复用它的文件和状态。
- **`check` 的输入：**
  - dev-3 各机器 daemon 的诊断：`source.drift`、`source.relist`、链路状态、`unknown` 持续时间、派单端到端延迟；
  - 产品仓中的状态面盘点脚本；
  - 测试团队的质量卡；
  - 隔离核验的结果。
- **拟议输出：**

```json
{"action":"preempt",
 "sync":{"redLines":[{"rule":"S3","machine":"dev3-mac","prefix":"m/dev3-mac/app/sync-team-a/team/","minutes":7}],
         "warnings":[{"rule":"SW3","release":"0.0.1-dev.12","mechanisms":{"before":{"readRpc":32,"frames":11,"features":21},"after":{"readRpc":32,"frames":11,"features":21}}}]},
 "isolation":{"ok":true},
 "phase":"P2","pilot":{"team":"sync-team-a","role":"qa","path":"sync"}}
```

- **验收（回放）：**
  1. 注入一次 `source.drift` 加 1，`check` 返回 `preempt` 和 S2；修正后不再出现 S2。
  2. 构造一个在已迁移的族里新增 `ServerFrame` 变体的候选，`check` 返回 SW6；在未迁移的族里新增，不报警。
  3. 拿掉试点机器的网络 6 分钟，权威端不可达期间不报 S3；网络恢复后子树仍显示未知超过 5 分钟，才报 S3。
  4. 人为让一个 dev-3 进程访问 dev-2 的端口，`isolation` 不通过，返回 SW7。
  5. 没有任何同步改动的发布上，`sync` 字段为空。

### 6.7 状态面盘点脚本（P0 的交付物，在 dev-3 分支上）

- **统计口径：**
  - `Request` 变体数，按读、写、流、连接分类；
  - `ServerFrame` 变体数；
  - 特性字符串数；
  - 版本概念数；
  - 已迁移族中的周期性轮询；
  - 新增组件的非测试行数。
- **用途：** CI 门禁（只对清单内的族，第 1.2 节）、观察 Skill 的 SW3、SW4、SW6，以及发布记录。一份口径三处使用。

## 7. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 长期分支和主干分叉 | 最终合入的冲突大，估计也会失准 | 每周合并主干（第 2.2 节）；冲突由 dev-3 解决；主干上的团队模板有变化时重新测量 |
| 最终合入时影响 dev-2 | dev-2 合并主干之后行为发生变化 | 兼容窗口内保留旧路径；门禁按族生效；用主干的全部现有测试验证"不改动就能照常运行" |
| 共享机器的资源竞争 | dev-3 的规模用例拖慢 dev-2 的团队 | 第 1.6 节：scope 配额、回收浏览器、磁盘余量、独立的时间窗口；SW7 |
| 测试团队不如真实团队有代表性 | 某些问题发现得晚 | 固定任务里一定包含跨机派单、并行和接手；加上合成负载；最终合入之后，再由各槽位按自己的节奏采用 |
| 测试团队的模型成本 | 预算超出 | 第 5.4 节：上限由 Human 确认，超出时退回合成负载 |
| 循环诱导打补丁 | 复杂度上升，背离 v9 | SW6 门禁，加"修复不得新增机制" |
| 回退路径本身有缺陷 | 止血失败 | 兼容窗口内旧路径只修缺陷；回退演练是 P2 的进入条件之一 |
