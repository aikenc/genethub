## 摘要

**体验影响。**
- v9 要解决的问题：十几台机器看不全；跨机读取每次建链、协作靠轮询所以慢；每一族状态各做一套机制，平台越来越复杂。
- 落地方式不对，会出现两种坏结果：
  - **只加不删。** 修问题时不断加新机制，复杂度反而上升。
  - **迁移打断使用。** 某一族切换后，团队或 Agent 依赖的 CLI 行为变了，派单丢失或结果送不回来。

**怎么解决（全部待实施）：**
1. **分层（第 1 节）：** 巡查会话负责观察、规则和验收；平台开发 Agent 负责实现、自测、发 dev、合入主干；测试团队用未修改的团队模板持续干活，作为真实负载。
2. **按阶段推进（第 3 节）：** 每个阶段一族一次切完、旧路径同阶段删除；自测、dev 发布、团队回归、巡查验收都通过后合入主干。
3. **打磨循环（第 5 节）：** 4 条红线、6 条警告线；"先回退，再修复"和"修复不得新增机制"两条处置规则。

**怎么防止复发：**
- 盘点脚本同时供 CI 门禁、巡查脚本和发布记录使用，口径只有一份（第 8 节）。
- 每个阶段的完成定义都包含删除项、机制数和稳定接口的回归结果。
- 巡查会话以平台开发的实际行为验收规则：规则写了但没被执行，就改规则或脚本，而不是靠一次次提醒。

**本次需要评审：**
1. 第 1 节的分工，以及第 3 节"每个阶段合入主干"的流程和授权方式；
2. 第 3 节的阶段和完成定义；
3. 第 5 节的同步信号和处置规则；
4. 第 6 节测试团队的规模、模型和预算；
5. 第 9 节的协议目标形态。

## 2. 槽位边界

dev-3 自成一体，和其他槽位的关系只经过主干。

| 维度 | dev-3 使用 | 不触碰 |
| --- | --- | --- |
| 代码 | dev-3 自己的开发分支；文档在 `docs/dev3-proposals-20261115` | 其他槽位的分支 |
| 环境 | `worktrees/dev-3/dev.env`，端口 `47103/48103/49103`，公开子路径 `/relay-dev-3`；数据与进程在 `worktrees/dev-3/.dev-runtime` | 其他槽位的 `dev.env`、端口、`.dev-runtime`、发布目录 |
| 账号 | dev-3 自己的 dev 用户，只配对 dev-3 的机器 | 其他槽位的用户和设备配对 |
| 共享网关 | 只使用已有的转发 | 不执行 `gateway-stop` 等影响所有槽位的操作 |
| 真机 | 每台真机上的独立目录 `~/GeneHub/dev-3-sync/`、服务名 `com.genethub.dev-3.daemon`（WSL 上是带 `dev-3` 的 systemd unit）、TLS 桥端口 `47103` | 同一台机器上其他槽位和 Beta/Stable 的目录、服务和 TLS 桥 |
| 团队 | dev-3 自建的测试团队（第 6 节） | 其他槽位的团队和会话 |
| Skill | dev-3 自己的观察 Skill（第 7 节），只有 dev-3 选用 | 共享的 `genethub-team-observer` |

**资源：** 开发服务器是共享的。规模用例和测试团队的 daemon 放在带配额的 systemd scope 里运行（`systemd-run --user --scope -p CPUQuota=… -p MemoryMax=…`，数字在 E0 按机器实测给出），并限制 testctl 的并发；每次运行结束回收测试用的浏览器；dev-3 的产物和日志设上限；在共用的真机上保持可用空间高于 20 GiB。

**边界核验：** 观察脚本的 `boundary` 子命令在每个阶段开始和结束时各跑一次：dev-3 进程只监听自己的端口、只访问自己的数据目录；真机上其他槽位的服务和目录摘要未变；规模运行期间没有超出配额，没有残留浏览器。任何一项不通过就暂停，先恢复，再继续。

**主干：** 每个阶段合入主干之后，其他槽位按自己的节奏合并。v9 第 4.5 节的稳定接口保证，未修改的团队模板和使用 CLI 的 Agent 在合并之后照常工作。

## 3. 阶段、完成定义与合入

### 3.1 每个阶段的固定步骤

1. **开发与自测：** 单元测试、属性测试、合同测试、CLI 合同测试（v9 第 11.3 节），以及该阶段相关的 testctl 用例。
2. **dev 发布：** 在 dev-3 发 `0.0.1-dev.N`，一次更新 dev-3 的全部机器（不做兼容，所有机器必须在同一版本）。
3. **团队回归：** 测试团队采用新版本后，至少连续运行 12 小时，没有红线（第 5.1 节）。
4. **巡查验收：** 巡查会话按本阶段的完成定义和观察脚本的结果验收。
5. **合入主干：** 基于最新主干重新跑第 1 步；按仓库现有的变更审查、CI 和 PR 流程合入。合入的授权方式本次需要评审确认。
6. **发布记录：** 写明阶段、族、删除项、机制数和行数的增减、团队回归结果。

## 4. 打磨阶段的完成定义

### 4.1 P2：会话目录与机器间链路

- **删除：** v9 第 10 节 P2 行的删除项在代码中都不存在（盘点脚本核对）。
- **稳定接口：** CLI 合同测试全部通过；`--since` 的五种续接情况都通过（v9 第 11.3 节）。
- **团队回归：** 未修改的团队模板在 dev-3 跨机派单、并行、结果回传、接手都正常；质量卡没有因为迁移出现新的红线。
- **性能：** `--machine` 读取 P95 < 100 ms，且不发跨机请求；团队空闲 10 分钟内没有跨机请求；规模用例下单项目读取 P95 < 1 秒。
- **内核冻结：** P2 期间只允许修内核的缺陷，每个修复都附带回归测试。需要改内核接口或语义，就触发 v9 第 9.5 节的失败条件，暂停，回到设计评审。
- **机制数：** 盘点脚本显示机制数下降，写进发布记录。

### 4.2 P3：汇聚转发

- **规模：** testctl 多机规模用例覆盖 15 台机器、20,000 个会话（多数机器是模拟的），满足 v9 第 11.2 节的条件，并且在第 2 节的资源配额内运行。
- **真实使用：** 手机只连 dev-3 的一台机器，查看全部 dev-3 机器的会话；拔掉汇聚机器的网络，设备显示 `unknown(via:…)` 并能直连兜底。
- **删除：** 连接池的目录保留和挤出规则已删除。

### 4.3 P4、P5

每迁一族都按同一个模板走：schema、数据源、合同测试、删除清单、静态门禁、团队回归，落在发布记录里。

## 5. 打磨循环

### 5.1 同步信号（拟议阈值，E1 用基线数据校准）

**红线（最高优先，立即处置）：**

| 编号 | 含义 | 判定 | 数据来源 |
| --- | --- | --- | --- |
| S1 | 已承诺的写入丢失，或重复执行 | 意图返回成功，但权威端最终没有这个值；同一个 `opId` 产生了两次副作用 | 意图回执与权威端节点核对 |
| S2 | 监听漏掉了变化 | `source.drift` 大于 0 | dev-3 daemon 诊断（v8 第 10 节） |
| S3 | 错误地显示"未知" | 权威端可达且版本一致，但它的子树连续 5 分钟显示 `unknown` | 链路状态与副本状态核对 |
| S4 | 稳定接口回归 | CLI 合同测试失败；或测试团队的结论超过 10 分钟没有送达请求方、出现错投或重复投递（沿用团队质量模型 R3 的判定） | CLI 合同测试；测试团队的质量卡 |

**警告线（本候选结束后处理）：**

| 编号 | 含义 | 判定 |
| --- | --- | --- |
| SW1 | 空闲时仍有跨机请求 | 团队空闲 10 分钟的窗口内，跨机状态请求数大于 0 |
| SW2 | 太慢 | `--machine` 读取 P95 超过 100 ms，或状态变化到达副本超过 1 秒 |
| SW3 | 机制没有减少 | 某个阶段的候选上，盘点脚本显示该阶段涉及的机制数没有下降 |
| SW4 | 预算超出 | 新增代码超过 v9 第 9.4 节的任一预算 |
| SW5 | 修复增加了机制 | 某个候选在已迁移的族里新增了 `Request` 变体、`ServerFrame` 变体、特性字符串或状态轮询 |
| SW6 | 越界 | 第 2 节的边界核验任一项不通过（按红线优先级处理） |
| SW7 | 落后主干 | dev-3 落后 `origin/main` |

### 5.2 检查点

每个候选边界（定向测试后、构建后、发布后），以及每次等待返回之后，平台开发运行观察脚本的 `check`：
- `preempt`（有红线或未读转达）：立即暂停当前工作，包括 Human 给的有序清单；
- `warn`：本候选结束后处理；
- `continue`：继续。

### 5.3 处置规则

1. **先回退，再修复。** 出现 S1–S4 时，先把 dev-3 的全部机器退回上一个没有红线的 dev 版本。不做兼容，所以按版本回退，不按族切换。之后在 dev-3 复现、修复、测试，再重新发布。回退本身不算修复完成。
2. **修复不得新增机制。** 违反 SW5 的候选不得发布。确实需要新机制，说明 v9 的抽象有缺口，按失败条件回到设计评审。
3. **SW6 立即处理：** 停下当前工作，先恢复边界。
4. **发版节奏：** 同步改动单独成版，版本说明写清阶段、族、对应的信号编号和机制数变化。红线修复随时发，其他改动攒批。
5. **团队自身的问题交给反思层。** 平台只负责让问题可见，不替团队改模板。

### 5.4 双记分

每个阶段在发布记录里同时写：
- **质量卡：** 各队的正式分、红线、连续达标张数；
- **同步：** S1–S4、SW1–SW7、机制数的增减、和第 6.3 节基线的对比。

一个阶段完成的条件：两边都达标，并且第 4 节的完成定义全部满足。

### 5.5 何时退出循环

- **正常退出：** P5 合入主干后，同步信号并入常规的 CI 门禁和发布检查；测试团队按第 2 节清理。
- **异常退出：** 出现 v9 第 9.5 节的任一失败条件，暂停循环，回到设计评审。

## 6. 测试团队与负载

### 6.1 为什么需要

真实团队的负载能暴露派单丢失、重复、结果没送达这类语义问题，这是合成用例做不到的。v9 不改团队模板，所以测试团队的作用是**回归负载**：证明每个阶段之后，未修改的模板照常工作并且变快。

### 6.2 组成（拟议）

- **一到两个测试团队：** 使用 dev-3 当时主干上的团队模板，不做任何修改；同一个模型、同一组固定任务；至少一个远程岗位绑定在另一台 dev-3 机器上（`TEAM_MACHINE`），保证跨机派单和跨机对账真的发生。
- **固定任务：** 为可重复而设计。例如在 fixture 仓库中实现若干小功能，交给远程 QA 岗位验证并回传结果。每轮任务包含跨机派单、并行岗位、结果回传和接手。任务内容不变，各阶段的数据才能直接比较。
- **合成负载：** 用不调用模型的脚本制造高频的 `--machine` 读取、并发的条件写（例如两方同时对同一会话做 `ifToken` 写）、机器上下线，覆盖真实团队频率达不到的并发和冲突。

### 6.3 基线（E1）

在 P1 版本上运行至少 24 小时，记录：
- 质量卡；
- 跨机派单的端到端延迟和结果回传延迟；
- 每轮对账的跨机请求数和耗时；
- 空闲时的跨机请求数；
- 盘点脚本输出的机制数。

P2 之后的数据都和这份基线比较。

### 6.4 预算

测试团队的模型调用量、运行时长和机器占用，在 E1 之前由 Human 确认上限。超出上限就暂停测试团队，只保留合成负载和 testctl 用例。

## 7. dev-3 的观察 Skill（拟议）

- **位置：** Spaces 仓新建 `skills/lifecycle/genethub-sync-landing`，只有 dev-3 选用。新增后运行 `pipebuilder build` 和 `pipebuilder verify`，并核对其他 Space 的生成物没有变化。
- **归属：** 由巡查会话维护。巡查会话在 E0 时还没启动的话，平台开发按本节提交初版，之后只由巡查会话修改。
- **内容：**
  - 第 5 节的规则文字；
  - 一个观察脚本，提供 `check`、`wait`、`report` 和 `boundary`。做法借鉴 dev-2 的观察脚本：检查点、等待唤醒、汇报首行，但不复用它的文件和状态。
- **`check` 的输入：**
  - dev-3 各机器 daemon 的诊断：`source.drift`、`source.relist`、`link.upstream`、`replica.read_ms`、`replica.unknown`；
  - CLI 合同测试的最近结果；
  - 产品仓中的盘点脚本；
  - 测试团队的质量卡；
  - 边界核验的结果；
  - dev-3 相对主干的落后情况。
- **拟议输出：**

```json
{"action":"preempt",
 "sync":{"redLines":[{"rule":"S3","machine":"dev3-mac","prefix":"m/dev3-mac/ws/","minutes":7}],
         "warnings":[{"rule":"SW3","release":"0.0.1-dev.12","mechanisms":{"before":{"readRpc":32,"frames":11,"features":21},"after":{"readRpc":32,"frames":11,"features":21}}}]},
 "boundary":{"ok":true},
 "phase":"P2","teams":[{"team":"sync-team-a","formalScore":82,"redLines":[]}]}
```

- **验收（回放）：**
  1. 注入一次 `source.drift` 加 1，`check` 返回 `preempt` 和 S2；修正后不再出现 S2。
  2. 构造一个在已迁移的族里新增 `ServerFrame` 变体的候选，`check` 返回 SW5；在未迁移的族里新增，不报警。
  3. 拿掉一台机器的网络 6 分钟，权威端不可达期间不报 S3；网络恢复后它的子树仍显示未知超过 5 分钟，才报 S3。
  4. 让 CLI 合同测试的一个字段不一致，`check` 返回 S4。
  5. 人为让一个 dev-3 进程访问其他槽位的端口，`boundary` 不通过，返回 SW6。
  6. 没有任何同步改动的发布上，`sync` 字段为空。

## 9. 协议结构的目标形态（补充 v9）

### 9.1 现状（主干 `158d7351`）

```text
业务层     exchange 方法 8 个：protocol.identity / rpc / events / asset.preview /
             shell.run / rtc.negotiate / service.preview / file.read
           rpc 内：Request 131 种变体与 Reply 枚举
           events 内：11 种 ServerFrame，用 seq 重放，Desync 处理失步
           协商：WEB_PROTOCOL_VERSION=4、DATA_PLANE_VERSION=4、protocol.identity 和
             connection.identity、21 个特性字符串（router.rs:497），工作台在 48 处判断其中 15 个
           CLI：argv 经 loopback /cli 进入 daemon，在 cli_front 里解析成 Request；输出 schema 手写
DataEndpoint  有界帧、逻辑流、credit、公平发送、取消
E2EE          PSK 双向证明、AES-256-GCM record
Carrier       loopback WS / Fabric / RTC
```

底下三层已经是"一种帧、一种流、一种加密"，**不改**。复杂度集中在业务层：一个大 RPC 枚举承载所有语义；读接口的形状每变一次就加一个特性开关；推送共用一条事件流；CLI 和工作台是两套入口。

### 9.2 目标形态

```text
hello   连接时交换：数据面版本 + 每族的 schema 描述（schema 哈希、节点种类、意图名单）+ 流能力
sync    一条长流：get/watch/ops/unknown（v7 第 10.2 节的帧）
call    一种信封：{key, name, args, ifToken, opId} → 结果或错误
        错误码只有 conflict/budget/tooLarge/unknownKey/handler/forbidden
补充流  live（有人观看时的逐字输出）· pty（每个终端一条）· shell.run ·
        asset.preview / file.read / blob.get（大内容）· service.preview（隧道与媒体）
连接    rtc.negotiate
```

| 维度 | 现在 | 目标 |
| --- | --- | --- |
| 业务入口 | `rpc` 131 种变体，加 `events` 11 种帧 | `sync` 加 `call`；写操作是各族 schema 里声明的意图名，合并同义名后约 59 个 |
| 能力协商 | 2 个版本号、2 次身份确认、21 个特性字符串 | `hello` 里的数据面版本和每族 schema 描述；版本不同就显示"需升级" |
| 推送 | 共用一条事件流 | 状态和小的不可变内容走 `sync`；逐字输出只在有人观看时走 `live`；每个终端一条 `pty` 流 |
| 类型来源 | Rust 枚举生成 TS，CLI schema 手写 | 一份 schema 同时生成 Rust、TS 和 CLI 的输入输出 |
| 逻辑连接续传 | 约 60 秒内接回流表和订阅 | 订阅靠令牌续接，写入靠 `opId`；`live` 断开后重新 `get` 即可。P5 之后评估：只剩终端和大内容读取需要它时，改为按流续接 |

### 9.3 每个阶段的协议增删

| 阶段 | 新增 | 同阶段删除 |
| --- | --- | --- |
| P0 | `sync`、`call`、`hello` 的定义 | `Notice` 帧 |
| P1 | `hello`、`sync`、`call` 方法；5 个流与传输能力（`fabric.channels.v1`、`asset.preview.*`、`service.preview.v1`、`session.file-upload.v1`）移进 `hello` 的描述 | `protocol.identity` 方法、`connection.identity` 请求、`WEB_PROTOCOL_VERSION`、工作台 `versions/v4.ts` |
| P2 | 会话目录族的 schema | `catalog.sync`、`session.page`、`session.changes`、`session.list` 的服务端游标、`Catalog` 帧；特性字符串 `catalog.sync.v1`、`session.page.v1`、`session.active-page.v1`、`session.changes.v1`、`session.summary.v1`、`session.previewAnnotations.v1`、`workspace.terminate.v1` |
| P3 | 汇聚转发 | — |
| P4 | 低频族的 schema | 5 种推送帧；对应的读取 RPC；`access.status.v1`、`process.services.v1`、`provider.configuration.v1`、`preview.feedback.v1` |
| P5 | `pty` 流；轮次节点与 `live` 流 | `events` 方法本身（`Event`、`Desync`、`PtyOutput`、`PtyClosed`）；`round.trunk.*`；`subscribe/unsubscribe`；会话族剩余的特性字符串；`rpc` 只剩写操作，改名并入 `call` |

团队模板依赖的两个名字 `session.create-id.v1`、`session.prepare.v1`，daemon 的特性表删除后，由 CLI 从意图名单推导，继续出现在 `genet context` 的 `daemon.features` 里（v9 第 4.5 节）。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 稳定 CLI 合同有遗漏 | 合入主干后，某个脚本或 Skill 依赖的输出细节变了 | P0 用 CLI 合同测试固定字段；检索仓库里的 `genet` 调用补充清单；S4 红线 |
| 不做兼容，版本不一致的机器不可用 | dev-3 内某台机器没更新时，只显示"需升级" | 每次发布一次更新全部 dev-3 机器；升级入口保持稳定；Beta、Stable 的多机更新方式由发布流程负责 |
| 自测偏乐观 | 问题到合入主干后才暴露 | 巡查会话独立验收；未修改的团队模板做真实负载；testctl 规模用例 |
| 共享机器的资源竞争 | dev-3 的规模用例拖慢其他槽位 | 第 2 节的配额、浏览器回收、磁盘余量；SW6 |
| 测试团队不如真实团队有代表性 | 某些问题发现得晚 | 固定任务一定包含跨机派单、并行和接手；加合成负载；合入主干后各槽位按自己的节奏采用 |
| 测试团队的模型成本 | 预算超出 | 第 6.4 节：上限由 Human 确认，超出时退回合成负载 |
| 循环诱导打补丁 | 复杂度上升，背离 v9 | SW5 门禁，加"修复不得新增机制" |
| 回退版本本身有缺陷 | 止血失败 | 每次发布前保留上一个无红线的版本；P2 之前做一次回退演练 |
