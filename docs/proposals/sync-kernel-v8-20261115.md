## 摘要

**体验影响。** 主干 Beta 接入多台机器后有两类问题：
1. **慢、超时、掉线。**
   - 项目列表读取超时：只有一条会话的项目，元数据阶段也等了 487 秒。
   - 前台连接约 8 秒掉线，在途的发送和读取结果未知。
   - 一个无关终端输出大量内容，所有页面的 RTC 和 Fabric 连接都会更换。
2. **复杂度杂乱。**
   - 每一族数据各做一套"变化通知、缓存、重连、版本判断"，"版本"至少有 8 种说法。
   - 每加一种实时数据，要改协议、daemon、工作台和 CLI 共 5 处。
   - 团队脚本只能轮询全量数据，这又反过来加重了问题 1。

**怎么解决（待实施，第 7.1 节除外）。** 以统一的同步框架作为平台状态面的设计框架，分四层：
- **数据源层（第 4 节）：** 所有状态都从"可靠监听 + 按需传播"得到，不再做全局扫描。
  - 本机写入由处理器直接发布；
  - 外部写入靠 host 提供的文件监听和进程事件发现；
  - 丢失事件时只把受影响的子树重新列出。
  - 每个数据源都要遵守可靠性合同。
- **同步内核（第 5 节）：** 沿用 v7 的节点树、令牌、订阅、意图和未知状态，但首期瘦身。
- **执行分区（第 6 节）：** 连接、路由、心跳和"重活"分到不同的执行单元。扫描、对账和进程收集不再与连接抢同一个线程。
- **传输存活（第 7 节）：** 心跳由不会被业务阻塞的一层应答，区分"连接断了"和"对端忙"。

另外，终端输出积压关闭整条连接的问题，已经在候选 `af487332` 修复（第 7.1 节）。

**怎么防止复发。**
- 每个数据源都有可靠性合同测试：监听溢出、外部写入、重启、事件丢失之后，状态都要收敛。
- 后台抽样对账，"对账发现的偏差数"作为监听可靠性的指标，目标为 0。
- 每一步迁移都附带删除清单；静态门禁禁止已迁移的族再新增推送帧或读取 RPC。
- 第 9 节按问题列出验收条件，均未执行。

**本次需要评审：**
1. 第 4 节的数据源可靠性合同和 WIT 文件监听接口的形状；
2. 第 6 节执行分区的边界和首期范围；
3. 第 8 节的迁移顺序，尤其是"先接第二个消费方（团队脚本）、再动会话目录"；
4. 第 5.2 节首期内核相对 v7 的删减。

## 1. 背景：两类问题和证据

### 1.1 问题一：多机器下慢、超时、掉线

| 现象 | 已确认的原因 | 来源 |
| --- | --- | --- |
| 单项目列表要等数百秒 | 局部读取先等全机器的全局 `sweep` 锁，继承了无关项目的全局扫描耗时。一次全局扫描覆盖 255 个 home、3442 次 stat，只重读 8 份元数据，却耗时 527 秒，其中让出后的等待占 498 秒 | `beta-daemon-stall-20261113/diagnosis.md`；局部读取的修复已随 0.21.0-beta.1 发布，设备要更新 App 才生效 |
| 扫描本身停不下来 | daemon 是单线程 wasm guest，会话目录、Space 发现、Timer 登记都在周期性地全量扫描磁盘 | [fs-change-discovery-proposal.md](../fs-change-discovery-proposal.md) |
| 整台机器都变慢 | 遗留的截图浏览器占约 23.9 核，容器 32 核配额被打满；guest 主线程在运行队列等待 | 同上诊断记录 |
| 后台负载持续增加 | 一个团队定时器反复调用已禁用的无界历史查询，累计失败至少 54660 次；进程预览收集单次 126–154 秒 | 同上诊断记录 |
| 无关终端输出导致掉线 | 所有终端输出和机器状态帧共用一个 1024 帧的广播，每条完整连接都订阅全部内容；落后后整条连接被关闭 | `fb-session-page-disconnect-20261112`，Run `261113-1549-pty-burst-61d7`；已在 `af487332` 修复 |
| 前台约 8 秒掉线 | 20 秒的 JS 停顿或 UDP 丢包都能触发心跳超时。daemon 的心跳判定和业务共用 guest 线程（[endpoint.rs](../../apps/daemon/src/dataplane/endpoint.rs) 的 `last_received` 判定）；浏览器端的连接也和 React 渲染共用主线程 | 同上；原事故的根因未闭环 |

**结论：** 这些原因都不是"缺少同步框架"本身。它们共同的根子是三件事：
- 数据源只能靠扫描发现变化；
- 所有工作挤在一个线程上；
- 连接存活和业务负载没有隔离。

所以，统一同步框架只有把这三层一起设计，才能解决问题一。只统一分发协议（v7 的范围）不够。

### 1.2 问题二：没有统一的设计框架

v7 第 1.2 节的清单仍然成立，2026-11-15 在主干上核对过：
- `ServerFrame` 有 11 种推送帧，工作台为每一种维护单独的监听器；
- "版本"有 8 种说法：目录按行 ETag、`expected_revision`、`plan_digest`、`context_revision`、`seq`、`cursor`、浏览器缓存 `checksum`、Cloud 的 `generation/revision`；
- `store.ts` 4318 行，`client.ts` 2547 行；
- 工作台依赖了 `@tanstack/react-query`，但全仓没有使用它。

新增的证据：
- 正在 dev-5 实现的 fs-change-discovery 又引入了一种"不透明变更游标"，作为第 9 种版本概念；
- PTY 修复前，终端输出和机器状态共用一个广播，结果终端洪泛会挤掉 Agent 和进程帧。这正是"每族自己做"缺少统一的数据面约束所致。

### 1.3 v7 的不足

| v7 的问题 | v8 的处理 |
| --- | --- |
| 数据源只有 `load/scan` 端口，会话目录写明"沿用缓存目录加后台对账"，文件监听推迟到 K6 | 第 4 节：数据源层成为一等设计，给出可靠性合同和 WIT 文件监听接口 |
| 内核和全部数据源都在 daemon 唯一的线程上 | 第 6 节：执行分区 |
| 第一个候选 K0–K3 只迁移设置、Agent、进程、更新下载，不碰超时路径 | 第 8 节：先修现场问题，再让团队脚本作为第二个消费方提前接入 |
| K7 要删除 `seq/ItemDelta`，触及 [architecture.md](../architecture.md) §4 的契约，却没有先移动边界 | 第 5.3 节：会话正文保留"追加日志"原语，不用 JSON Patch 模拟 |
| 副本端核对令牌，要求 Rust 和 TS 双端实现规范化 JSON 和 SHA-256 | 第 5.2 节：副本端只把令牌当不透明值，校验只在调试模式 |
| 没有写清与逻辑连接续传、fs-change-discovery 的关系 | 第 4.7 节、第 7.3 节 |
| 第二个应用（预览进展页）排在 K4 之后，违背 G02 | 第 8 节：团队脚本 `watch` 作为第二个消费方，放进第一个候选 |

## 2. 目标与范围

**成功标准：**
1. **问题一：**
   - 多台机器、上百个项目、团队定时器并行、加 CPU 竞争的负载下，单项目读取的 P95 不受无关项目影响；
   - 稳态下不出现全局扫描；
   - 无关终端输出不导致连接更换；
   - 对端忙时显示"响应慢"，而不是断开。
2. **问题二：**
   - 已迁移的族只用节点令牌判断变化、只用 `ifToken` 做条件写；
   - 新增一族数据只需写 schema 和数据源；
   - 每一步迁移都有删除清单，并且真的执行。

**本期不做：**
- 不改会话存储格式（`SESSION_FORMAT`）、写锁、inbox 和执行围栏；
- 字节流（PTY 输入输出、音视频、文件内容）不进节点；
- 不做 CRDT 和多人同时编辑文本；
- 不引入外部同步引擎或数据库依赖；
- 不做 Hub 权威端；
- 不做跨机器副本型数据源的持久缓存。

## 3. 总体结构

```text
消费方：工作台（TS 副本端）· CLI/Python（genet sync watch）· 预览页 · 团队脚本
   │ 订阅（节点、子树、视图）/ 意图
同步内核（v7 第 2、3、10 节）：节点树 · 令牌 · 订阅与脏集合 · 视图 · 未知 · 预算
   │ 端口：Source（快照 + 增量）· Handler（意图）· Link（传输）
数据源层（第 4 节）：自有写入 · 文件监听 · 进程事件 · 有界对账 · 可靠性合同
   │ host 能力：fs-watch（新增）· process 事件（扩展）
执行分区（第 6 节）：控制分区（连接/路由/心跳/意图）│ 工作分区（监听/对账/进程/定时）
   │
传输与存活（第 7 节）：WebSocket · Fabric · RTC；存活由 host / Web Worker 应答
```

各层的职责划分：
- **数据源层**决定"什么变了"；
- **内核**决定"谁需要知道、发什么"；
- **执行分区**决定"在哪个线程上算"；
- **传输层**决定"连接是否还活着"。

任何一层出故障，只把受影响的子树标为未知，不拖垮其他层。

## 4. 数据源层：变化发现与可靠性合同

### 4.1 三类变化来源

| 来源 | 例子 | 怎么发现 | 现状 |
| --- | --- | --- | --- |
| 本机通过意图写入 | 重命名会话、修改设置、启动进程 | 处理器提交后直接 `put` 对应节点，不等监听回调 | 现在各族自己发专用失效事件，或者不发 |
| 外部写入，可以监听 | 其他渠道的 daemon、Agent 进程、CLI、用户编辑器写 `.genethub/` 和工作区文件；`git checkout` | host 文件监听（第 4.3 节）。收到事件后只读对应路径的元数据，内容不变就不推送 | guest 没有监听能力（`wit/genehub-host.wit` 里没有 watch），只能扫描 |
| 外部变化，无法监听 | 进程退出、Agent 孙进程、端口占用、Git 工作区里的派生状态 | host 进程事件（第 4.5 节）；其余用**有预算的增量对账** | 轮次结束时采样，或者每次请求临时收集 |

### 4.2 可靠性合同

每个数据源都必须实现这份合同，并通过对应的合同测试。设计参考 Kubernetes 的 list-watch 和 Watchman 的时钟加全量重建标记（第 11 节）。

```rust
/// 数据源端口（拟议）。所有方法都有工作预算，可以分批返回。
trait Source {
    /// 带代际号的快照。代际在数据源重启、监听重建时变化。
    fn snapshot(&self, prefix: &Key, budget: &mut Budget) -> Snapshot; // {generation, version, entries, next}
    /// 某个版本之后的增量；版本过旧或代际变了时返回 Expired。
    fn changes(&self, since: Version, budget: &mut Budget) -> Changes;  // Events{..} | Expired
}
```

| 合同条款 | 要求 | 合同测试 |
| --- | --- | --- |
| C1 快照加增量 | 每个变化都带单调递增的版本；增量可以从任意未过期的版本续接 | 随机交错写入、续接，最终状态等于快照 |
| C2 丢失必须显式 | 监听溢出（inotify `IN_Q_OVERFLOW`、FSEvents `MustScanSubDirs`、Windows 缓冲区溢出）、增量过期、数据源重启时，**只把受影响的子树标为 `unknown`**，再有界地重新列出这棵子树；不允许静默丢失，也不允许扩大成全局扫描 | 注入溢出，断言只重列该子树，收敛后 `unknown` 被清除 |
| C3 自己的写入不重复 | 处理器先 `put`；随后监听回调带来同一份变化时，令牌相同就丢弃 | 同一次写入只推送一次 |
| C4 降级同形 | 旧 host 没有监听能力时，用同一接口加预算轮询；调用方无感，只是延迟变大 | 关闭监听能力后，同一组合同测试通过 |
| C5 兜底对账 | 后台低速抽样，把数据源的当前值和真实磁盘或进程状态做比对。发现偏差就修正，并计入 `source.drift` 指标 | 人为绕过监听修改文件，对账周期内修正，`drift` 计数加 1 |
| C6 有界 | 单次 `snapshot`/`changes` 的工作量受预算约束，协作让出；每个数据源的内存有上限 | guest 前台延迟不受单个数据源影响 |

**可靠性的判定标准：** 稳态下 `source.drift` 应为 0。不为 0 就说明监听漏了事件，按缺陷处理，不能用缩短对账周期来掩盖。

### 4.3 新增 host 能力：文件监听（需要完整模式发布，G04）

拟议的 WIT 形状，具体签名在 K0 定稿：

```wit
interface fs-watch {
  resource watcher {
    /// root 必须在已授权的 preopen 之下；recursive=false 时只监听单层。
    constructor(root: string, recursive: bool);
    /// 非阻塞取出已到达的事件；溢出时返回 overflow，调用方按 C2 重列。
    poll: func(max: u32) -> result<batch, watch-error>;
  }
  record event { path: string, kind: event-kind }
  enum event-kind { created, modified, removed, renamed, attributes }
  variant batch { events(list<event>), overflow }
}
```

- host 用 `notify` 一类的跨平台实现，三平台各自映射；
- 事件只是"可能变了"的提示，guest 收到后自己读元数据确认，不信任事件内容；
- watcher 数量和事件队列都有上限，超过上限返回 `overflow`，不阻塞 host。

### 4.4 会话目录：用监听替代全局扫描

- 每个 Space 的 `.genethub/` 一个 watcher。事件到达后，只核对对应会话目录的 `(mtime, size, ctime)` 指纹，变化了才重读元数据。
- dev-5 的磁盘指纹索引保留，作为 C2 重列和 C4 降级时的实现。目录 mtime 剪枝、热数据和冷数据分级核对都沿用。
- 锁按 home 划分：一个 home 的重列不阻塞其他 home 的读取。这延续了 0.21.0-beta.1 已发布的局部读取修复。
- 冷启动沿用主干已有的缓存目录加后台对账（`e46dae7d`），首次订阅时按需加载。

### 4.5 进程：事件驱动

- daemon 通过 host `process` 接口启动的进程，host 是父进程，**由 host 主动推送退出事件**。这需要扩展 WIT，并入第 4.3 节的同一次完整模式发布。
- Agent 再启动的孙进程，按进程组或 cgroup 跟踪。Linux 用 `cgroup.events` 的 `populated` 或 pidfd，其他平台退化为有预算的定时核对。
- 进程预览（端口、命令行）改为观察者：只对状态发生变化的进程做收集，结果写入 `m/<机器>/process/<id>` 节点。不再每次请求时遍历全部进程。

### 4.6 Git 和文件树

- 监听 `.git/HEAD`、`.git/index` 和 `refs/`，以及已展开目录的单层。事件合并去抖之后，在预算内执行一次 `git status`。
- 目录节点区分四种状态：未展开、已截断、未知、确认不存在（沿用 v7 K6 的门槛）。

### 4.7 与 fs-change-discovery（dev-5）合并

| fs-change-discovery 的部分 | 在 v8 里的位置 |
| --- | --- |
| 磁盘指纹索引、目录 mtime 剪枝、冷热分级 | 文件型数据源在 C2 重列和 C4 降级时的实现 |
| 不透明变更游标 | 就是数据源的 `Version`，**不另立对外协议**。团队定时器改用 `genet sync watch`（第 8 节 K5） |
| 规模用例（450 工作区 / 2500 会话 / 5 个团队定时器） | 并入第 9.1 节的验收 |

建议 dev-5 现在就把游标限定为内部接口，不扩展到对外协议，以免被迁移时还要再删一次。

## 5. 同步内核：沿用 v7，首期瘦身

### 5.1 沿用的部分

v7 的以下设计全部沿用：
- 节点外是键路径树，节点内是 JSON 对象；
- 父节点不嵌入子节点；
- 权威边界是顶层子树，权威不可达时它的子树显示"未知"；
- 令牌是规范化 JSON 的 SHA-256 截取 128 位，在权威端惰性计算；
- 每条连接只记录"已发送的令牌"，写不动时只积累脏键，可写后再合并推送；
- 意图和 `ifToken` 条件写；
- 帧的种类、错误码和按族协商。

### 5.2 相对 v7 的删减

| v7 首期 | v8 首期 | 理由 |
| --- | --- | --- |
| 副本端收到新值后核对令牌 | 副本端只把令牌当不透明值，用于回传和比较；核对令牌只在调试模式下进行 | 传输可靠有序，AEAD 已经保证完整性。这样 TS 端不用实现 JCS 规范化和哈希，双端一致性测试面缩小一大半 |
| schema 声明的集合索引，内核在内存中维护有序索引 | 首期只做内核内置的子节点视图；集合索引由数据源提供（例如会话摘要按 `updatedAt` 排序的视图，由会话数据源维护） | 内核不变成查询引擎；索引成本落在拥有数据的执行分区里 |
| 只有值节点 | 值节点加**追加日志节点**：令牌为 `(epoch, 长度)`，续接时从断点取尾部，超出保留窗口时返回快照 | 会话正文本质是日志（第 5.3 节） |
| K1 的门槛只测内存 | K1 的门槛同时测 CPU：单次 `put` 的独占时间上界，以及内核占 guest 轮询时间的比例 | daemon 线程是现网瓶颈 |

### 5.3 会话正文

会话正文保留现有的 `seq`、`ItemDelta` 和逻辑连接续传，以追加日志节点的形式接入内核，不改成"JSON Patch + 每连接保留已发送版本"。这样做不触碰 [architecture.md](../architecture.md) §4 的 `TimelineItem/ItemDelta` 契约。

将来如果要改这份契约，必须先改 architecture.md，再单独立项。

## 6. 执行分区

### 6.1 为什么要分区

现在所有工作都在 daemon guest 的一个执行线程上：
- 会话、页面、CLI 请求；
- 心跳；
- 扫描、对账；
- hook 定时器；
- 进程收集。

一项慢了，全部跟着慢。0.21.0-beta.1 修掉了"局部读取等全局锁"，但扫描、进程收集和定时器仍会挤占连接和路由。

### 6.2 形态

```text
host 进程
 ├─ 控制分区（guest 实例 A，独立 OS 线程）：连接、认证、路由、心跳应答、意图分发、内核的订阅表
 └─ 工作分区（guest 实例 B…，各自独立线程）：文件监听与重列、对账、进程观察、hook 定时器、预览收集
        └─ 通过 host 提供的分区间通道，以 v7 的 Link 端口交换 put/del/unknown 与意图
```

- **先例：** 内置 Agent 已经由另一个 host 进程装载同一份 wasm 制品的 agent 入口运行（[architecture.md](../architecture.md) §1）。工作分区可以是同一个制品的 worker 入口，放在同一个 host 进程的独立线程（同一 Wasmtime 引擎、独立 Store）上，也可以放在独立进程里；K0 时比较这两种做法。
- **挂载表：** 工作分区是若干子树的数据源，例如 `m/a/ws/<id>/` 下的会话摘要、`m/a/process/`。控制分区只做路由和合并，相当于 v6 所说的"副本型数据源"。
- **分区崩溃：** 它的子树标为 `unknown`，host 重启该分区，重启后按 C2 重新列出。控制分区和连接不受影响。

### 6.3 约束

- 新增 worker 入口和分区间通道需要改 WIT，属于**完整模式的 App 发布**。和第 4.3、4.5 节合并为同一次 App 发布，避免多次升级 App。
- `SessionManager` 的原子性只在分区内保证。写入意图按键前缀路由到拥有该子树的分区，跨分区的写入不做原子保证；视图由控制分区合并。
- 多线程修不了锁设计本身的缺陷，也挡不住外部进程抢 CPU。它保证的是：重活再慢，也不影响连接、心跳和小请求。
- 首期只拆一个工作分区，把所有后台工作移出控制分区。按 Space 分多个分区，等实测证明单个工作分区成为瓶颈时再做。

## 7. 传输与存活

### 7.1 终端输出积压（已修复，候选 `af487332`）

- **修复前：** 终端输出和机器状态帧共用一个 1024 帧的广播。某条连接落后后，整条连接被关闭，所有页面重连。
- **修复后：**
  - 机器状态帧（Agent、请求、进程、下载进度）走独立的 `machine_events` 广播，终端洪泛挤不掉它；
  - 某条连接落后终端输出时，保留连接，在它显示的每个终端里写入"终端输出过快，部分输出没有送达本窗口"，并记录 `dataplane/terminal.fanout/lagged` 诊断；
  - 机器状态帧如果丢失，仍按原语义结束连接，由重连重新读取。
- **验证：**
  - daemon 新增 4 个单元回归；把"落后即返回"改回旧行为后，其中 2 个失败；
  - `cargo test -p genet-daemon` 667/667；
  - testctl `dev-feedback` Run `261115-1026-pty-fanout-lag-52e3` 13/13 qualified；
  - 完整 merge gate Run `261115-1039-pty-fanout-merge-2fd7` 853/859 通过，未取得资格。其中 3 个失败在同一候选低并发重跑时通过；另外 3 个在主干 `24eb228d` 同条件下同样失败或中断，属于共享机负载下的既有问题；
  - 合入走 [PR #93](https://github.com/aikenc/genethub/pull/93)，状态以 PR 和任务记录 `fix-pty-fanout-lag-20261115` 为准。
- **未覆盖：** 真实 Hosted 环境下 RTC/Fabric 的 32 MiB 洪泛，对应的诊断用例不在主干上。
- **后续：** 每条连接只接收自己打开的终端的输出；终端输出按时间片合并。

### 7.2 存活由不会被饿死的一层应答

- **浏览器：** 连接、心跳和解帧移进 Web Worker，React 渲染卡顿不再拖断连接。现在 workbench 没有使用 Worker。
- **daemon：**
  - 物理连接的存活由原生 host 应答，host 本来就负责 ICE、DTLS 和 SCTP；
  - guest 只负责业务层的"对端忙"：控制分区报告排队时长，超过阈值时，客户端显示"响应慢"，不断开连接，在途的只读请求也不判定为失败。
- **区分两种情况：**
  - "传输断了"：走现有的逻辑连接续传；
  - "对端忙"：保持连接，只更新界面状态。
- 约 8 秒的前台掉线，根因仍未闭环。本节是方向，不是那次事故的结论。

### 7.3 与逻辑连接续传的关系

[logical-connection-core.md](../logical-connection-core.md) 已经能在约 60 秒窗口内，把重新拨通的连接接回原来的流表和订阅。同步内核的恢复机制（重连时上报已知令牌，只重发变化的节点）只在三种情况下起作用：超出续传窗口、daemon 重启、换设备。两者不重复实现。

## 9. 验收（均未执行，K0 时细化数字）

### 9.1 问题一：性能与可用性

| 场景 | 通过条件 | 步骤 |
| --- | --- | --- |
| 无关终端洪泛 | 无关工作区的终端输出 32 MiB，RTC 和 Fabric 连接不更换；落后的终端出现缺口提示；其他页面的 Agent 和进程状态照常更新 | S0（候选已有单元回归） |

| 对端忙 | guest 控制分区被人为阻塞 20 秒时，页面显示"响应慢"，连接不更换，在途只读请求在恢复后返回正确结果 | S0、X1 |
| 局部读取隔离 | 450 工作区 / 2500 会话 / 5 个团队定时器 / 外部元数据修改 / CPU 竞争同时存在时，单项目读取的 P95 低于 1 秒，且不明显劣于同轮的轻量请求 | X1、K4 |

| 多机器 | 一台远端机器断开，它的子树显示"未知"；其他机器的读写不受影响；恢复后自动收敛 | K2 起 |

### 9.2 数据源可靠性

| 场景 | 通过条件 |
| --- | --- |
| 监听溢出 | 注入溢出后只重列受影响的子树，收敛后 `unknown` 被清除，期间其他子树不受影响 |
| 外部写入 | 另一渠道的 daemon、CLI 或编辑器修改 `.genethub/` 后，对应节点在去抖周期内更新 |
| 数据源重启 | 工作分区崩溃并重启后，子树先显示 `unknown`，然后收敛；副本只收到变化的节点 |
| 漏事件兜底 | 绕过监听人为修改文件，抽样对账在一个周期内修正，`source.drift` 计数加 1；稳态下 `drift` 为 0 |
| 降级 | 在没有 `fs-watch` 的旧 host 上，同一组合同测试通过，只是延迟变大 |

### 9.3 问题二：统一性

沿用 v7 第 13.1 节的四条：旧路径删除、静态门禁、新增一族的改动面、版本概念收敛。另加一条：
- 每一步合入时，统计删除的帧、RPC、监听器和刷新点，以及新增的代码行数，写进发布记录。"删掉的比加的多"是 K3、K4 的通过条件之一。

## 11. 取舍与替代方案

### 11.1 方案比较

| 方案 | 结论 |
| --- | --- |
| 维持现状，逐个修 | S0 必须做，但只修不统一的话，第 10 族数据还会再造一套通知和版本 |
| 只统一工作台（react-query 加失效通知） | 改动最小，但 daemon、CLI、脚本和预览页仍然各一套，数据源仍然靠扫描 |
| v7 原样实施 | 分发统一了，但数据源和线程问题没解决，第一个候选也不碰超时路径 |
| 直接引入现成引擎（Zero、Electric、PowerSync、Replicache 等） | 不建议：多数假设服务端是 Postgres 或 Node，和"每台机器各自是权威、单线程 Rust wasm、relay 不理解内容"不匹配。另外 Replicache 已进入维护模式，Electric 被收购，Realm Device Sync 已关停，同步层是很难替换的基础设施 |
| **v8：数据源合同 + 瘦身内核 + 执行分区 + 存活隔离（推荐）** | 两个问题都对应到具体改动和验收；成本是一次完整模式的 App 发布（W1），以及两份副本端实现 |

### 11.2 借鉴来源

| 借鉴什么 | 来源 |
| --- | --- |
| 快照加增量、版本过期后重新列出、本地缓存（C1、C2） | [Kubernetes API：高效检测变化](https://kubernetes.io/docs/reference/using-api/api-concepts/#efficient-detection-of-changes) |
| 监听溢出时显式要求全量重建（C2） | [Watchman 时钟与 fresh instance](https://meta.github.io/watchman/docs/clockspec) |
| 每类数据一个 `state`，`/changes` 返回增量 | [JMAP，RFC 8620](https://www.rfc-editor.org/rfc/rfc8620) |
| 层级键表达式、queryable 数据源、liveliness 作为"未知"的来源、路由节点分担传播（第 6 节） | [Zenoh 文档](https://zenoh.io/docs/) |
| 按前缀订阅、具名意图、"poke 只敲门" | [Replicache 文档](https://doc.replicache.dev/) |
| 按模型声明加载策略、全局 syncId 加补缺 | [Linear 同步引擎逆向分析](https://github.com/wzhudev/reverse-linear-sync-engine) |
| 节点观察本地并回写状态、controller 拆到独立进程 | Kubernetes 的 kubelet / controller 模型 |
| 每连接状态必须设预算（反例：Meteor mergebox 的内存随连接数膨胀） | Meteor DDP |

这些只是方法参考，不能代替本项目的证据。GeneHub 自己的现场数据以第 1 节为准。

## 12. 兼容、迁移与恢复

- **协议：** 沿用 v7 第 10.1 节，按族协商；旧 daemon 不返回 `sync` 字段，客户端对它继续走旧路径。跨机器时每个权威单独协商，新旧版本可以混连。
- **host 和 guest：**
  - 新 guest 在旧 host 上运行时，检测不到 `fs-watch`、进程事件和 worker 入口，就按 C4 降级为预算轮询，并且不分区；
  - 新 host 上运行旧 guest 时，新能力不使用。
  - 两种组合都要进第 9.2 节的降级用例。
- **数据：** 会话存储格式不变；节点是从现有存储投影出来的读模型，删除内核状态不丢业务数据。
- **回滚：** 每一步都能单独回退到上一个 Live 版本。W1 回滚到旧 App 后，新 guest 自动降级。
