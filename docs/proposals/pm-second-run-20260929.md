# 第二轮 Workflow 跑测：PM 决策与人工沟通改进提案

日期：2026-09-29。反馈：`fb_EF3jLR-DS8UP`。来源会话：`s_82d8597bae714c8f85bd137e9cbdb5eb`。本提案供下一轮设计与实施，不表示以下建议已实现或已端到端验收。

## 结论与设计边界

已确认的直接缺陷是宿主把恢复 Reviewer 的通用 `human` 结果按角色名称解释为目标缩减，随后拼接预算说明和目标调整按钮。更深的设计问题是：PM 提出、解释、协商和纠正方案的责任，与平台最终落实授权的责任没有清楚分开。

应保留 PM 的自由对话与判断；平台在执行预算变更、目标修改、取消和验收等动作时，校验具体方案、真实用户答复、当前事实及一次性效果。仅收紧卡片类型会把错卡变成发卡失败，不能完成 PM 的协调职责。完全取消动作约束又会失去迟到答复、重复执行和目标保护边界。

## 同步候选已具备的机制与剩余缺口

以下为来源 dev-ui 候选的历史状态；本槽位合入采用 Run/LLM 次数预算和独立恢复额度，不采纳处理时间授权。

当时 dev-ui 候选主要是此前 dev-agent 改版的合入：统一需求级请求次数与有效处理时间预算，取消独立恢复额度；内置恢复作为普通 v2 诊断报告；同一停止边界只自动复查一次；预算提案绑定明确总上限和 revision；拒绝追加保留目标；人工待办无默认答复期限；历史 Run 结果与需求交付分离。这些机制应保留并机械验证。

仍需改进：

- 当前待答输入仍禁止取消/替换；未答方案变更会返回 requirementAwaitingHuman。
- CLI schema 已提供预算总量、目标内容及版本参数，但 kind 的 a/b/d/e/f 仍主要是枚举，缺少直接可读的动作效果说明。
- 单一预算和停止边界去重提供基础，不能仅凭它们认定旧 Run 的所有晚到通知都已正确收束。
- `game-dev.yaml` 仍在独立验收入口检查剩余 32 次调用；该检查不等于实施开始前已经预留验收和返工成本。

## 建议实施顺序

### P0：让错误提案可以正式撤回或更新

在现有 Human 请求机制内增加 PM 受控撤回/替代动作，绑定请求 ID、目标、当前版本及原因。撤回只结束该待答方案，不取消原需求、不批准预算、不改变验收。替代保存新方案和旧方案的关联；旧请求的迟到答复返回明确“已被替代”，不得作用于新方案。并发“用户答复”和“PM 撤回”必须原子决定唯一有效结果；已执行的批准不能被当作未批准提案撤回。

调整 consultation 指令：允许解释、比较、提出和撤回未批准方案；继续禁止 Agent 代答用户、从讨论文字推断批准或执行依赖待批权限的动作。已有授权内、与待答事项无关的工作是否可继续，应按具体动作权限判定，不能统一冻结 PM。

用户可以追问、追加条件或提出新方案。选项提供快捷答复；自由文本由 PM 理解并整理为可审阅方案。含义明确、来源真实且绑定当前方案的一次用户答复应足够；不要生成“先答意向，再正式批准”的重复决定。未明确满足授权条件的讨论不作为批准。

### P0：PM 接收诊断并负责形成可执行建议

通用 human/需要人讨论的报告交回 PM，不由恢复角色名称推导预算、缩减目标或取消。沿当前 v2 报告路径推进，清理仍可能生成旧式业务推断的兼容入口；保持业务验收结论与报告完成分离。

给 PM 一份能一次完成判断的事实：原目标及最新纠正、当前进展与缺证、停止原因/边界、可用预算与授权上限、现有后继、未答方案及处置回执。常规问题在已有权限内处理；超权限投入、改变目标或接受未达标结果时，才给用户具体取舍、建议、投入上限和再次停止条件。

### P1：接口说明与运行事实一致

在 capability/schema 中直接描述 a/b/d/e/f 的含义、效果、前置条件及拒绝后行为；预算用总上限与预算 revision，范围用具体目标和变化。提供由当前 daemon 返回的事实示例，避免 Skill、文档和运行接口各自描述不同合同。记录跑测构建身份、包/候选摘要及实际加载 Skill，不仅记录槽位 HEAD。

### P1：提前检查验收资源与后继责任

WM 在流程中安排依赖预检及“实施＋验收＋必要返工”预算检查；PM 结合事实选择追加、定向验收或带着具体失败回来。验收工具缺失报告“无法验证”，不能据此认定业务功能失败；不能自动降低验收标准。

旧 Run 通知处理要核对同需求的新后继、停止边界与已落实动作。重复投递复用处置回执；新的故障保留独立责任。PM 尚未落实报告与用户在等待答复是不同条件，前者可提醒，后者不能因为离线而取消目标或转反馈。

## 下一轮验收

先跑小预算的真实 CLI/client/daemon 闭环，再跑五关游戏：

1. 恢复报告明确建议追加预算时，不产生缩减目标按钮；PM 能形成一次可落实提案。
2. 用户追问、要求改条件，PM 可以撤回并提出新方案；旧答复失效，原目标保留。
3. 重复批准、重启后重送、迟到答复、答复与撤回并发，都只能产生一次正确效果。
4. 拒绝预算保留需求；批准范围只调整范围、不标记交付；Run completed + done:false 显示未交付。
5. 后继运行时旧故障不再重复要求同一决定；真正新故障能独立处置。
6. 剩 6 次而验收需 32 次时，在新增实施投入前返回明确决策；缺浏览器能准确报告且不进入无效修复。
7. 人隔夜返回仍能查看待答；项目/预算事实改变时解释失效原因，不能以等待时间作废。

观察协调成本、重复通知、错误授权数、从阻塞到有效决定耗时、验收证据完整度。先保存这一轮基线，再设目标；不为追求少调用降低验收。
