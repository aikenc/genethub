## 摘要

**体验影响。** 同一台机器上的不同数据，"变了以后界面怎么知道"各有各的做法：
- 有的实时推送：会话目录、会话正文、Agent 状态、更新下载进度。
- 有的只在特定时刻采样推送：后台进程只在轮次结束时推。
- 有的只能拉取：设置、设备、Git 状态、文件树、工作区列表、机器列表。这些什么时候刷新，由各个面板自己决定。

用户因此会看到：
- 两个窗口显示不一致，例如一个窗口改了设置，另一个窗口不变。这一条是源码推断，未复现。
- 重开面板或手动刷新后才更新。
- 漏了失效处理就停留在旧值：源码注释里记录过侧栏一直显示"新会话"，见第 1.2 节。

团队脚本只能周期性地全量读取。每加一种实时数据（例如团队进展预览页），就要在协议、daemon、工作台和 CLI 各改一遍。

**怎么解决（待实施）。** 读取和订阅收敛为一种机制，并按族替换、删除旧机制：

| 级别 | 结构 | 判断变化 | 更新方式 |
| --- | --- | --- | --- |
| 节点外 | 键路径树（例如 `m/<机器>/ws/<工作区>/session/<会话>/summary`） | 节点令牌，即对规范化 JSON 整体求哈希 | 节点级别的增、删、整份替换；按子树和视图订阅 |
| 节点内 | 一个 JSON 对象 | 首期：令牌不同就整份替换；二期：直接比较 JSON 值 | 二期才引入 JSON Patch 增量（字段、数组、字符串追加） |

写入仍然是具名意图，由原有的处理器执行。字节流（终端、音视频、文件内容）保留原有通道。

**怎么防止复发。**
- 每一步迁移的验收都包含"旧路径已删除"。另设静态门禁：已迁移的族，不允许再出现读取类 RPC、专用推送帧或客户端自管的缓存和刷新点（第 13.1 节）。
- 内核不依赖文件、网络和异步运行时，可以只用假端口单独测试。
- Rust 和 TS 共享测试向量，令牌逐一相同。
- 节点大小和每条连接的状态都有上限，由内核强制。
- 第 13 节验收，均未执行。

### 1.3 为什么这是结构问题

- **每加一族，改动点有 5 处：** `ServerFrame` 变体或读取 RPC、daemon 推送点、`client.ts` 监听器、`store.ts` 状态与刷新时机、CLI 命令。
- **失效靠每个开发者记得处理。** `TitleChanged` 的注释就是一次漏处理留下的记录。
- **重连语义各不相同。** 目录有条件修复，正文按 `seq` 续传，其他族依赖页面初始化流程，有的根本不恢复。
- **没有统一的"未知"状态。** 远端不可达时，各面板要么显示旧值，要么报错。
- **CLI、Python 和团队脚本没有订阅能力**，只能轮询全量数据。

### 1.4 对初稿动机的更正

- 会话目录已经按行比较 ETag，只下发变化的行（[catalog.rs:27](../../apps/daemon/src/session/catalog.rs)）。一行摘要估计在几百字节到 2 KB，未实测。
- 流式输出已经只发追加部分（`ItemDelta::Text`），并且按 `seq` 无缺口续传。
- 近期 Beta 目录变慢的修复（主干 `e46dae7d`、`e331cddf`），根源在 daemon 侧的扫描和前台对账，不在传输体积。

所以首期不以减少字节为目标，节点内增量推到二期。传输体积只有在实测证明成为瓶颈时，才作为二期的启动理由之一。

## 2. 节点外：键路径树

### 2.1 规则

1. **每个节点有且只有一个键路径。** 父路径就是它的归属：
   - 删除父节点时，整棵子树一起删除。
   - 授权和订阅都可以按子树进行。
2. **节点的值必须是 JSON 对象**，不能是数组或标量，方便以后加字段。
3. **父节点的 JSON 里不嵌入子节点。** 子节点通过内核内置的子节点视图列出，例如 `children(前缀, 排序, limit, after)`。所以一个工作区下有一万个会话，也不会让工作区节点变大。
4. **树之外的关系用引用表示。**
   - 节点里用键字符串指向别的节点，例如 `"agent": "m/a/agent/codex"`。
   - 列表、搜索结果、跨分支的集合，都是视图节点，值为 `{items:[键…], next}`。
   - 内核不自动展开引用，消费方按需订阅被引用的节点。
5. **权威边界是顶层子树。**
   - `m/<机器>/…` 归那台机器的 daemon，`hub/…` 归 Hub。
   - 客户端连接多个权威时，看到的是这些子树拼成的一棵树。某个权威不可达时，它的子树显示为未知。
6. **统一的地址：** 节点键加上节点内的 JSON Pointer，例如 `m/a/ws/w_1/session/s_9/summary#/title`。
   - 同步的最小单位是节点，不支持只订阅节点内的某个字段。
   - 需要单独订阅的部分，应该拆成单独的节点。

### 2.2 为什么是"树加节点"，而不是一棵 JSON 树

| 系统 | 结构 | 经验 |
| --- | --- | --- |
| Firebase Realtime Database | 整个数据库是一棵 JSON 树 | 监听父节点会下载所有后代，深层嵌套代价很大。官方建议把数据拍平，再用索引关联 |
| Firestore | 集合、文档、子集合组成的树；文档是 JSON，**子集合不包含在文档里** | 文档就是同步和计费的单位；读取文档不会带出子集合 |
| Git | 目录树，叶子是文件 | 判断是否变化按对象（哈希）进行，文件内的差异另算 |

我们采用 Firestore 和 Git 的形态：
- 树负责组织。
- 节点是同步单位，令牌按节点计算。
- JSON 只存在于节点内部。

这样，节点边界同时就是订阅、令牌和授权的边界，不会出现"订阅父节点就拖下整棵子树"的问题。

### 2.3 节点边界怎么划

**原则：**
- **一起变化、一起读取的放进同一个节点。**
- **变化频率不同的拆开。**
- **会无限增长的拆开。**

平台树示意如下，实际层级以 K0 的平台 schema 为准。标注的批次对应第 12 节。

```text
m/<机器>/
  ├ status                         机器状态（低频）                      K3
  ├ settings                       设置的可展示视图（不含密钥）            K3
  ├ device/<设备>                   设备摘要                              K3
  ├ agent/<agent>                  单个 Agent 的定义、能力与状态           K3
  │   └ request/<请求>              待人回答的 Agent 级请求                 K3
  ├ process/<进程>                  后台进程                              K3
  ├ update/download                更新下载进度                           K3
  └ ws/<工作区>/
       ├ meta                      工作区名称、路径、设置                  K3
       ├ space/<space>             Space 配置                            K3
       ├ git/status                Git 状态（观察型）                     K6
       ├ files/<目录句柄>           单层目录清单（观察型）                  K6
       └ session/<会话>/
            ├ summary              标题、状态、草稿数、更新时间（会话列表引用它）  K4
            ├ drafts               草稿内容（只在打开输入框时订阅）            K4
            ├ annotations          预览批注                                  K4
            ├ run                  运行状态、当前动作（高频）                 K7
            ├ turn/<轮次>           已完成的轮次（写入后不再变化）             K7
            └ open                 进行中的轮次：{turnId, items:[条目键…]}    K7
                 └ item/<条目>      进行中的一个条目（流式追加）               K7
```

**这样划分的效果：**
- 标题、草稿数、批注都只是节点值的一部分，不再需要 `TitleChanged`、`DraftsChanged`、`PreviewAnnotationsChanged` 这样的专用失效事件。
- 一个 Agent 变化只推它自己的节点，不再推完整列表。
- 流式输出只改动 `open/item/<条目>` 这一个节点，会话列表引用的 `summary` 不会跟着变。进行中的轮次按条目拆分，所以长轮次不会撞上节点大小上限。
- 已完成的轮次不再变化，副本缓存一次就永远有效，令牌相同就不用重发。

**节点大小上限（由内核强制）：**
- 规范化编码后不超过 1 MiB，嵌套不超过 32 层，单个数组不超过 1 万个元素。
- 超出上限的数据必须拆成子节点，再用视图组织。写入超限时返回 `tooLarge` 错误（第 10.3 节），不截断。

### 2.4 键的规范（新增）

- **段的字符集：** 每段是非空的 UTF-8 字符串。`/`、`#`、`?`、`%` 和控制字符按百分号编码。整个键不超过 1024 字节。
- **不同来源的 ID 不混用：**
  - `m/<机器>/` 用 daemon 的机器 ID。
  - `ws/<工作区>` 用 daemon 本地的工作区 ID。
  - Hub 的工作区 ID 只出现在 `hub/…` 子树里；两者的对应关系放在节点值里做引用，不混成同一个键。
- **文件路径和根句柄不进键。** 目录节点用 daemon 颁发的句柄 ID，节点值里再带可展示的路径。这样路径改名不会改变键，也不会把绝对路径暴露在授权前缀里。
- **视图键：** `m/<机器>/view/<视图名>?<规范化参数>`。参数按名字排序，值做百分号编码。同一组参数总是生成同一个键。
- **数字：** 超过 2^53 的整数（例如 `Usage` 里的 u64）在 schema 中声明为字符串；浮点数必须是有限值。这两条由内核在校验时强制。

### 2.5 节点是读模型，不是存储格式（新增）

- 会话文件格式（`SESSION_FORMAT=10`）、写锁、inbox、执行围栏和清理回执**保持不变**。
- `summary`、`run` 这些节点由接入层的"计算者"从现有存储投影出来，通过 `put` 写入内核，不把会话元数据按节点拆开存储。已接收输入的原子性仍由 `SessionManager` 保证。
- 写入统一走意图（第 7.3 节），由现有的处理器执行。处理器提交成功后，计算者更新对应节点。
- 冷启动不做前台扫描：
  - 会话目录沿用主干已有的缓存目录加后台对账（`e46dae7d`）；
  - 其他族在首次订阅时按需加载。

## 3. 节点令牌（唯一使用哈希的地方）

- **定义：** 令牌 = SHA-256（截取 128 位）作用于节点值的规范化 JSON（RFC 8785 JCS），数字规则见第 2.4 节。
- **用途：**
  - 在线推送时判断节点是否变化：令牌相同就不推送。
  - 断线恢复时，副本报告已知令牌，令牌不同的节点才重发。
  - 节点级条件写 `ifToken`，统一取代各族的 `expected_revision`。
  - 副本收到新值后核对令牌（第 6.2 节）。
- **惰性计算：** 节点被修改时只标记"令牌失效"，到推送、回答 `get` 或处理 `ifToken` 时才计算。节点大小上限保证每次计算都有上界。
- **文件类数据：**
  - 文件条目节点的值记录 inode、大小、mtime、ctime 等元数据，令牌仍然是这个 JSON 的哈希。
  - 判断文件是否变化不需要读文件内容（沿用 v5 第 3.2 节的元数据机制）。
- **各族不再自定义令牌算法。** 迁移完成的族，删除它自己的 ETag、revision 或 checksum（第 12 节）。

## 4. 首期：整份值同步

首期每个节点只有两种变化：整份新值，或删除。
- **权威端每条连接只记录"已发送的令牌"**，即每个节点一个 16 字节的令牌加键。首期不保留节点的旧版本，所以每条连接的内存只与订阅的节点数成正比，上限由预算强制（第 7.1 节）。
- **背压合并：** 连接写不动时只积累脏键。可写后对每个脏键比较一次令牌，期间的多次修改自然合并为一次推送。
- **断线恢复：** 副本报告已知令牌，令牌相同的节点不发，不同的整份重发。

整份同步对首期迁移的各族已经足够：设置、Agent、进程、摘要这类节点都很小，且变化频率低到中等。进行中轮次的流式条目要到 K7 才迁移，届时引入二期增量（第 5 节）。

## 5. 二期：节点内 JSON 增量

**启动条件（满足其一）：**
- K7 迁移会话正文，流式条目需要 `append`；
- 实测证明某个已迁移族的传输体积成为瓶颈。

协议在首期就允许 `ops` 的每一项带 `patch` 字段（第 10 节），所以二期上线不是破坏性变更。不支持补丁的副本在 `open` 时声明，权威端对它只发整份值。

### 5.1 补丁格式

采用 JSON Patch（RFC 6902）的一个子集，外加一个扩展操作。路径用 JSON Pointer（RFC 6901），相对于节点的根对象。

| 操作 | 含义 | 例子 |
| --- | --- | --- |
| `replace` | 替换某个位置的值 | `{"op":"replace","path":"/status","value":"done"}` |
| `add` | 对象加字段；数组在某个位置插入，`-` 表示末尾 | `{"op":"add","path":"/members/-","value":{"id":"u3"}}` |
| `remove` | 删除字段或数组元素 | `{"op":"remove","path":"/tags/2"}` |
| `test` | 字段级条件写：某个位置的值必须等于给定值 | `{"op":"test","path":"/title","value":"旧标题"}` |
| `append`（扩展） | 字符串尾部追加 | `{"op":"append","path":"/text","value":"新的 token"}` |

`move` 和 `copy` 不使用。

### 5.2 差异函数 D：直接比较值

```text
D(path, 旧, 新):
  同一个引用（结构共享，没动过） → 无补丁
  类型不同                       → replace path
  对象：逐个键比较
        只在新侧 → add；只在旧侧 → remove；两侧都有 → D(path/键, …)
  数组：从两端比较元素，去掉相同的前缀和后缀，只看中间不同的一段
        两段长度相同 → 逐个元素 D(path/i, …)
        长度不同     → remove 旧段 + add 新段
  字符串：新串以旧串开头 → append 尾部；否则 replace
  标量：值不同           → replace
  最后：补丁编码后比整份值还大 → 改为一次 replace /（整个节点）
```

- 节点值用持久化树表示，修改时只复制被改动的路径。没动过的子树保持同一个引用，比较时直接跳过，所以 D 的代价与改动范围成正比。
- 不做 LCS 和移动检测。需要频繁重排的大集合应拆成子节点加视图。

### 5.3 二期的推送、校验与资源

- **权威端保留已发送版本：** 为每条连接、每个已订阅节点保留已发送的版本（结构共享，只多占被改动路径的内存）。超出内存预算时淘汰旧版本，下一次推送退化为整份值。这样只是变慢，不会出错。
- **补丁校验：** 补丁带 `from` 和 `to` 两个令牌。副本先确认自己的令牌等于 `from`，应用补丁后再确认等于 `to`。任一项不一致，就用 `get` 重新读取这个节点。
- **字段级条件写：** 用补丁里的 `test`。两个人同时改同一条记录的不同字段，两次修改都生效；改同一个字段时，后到的被拒绝并收到当前值。
- **预表现：** 待确认的意图带着预测补丁，界面显示"权威值 + 依次应用的待确认补丁"。收到对应 `opId` 的回执后移除这条预测；预测应用失败时直接丢弃，以权威为准。

## 6. 分层

```text
应用：平台 schema、预览页面、Agent 应用、团队与 PM 脚本
  │
接入层（IO 与绑定）
  ├ 存储与计算：会话 Store 投影、配置文件、SQLite、纯内存
  ├ 观察：文件元数据、Git、进程状态
  ├ 意图处理：现有的 Rust 处理器；进程型处理器（CLI 或 Python）
  ├ 传输：WebSocket、Fabric、/cli 回环、postMessage、进程内
  └ 绑定：React hooks、预览注入 API、CLI 命令、Python 包
  │ 只通过第 8 节的端口
同步内核（Rust 实现权威和副本两端；TS 实现副本端）
  ├ 节点树：键路径、挂载表（前缀 → 来源）、子节点视图、引用
  ├ 节点：JSON 对象、大小上限、schema 校验、节点令牌
  ├ 同步：每条连接的已发送令牌、订阅、脏集合、调度与背压、恢复、未知、回执、授权、预算
  ├ 写入：意图路由、ifToken
  ├ 视图：集合索引与窗口
  └ 二期：差异函数 D、补丁应用与校验、已发送版本保留、预表现
```

**判定一件事归哪一层：**
- 需要读写磁盘、开 socket、启动进程或调用业务函数的，归接入层。
- 只在节点树和 JSON 上做计算的，归内核。

### 6.1 首期规模

首期内核只包含树、令牌、整份同步、订阅、视图、意图、授权和预算。没有差异函数、补丁和持久化结构，规模明显小于完整版。具体规模以 K1 原型实测为准，本文不给代码量和工期。

## 7. 同步机制

### 7.1 权威端

- 处理订阅：单个节点、子树、视图窗口。
- 为每条连接记录每个节点的已发送令牌，并维护脏集合。
- 按"连接可写"调度推送，写不动时只积累脏节点，不排队。
- 处理授权（键前缀加意图名单）、未知状态、回执和预算。
- **预算：**
  - 每条连接的订阅节点数和待发脏键数都有上限。
  - 超出订阅上限时，订阅被拒绝并返回 `budget` 错误；不静默丢弃。
  - 具体数值在 K1 按 1 万会话、十几台机器的规模实测后确定。

### 7.2 副本端

- 保存节点值和令牌，收到新值后核对令牌。不一致就丢弃，用 `get` 重读。
- 管理订阅和重连：重连时用 `get` 报告已知令牌。
- 维护未知状态。

Rust 副本端用于 CLI、跨机副本，以及 daemon 连接其他机器。TS 副本端用于网页（第 9 节）。

### 7.3 写入：意图和条件写

- **意图：** `call {opId, key, name, args}` 按键前缀路由给接入层的处理器。处理器提交后通过 `put` 更新节点，回执里带上受影响节点的新令牌。
- **现有动作直接映射为意图：** 例如 `session.rename` 变为 `call {key: ".../session/s_9", name: "session.rename"}`。处理器就是现有的实现，参数和语义不变。
- **条件写：** 首期只有节点级的 `ifToken`，节点自某个版本以来有任何变化就拒绝，并返回当前令牌和值。字段级 `test` 在二期（第 5.3 节）。
- **回执不冒充结果：** 不可重放的动作（`process.kill`、`session.send`、设备撤销等）的回执，只表示处理器已经接收。最终结果以对应节点的状态为准。这一点沿用接口审查附录的约定。

### 7.4 视图

- **子节点视图：** 由内核内置，按键前缀列出子节点，支持排序和分页。
- **集合索引：** 由 schema 声明，例如"`m/*/ws/*/session/*/summary` 按 `/updatedAt` 降序，可按工作区过滤"。内核在内存中维护有序索引，节点写入时更新被索引的字段。
- **视图窗口：** `{view, params, limit, after}` 本身也是一个节点，值为 `{items:[键…], next}`，和普通节点一样同步。
- **跨权威的视图：** 例如"所有机器最近的会话"，由副本端合并各权威的视图窗口得到。
- **冷启动：** 见第 2.5 节，不做前台全量扫描。

## 8. 端口：内核的输入和输出

| 端口 | 方向 | 接口 | 实现方（接入层） |
| --- | --- | --- | --- |
| 来源 `Source` | 内核 ↔ 数据来源 | `load(keys)`、`scan(prefix, budget)`（分批） | 会话 Store 投影、配置文件、SQLite；瞬态子树不挂来源 |
| 传输 `Link` | 内核 ↔ 对端 | `send(bytes) -> 是否还可写`、`on_writable`、`on_frame(bytes)`、`on_close` | WebSocket、Fabric、`/cli` 回环、postMessage、进程内 |
| 外部变化 | 接入层 → 内核 | `put`、`del`、`unknown(keys, 原因)`；二期加 `patch` | 观察者（文件、Git、进程）、计算者（摘要等） |
| 意图处理 `Handler` | 内核 → 接入层 | `handle(intent, cx) -> 回执`，`cx` 内可调用 `put` | 现有 Rust 处理器；进程型处理器（`genet sync serve`、Python） |
| 时钟 `Clock` | 内核 ← 宿主 | `now()`、定时器 | 宿主运行时 |

- **挂载表：** 键前缀对应来源，例如 `m/a/ws/*/session/*/summary` 挂会话摘要计算者，`m/a/process/` 挂进程观察者。
- 帧的编码由内核负责，传输端口只搬运字节，这与 relay 不理解内容的律法 L03 一致。
- 令牌算法和规范化编码在内核里固定，两端必须一致。
- 内核本身是同步代码，不依赖异步运行时。Rust 版编译进 daemon guest wasm，也编译进 CLI。在 guest 里，单次计算受现有 `WorkBudget` 协作让出约束。

## 9. 网页层接入与取舍

| 方案 | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| A. 内核不管网页 | 各页面自己做缓存、重连和刷新 | 内核最小 | 正是现在的问题：每个页面一套，完备性无从保证 |
| B. Rust 内核编译成 wasm 进浏览器 | 一份实现 | 实现不会漂移 | 包体积增加几百 KB；每次读数据都要在 wasm 和 JS 之间转换 JSON；React 需要稳定的对象引用，最后 JS 侧还得再存一份 |
| **C. 内核规范 + Rust 两端 + TS 副本端（推荐）** | TS 实现副本端：令牌核对、整份替换、订阅与恢复；二期加补丁应用和预表现 | 网页里的值就是普通的冻结 JS 对象，React 只重渲变化的节点；包体积小 | 两份实现要防漂移：`packages/proto/fixtures/sync` 共享测试向量，加 Rust 权威端与 TS 副本端的端到端互通测试 |

**推荐 C 的理由：** TS 副本端不需要差异函数 D。首期只有规范化编码、哈希、整份替换和订阅状态机，代码量小。

**网页里的接入形态：**
- **工作台：** TS 副本端，配合现有的 WebSocket 数据面，外加 React 绑定 `useNode`、`useView`、`call`。已迁移族在 `store.ts` 里的状态和刷新逻辑由这些 hooks 取代并删除。
- **预览页面（团队进展页等）：**
  - iframe 内运行同一个 TS 副本端，以 postMessage 作为传输端口。
  - 工作台只做中继，转发帧但不解读内容。授权由 daemon 按受限凭证执行：子树只读，加意图名单。
  - 本地双击打开时没有桥接，降级为静态内容。
- **Agent 应用页面：** 同预览页面，授权范围是该应用的子树。
- **Hub（Cloud 服务端，TS）作为权威：** 需要 TS 权威端，或在 Node 中运行 Rust 内核的 wasm。这是后续阶段的事，列为待定问题。

## 10. 协议

### 10.1 承载与协商（拟议）

- **承载：** 不新开连接，沿用现有的两条路径。
  - 客户端发往 daemon 的 `open/get/drop/call`：在类型化请求 `Request`（[rpc.rs:32](../../packages/proto/src/rpc.rs)，经 `rpc` 流方法承载）中增加一个 `sync` 变体。
  - daemon 推送的 `ops/error`：在 `ServerFrame`（经 `events` 流方法承载）中增加一个 `sync` 变体。
  - 帧定义只在 `packages/proto/src/sync/` 中（G03）。
- **协商：**
  - `protocol.identity` 返回的 `ProtocolIdentity` 目前只有 `webProtocol`，当前值为 4（[rpc.rs:25](../../packages/proto/src/rpc.rs)）。增加一个可选字段 `sync: {version, families}`，列出这个 daemon 已迁移的族。旧版本 daemon 不返回这个字段。
  - 客户端只对已列出的族使用新路径，其他族继续走旧路径。
  - 跨机时每个权威单独协商，所以新旧版本的机器可以混连。
- **分帧：** 一个 `ops` 帧的编码不超过 128 KiB（沿用现有目录分块的上限），更多的变化分多帧发送，最后一帧带 `done: true`。

### 10.2 帧

帧的种类：`open/get/drop/call/ops/error`；`ack` 和 `tick` 预留给不可靠传输，前期不做。

```json
{"type":"open","schema":"genehub.platform","schemaHash":"7c…","accept":["value"]}
```

二期支持补丁的副本，在 `accept` 里写成 `["value","patch"]`。

```json
{"type":"get","scope":{"view":"sessions.recent","ws":"w_1","limit":100},"known":[["m/a/view/sessions.recent?limit=100&ws=w_1","c210…"],["m/a/ws/w_1/session/s_9/summary","9f2c…"]],"watch":true}
```

```json
{"type":"ops","ops":[
  {"key":"m/a/ws/w_1/session/s_9/summary","to":"d41a…","value":{"title":"修复登录","status":"running","draftCount":1}},
  {"key":"m/a/agent/codex","to":"5e8d…","value":{"state":"ready","models":["…"]}},
  {"key":"m/a/ws/w_1/session/s_3/summary","to":null},
  {"key":"m/b/process/","unknown":"offline"}
],"done":true}
```

- 带 `value` 的是整份值；`"to":null` 表示删除节点。
- 带 `unknown` 的表示这个键或前缀暂时无法提供，原因取值为 `offline`、`budget`、`error`。
- 二期增加带 `from` 和 `patch` 的形态：`{"key":…,"from":"9f2c…","to":"d41a…","patch":[…]}`。

```json
{"type":"call","opId":"op_7f2","key":"m/a/ws/w_1/session/s_9","name":"session.rename","args":{"title":"写周报"},"ifToken":"9f2c…"}
```

### 10.3 错误

```json
{"type":"error","opId":"op_7f2","key":"m/a/ws/w_1/session/s_9","code":"conflict","message":"节点已被修改","current":{"to":"d41a…","value":{…}}}
```

| `code` | 含义 | 副本的处理 |
| --- | --- | --- |
| `conflict` | `ifToken` 不匹配；附带当前令牌和值 | 用当前值更新本地，交给界面决定是否重试 |
| `forbidden` | 键前缀或意图不在授权范围内 | 不重试；界面显示无权限 |
| `tooLarge` | 写入的值超过节点上限，或者帧超过上限 | 不重试；调用方拆分数据 |
| `budget` | 订阅数或速率超出预算 | 缩小订阅范围后重试 |
| `unknownKey` | 键不符合 schema | 不重试；属于实现错误，记录诊断 |
| `handler` | 处理器执行失败；附带处理器自己的错误码和用户可读的消息 | 按处理器的错误码处理 |

## 11. 不在内核里的东西

| 事物 | 理由 | 去处 |
| --- | --- | --- |
| 文件、数据库、进程等 IO | 内核要能在任何宿主中运行，用假端口就能测试 | 接入层的来源、观察者和处理器 |
| 网络传输 | 传输方式多种多样，并且受律法 L03 约束 | 传输端口实现 |
| 业务派生（摘要怎么算、项目状态卡包含什么） | 属于业务 | 接入层的计算者，通过 `put` 写入 |
| 渲染和界面框架 | 属于消费 | React 绑定、预览注入 API |
| 字节流：PTY 输出与输入、音视频与 RTC、文件内容、产物上传、`shell.run`、远程桌面输入 | 有顺序、有背压、不能按"最新值"合并或重放 | 保留现有通道；它们的实例状态和回执可以作为节点暴露，字节不进节点 |
| 通知（`notice` 帧） | 一次性消息，不是状态 | 保留现有帧 |
| 签名制品校验、更新激活与回滚 | 安全流程，与数据令牌用途不同 | 保留现有更新流程；只有下载进度和状态作为节点 |
| 可合并类型（多人同时编辑同一段文本） | 需要 CRDT，复杂度高 | 前期不做；记录类数据的并发编辑用二期的字段级条件写 |

## 12. 迁移计划与删除清单

**规则：**
- **每一步迁移一组族，并在同一批交付里让旧路径进入兼容窗口。**
- **兼容窗口：** 新旧路径并存，直到新路径进入 Stable 之后的下一个 Stable 版本，再删除旧路径。删除前，daemon 诊断要能统计旧路径的调用次数，用来确认没有当前版本的客户端仍在使用（统计方式见待定问题 1）。
- **窗口期内旧路径只修缺陷，不加功能。** 新功能只能做在新路径上。

## 13. 验收（均未执行）

### 13.1 统一性

| 场景 | 通过条件 |
| --- | --- |
| 旧路径删除 | 每一步的兼容窗口结束后，对应的 `ServerFrame` 变体、监听器、读取 RPC 和刷新逻辑已从源码中删除；删除提交与迁移提交可以一一对应 |
| 静态门禁 | 对已迁移的族，工作台中不出现对其读取 RPC 的 `client.call`；proto 中不新增该族的 `ServerFrame` 变体；违反时 lint 失败 |
| 新增一族的改动面 | 用 K5 的团队进展页验证：新增数据只需写 schema 和来源，协议、`client.ts` 和 CLI 都不改 |
| 版本概念收敛 | 已迁移族的变化判断只用节点令牌，条件写只用 `ifToken`；不再有该族自己的 ETag、revision 或 checksum |

### 13.2 行为

| 场景 | 通过条件 |
| --- | --- |
| 跨窗口一致 | 两个窗口打开同一台机器，A 修改设置、Space 配置或 Agent 配置，B 在 1 秒内显示新值，且不需要刷新 |
| 进程实时性 | Agent 在轮次中途启动又结束一个后台进程，进程节点在轮次结束前就反映这两次变化 |
| 节点级判断 | 节点内容不变时（包括整份重写了相同的值），令牌不变，不推送 |
| 合并 | 连接写不动的 1 秒内发生 100 次修改，恢复后每个节点只推送一次 |
| 断线恢复 | 离线期间只有 1 个节点变化时，恢复只重发这 1 个节点 |
| 未知 | 一台远端机器断开后，它的子树在界面上显示为未知，而不是旧值或报错；恢复后自动收敛 |
| 自愈 | 人为注入错误的值或丢帧后，副本发现令牌不一致，重新读取，最终收敛 |
| 条件写 | 两个窗口用同一个 `ifToken` 修改 Space 配置，后到的收到 `conflict` 和当前值 |
| 树的规则 | 删除工作区节点时整棵子树删除；子树订阅不包含越权的前缀；父节点的值不包含子节点 |
| 混合版本 | 新版工作台同时连接一台新版 daemon 和一台旧版 daemon，两台机器的数据都正常显示和更新 |

### 13.3 资源与一致性

| 场景 | 通过条件 |
| --- | --- |
| 内核独立 | `sync-kernel` 的依赖中没有文件、网络和异步运行时；只用假端口跑完全部测试 |
| 连接状态有上界 | 1 万会话、10 个客户端时，权威端用于每条连接同步状态的内存不超过 K1 确定的预算；超出时返回 `budget` 错误 |
| 两端一致 | 10 万组随机 JSON 值，Rust 与 TS 的令牌逐一相同；二期另加 `apply(旧, D(旧, 新)) == 新` |
| 二期增量 | 50 KiB 的节点改一个短字段，推送补丁小于 200 字节；流式输出期间 `summary` 和会话列表视图不推送 |
| 预览页与 Python | 同 v6 第 11 节对应条目 |

所有数字都是设计目标，需要实测确认。

## 14. 取舍与替代方案

| 方案 | 做法 | 后果 |
| --- | --- | --- |
| 维持现状 | 每族继续各自优化 | 族越多越乱；每个新实时功能都要改 5 处；漏失效类缺陷会反复出现；脚本只能轮询 |
| 只在工作台统一 | 在 `client.ts` 外包一层统一的监听和缓存 | 改动小，但 daemon、CLI、Python 和预览页仍然各一套，重连和未知语义无法统一 |
| 原 v7 一次性完整落地 | 首期就做补丁、结构共享、预表现，第一个迁移会话族 | 首期规模最大、风险最高；第一个迁移的是最难的族；Rust 和 TS 两端的一致性面最大 |
| **收窄内核加按族替换（推荐）** | 首期只做整份同步，从简单族开始，每步带删除清单 | 每一步都可以单独发布和回滚；补丁等优化按需要再上，协议提前留位；**前提是严格执行删除**，否则会变成在现有 N 套之外再加一套 |

**主要成本与风险：**
- **兼容窗口期，新旧两套并存。** 测试面会暂时变大，所以窗口必须有期限。
- **Rust 和 TS 两份实现。** 靠共享测试向量和互通测试防止漂移。
- **在 guest wasm 里，令牌计算和视图索引受 `WorkBudget` 约束。** 需要在 Wasmtime 下实测前台延迟，不能用 Node 原型的数字代替。
- **K4 的范围。** 它同时触及会话目录和浏览器缓存，是第一个改动现有热路径的步骤，需要沿用主干已有的缓存目录和后台对账，不重新引入前台扫描。
