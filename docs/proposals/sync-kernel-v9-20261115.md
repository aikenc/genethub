## 摘要

**体验影响。** 一个用户控制十几台电脑、让大量 Agent 协同时，现在的平台会遇到三类问题：
- **看不全。** 页面最多同时保持 8 个机器连接，手机只有 4 个（[machine-connections.md](../machine-connections.md)）。机器一多，只能轮流连，列表靠可见时每 30 秒刷新一次。
- **协作慢。** 跨机派单走"远程执行脚本"，结果靠派单方每轮查询。团队脚本甚至自己写了一个带游标的增量同步引擎（第 2.2 节）。协作状态的延迟取决于轮询周期，负载随"待办数 × 机器数"增长。
- **越来越复杂。** 每一族状态各自实现"推送、读取、缓存、版本、过期判定"，现在已有：
  - 32 个读取 RPC；
  - 11 种推送帧；
  - 9 种"版本"概念；
  - 至少 13 处周期性轮询或扫描。

  再加一种协作形态，又要再造一套。

**怎么解决（全部待实施）。** 平台的状态面只保留**一条规则、两个原语**，其余交给框架之外的补充流：
- **规则：** 每台机器是自己子树 `m/<机器>/…` 的唯一权威，其他地方拿到的都是副本；权威不可达时，副本显示为"未知"。
- **两个原语和补充流：**
  - 订阅子树或视图：先给快照，之后只推变化，靠令牌续接；
  - 意图：发给权威端，用 `ifToken` 做条件写；
  - 流：实时输出、终端、shell、大内容读取、隧道和媒体，作为同步框架之外的补充（第 4.3 节）。

工作台、CLI、团队脚本和其他机器的 daemon 都使用这同一套原语。在此之上增加三项能力，专门为规模服务：
1. **机器间订阅与汇聚转发（第 5 节）：** 任何 daemon 都可以把它订阅到的其他机器的副本转发给设备。手机只需连一台机器就能看到全部机器。
2. **应用子树（第 6.1 节）：** 团队等用户脚本声明自己的命名空间，平台负责存储、传播和条件写，但不解释内容。
3. **变化触发 hook（第 6.3 节）：** hook 除了定时，还可以在某个前缀发生变化时运行，对账从轮询改为事件驱动。

**复杂度增减（第 9 节）：**
- 机制数量大幅减少：
  - 读取 RPC 从 32 个降到 0，由一组通用订阅替代；
  - 推送帧从 11 种降到 1 组 sync 帧，加 2 种 PTY 帧；
  - 版本概念从 9 种降到 2 种；
  - 跨机获取状态的方式从 3 种降到 1 种；
  - "健康、不确定、过期"的判定从每族各一套降到只看"权威可达性"。
- 新增约 10 个平台级概念。
- 代码行数**在前期大致持平，全部族迁完、兼容窗口关闭后才明显净减少**。真正的收益是机制数量、新增一族的边际成本和规模性质，不是行数。

**怎么防止复发：**
- 在 [architecture.md](../architecture.md) 新增边界："可观察状态只通过节点订阅暴露"，并配静态门禁。已迁移的族、以及所有新增的族，都不得再加推送帧、读取 RPC 或轮询。
- 每一步都带删除清单，并统计机制数和行数的增减。
- 新增代码设预算，超出就重新评审（第 9.4 节）。

**本次需要评审：**
1. 第 3 节的规模目标数字；
2. 第 5 节的汇聚转发，是否接受"由用户自己的某台机器担任汇聚点"；
3. 第 6 节的应用子树与变化触发 hook；
4. 第 10 节的迁移顺序：用团队跨机派单作为第二个消费方；
5. 第 9 节复杂度评估的口径和预算。

### 2.2 团队脚本已经自己造了一个同步引擎

## 3. 目标与范围

### 3.1 简化目标（可度量）

- 迁移完成后，第 9.2 节表中的每一项机制数都达到目标列，由静态门禁守住。
- 新增一族状态只需要 schema 加数据源，不改协议帧，不改工作台监听器。
- 本机写和远程写走同一条路径。

### 3.2 规模目标（拟议，需要评审确认数字）

**沿用 v5 第 2 节：** 每个用户 15 台机器、1,000 个 Space、20,000 个会话（单台最多 12,000 个）、3 个同时在线的客户端，以及若干 CLI `watch`。

**新增两条：**
- 同时活跃 200 个 Agent 会话、20 个团队；
- 跨机派单从发出到执行端开始执行，P95 不超过 2 秒；跨机状态变化在 1 秒内到达订阅方，不含 Agent 自身的耗时。

**性能性质沿用 v5 的 G1–G5**，另加两条：
- **G6：** 每台设备的连接数与机器数无关，是常数。
- **G7：** 空闲时，团队协作的流量和 CPU 为零，不靠定时轮询发现变化。

### 3.3 不做

- 不改会话存储格式、写锁、inbox、执行围栏，也不改 `TimelineItem/ItemDelta` 契约（第 4.3 节：条目进节点，增量走实时流）。
- 流式输出、终端、shell、大文件和高清媒体都不进节点（第 4.3 节）。
- 不做 CRDT，不做多人同时编辑文本。
- 不做 Hub 权威端。Cloud 的 `generation/revision` 保持不变。
- 不引入外部同步引擎或数据库。
- 内核不认识团队语义：任务、岗位、档位路由都留在团队脚本里（B1，[teams.md](../teams.md) 的 L0/L1 分层）。
- 不新增任何权限层。按产品权限契约（Spaces 仓 `genethub-agent-workflow/references/product-authority.md`），已认证的完整连接拥有目标 OS 用户的权限；仅展示的分享保持现有的受限边界。

## 4. 架构：一条规则、两个原语，加框架之外的补充流

### 4.1 权威规则

- `m/<机器>/…` 只由该机器的 daemon 写入和计算令牌。
- 其他机器和设备上的都是副本，副本可以随时丢弃。
- 权威端不可达时，它的子树标为 `unknown`，并附原因（`offline`、`via:<汇聚机器>`、`budget`、`error`），不显示过期数据冒充最新。
- 跨机写入是发给权威端的意图，没有分布式事务。锁、认领、派单，都是权威端上的一次 `ifToken` 条件写。

### 4.2 两个原语（拟议接口）

```ts
// 工作台：读副本，界面状态 = 副本 ⊕ 预表现（v5 第 8 节）
const summary = useNode("m/b/ws/w_1/session/s_9/summary");          // {state:"ok"|"unknown"|…, value, token}
const recent  = useView("sessions.recent", { machines: "*", limit: 100 });
await call("m/b/ws/w_1/session/s_9", "session.rename", { title: "写周报" }, { ifToken: summary.token });
```

```text
genet sync get   m/b/ws/w_1/session/s_9/summary
genet sync ls    m/b/app/team-x/team/tasks/
genet sync watch m/b/app/team-x/team/ --jsonl           # 空闲时无输出；变化时每行一个节点
genet sync call  m/b/app/team-x/team/locks/qa put @lock.json --if-token absent
```

- 帧和错误码沿用 v7 第 10 节（`open/get/drop/call/ops/error`；`conflict/budget/tooLarge/unknownKey/handler`）。
- 流和大内容沿用或改进现有通道，划分见第 4.3 节。
- 为 Agent 设计的 CLI 动词（`session list` 等）保留，改为视图上的薄封装。CLI 的形态不因为迁移而变差。

### 4.3 同步框架的边界：节点、补充流与内容读取（2026-11-15 Human 决定）

同步框架只负责**会收敛的状态**和**小的不可变内容**。下面三类不进同步框架：

**1. 流式输出：作为框架之上的补充。**
- 会话正文按"轮次"和"已完成的条目"进节点。正在运行的轮次是可变节点，每完成一个条目更新一次；封存之后变为不可变节点。
- Agent 逐字输出的增量（`ItemDelta`）**只在有人观看时**通过实时流推送。用户没有打开页面时不推送，团队脚本和摘要只看节点。
- **实时流的合同：** 不保证可靠，不做 `seq` 重放，也不做失步处理。流断开或出现缺口时，客户端重新 `get` 对应的节点就能收敛。正确性靠节点，实时流只负责让人看得更快。
- `TimelineItem/ItemDelta` 契约不变（[architecture.md](../architecture.md) §4）：节点里放 `TimelineItem`，实时流里放 `ItemDelta`。
- 内核因此**不需要追加日志节点**，节点只有一种 JSON 值，外加"可变或不可变"这一个属性。

**2. 不可变内容只包括内联的小对象。**
- 已封存的轮次和 trunk（包括里面内联的缩略图 `ImageThumb`，64/128 px）作为不可变节点：令牌就是内容 id，只 `get` 不 `watch`，副本命中缓存后零往返，汇聚机器可以放进内存缓存。
- 单个节点有大小上限（P0 定数字），超出时按现有的 trunk 拆分规则拆开。**不支持大文件，不支持续传。**
- 工具输出全文（`blob.get`）、高清图片和视频、工作区文件的预览与下载（`asset.preview`、`file.read`），都不走同步框架，保留现有的读取方式。节点里只放 `BlobRef` 和概要。

**3. 终端和 shell 保持成熟的流式协议。**
- 终端：从共用的事件流里拆出来，每个终端一条独立的双向流，承载输入、输出和窗口大小变化，用流控（credit）做背压，做法和 SSH 通道一致。慢的观看者只会拖慢自己那条流，不影响别的连接。
- `shell.run`：保持现状。
- 终端是否存在、是否已退出这类**状态**，仍然作为节点。

**最终的分层：**

```text
传输层   carrier / E2EE / DataEndpoint + hello + rtc.negotiate
同步框架 sync：会收敛的状态 + 小的不可变内容（含内联缩略图）
         call：所有动作
补充流   实时输出（有人观看时）· 终端 · shell.run · 内容读取（blob、预览、下载）· 隧道与媒体（service.preview）
```

判断标准：**状态和小内容进同步；"现在正在发生的"和"大块内容"走流。** 流只追求实时，正确性回到节点上核对。

### 4.4 消费方都一样

| 消费方 | 现在 | v9 |
| --- | --- | --- |
| 工作台 | 32 个读 RPC 加 11 种帧，`store.ts` 手工刷新 | `useNode/useView/call` |
| CLI | 每个查询一个子命令，`--machine` 每次建链 | 本机 daemon 保持远端链路和副本，CLI 读副本 |
| 团队脚本、看板 | 轮询、`_sync_*`、远程执行脚本 | `genet sync watch/call`，加变化触发 hook |
| 其他机器的 daemon | 没有这种消费方 | 订阅远端子树，作为本机副本（第 5 节） |
| 预览页 | 各自通过 RPC 读取 | 受限订阅（v6 第 6 节） |

## 5. 多机器拓扑

### 5.1 机器间订阅

- 每个 daemon 维护到其他机器的长链路池，订阅它需要的远端子树，副本放在内存缓存层（v5 第 7 节已有这个设计）。
- 有三类订阅需求：本机 CLI 的 `--machine` 读取、本机团队对远端子树的 `watch`、经本机转发给设备的订阅（第 5.2 节）。
- 同一棵远端子树只订阅一次，多个消费方共享。链路断开时，这棵子树标为 `unknown(offline)`。恢复后携带已知令牌重新 `get`，权威端只回传变化的节点。

### 5.2 汇聚转发

设备可以通过一台机器（汇聚机器）订阅其他机器的子树，汇聚机器从 5.1 的副本里转发：
- **不是权威：** 令牌由各机器的权威端产生，汇聚机器原样转发，不重新计算。设备收到的令牌和直连时完全一样。
- **意图透传：** 汇聚机器把意图转给权威端，自己不执行，也不预先应用。
- **未知会传递：** 汇聚机器到权威端的链路断开时，设备看到的是 `unknown(via:<汇聚机器>)`。设备可以选择直连兜底。
- **加密边界不变：** 设备到汇聚机器、汇聚机器到权威端，两段都是 E2EE，relay 照样只搬密文（B4）。汇聚机器能看到明文，这与"已授权的完整连接拥有该账号对这些机器的完整能力"一致，不扩大权限面。
- **仅展示的分享**不能借汇聚机器访问其他机器。
- **不做持久缓存：** 汇聚机器重启后，副本从权威端重新获取。

**设备连接策略（拟议默认值）：**
- 手机：只连汇聚机器，前台会话可以直连该会话所在的机器以启用 RTC。
- 桌面：总览走汇聚机器，前台会话直连。
- 现有连接池的上限只约束直连，不再约束能看到的机器数。

**汇聚机器的选择：**
- 默认是设备最近一次成功连接的、用户自己的常在线机器；用户可以在设置里指定。
- 如何自动发现汇聚机器、故障时如何切换，见第 13 节第 1 条。

### 5.3 规模下的成本（设计目标，未测量）

| 旅程 | 传输与处理 | 与什么有关 |
| --- | --- | --- |
| 手机打开工作台，15 台机器 | 1 条连接；汇聚机器为每台返回总览、待处理和头部视图。冷启动约 15 × 60 KB，有副本且无变化时约 15 × 300 B（沿用 v5 的估算） | 机器数和窗口大小 |

## 6. Agent 协作

### 6.1 应用子树

- **键：** `m/<机器>/app/<Space ID>/<命名空间>/<路径>`。
- **声明（拟议）：** 在 Space 描述文件 `agent-space.genet.json` 里声明 `sync.namespaces`，每个命名空间包括：

  | 字段 | 含义 |
  | --- | --- |
  | `name` | 命名空间名 |
  | `dir` | 存放节点文件的目录 |
  | `schema` | 节点值的 JSON Schema |
  | `maxNodes` | 节点数上限 |
  | `maxBytes` | 总字节数上限 |

- **存储：** 每个节点是声明目录下的一个 JSON 文件，仍然放在 Space 目录里（[storage-layout.md](../storage-layout.md)），平台不新增持久数据位置。daemon 把这个目录当作文件型数据源，通过监听或指纹对账发现变化。
- **写入：**
  - 通过意图写入：`put`、`del`、`ifToken`，`ifToken: "absent"` 表示仅创建。
  - daemon 在文件锁下原子写入，然后返回新令牌。
  - 锁、认领这类需要互斥的节点，规定只能通过意图写。普通节点允许脚本直接写文件，按外部写入处理（C2、C5）。
- **校验：** schema 校验、配额、来源标记（写入方的机器、会话和 opId），沿用 v6 第 6 节对不可信输入的要求。
- **平台不解释内容：** 内核只知道"这是某个 Space 的某个命名空间"，不认识任务、岗位或收件箱（B1）。

### 6.2 跨机派单：改前与改后

**改前（`team.py`）：**
1. A 的 timer 运行 `dispatch_remote`，通过 `shell --machine B` 执行 B 上的 `team.py receive`。
2. B 校验岗位、申请写锁、创建会话，写回执。
3. A 记账 `pending`，此后每轮 `reconcile`：先用 `_sync_pull` 拉 B 的会话增量；拉不到时逐条读取。
4. A 读到最终回复后，确认 B 已释放写锁，再销账。

**改后：**
1. A 执行 `call m/B/app/<团队>/team/requests/<派单编号> put {…} ifToken=absent`。同一个编号只能创建一次，重试是幂等的。结果未知时，重放同一编号，会得到 `conflict` 并附带已有内容，不会重复派单。
2. 这个节点的变化触发 B 上的 `change` hook。B 的 `team.py receive` 读取请求，对 `…/team/locks/<工位>` 做 `ifToken` 认领，然后创建会话，写入 `…/team/claims/<派单编号>`。
3. A 通过本机 daemon 对 B 的副本订阅 `…/team/claims/<派单编号>` 和对应的会话摘要节点，状态一变化就收到，不需要轮询。
4. 完成后，B 释放锁节点，A 看到锁节点和认领节点的变化后销账。

**不变的部分：** 账本留在派单方，写锁和创建回执在执行端，暂停语义不变，回执和幂等规则不变（[teams.md](../teams.md) 第 6 节）。变的只是读写状态的方式。

### 6.3 变化触发 hook

- **新增事件：** 现在 hook 只有 `timer` 事件，新增 `change` 事件，参数为 `prefix` 和 `debounce`（默认 500 毫秒）。合并后的变化键列表通过 stdin 以 JSON 传入。
- **语义：**
  - 至少执行一次，脚本必须幂等。
  - 同一个 Space 内同时运行的 hook 数有上限，超出时排队合并，不丢失变化键。
- **防止循环：** hook 自己写入的节点带有来源标记，默认不再触发同一个 hook。
- **`timer` 保留，**但只作为低频兜底对账，不再承担"发现变化"的职责。
- **对规模的作用：** 20 个团队空闲时开销为零（G7）。协作延迟从"轮询周期"变为"变化触发加 debounce"。

### 6.4 团队模板的变化范围

- 删除 `_sync_*`；`reconcile` 和 watchdog 中的轮询读取改为读本机副本；远程接单不再走 `shell`；收件箱锁改为条件写。
- 保留选岗位、档位路由、回执格式、暂停和接手规则。
- 用户已部署的团队模板如何升级，需要和团队模板升级机制对齐（第 13 节）。

## 7. 数据源层与单机运行时

- **数据源合同：** 沿用 v8 第 4.2 节的 C1–C6。文件型数据源先用主干已有的指纹索引加冷热分级作为 C4 降级实现。所以会话目录迁移（第 10 节 P3）**不依赖** `fs-watch` 的完整模式发布。`fs-watch` 到位后，同一份合同测试照样通过，延迟更低。
- **`fs-watch` 和进程事件：** 按 v8 第 4.3、4.5 节，作为运行时线的完整模式发布（R1），可以和主线并行。
- **执行分区（v8 第 6 节）：** 不放进主线。触发条件是：P3 完成后，在第 3.2 节的规模用例下，`partition.queue_ms` 的 P95 仍超过阈值（阈值在 P0 定）。只有满足这个条件才立项，届时再比较同进程多 Store 和独立进程两种做法。
- **存活：** 沿用 v8 第 7.2 节。另加一条：如果"对端忙"持续超过上限（P0 定），就升级为故障，避免 host 一直代答心跳、guest 却已经卡死的"连着但不动"。

## 9. 复杂度增减评估

### 9.1 口径

- **实测：** 现有代码的行数和机制数，来自基线 `158d7351` 的非测试代码。
- **估计：** 可以删除的比例。逐函数清点得到，没有经过原型验证。
- **预算：** 新增代码不做预测，只给上限，作为门槛；超出预算就停下来重新评审。
- 测试代码不计入。迁移后每个数据源都会新增合同测试，测试量会上升，这是有意为之。

### 9.2 机制数量（主要收益）

| 维度 | 现在 | 迁移完成后 |
| --- | --- | --- |
| 状态读取 RPC | 32 | 0（由一组通用的 `get/watch` 替代） |
| 推送帧 | 11 | v7 的 sync 帧一组，加 2 种 PTY 帧 |
| 版本概念（不含 Cloud） | 9 | 2 |

### 9.3 新增的概念（复杂度增加项）

| 新概念 | 解决哪个问题 | 控制手段 |
| --- | --- | --- |
| 键路径和节点 | 统一的寻址 | v7 第 2.4 节的键规范 |
| 节点令牌 | 统一的版本 | 只在权威端计算；副本端把它当不透明值（v8 第 5.2 节） |
| 视图 | 列表、排序和分页 | 首期只做子节点视图，集合索引由数据源提供 |
| 可变/不可变属性 | 会话轮次、历史和缩略图 | 不可变节点的令牌就是内容 id，只 `get`，有大小上限 |
| 实时补充流 | 有人观看时的逐字输出 | 不保证可靠；正确性靠节点；无人观看时不推送 |
| 意图与 `ifToken` | 统一的写入和互斥 | 处理器沿用现有逻辑 |
| `unknown` | 统一的不确定状态 | 原因限定为固定枚举 |
| 数据源合同 C1–C6 | 可靠地发现变化 | 合同测试，`source.drift` 指标 |
| 机器间链路与汇聚转发 | 规模（G5、G6） | 不持久化，令牌原样透传 |
| 应用子树 | Agent 协作 | schema、配额、来源标记；内核不解释内容 |
| 变化触发 hook | 空闲零开销（G7） | debounce、并发上限、防止循环 |

一共约 10 个平台级概念，用来替换第 9.2 节里数十个按族存在的机制。新概念的价值在于全平台只有一份；如果某一族绕开它们另造，复杂度会叠加而不是减少，所以必须有门禁（第 9.5 节）。

### 9.4 新增代码预算（门槛，不是预测）

| 组件 | 预算（非测试行数） | 超出时 |
| --- | --- | --- |
| Rust 内核首期（树、令牌、订阅、视图、未知、意图、预算、端口） | ≤ 3,000 | 停下来评审，缩减首期范围 |
| TS 副本端和 React 绑定 | ≤ 1,500 | 同上 |
| 机器间链路池和汇聚转发 | ≤ 1,500 | 同上 |
| 应用子树和变化触发 hook | ≤ 1,000 | 同上 |
| 每个族的数据源适配 | 平均 ≤ 150；约 12 个族，合计约 1,800 | 单个族超过 300 时单独评审 |
| sync 帧、错误码、CLI `sync` 动词 | ≤ 600 | — |
| **合计上限** | **约 9,400** |  |

### 9.5 净值判断

- **行数：** 预计删除 4,400–6,900 行，新增预算上限约 9,400 行，另有 1,500–2,500 行只是搬移。
  - 如果新增代码贴着预算上限写，行数上可能**净增**。
  - 新增代码实际落在预算的六到七成时，全部迁完后大致持平，或略有净减。
  - **结论：** 行数不是这个方案的收益来源，也不应该作为主要的验收指标。
- **真正的收益：**
  - 第 9.2 节的机制数从数十个降到个位数；
  - 新增一族的边际成本从 5 处降到 2 处；
  - 规模性质 G1–G7 由内核统一保证，不再每族各自实现；
  - 团队模板从"自己造同步"变成"声明命名空间加处理变化"。
- **失败条件（满足任一条就停下来重新评审）：**
  1. 第二个消费方（P2 的团队跨机派单）期间需要修改内核；
  2. 任一预算超出；
  3. P3 之后第 9.2 节的指标没有按计划下降，即旧路径没有真的删掉；
  4. 规模用例里内核本身成为瓶颈（P1 的 CPU 门槛）。
- **防止"新旧并存"的门禁：**
  - 已迁移的族，以及所有新增的族，不得新增推送帧、读取 RPC 或轮询（静态检查）；
  - 每一步合入时，在发布记录里写明机制数和行数的增减；
  - 兼容窗口沿用 v7 第 12 节：新路径进入 Stable 后，再过一个 Stable 版本删除旧路径。

## 10. 迁移顺序

| 阶段 | 交付 | 删除或进入兼容窗口 | 通过门槛 | 发布模式 |
| --- | --- | --- | --- | --- |
| P0 规范与覆盖检查 | `packages/proto/src/sync/` 帧与错误码；数据源合同；应用子树、`change` hook、汇聚转发的合同；用最难的五族做覆盖检查：会话目录（分页、排序、搜索）、会话正文（轮次节点加实时流）、进程（观察者）、远端不可达（`unknown`）、团队互斥（`ifToken`）；修订 architecture.md，增加"可观察状态只通过节点订阅暴露"并冻结旧机制 | — | 五族都能用两个原语（加补充流）表达，否则先补内核；architecture.md 修订合入；静态门禁生效 | 高频 |
| P1 内核、副本端、CLI | Rust 内核；TS 副本端；`genet sync get/ls/watch/call` | — | 只用假端口跑完全部测试；内存和 CPU 预算实测；与 Rust 权威端互通；第 9.4 节的预算 | 高频 |

**为什么用团队跨机派单做第二个消费方：** 它同时检验三件事：机器间订阅、应用子树的条件写、变化触发。它也是"大量 Agent 协同"的核心路径。如果抽象在这里站不住，后面的族迁得越多，代价越大。

## 11. 验收（均未执行，P0 时细化数字）

### 11.1 简化

| 检查 | 通过条件 |
| --- | --- |
| 机制数 | 每个阶段结束时，第 9.2 节的指标达到该阶段的目标，并写入发布记录 |
| 静态门禁 | 已迁移和新增的族中，出现新的推送帧、读取 RPC 或 `setInterval` 式的状态轮询时，CI 失败 |
| 新增一族 | 用一个新族演练：只改 schema 和数据源，工作台和 CLI 不改协议层就能用 |
| 预算 | 新增代码在第 9.4 节的预算之内 |

### 11.2 规模

| 场景 | 通过条件 |
| --- | --- |
| 15 台机器、20,000 个会话、手机 | 1 条连接；冷启动只与"机器数 × 窗口大小"有关；无变化时恢复，每台机器只有几百字节 |
| 200 个活跃 Agent 会话、20 个团队 | 跨机状态变化在 1 秒内到达订阅方；派单到执行端开始执行的 P95 不超过 2 秒；团队空闲时零请求、零 hook 运行 |
| 汇聚机器离线 | 设备看到 `unknown(via:…)`；可以直连兜底；汇聚机器恢复后自动收敛，期间不丢已承诺的写入 |
| 某台机器离线 | 只有它的子树显示为未知；其他机器照常读写；恢复后只重发变化的节点 |

### 11.3 可靠性

- 沿用 v8 第 9.2 节：监听溢出、外部写入、数据源重启、漏事件兜底、降级。
- 新增两条：
  - **`change` hook：** 突发 1,000 个变化时合并执行、不丢变化键；hook 写入自己监听的前缀时不形成循环。
  - **应用子树：** 超出配额或违反 schema 时拒绝写入；并发认领同一把锁时只有一方成功。

## 12. 兼容、迁移与恢复

- **混合版本：** 15 台机器不会同时升级。每台机器的权威端单独协商，旧 daemon 不返回 `sync` 字段。
  - 汇聚机器把旧机器标为"不支持"，设备对它沿用旧路径直连。
  - 团队派单发现目标机器不支持应用子树时，在兼容窗口内回到 `shell` 接单，并在界面和回执里标明走的是旧路径。
- **团队模板：** 新模板同时支持两种路径，按目标机器的能力选择。用户修改过的模板只提示升级，不自动覆盖（[teams.md](../teams.md) 第 2 节 L2）。
- **数据：** 会话存储格式不变。节点是从现有存储投影出来的读模型；应用子树就是 Space 目录里的文件。删除内核状态和副本，不会丢失业务数据。
- **回滚：** 每个阶段都能单独回退到上一个 Live 版本。R1 回滚到旧 App 后，按 C4 降级为预算轮询。

## 13. 风险与未决问题

1. **汇聚机器的发现和切换：** 默认选哪台，设备如何得知；汇聚机器正好离线时如何切换；是否允许同时使用两台。P3 之前需要原型。
2. **跨渠道共用同一个 home：** dev、Beta、Stable 的 daemon 同时把同一个 `.genethub/` 当权威时，"每台机器唯一权威"规则下谁是权威（v8 第 14 节第 5 条）。P0 必须定下来，因为它影响键空间。
3. **应用子树被滥用为通用 KV：** 配额、schema 和节点大小上限要在 P0 定数字；超出时的界面提示也要设计。
4. **`change` hook 风暴：** debounce、并发上限、循环判定的默认值，在 P2 实测后确定。
5. **内核成为单点设计风险：** 所有族都依赖它。缓解办法是 P0 的覆盖检查、P2 期间冻结内核、第 9.5 节的失败条件。
6. **令牌计算的 CPU 开销：** daemon 是单线程 guest，规范化 JSON 加 SHA-256 不能成为新瓶颈，靠 P1 的 CPU 门槛把关。
7. **兼容窗口过长导致新旧并存：** 删除条件需要统计旧路径的调用次数（v7 第 15 节第 1 条）。
8. **规模目标的数字**（第 3.2 节）需要评审确认。
9. 沿用 v7 第 15 节的第 4 条（机器列表的权威）和第 5 条（Hub 权威端）。

## 14. 方案门声明（engineering-guidance）
