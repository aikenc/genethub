## 摘要

**体验影响。** 一个用户控制十几台电脑、让大量 Agent 协同时，现在的平台有三类问题：
- **看不全。** 页面最多同时保持 8 个机器连接，手机只有 4 个（[machine-connections.md](../machine-connections.md)）。机器一多就只能轮流连，列表靠"可见时每 30 秒刷新"。
- **协作慢。** 每次 `genet … --machine B` 都要新建一条到 B 的远程链路。团队脚本每轮对每台机器跑 `session list --since`、逐条查远端状态，延迟取决于建链和轮询，负载随"待办数 × 机器数"增长。团队脚本甚至为此自己写了一个带游标的增量同步（第 2.2 节）。
- **越来越复杂。** 每一族状态各自实现"推送、读取、缓存、版本、过期判定"：32 个读取 RPC、11 种推送帧、9 种"版本"概念、至少 13 处周期性轮询或扫描。再加一种状态，就要再造一套。

**怎么解决（全部待实施）。** 状态面只保留**一条规则、两个原语**，其余交给框架之外的补充流：
- **规则：** 每台机器是自己子树 `m/<机器>/…` 的唯一权威，其他地方拿到的都是副本；权威不可达时，副本显示为"未知"。
- **两个原语：**
  - 订阅子树或视图：先给快照，之后只推变化，靠令牌续接；
  - 意图：发给权威端，用 `ifToken` 做条件写。
- **补充流：** 实时输出、终端、shell、大内容读取、隧道和媒体，不进同步框架（第 4.3 节）。

工作台、CLI 和其他机器的 daemon 都只用这两个原语。为规模再加两项能力：
1. **机器间链路池和副本（第 5.1 节）：** 每个 daemon 对远端机器保持长链路，订阅需要的子树。CLI 的 `--machine` 读取改为读本机副本，不再每次建链。
2. **汇聚转发（第 5.2 节）：** 手机只连一台机器，就能看到全部机器。

**不做兼容。** 每一族在一个阶段里一次切完，旧路径同阶段删除。对外只保持一组稳定的产品接口：`genet` CLI 的动词和输出、连接握手里的版本，以及升级入口（第 4.5 节）。版本不一致的机器显示"需升级"，不维护旧协议适配（第 12 节）。

**复杂度增减（第 9 节）：**
- 机制数量大幅减少：读取 RPC 从 32 个降到 0；推送帧从 11 种降到 1 组 sync 帧；版本概念从 9 种降到 1 种令牌；跨机获取状态的方式从 3 种降到 1 种；"健康、不确定、过期"的判定从每族一套降到只看"权威可达性"。
- 新增约 8 个平台级概念。
- 不做兼容后不再有新旧并存期，每个阶段结束时该族的旧代码就已删除。行数仍然不是主要收益（第 9.5 节）。

**怎么防止复发：**
- 在 [architecture.md](../architecture.md) 新增边界"可观察状态只通过节点订阅暴露"，并配静态门禁：已迁移的族和所有新增的族，不得再加推送帧、读取 RPC 或状态轮询。
- 每个阶段都带删除清单，由盘点脚本统计机制数和行数的增减，写进发布记录。
- 新增代码设预算，超出就停下来重新评审（第 9.4 节）。
- 团队模板不改，作为每个阶段的回归负载（第 11.3 节）。

**本次需要评审：**
1. 第 3.2 节的规模目标数字；
2. 第 4.5 节的稳定接口清单，以及第 12 节"版本不一致显示需升级"的代价；
3. 第 5.2 节的汇聚转发：是否接受"由用户自己的某台机器担任汇聚点"；

## 3. 目标与范围

### 3.1 简化目标（可度量）

- 每个阶段结束时，该阶段涉及的族在第 9.2 节表中达到目标列，旧路径已删除，由静态门禁守住。
- 新增一族状态只需要 schema 加数据源，不改协议帧，不改工作台监听器。
- 本机写和远程写走同一条路径。

### 3.2 规模目标（拟议，需要评审确认数字）

**沿用 v5 第 2 节：** 每个用户 15 台机器、1,000 个 Space、20,000 个会话（单台最多 12,000 个）、3 个同时在线的客户端，以及若干 CLI `watch`。

**新增两条：**
- 同时活跃 200 个 Agent 会话、20 个团队；
- 跨机状态变化在 1 秒内到达订阅方的副本；`genet … --machine` 的读取命令在副本已就绪时 P95 低于 100 毫秒，不发跨机请求。团队感知到的延迟 = 自己的 timer 周期 + 1 秒。

**性能性质沿用 v5 的 G1–G5**，另加两条：
- **G6：** 每台设备的连接数与机器数无关，是常数。
- **G7：** 空闲时没有跨机的状态流量。团队的 timer 仍按周期在本机运行，但只读本机副本。

### 3.3 不做

- **不做兼容：** 不保留旧 RPC、旧帧和旧特性字符串的适配，不设兼容窗口，不做按族协商（第 12 节）。
- **不改团队模板。** 团队模板通过第 4.5 节的稳定 CLI 使用平台；`_sync_*`、对账、watchdog、看板保持原样。
- **不做应用子树，也不做变化触发 hook。** hook 继续只有 `timer` 一种事件（`hooks/mod.rs` 开头的设计约定）。触发重新评估的条件见第 6.3 节。
- 不改会话存储格式、写锁、inbox、执行围栏，也不改 `TimelineItem/ItemDelta` 契约。
- 流式输出、终端、shell、大文件和高清媒体都不进节点（第 4.3 节）。
- 不做 CRDT，不做多人同时编辑文本。
- 不做 Hub 权威端。Cloud 的 `generation/revision` 保持不变。
- 不引入外部同步引擎或数据库。
- 不新增任何权限层。按产品权限契约（Spaces 仓 `genethub-agent-workflow/references/product-authority.md`），已认证的完整连接拥有目标 OS 用户的权限；仅展示的分享保持现有的受限边界。

## 4. 架构：一条规则、两个原语，加框架之外的补充流

### 4.1 权威规则

- `m/<机器>/…` 只由该机器的 daemon 写入和计算令牌。
- 其他机器和设备上的都是副本，副本可以随时丢弃。
- 权威端不可达时，它的子树标为 `unknown`，并附原因（`offline`、`via:<汇聚机器>`、`budget`、`error`、`upgrade`），不显示过期数据冒充最新。
- 跨机写入是发给权威端的意图，没有分布式事务。需要互斥的写，是权威端上的一次 `ifToken` 条件写。

### 4.2 两个原语（拟议接口）

```ts
// 工作台：读副本，界面状态 = 副本 ⊕ 预表现（v5 第 8 节）
const summary = useNode("m/b/ws/w_1/session/s_9/summary");          // {state:"ok"|"unknown"|…, value, token}
const recent  = useView("sessions.recent", { machines: "*", limit: 100 });
await call("m/b/ws/w_1/session/s_9", "session.updateMeta", { title: "写周报" }, { ifToken: summary.token });
```

```text
genet sync get   m/b/ws/w_1/session/s_9/summary
genet sync ls    m/b/ws/w_1/session/
genet sync watch m/b/ws/ --jsonl            # 空闲时无输出；变化时每行一个节点
```

- 帧和错误码沿用 v7 第 10 节（`open/get/drop/call/ops/error`；`conflict/budget/tooLarge/unknownKey/handler/forbidden`）。
- `genet sync` 是给调试和新脚本用的通用入口；面向 Agent 的动词保留（第 4.5 节）。

### 4.3 同步框架的边界：节点、补充流与内容读取（2026-11-15 Human 决定）

同步框架只负责**会收敛的状态**和**小的不可变内容**。下面三类不进同步框架：

**1. 流式输出：作为框架之上的补充。**
- 会话正文按"轮次"和"已完成的条目"进节点。正在运行的轮次是可变节点，每完成一个条目更新一次；封存之后变为不可变节点。
- Agent 逐字输出的增量（`ItemDelta`）**只在有人观看时**通过实时流推送。没人打开页面时不推送，团队脚本和摘要只看节点。
- **实时流的合同：** 不保证可靠，不做 `seq` 重放，也不做失步处理。流断开或出现缺口时，客户端重新 `get` 对应节点即可收敛。正确性靠节点，实时流只负责让人看得更快。
- `TimelineItem/ItemDelta` 契约不变（[architecture.md](../architecture.md) §4）：节点里放 `TimelineItem`，实时流里放 `ItemDelta`。
- 内核因此**不需要追加日志节点**：节点只有一种 JSON 值，外加"可变或不可变"一个属性。

**2. 不可变内容只包括内联的小对象。**
- 已封存的轮次和 trunk（包括内联的缩略图 `ImageThumb`，64/128 px）作为不可变节点：令牌就是内容 id，只 `get` 不 `watch`，副本命中缓存后零往返，汇聚机器可以放进内存缓存。
- 单个节点有大小上限（P0 定数字），超出时按现有的 trunk 拆分规则拆开。**不支持大文件，不支持续传。**
- 工具输出全文（`blob.get`）、高清图片和视频、工作区文件的预览与下载（`asset.preview`、`file.read`），都不走同步框架，保留现有的读取方式。节点里只放 `BlobRef` 和概要。

**3. 终端和 shell 保持成熟的流式协议。**
- 终端：每个终端一条独立的双向流，承载输入、输出和窗口大小变化，用流控（credit）做背压，做法和 SSH 通道一致。慢的观看者只拖慢自己那条流。
- `shell.run`：保持现状；CLI 的 `shell --machine` 复用机器间长链路（第 5.1 节）。
- 终端是否存在、是否已退出这类**状态**，仍然作为节点。

**最终的分层：**

```text
传输层   carrier / E2EE / DataEndpoint + hello + rtc.negotiate
同步框架 sync：会收敛的状态 + 小的不可变内容（含内联缩略图）
         call：所有动作
补充流   实时输出（有人观看时）· 终端 · shell.run · 内容读取（blob、预览、下载）· 隧道与媒体（service.preview）
```

判断标准：**状态和小内容进同步；"现在正在发生的"和"大块内容"走流。** 流只追求实时，正确性回到节点上核对。

## 5. 多机器拓扑

### 5.1 机器间链路池与副本

- 每个 daemon 维护到其他机器的长链路池，订阅它需要的远端子树，副本放在内存缓存层（v5 第 7 节已有这个设计）。
- 订阅需求有两类：本机 CLI 的 `--machine` 读取，以及经本机转发给设备的订阅（第 5.2 节）。
- CLI 第一次读某台机器的某棵子树时，daemon 建立订阅并在快照到达后返回；之后同一棵子树只订阅一次，多个消费方共享。一段时间没人读时退订（空闲时长 P0 定）。
- 链路断开时，这棵子树标为 `unknown(offline)`；CLI 读到 `unknown` 时返回明确的错误和原因，不返回过期数据。恢复后携带已知令牌重新 `get`，权威端只回传变化的节点。
- `shell --machine`、`file download --machine` 等流也复用这条链路。

### 5.2 汇聚转发

设备可以通过一台机器（汇聚机器）订阅其他机器的子树，汇聚机器从 5.1 的副本里转发：
- **不是权威：** 令牌由各机器的权威端产生，汇聚机器原样转发，不重新计算。设备收到的令牌和直连时完全一样。
- **意图透传：** 汇聚机器把意图转给权威端，自己不执行，也不预先应用。
- **未知会传递：** 汇聚机器到权威端的链路断开时，设备看到 `unknown(via:<汇聚机器>)`，可以选择直连兜底。
- **加密边界不变：** 设备到汇聚机器、汇聚机器到权威端，两段都是 E2EE，relay 照样只搬密文（B4）。汇聚机器能看到明文，这与"已授权的完整连接拥有该账号对这些机器的完整能力"一致，不扩大权限面。
- **仅展示的分享**不能借汇聚机器访问其他机器。
- **不做持久缓存：** 汇聚机器重启后，副本从权威端重新获取。

**设备连接策略（拟议默认值）：**
- 手机：只连汇聚机器；前台会话可以直连该会话所在的机器，以启用 RTC。
- 桌面：总览走汇聚机器，前台会话直连。
- 现有连接池的上限只约束直连，不再约束能看到的机器数。

**汇聚机器的选择与切换：** 默认是设备最近一次成功连接的、用户自己的常在线机器，用户可以在设置里指定。自动发现、离线时切换、用户没有常在线机器时的退化行为，在 P1 用原型验证后写进合同（第 10 节）。

### 5.3 规模下的成本（设计目标，未测量）

| 旅程 | 传输与处理 | 与什么有关 |
| --- | --- | --- |
| 手机打开工作台，15 台机器 | 1 条连接；汇聚机器为每台返回总览、待处理和头部视图。冷启动约 15 × 60 KB，有副本且无变化时约 15 × 300 B（沿用 v5 的估算） | 机器数和窗口大小 |

### 6.2 不变的部分

### 6.3 为什么不做应用子树和变化触发 hook

- 团队目前用 timer 加 CLI 读取发现变化。副本到位后，读取从"跨机建链加现查"变为本机内存读取，延迟的主要来源只剩 timer 周期（最短 1 秒，`hooks/file.rs:27`）。
- 应用子树要求团队把锁、认领和请求改成节点写入，必须改团队模板，与"团队模板不改"冲突。
- `change` 事件会打破 hook 模块的设计约定："只有 timer，错过的通知不可能存在；hook 做的任何事都不会触发 hook"（`hooks/mod.rs` 开头）。
- **重新评估的条件：** P2 之后实测，如果空闲时的 timer 进程启动成为主要 CPU 开销，或者团队需要低于 1 秒的跨机感知，再提案。优先考虑的形式是 timer 上的可选条件"某个前缀的令牌没变就跳过本次运行"，仍然是 timer 语义。

## 7. 数据源层与单机运行时

### 7.1 数据源合同

- 沿用 v8 第 4.2 节的 C1–C6。文件型数据源先用主干已有的指纹索引加冷热分级作为 C4 降级实现，所以会话目录迁移（P2）**不依赖** `fs-watch` 的完整模式发布。`fs-watch` 到位后，同一份合同测试照样通过，延迟更低。
- **`fs-watch` 和进程事件：** 按 v8 第 4.3、4.5 节，作为运行时线的完整模式发布（R1），和主线并行。

### 7.2 跨渠道共用 Space 目录时的权威（定案）

- 按 [storage-layout.md](../storage-layout.md) 第 12–13 行：Space 下的 `.genethub/` 各渠道共用，daemon 数据目录每个渠道一份，机器身份（`state.json`）也在数据目录里。
- **规则：** 每个渠道的 daemon 就是一台独立的"机器"，有自己的 `m/<机器>/` 子树。同一台电脑上的 dev、Beta、Stable daemon 各自把同一批 Space 文件投影成节点，彼此不需要协调。
- **写入：** 沿用现有的文件锁（会话写锁、`.genethub/hooks/.locks/` 等），在锁内重新读取文件、核对令牌之后再写。另一个渠道的写入，对本渠道来说就是外部写入，按 C2 和 C5 发现。
- **影响：** 不改键空间，不需要跨渠道选主。用户同一时间通常只用一个渠道；同时打开两个渠道时，两边各自正确，最多相差一个发现周期。

### 7.3 令牌怎么算（定案）

常用路径上不对 JSON 做哈希：

| 节点来源 | 令牌 | 说明 |
| --- | --- | --- |
| 文件型（会话目录、Space 描述等） | 现有指纹 `fs_stamp::Stamp`（`fs_stamp.rs:26`）的编码 | 指纹索引已经在主干上算好，原子替换也会改变指纹（`fs_stamp.rs:172` 的测试） |
| 内存型（进程、Agent、更新下载等） | daemon 启动编号 + 单调计数器 | 重启后启动编号变化，订阅方重新 `get` 一次该子树 |
| 不可变（封存的轮次、trunk） | 内容 id，封存时计算一次 | 之后只读 |
| 视图 | 成员令牌的组合摘要，只在成员变化时更新 | 不按读取次数计算 |

P1 的 CPU 门槛仍然保留，用来确认这一套在单线程 daemon 上不是瓶颈。

### 7.4 执行分区与存活

- **执行分区（v8 第 6 节）：** 不放进主线。触发条件是：P2 完成后，在第 3.2 节的规模用例下，`partition.queue_ms` 的 P95 仍超过阈值（阈值在 P0 定）。满足条件才立项，届时再比较同进程多 Store 和独立进程两种做法。
- **存活：** 沿用 v8 第 7.2 节。另加一条：如果"对端忙"持续超过上限（P0 定），就升级为故障，避免 host 一直代答心跳、guest 却已经卡死的"连着但不动"。

| 意图与 `ifToken` | 统一的写入和互斥 | 处理器沿用现有逻辑 |
| `unknown` | 统一的不确定状态 | 原因限定为固定枚举 |
| 数据源合同 C1–C6 | 可靠地发现变化 | 合同测试，`source.drift` 指标 |
| 机器间链路池与汇聚转发 | 规模（G5、G6） | 不持久化，令牌原样透传 |

一共约 8 个平台级概念（链路池和汇聚转发算一个），用来替换第 9.2 节里数十个按族存在的机制。如果某一族绕开它们另造，复杂度会叠加而不是减少，所以必须有门禁。

### 9.4 新增代码预算（门槛，不是预测）

| 组件 | 预算（非测试行数） | 超出时 |
| --- | --- | --- |
| Rust 内核首期（树、令牌、订阅、视图、未知、意图、预算、端口） | ≤ 3,000 | 停下来评审，缩减首期范围 |
| TS 副本端和 React 绑定 | ≤ 1,500 | 同上 |
| 机器间链路池和汇聚转发 | ≤ 1,500 | 同上 |
| 每个族的数据源适配 | 平均 ≤ 150；约 12 个族，合计约 1,800 | 单个族超过 300 时单独评审 |
| sync 帧、错误码、`hello` 描述、CLI 的副本读取与 `sync` 动词 | ≤ 800 | — |
| **合计上限** | **约 8,600** |  |

### 9.5 净值判断

- **行数：** 预计删除约 4,530–5,530 行，新增上限约 8,600 行，另有约 1,300 行搬移。新增代码贴着预算写时会净增；落在预算的六成左右时大致持平。**行数不是这个方案的收益来源，也不作为主要验收指标。**
- **不做兼容带来的变化：** 不再有新旧并存期。每个阶段结束时，该族的复杂度就已经降下来；不需要等"新路径进 Stable 再过一个版本"。
- **真正的收益：**
  - 第 9.2 节的机制数从数十个降到个位数；
  - 新增一族的边际成本从 5 处降到 2 处；
  - 规模性质 G1–G7 由内核统一保证；
  - 团队和 Agent 不改代码就获得跨机读取的加速。
- **失败条件（满足任一条就停下来重新评审）：**
  1. 第二个消费方（P2 的会话目录加机器间链路）期间需要修改内核接口或语义；
  2. 任一预算超出；
  3. 某个阶段结束后，盘点脚本显示该阶段的机制数没有下降，即旧路径没有真的删掉；
  4. 规模用例里内核本身成为瓶颈（P1 的 CPU 门槛）；
  5. 未修改的团队模板在某个阶段出现回归，并且只能靠改团队模板解决。
- **防止机制回流的门禁：** 已迁移的族和所有新增的族，不得新增推送帧、读取 RPC、特性字符串或状态轮询（静态检查）；每个阶段在发布记录里写明机制数和行数的增减。

| P5 文件、Git、会话正文、终端 | 观察型节点（v8 第 4.6 节）；轮次节点（运行中可变，封存后不可变）加实时流；每个终端一条独立流 | `git.status`、`file.tree` 的手工刷新；`session.narrative`、`round.trunk.*`、`subscribe/unsubscribe`；`Event`、`Desync`、`PtyOutput`、`PtyClosed`；最后删除 `rpc` 里的读取部分和 `events` 方法本身 | 外部修改在去抖周期内反映；没人观看时零推送；实时流断开后重新 `get` 即收敛；终端洪泛只影响自己的流 |

| R2 运行时：执行分区 | 只在满足第 7.4 节的触发条件时立项 | 控制线程上的后台工作 | v8 第 9.1 节的对应条目 |

**为什么用"会话目录加机器间链路"做第二个消费方：**
- 第一个消费方是工作台，第二个是 CLI 以及它背后未修改的团队模板和 Agent。两者形态完全不同（React 订阅对比命令行一次性读取），能检验抽象是否只适合一种用法。
- 它同时覆盖最难的视图（2 万会话的分页和排序）、机器间订阅、`unknown`，以及"稳定 CLI 合同"这条不做兼容的边界。
- 它是用户最先感受到的收益：团队对账和 Agent 的跨机读取立刻变快。
- 抽象在这里站不住，后面迁得越多代价越大；所以 P2 期间冻结内核接口。

## 12. 版本、迁移与恢复（不做兼容）

- **一族一次切完：** 每个阶段把该族的 daemon、工作台、CLI 一起切到新原语，旧的 RPC、帧、特性字符串和工作台代码同阶段删除。不保留适配层，不设兼容窗口。
- **版本不一致时：**
  - 每个改变线上协议的阶段都提升 `hello` 里的数据面版本。
  - 工作台连到版本不同的机器时，这台机器显示"需升级"（`unknown(upgrade)`），只提供升级入口，不尝试用旧协议读取。
  - 汇聚机器对版本不同的上游，同样标为 `unknown(upgrade)`。
  - CLI 用 `--machine` 访问版本不同的机器时，返回明确的错误码和升级提示，不返回部分结果。
  - 升级入口（`update.*`）和 `hello` 是第 4.5 节的稳定接口，每个阶段都不改它们的形状，保证任何版本的工作台都能把旧机器升上来。
- **发布方式：** 一个用户的全部机器同步升级。dev-3 内由平台开发 Agent 一次更新全部 dev-3 机器；Beta、Stable 的发布节奏和多机更新方式由发布流程决定，不在本文范围。
- **数据：** 会话存储格式不变。节点是从现有存储投影出来的读模型；删除内核状态和副本不会丢失业务数据。
- **回滚：** 回滚就是把全部机器一起退回上一个版本。因为数据格式不变、副本可丢弃，退回后旧版本照常读取同一批文件。R1 回滚到旧 App 后，按 C4 降级为预算轮询。
- **代价（需要评审确认）：** 一个用户的机器没有全部升级时，没升级的那些机器在新工作台里只显示"需升级"，直到升级完成。这是不做兼容换来的简单性。

## 13. 风险与未决问题

1. **汇聚机器的选择与切换：** 默认选哪台、设备如何得知、离线时如何切换、是否允许两台同时使用、用户没有常在线机器时怎么办。P1 原型 B 给结论，P3 之前写进合同。
2. **2 万会话视图：** 分页、排序、搜索在单线程 daemon 上的内存和 CPU。P1 原型 A 给结论；不达标时先改视图设计，再进入 P2。
3. **混合版本期的体验：** 不做兼容后，部分机器未升级时只显示"需升级"。缓解：同步升级全部机器，升级入口保持稳定。是否接受这一代价需要评审。
4. **稳定 CLI 合同的覆盖面：** 团队模板之外，内置 Skill 和用户脚本也可能依赖 CLI 输出的细节。缓解：P0 用 CLI 合同测试固定字段，并在仓库中检索 `genet` 调用作为补充清单。
5. **内核成为单点设计风险：** 所有族都依赖它。缓解：P0 覆盖检查、P1 两个原型、P2 期间冻结内核接口、第 9.5 节的失败条件。
6. **timer 周期决定团队延迟：** 团队感知延迟 = timer 周期 + 1 秒。需要更快时按第 6.3 节的条件重新评估，不提前做。
7. **规模目标的数字**（第 3.2 节）需要评审确认。
8. 沿用 v7 第 15 节的第 4 条（机器列表的权威）和第 5 条（Hub 权威端）。
