## 1. 用户场景与建议

用户让团队开发一款 3D 游戏，服务器承担研发和数值检查，Mac 制作资产并做实机验收，4090 承担 GPU 游玩评审。用户预期只与前台交代目标，团队能持续推进，只有确需判断时才来找人。

实际已经跑通多岗位、worktree、跨机资产制作、QA 与版本产出，但用户仍反复催进度、指出错链、处理桌面弹窗，并发现数值检查之外的体验问题。前台、账本、文件和实机结果又可能表达不同的“完成”。

| 场景 | 改前的可观察问题 | 目标行为 |
| --- | --- | --- |
| 前台失败但用户输入仍在 | 系统消息遵守不解除暂停的合同，团队无法分辨故障暂停与用户主动停止，只能等用户再发一句 | 明确暂停原因、关联轮次和输入处置；可恢复的系统失败有正式恢复入口；用户停止和待批准事项继续保留 |
| 资产任务已经完成 | 完成结果可能受同批慢任务、对账错误或回传状态不明影响，上级继续等 | 能分别查询接收、执行、结果取得、回传与采用；独立结果按依赖条件提前交棒 |
| 远端 QA 接到 v6 | 实机只有 v1，检查尚未开始就因缺包失败 | 派验收前取得目标机的候选就绪回执，绑定版本、文件摘要及目标位置 |
| 用户试玩 | 发布入口已可打开，但实机报告 FAIL，且前台没有及时收敛口径 | 区分“候选可预览”和“验收放行”；FAIL 阻止标记为已验收版本 |

本期建议优先评审三个决定：恢复能力是否采用带版本条件的显式操作；独立成果是否允许先于整批汇总交付；跨机产物第一阶段是否复用接收端下载，反向不可授权的情况单列后续传输能力。

## 4. P0：会话恢复与故障可观测性

### 4.1 分开表达输入接收、执行结果与暂停

调整 [session/inbox.rs](../../apps/daemon/src/session/inbox.rs)、[session/manager.rs](../../apps/daemon/src/session/manager.rs)及其元数据、公开 schema 与工作台状态消费。

输入账本、轮次和暂停是不同事实，分别保存；保留旧 `status`、`inputSummary.paused` 和 `pendingMessageIds`。拟议新增诊断字段：

```json
{
  "inputSummary": {
    "paused": true,
    "revision": 42,
    "pause": {
      "reason": "turnFailure",
      "causedBy": "platform",
      "roundId": "r_example",
      "resumePolicy": "reconcileBeforeRetry"
    }
  }
}
```

这是拟议合同，当前 CLI 不保证返回这些字段。`reason` 至少覆盖 humanStop、turnFailure、watchdog、待 Human 决策及 legacyUnknown；记录调用主体来源，避免团队脚本造成的暂停被误报为用户操作。`revision` 是源 daemon 持久化的会话控制版本，不是团队自己生成的计数。

同时提供按消息 ID 查询的只读接收记录，返回内容摘要、接收状态、关联轮次及执行处置。复用已有账本，不复制任务系统。查询结果必须能区分“未收到”“已持久接收”“交给执行器，效果待核对”“明确结束”；记录已过保留期时返回 receiptExpired，不能把它当作未执行。

所有失败路径，包括执行器启动失败、superseded 交接、通道关闭和无 trunk 的失败，都需有结束时间、可追溯原因和关联输入。若只有终态落盘失败，也应暴露存储故障，不能报告正常完成。

### 4.2 提供无正文的显式恢复操作

拟议 CLI：`genet session resume <id> --expected-revision <n>`，同样支持原有 machine 选择。它是会话控制操作，不制造 Human 消息，不改变批准结果。

1. daemon 在会话串行控制边界内检查调用者、版本、执行状态、暂停原因与未决交互，再持久化恢复决定。
2. 普通 Agent 仅可恢复允许的系统失败；humanStop、legacyUnknown 和待 Human 决策不自动清除。Human 明确恢复走既有授权的控制入口；系统通知仍不解除暂停。
3. 调用重复或并发到达只执行一次状态转换；旧版本返回冲突和可读取的新状态，不盲目重试。
4. 对已确认未开始的输入可以继续调度；已送执行器、可能产生外部效果的输入标为待核对，不自动重跑。恢复成功只表示恢复决定已持久化，不表示任务完成。
5. 失败附件导致持续上游拒绝时，保留原始历史；后续只对明确的执行投影做替换/排除并记录引用。第一阶段先提供诊断和保留来源的新会话接管，附件编辑能力另行验证，不能静默删历史。

该操作应与现有会话发送、interrupt、respond 共享串行化规则，首先用 E1 的补发场景验证，避免“用户追加输入”与旧执行收尾互相覆盖。旧端不支持时明确报 capability 不足，不用一条伪造用户文本模拟恢复。

### 4.3 故障分类与有限恢复

保留现有错误信封和权限检查，增量暴露 `reason`、`stage`、`retryable`、结果确定性及关联执行标识。团队据此处理，逐步去掉对中文文案和 HTTP 数字的正则猜测。

| 条件 | 允许的动作 |
| --- | --- |
| 明确在接收前被拒、且标记可重试 | 同消息身份、有界退避后重试 |
| 派单创建回复丢失 | 按已有 request ID 取执行端回执；unknown 不另建 |
| 上游 5xx，可能已有工具效果 | 报告失败和核对所需证据；不对整个业务任务无条件重试 |
| 身份被拒、权限撤销 | 停止自动重试并显示原因；不清凭据、不自动重新配对或切换身份 |
| 人主动暂停、待批准 | 保留输入与写锁语义；仅由相应授权流程继续 |

## 5. P0：隔离运行时故障并看清资源

检查 [adapter/mod.rs](../../apps/daemon/src/adapter/mod.rs)、共享 Agent SDK 的会话控制、manager 事件泵及运行时注册。SDK 的 `CONTROL_TIMEOUT=30.0` 与团队的 90/300s 静默判断不是同一个计时器；实施前需把历史 daemon 收件超时对应到确切调用路径，不能看到一个 30s 常量就认定找到事故根因。

目前 manager 对 broadcast Lagged 记录丢失后继续，源码支持“消费者可能落后”的风险，不足以证明某条终态已在线上丢失。先做按执行区分的故障注入，再选择最小修补：

- 用户输入、控制响应、终态和证据引用需有可补读的可靠路径及执行关联；可合并的是派生进度，不能静默丢业务事件。采用有界队列和源端背压，持续过载明确失败并保存检查点，不用无限内存队列兜底。
- 单次控制请求超时先标记该操作结果未知，核对脚本/原生句柄与执行代。只有确认必须重建时才终止对应实例；共享适配器涉及的其他会话要各自收尾或重连，不能复用一条日志尾巴当所有会话失败原因。
- 增加运行时 ID、所属 adapter/实例、关联会话、活动引用数、最后活动和资源度量。共享脚本进程可能服务多个会话，不能建立“关一会话就 kill 一进程”的规则。
- 按零活动引用、无未结操作、无必要恢复句柄的条件执行空闲回收；有上限的空闲保留与内存/进程预算，并让“会话关闭”和“运行时是否释放”分别可观察。回收不得破坏仍活跃会话或丢失原生续接证据。

具体空闲 TTL、队列大小和资源上限由隔离实验确定，本提案不承诺精确容量。需复用 dev-2 的控制/正文分流，避免应用层和 Fabric 层各自叠加无关队列。

## 6. P1：跨机消息、产物与运行环境

### 6.1 复用派单回执，补齐观测

执行端继续拥有创建回执与写锁，派单方拥有依赖和回传进度；平台拥有消息接收和会话执行事实。对外展示 request ID、目标 machine/workspace、结果引用、最后成功核对时间、当前错误及下一步。凭据拒绝、超时、机器离线分别显示，不把“查询失败”展示成空岗或完成。

独立条目错误继续不阻塞其他条目。对账按机器批量取摘要，单机设预算与退避；不能每五秒逐任务扫描所有历史正文。详细正文仅按引用读取，承接已有 dev-2 工作。

### 6.2 派 QA 前准备候选

团队样板增加“准备候选”步骤，其回执绑定 `{releaseId, buildRevision, artifactSha256, targetMachineId, targetWorkspaceId, destination}`。目标机验证文件存在与摘要一致之后才产生 ready；入口存在、shell exit 0 或传输已接收均不能替代。

第一阶段沿用接收端 `file download`：验证目标能以已有授权读取源；调用现有 daemon 传输任务，断线后按 transfer ID 查结果，完成后核对目标 SHA-256。接收端写路径、覆盖策略和权限仍由接收端判定。若是多文件版本，先使用固定归档和清单，校验解包路径、文件摘要及入口，避免只比 index.html。

源机反向不可达或目标无权读源时，返回具体 blocked 原因；不得因派单方能访问两端就假设目标也拥有反向授权。只有证明需要后，再设计复用现有已授权连接的发送/接收能力，明确目标授权、配额、续传和原子提交。该增量若涉及新 wire/Host 能力，需双端 capability 与混合版本门禁，不能把提高 shell stdin 上限当正式传输方案。

为本期可实现的下载路径单独验收；在不能授权反向读取的拓扑上，不宣称跨机准备已完整覆盖。

### 6.3 无窗口与真 GPU 分开表达

团队岗位可声明拟议运行需求，如 `visibility=offscreen`、`gpu=required`。受支持的浏览器/渲染 launcher 在启动前检查，并回传实际 renderer、窗口模式与资源配置；GPU 不可用时明确 UNVERIFIABLE，不静默切软渲染或改开有头窗口。

这首先是托管 launcher 与样板的合同，不是对任意 shell 的 OS 沙箱保证。WSLg 环境配方应由目标机能力探测产生；不能把某台 4090 的参数复制给所有平台。用户正在使用的设备默认不产生可见窗口，例外由明确设备策略决定。

## 7. P1：回收团队样板的接力与反思改进

修改拥有源文件的 [team-template/tools/team.py](../../apps/daemon/builtin-skills/genehub/references/team-template/tools/team.py)、看板、岗位 Skill 与升级说明。用户团队已有修补只作为候选来源，逐项复核再回收。

### 独立结果提前交棒

保留当前整批汇总的兼容模式，新增显式的独立交付策略及必要依赖。不要仅凭某个子任务结束就唤醒所有上级。

- 独立子任务取得终态和固定结果引用后，持久化可交付检查点；父会话就绪且无阻断依赖时，用稳定交付 ID 提交一次。父会话忙时入队，不抢占、不解除用户暂停。
- 同批汇总仍产生，但只汇总尚未交付项和最终状态，不把已经采用的成果作为新任务重复处理。发送失败保留待交付状态；发送成功后崩溃，重试同消息身份。
- 执行端锁仍按既有协议释放：最新结果、未处理输入与回复版本必须一致，不能因为提前发了一条进度就释放仍在写的目录。
- 合并、排期与发布仍由组长承担；反思岗位不会因此获得这些职责。

### 看门狗使用活动证据

先提供 warning 和核对，再按任务声明的时限取消。证据包括执行器存活、工具调用开始/结束、构建/渲染活动、显式检查点；文件 mtime 只是补充。远端路径无法本机 stat，temp 中的产物也不能被忽略。

仍需最长预算，防止真的卡死无限运行；取消记录来源和原因，确认终止后才给任务失败终态。Agent 派单后继续保持纯异步，不引入 sleep 或守着轮询。源码中批次剩余任务默认 90s 的策略应先作为隔离复现点，不直接把所有超时改成无限大。

### 反思闭环与通知

反思采用单例、触发合并、最小间隔及有界预算；已有待复检事项时优先复检，不禁止新的紧急故障进入同一待办。时间与轮次数分别定义，必须检查实际计数，不能仅把 `budgetRounds` 写进 JSON 就宣称已执行预算。

Skill 增加根因、反例、证据和落地判据。事项明确责任人、到期及可观察验收，超期送责任人或进入阻断；“写进记忆”“新增脚本”“包含 commit 字符串”均不等于闭合。产物证据带来源机器、路径、hash 和验证时间；远端暂不可读标为未核验，不能直接认定不存在或造假。

前台使用明确登记的 session ID，内部消息按用途分层。拟议通用关联字段为 task/correlation、回复对象、通知级别；用途分类不赋予新权限。内部状态进看板或可检索记录，决策与阻断才形成用户通知；合并同一事件的更新，避免 note 与 result 双投。旧端不认识新字段时先在样板本地抑制，不假装字段已生效。

## 8. P1：身份生效与交付门禁

### 身份预算与版本

SpaceBuilder 保留 SB019 超限拒绝与 SB017 输入漂移保护。预算按最终合成字节与各 Agent 的限制计算，预检展示来源贡献，不能继续只用“≤30 行”控制记忆。SB017 需区分输入仍在编辑的瞬态与真正所有权漂移；只有前者可短暂退避，不能笼统吞掉所有 SB017。

团队写回记忆前做预算检查，索引超预算归档并保留证据指针。身份同步只编译稳定源输入，失败保留上一版生成物和可见错误。持续失败只合并通知一次，状态变化后再更新。

分别记录源内容 digest、生成身份 digest、会话启动时的身份 digest。运行中的会话不一定自动读取改动，无法证明已加载就标 unknown 或 needsRestart；不为了更新身份打断活跃任务。自动刷新继续使用 `--require-no-post-commands`，保留 SB018 门禁，身份维护不能触发部署。

### 候选预览与验收放行

团队发布状态明确区分 candidate/validated/rejected（拟议样板状态）。允许向用户给候选试玩入口，但必须标明待验收；只有绑定同一构建和资产 hash 的必要验收全部 PASS，才更新“已验收版本”的指针。验收缺失、UNVERIFIABLE、FAIL 或对象 hash 不同均阻断放行。

QA 保持独立；实机性能和真实键鼠链路不能由本机 SwiftShader 检查代替。门禁只核证据有效性，不承诺自动评价所有美术风格；用户体验反馈能重新打开问题并撤销放行。业务具体阈值由项目定义，平台不固化 30 FPS 等游戏判据。

## 9. 优先级、依赖与交付边界

| 阶段 | 可独立交付的结果 | 依赖与尚未开放的能力 |
| --- | --- | --- |
| A / P0 | 原始故障的隔离复现、完整终态、暂停原因、消息接收查询、带版本条件的恢复；错误确定性可查 | 先锁定 schema 和授权合同；尚不宣称运行时压力、跨机产物或团队交付整体通过 |
| B / P0 | 有界事件可靠处理、单实例故障隔离、运行时归属和空闲回收 | 与 A 共用执行身份；与 dev-2 对齐队列和传输工作；不先承诺生产容量 |
| C / P1 | 样板独立成果交棒、活动判断、反思和通知收敛；身份预算；可执行的候选放行门禁 | 可先以旧端兼容方式交付；旧平台没有暂停原因时保守处理，不能伪装自动恢复 |
| D / P1 | 基于既有下载的目标产物 ready 回执、托管离屏/GPU 能力探测 | 对反向不可授权拓扑仍报告 blocked；真正的单向推送协议另经原型决策 |

开发候选、dev 实际体验、Beta 制品与真实设备安装分别验收。用户团队升级与平台发布也是两件事，不能用源码或安装包已生成替代实际安装验证。没有实验依据不给精确工期、代码量或并发上限。

## 10. 验收矩阵

以下是拟议验收，不是本轮测试结果。实施时先查已有专项，扩展必要场景；机械验证、完整候选审查和发布资格按所属开发/测试/发布 Skill 执行。测试应通过公共 CLI/Client 和真实 daemon/Host/Relay 边界观察最终状态，默认只替换 LLM endpoint。

| 场景 | 输入条件 | 必须观察的结果 |
| --- | --- | --- |
| A1 补发与终态竞态 | 正在执行时收到下一条 Human 输入，旧轮结束与调度交错；启动失败为零 trunk | 每条输入有确定处置，轮次结束时间和原因完整；新输入继续或明确失败；不静默消失，不双执行 |
| A2 恢复与人停止并发 | 故障暂停后并发 resume、Human stop 和重复 resume；含旧 revision | 版本冲突可见；人的停止和待批准项不被系统恢复越过；恢复不新增聊天正文、不伪造批准 |
| A3 副作用不确定 | 工具已写唯一 marker 后断开，在接收/调度/完成边界重启 | 不自动重跑 marker 写入；同消息查到原执行，结果未知有核对入口；接收回执不被当成完成 |
| A4 上游与非法附件 | 522、网络失败、被服务拒绝的媒体，随后补充纠正输入 | 失败类别与效果确定性可查；非法附件不靠盲目续跑循环；接管保留原来源 |
| B1 事件压力 | 预先固定 N 个会话与每路 M 个带序号事件，慢消费者与断链；记录 N/M 和机器资源 | 所有输入、控制和终态可补读且不重复；有界内存；过载明确失败；单条异常不无故重启其他会话 |
| B2 冷启动与共享脚本 | 一路冷启动慢、另一路正常；共享 adapter 下取消/关闭单会话 | 正常会话结果和句柄保留；异常归属准确；不能用一条日志尾巴代替多路证据 |
| B3 资源回收 | 多批启动/结束、保留一个活动会话并关闭其他会话，经过声明 idle TTL | 零引用实例按策略退出，资源趋于稳定；活动会话仍可调用与续接；进程按运行时归属核对，不能只比较会话数量 |
| C1 接力 | 一个独立子任务结束、同批另一路长构建、父忙、派单方在回传前后崩溃 | 独立结果按策略只交付一次；不抢占父；全批汇总不重复采用；执行端锁在真正终止后释放 |
| C2 长任务 | 单次工具调用超过旧 90/300s、产物写 temp、远端长渲染；另设真死锁 | 有活动不误杀；真超时按声明预算停止并可追溯；Agent 无阻塞等待 |
| C3 反思与证据 | 并发触发满轮次/投诉/状态通知，已有未结项；远端证据暂不可读 | 单例、有界预算；紧急项合并；未知证据不闭合也不造假定性；事项到期升级但不刷用户窗口 |
| C4 身份与升级 | 输入持续变化、真正 ownership drift、超限、含 post hook、运行中旧身份 | 只有适合重试的漂移退避；旧产物安全保留；post 不执行；生成与加载版本分别显示 |
| C5 发布状态 | 同一候选本机 PASS、Mac FAIL/缺失，或验收 hash 不匹配 | 候选可预览但不能提升 validated；已验收指针保留前一合格版本，反馈可重新阻断 |
| D1 产物传输 | 缺包、CLI 断开、目标 daemon 重启、源变更、目标已有不同文件、权限撤销 | 任务按 transfer ID 恢复；SHA-256 对齐后原子可见；ready 绑定目标与构建；拒绝条件不通过新授权绕开 |
| D2 路由与运行环境 | 目标可读源/反向拒绝两种拓扑；WSLg 用户桌面、GPU 不可用 | 可行路径真正落盘；不可行路径明确 blocked；受支持 launcher 无可见窗口且 renderer 符合需求，不静默降级 |
| M1 混合版本 | 新旧 daemon、CLI、样板组合，重复回执和不支持 capability | 旧字段可读；不支持功能显式降级；unknown 与暂停保持保守；不重复创建任务 |

容量门应记录控制 RPC 延迟、事件丢失、资源峰值、断线恢复、队列高水位及环境预算。阈值在跑测前写入配置，保留失败，不以调大预算后的一轮绿色覆盖此前故障。

团队效率使用“结果可交付→父采用”“阻断持续时间”“关键路径等待”“返工/重复派单”“需要用户催促才恢复”的时间与次数。30% 激活率仅作辅助；按业务岗位和维护岗位分别计数，来源缺失、更新时间和分母可见，不为凑比例制造无用任务。

## 11. 兼容、升级与恢复

- 元数据采用可选增量字段，旧记录暂停原因记 legacyUnknown，不能推定用户已同意恢复；旧 CLI 不支持恢复时给出能力缺口。
- 稳定消息/派单 ID 与原回执继续使用；保留期和过期错误先确定，不能清空回执后允许旧 ID 再次执行。
- 样板新批次策略默认兼容整批汇总，已有 pending 按记录版本解释；不能在未结任务中途偷偷切换交付和锁释放语义。
- 用户团队通过既有 platform 分支三方升级，保留定制，先在复制的隔离团队验证，再选择空闲窗口启用。修改源文件后编译，不手改生成 AGENTS、Skill 副本或 hooks。
- 回滚前停止新派单，保存 pending、执行端回执、未处理输入和产物清单；新 schema 记录继续可读，不能用不认识新记录的旧脚本接管正在运行的任务。
- 本期不更换 daemon 身份、不自动修复配对、不因 401 重启，不在评估中停止用户进程。正式发布沿用既有发布授权、制品溯源、回滚和安装验收流程。

## 12. 取舍与未决项

只加记忆条目成本最低，但现场已反复证明不能保证落地；直接无条件重试可能重复外部效果；统一放宽超时会掩盖死锁；新增中央调度器则会跨越用户团队边界。本提案选择复用持久输入与回执，逐步补足通用诊断、可靠恢复和样板约束，代价是需要明确旧数据和混合版本行为。

实施前必须解决：

1. **当前候选差异**：dev-3 的固定基线与后续主干/其他槽位差异未在本文合并；逐项检查已经实现的能力，避免重复修复。历史事故需在最终共同候选复验，不能直接认定最新版仍有缺陷。
2. **恢复合同**：暂停原因、执行确定性及 revision 的实际存储位置；普通 Agent 与 Human 恢复权限；superseded 竞态的真实调用链。阻断 A 阶段接口开放。
3. **运行时共享**：实际 adapter 实例服务哪些会话、原生句柄是否可脱离进程继续、回收边界在哪。阻断 B 阶段自动回收，诊断可先交付。
4. **反向授权**：E5 的 Hub 取票拒绝来自账户目录、旧绑定还是预期权限，尚未定位。先验证既有下载路径；只有真实拓扑仍需要才进入新传输合同，不阻断 A–C。
5. **模板修补质量**：团队新增反思、指标和门禁尚未通过平台回归；字面包含证据 token 不等于证据有效。先审查和隔离验收，不直接复制用户代码。
6. **资源策略强度**：offscreen/GPU 策略只约束支持的 launcher，若要对任意代码强制限制，需要独立 OS 能力设计，不隐含在本期承诺里。

本轮完成判据为：文档与脱敏证据落在 dev-3、引用可追溯、本地链接有效、拟议接口标明未实现、产品双仓保持原状。上述 A–D 功能与验收均为后续实施目标。
