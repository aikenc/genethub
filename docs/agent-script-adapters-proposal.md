产品约束以 [architecture.md](./architecture.md) §3.4 的持久化暂停点为准：用户不需要守在场，等待用户时停止执行，回答后通过持久记录继续同一 Session / 用户 round。第 16 节是对这一既有原则的落实，安装或登录方式不能改变这条边界。

## 1. 目标与判据

1. **内核与具体 Agent 无关。** daemon 与工作台代码里不出现任何 Agent 的名字、命令、参数、协议或登录方式。
2. **第三方变化不需要发版。** 新增 Agent、CLI 升级、登录方式改变，都通过「改脚本 → 验收 → 热加载」解决，
   可以由人改，也可以由 Agent 改。
3. **终端用户不执行任何 CLI。** 安装、登录、更新都在工作台里完成，包括人不在那台机器前、只拿着手机的时候。
4. **密钥和登录链接不经过 LLM。** 它们不进时间线、不进任何 Agent 的上下文、不进日志。
5. **坏脚本拖不垮平台。** 一个脚本卡住或崩溃只影响它自己，并能自动退回上一个可用版本。
6. **等待用户时停止当前执行。** 用户可能很久以后才回复；问题和恢复信息先保存，当前执行结束，不保留等待回答的 RPC、会话子进程或连接。用户回答后启动新执行，继续原 Session / 用户 round。会话已有这条机制，Agent 级请求的缺口与下个版本目标见第 16 节；给等待加超时不能替代停止。

## 3. 总体分层

```
┌──────────────────────────────────────────────────────────┐
│ 工作台：Agent 列表、安装/更新进度、用户请求卡片、会话界面 │  通用渲染，不认识任何 Agent
├──────────────────────────────────────────────────────────┤
│ 内核（不可改）：扫描目录、托管 serve 进程、状态快照、      │
│ 受控重启、动作与 job、用户请求、会话事件校验              │
├──────────────────────────────────────────────────────────┤
│ 脚本层（可改）：agents/<id>/agent.py                       │  Agent 的全部知识都在这里
│   安装/更新/登录/探测/目录/会话/导入/自愈                  │
├──────────────────────────────────────────────────────────┤
│ 内置 Python 运行时 + SDK `genehub_agent`                   │
└──────────────────────────────────────────────────────────┘
```

内核只做第 6 节列出的那几件事。其余全部属于脚本：装什么、怎么装、怎么登录、登录态怎么判断、
怎么拉起 CLI、什么时候重启进程、怎么翻译事件。

**内置 Agent 不改。** 它不走脚本层，`apps/daemon/src/adapter/genet.rs` 保持原样。

- 它的协议是我们自己定的，没有「上游变了要追」的问题，所以不需要脚本化。
- 它在列表里和其他 Agent 并列显示，但实现是原生的，保证永远有一个能用的 Agent 去修别的。
- 以后可以让它直接说 `serve` 协议，省掉 `genet.rs` 的翻译。但这不是这次要解决的问题，不放进范围。

## 4. 目录规范与动态加载

### 4.1 两层目录

```
<渠道数据目录>/agents/
  builtin/<id>/    和内置 Skill 一样编进 wasm、启动时物化出来，只读；随组件更新整体替换（第 10.1 节）
  user/<id>/       用户或 Agent 新建、或从内置复制出来改的；同名时整个目录覆盖 builtin
  state/<id>/      脚本自己的持久状态（装在哪、记下的密钥、缓存），只允许 owner 读写；reset 时保留
```

- **id 就是目录名**，格式 `^[a-z][a-z0-9-]{1,31}$`。会话里存的是 id 加恢复句柄。目录改名等于换了一个新 Agent，
  旧会话只能只读回放。
- **放在渠道数据目录，不放安装目录。** Windows 的 Program Files 和 macOS 的 .app 包都不可写。
- **不支持工作区里的 Agent 定义。** 否则 clone 一个仓库，就等于往机器里植入了一个能看到全部对话的 Agent。

### 4.2 单个目录

```
<id>/
  agent.toml     静态清单；扫描时只读这个文件，不执行代码
  agent.py       入口；平台只调用 `agent.py serve`
  lib/           可选；放在 sys.path 最前面，可以覆盖 SDK 里的同名模块
  tests/         录好的标准对话和测试数据，供 `agent.py test` 用
  README.md      写给 Agent 看的定制说明
```

```toml
protocol    = 1
label       = "Kimi Code"
description = "Moonshot 的终端编程 Agent"
entry       = "agent.py"
```

清单里只放列表页在脚本跑起来之前就要显示的东西。`protocol` 同时就是 SDK 的主版本（第 10.3 节）。
能力、模型、设置轴、版本、状态都是动态的，由脚本运行后上报（第 6.3 节）。
可以另带 `icon = "icon.svg"`，工作台不再按 Agent id 内置图标（现在写在 `packages/workbench/src/assets/agents/index.ts`）。

### 4.3 加载规则

**热加载、崩溃恢复、升级只有一条路径：受控重启。** 同一个 Agent 任何时候只有一个 `serve` 进程，
不存在新旧两个版本并存、旧版本等会话结束再退出这种逻辑。

受控重启的步骤：

1. 等这个 Agent 没有正在进行的一轮，最多等一个固定上限。
2. 发 `shutdown`，结束旧进程。
3. 用当前生效的目录拉起新的 `serve`。
4. 脚本按持久化的恢复句柄把会话接回来。

崩溃恢复本来就必须走这条路，热加载和升级直接复用。

什么时候触发：

- **`user/` 有变化。** 只认 `genet agent reload <id>`，不轮询目录。改多个文件改到一半时不会被拉起半成品。
  先校验清单，合规才重启；不合规就在列表里显示「无效」并写明原因，旧进程继续跑。
- **`builtin/` 有变化。** 只会随组件更新一起变。应用组件更新时 guest 整体重新加载（第 2 节），所有 `serve` 自然重启，
  不需要再轮询这个目录。
- **崩溃。** 按退避节奏重启。连续失败超过阈值，`user/` 版本自动停用，退回 `builtin`。
- **新组件生效后。** 有 `user/` 版本覆盖内置版本的，照常保留，标出「基于旧内置版本」并提供「恢复内置」。
  内核不跑任何 `test`；真坏了就走崩溃退回内置的路径。
- **重置。** `genet agent reset <id>` 删掉 `user/<id>`，触发一次受控重启，退回内置版本，`state/<id>` 保留。

## 5. 进程模型：serve 承载全部会话

**结论：每个 Agent 只有一个常驻 `serve` 进程，这个 Agent 的所有会话都由它承载。**
上一版设计里「`serve` 加每个会话一个 `session` 进程」的拆法放弃。

理由：

1. **内核更小。** 内核眼里一个 Agent 就是一条 stdio 通道，不用管会话进程的拓扑。
   要不要按会话拆子进程是脚本自己的事，脚本可以在内部再起子进程。
2. **生命周期才能真正交给脚本。** 登录文件变了，或者令牌被吊销了，要统一重启这个 Agent 的所有 CLI 子进程。
   只有同时持有全部会话的进程才能做这个决定。反馈里的令牌问题就属于这一类。
3. **和上游的形状一致。** Codex 的 `app-server` 本身就在一条连接上复用多条线程
   （`apps/daemon/src/adapter/codex.rs:2813`），OpenCode 是一个 `serve` 承载多个会话。
4. **真正需要隔离的是 CLI 子进程，它们本来就是独立进程。** Python 这一层只做翻译和编排。

代价和对策：

| 代价 | 对策 |
|---|---|
| `serve` 崩溃会中断这个 Agent 的全部会话 | 走第 4.3 节的受控重启，脚本按持久化的恢复句柄接回每个会话。进行中的那一轮可能中断，但用户看得见、能恢复，这和 B5 对 Live Release 的要求一致 |
| 一个同步调用会卡住整个事件循环 | SDK 强制用 asyncio，重活交给线程。不设心跳：每个请求都有时限，超时就触发受控重启；没有请求在等时，卡住也不影响谁 |
| 没装的 Agent 也常驻一个 Python 进程 | 第一期只有两个 Agent，常驻即可，不做空闲退出。以后 Agent 多了再加 |

## 6. 内核与脚本之间的协议（最小集）

`agent.py serve` 在 stdio 上跑 JSON-RPC 2.0，按 `\n` 分帧，stderr 是日志。数据结构从 `genehub_proto` 生成，
Python 一侧由 SDK 提供。

### 6.1 内核调用脚本

| 方法 | 作用 |
|---|---|
| `initialize` | 下发协议版本、平台信息、渠道、`state/<id>` 路径、前门 CLI 路径；脚本回自己支持的协议版本 |
| `refresh` | 要求重新探测并上报状态（用户打开列表、定时刷新时调用） |
| `action.run {action}` | 执行脚本在状态里声明的一个动作，返回 job id。平台不认识任何动作名，安装、更新、登录都只是脚本声明的动作 |
| `request.answer {id, outcome}` | 用户对一个 Agent 级用户请求的回答或取消（第 7 节） |
| `session.start`（带 `resume` 即恢复）/ `send` / `interrupt` / `setModel` 等 / `respond` / `fork` / `close` | 会话命令，参数里带 `sessionId`；完整列表见 `agent-serve-protocol.md` |
| `import.list` / `import.show` | 导入外部历史会话 |
| `shutdown` | 有限时间内退出 |

### 6.2 脚本通知内核

| 通知 | 作用 |
|---|---|
| `state` | 整份状态快照（6.3）；只要有变化就推 |
| `job.progress {job, phase, percent?, message, done?, error?}` | 任何动作的进度。安装、更新、登录等待、修复，进度、日志和失败原因都只有这一套 |
| `request.open` / `request.close` | 发起或收起一个 Agent 级用户请求（第 7 节）。会话里的权限请求和提问不走这里，仍是现有的会话事件 |
| `session.event {sessionId, event}` | 归一化后的 `SessionEvent`，内核按结构校验，不合规就拒收并记进健康状态 |

### 6.3 状态快照

```jsonc
{
  "ready": true,              // 只有这一个状态位
  "message": "已登录：xxx@example.com",   // 唯一的说明文字；像「未能确认登录状态」这样的提示也写在这里
  "version": "0.160.0",       // 只用于显示
  "actions": [                // 当前可用的动作，平台只按通用按钮渲染；安装、更新也只是这里的普通动作
    { "id": "login",  "label": "登录",     "primary": true },
    { "id": "logout", "label": "退出登录" }
  ],
  "capabilities": { /* 现有 Capabilities，原样 */ },
  "catalog": { /* 现有 Catalog，原样：models（含 efforts）、modes、commands、runtimeAxes、默认值 */ }
}
```

- **只有 `ready` 的 Agent 能被选中、被路由。**
  - 不可用时，显示 `message` 和带 `primary` 标记的动作。平台不知道这个动作是「安装」还是「登录」。
  - 「安装中」就是有一个 job 在跑，显示它的进度。
  - `serve` 起不来、握手失败或反复崩溃，由内核自己发现，显示原因和「让内置 Agent 修复」入口。
- **能力和目录沿用现有类型，不重新设计。** `Capabilities` 与 `Catalog`（`packages/proto/src/domain.rs:15-140`）
  本来就和具体 Agent 无关：模型、思考强度、模式、Fast 和 `runtimeAxes` 都已经是通用结构。
  脚本照这个形状上报，工作台的控件代码不用改。新出现的维度一律走 `runtimeAxes`。
- **路由 tag 保持现状**（Max / Pro / Flash / 视频理解 / 图片理解，`apps/daemon/src/agent_routing.rs:18-24`）。
  脚本只能给模型「建议」tag，最终以用户在偏好里的设置为准。
- **内核只在内存里保留快照，不写盘。** 脚本自己把上次的模型目录缓存在 `state/<id>`，启动时先推缓存，再推新探测的结果。

以上是第一期的状态约定。下个版本保留 `ready` 的选择和路由作用，补充各项能力的健康状态；待答请求的持久记录与模型目录快照分开，见第 16 节。

## 7. 用户请求：平台唯一的人机交互能力

登录、安装确认、会话里 Agent 的权限请求和提问、平台自己的审批，本质上是同一件事：向用户要一个决定，
形式不外乎「N 选 1」「填写」或者两者都有。平台只提供这一个能力，叫「用户请求」。
脚本、各家 Agent 自己的交互流程，以及平台的需求，都接到这一个能力上。

### 7.1 登录方式归纳

| 编号 | 方式 | 例子 | 在脚本层怎么做 |
|---|---|---|---|
| L1 | 粘贴 API key 或 token | DeepSeek 端点、各家 API key | 发一个带 `secret` 问题的用户请求；用 CLI 自己的方式保存（例如它的登录子命令或配置文件）。只认环境变量的，脚本把密钥存进 `state/<id>`，拉起 CLI 时注入 |
| L2 | 设备码 | Codex 的设备码登录（以实测为准）、`gh` 一类 | `display` 放链接和代码，然后盯着 CLI，登录完成后收起请求 |
| L3 | 浏览器 OAuth，回调到本机端口 | Codex 默认方式、Cursor、Claude 系 | `display` 放授权链接。用户的浏览器如果不在这台机器上，回调会打到他自己设备的 localhost 上失败。所以同一个请求里再加一个 `secret` 问题，让用户把浏览器最后跳转到的地址粘贴回来，脚本再转给本机的回调端口 |
| L4 | 企业 SSO 或 OA | TClaude | 通常是 L3 的变体，可能要求内网，用同样的结构 |
| L5 | 只能在 TUI 里操作（`/login`） | Kimi Code、Claude 系 | 脚本在伪终端里驱动这个 TUI，把里面出现的链接、代码、输入提示转成 L1–L3 的用户请求（第 7.5 节） |
| L6 | 扫码 | 部分国内产品 | `display` 放链接，用二维码显示 |
| L7 | 不需要登录，或用户在外部配置好了 | 本地模型、事先设好的环境变量 | 直接报 `ready` |

TClaude、CodeBuddy 这类查不到登录态的，脚本报 `ready`，在 `message` 里写明「未能确认登录状态」，
同时提供 `login` 动作，不再假装确定。

### 7.2 统一的用户请求

现有会话里的 `PermissionRequest` 已经是「一组 N 选 1 加若干问题」（`packages/proto/src/event.rs:131-236`）。
Agent 级的用户请求沿用同样的形状（`AgentUserRequest`，选项与问题复用 `InteractionOption` / `InteractionAnswer`），只多两样：只读展示项和密钥输入。它是独立类型，会话里的 `PermissionRequest` 没有改动。
会话里的权限请求和提问照旧走现有会话事件，暂停和恢复机制一行不动。

这里的「暂停」是保存问题和恢复信息后，停止当前会话执行及其子进程；用户回答后重新启动执行，不依赖一直存活的原生工具调用。共享 `serve` 可以继续服务其他会话。Agent 级请求在第一期尚未采用同样的持久恢复机制，下个版本按第 16 节补齐。

```jsonc
{
  "id": "r_…",              // 由哪个 Agent 发起，内核从通道就知道，不需要写作用域
  "title": "登录 Codex",
  "detail": "在任意设备上打开链接，输入下面的代码。",
  "display": [              // 只读展示项；可以没有
    { "kind": "link", "value": "https://…", "render": "button" },  // render 也可以是 "qr"
    { "kind": "code", "value": "ABCD-1234" }
  ],
  "questions": [            // 填写项；可以没有
    { "id": "method", "prompt": "登录方式", "options": [ { "id": "device", "label": "设备码" } ] },
    { "id": "key",    "prompt": "API Key",  "input": "secret" }   // input：text | secret
  ],
  "options": [              // 最终的 N 选 1；至少一项
    { "id": "ok", "label": "继续" },
    { "id": "cancel", "label": "取消" }
  ]
}
```

回答只有两种：选了某个 `options` 并附带各问题的答案，或者取消。这和现有的 `Answered` / `Canceled` 对应。
内核不计时；过期由脚本自己判断，到点就 `request.close`。

几种常见形态都落在这一个结构里：

| 场景 | 结构 |
|---|---|
| 确认安装 | `detail` 写清命令、来源、大小；`options` 是「安装」「取消」 |
| 设备码登录 | `display` 放链接和代码；`options` 只有「取消」；登录完成后由脚本 `request.close` |
| 粘贴 API key | 一个 `secret` 问题；`options` 是「保存」「取消」 |
| 从别的设备完成浏览器授权 | `display` 放授权链接，加一个 `secret` 问题「粘贴浏览器最后跳转到的地址」 |
| 选登录方式或组织 | 一个带 `options` 的问题，或者直接用顶层 `options` |
| Agent 在会话里请求执行命令 | 现有会话事件 `PermissionRequest`，`options` 是「允许」「拒绝」 |
| Agent 在会话里出多项选择题 | 现有会话事件 `PermissionRequest` 带 `questions` |

### 7.3 作用域决定去向

结构只有一个，但会话里的和 Agent 级的去向不同。这些规则由平台执行，脚本绕不过去：

| | 会话里（现有会话事件） | Agent 级（`request.open`） |
|---|---|---|
| 显示在哪 | 会话时间线里的卡片 | Agent 列表行，加上所有已认证工作台客户端上的通知 |
| 是否持久化 | 是，作为暂停点，daemon 重启后还在（现有机制，`docs/third-party-agents.md` §2.2） | 否，只在内存里；过期或脚本重启后，由脚本重新发起 |
| 回答交给谁 | 发起的脚本，再由脚本交给 Agent，所以会进入 LLM 的上下文和时间线 | 只交给发起的脚本，或平台自己 |
| 能否包含 `secret` 输入和 `display` | 不能，内核直接拒收 | 能 |
| 是否进日志和反馈诊断包 | 和时间线规则一致 | 一律不进；`secret` 在内核里只经过、不留存 |

此表的 Agent 级 `request.open` 记录第一期兼容行为。首批新增 `request.suspend`：持久保存非秘密的待答元数据和恢复步骤，任务先结束并清理子进程，再展示请求，回答交给新执行。密钥答案、授权链接和一次性代码的保密边界不变，具体见 §16.3、§16.7 和线协议文档。

通用规则：

1. 只显示给已认证的工作台客户端，走端到端加密通道。
2. 多台设备同时打开时，先答的生效，其他设备上的卡片自动收起。
3. **Agent 级的请求，只有人能回答。** 会话里的 Agent（`SessionController`）既不能列出也不能回答；
   `agent.action` / `agent.reset` 和请求的列出、回答都要 Settings 能力。会话里的 Agent 可以用 `agent logs` /
   `agent test` / `agent reload`（Session 能力）去修复一个脚本 Agent；`agent action codex login` 这类会弹出请求的
   动作，会话里的 Agent 调用会被拒绝（`forbidden`），只能提示用户去工作台点。链接、代码和密钥都碰不到它。
4. 会话作用域的应答规则保持现状，包括 Agent 回答自己受管子会话的权限请求。
5. SDK 对日志做自动遮罩：经 `secret` 拿到的值，不会原样出现在 stderr 里。

### 7.4 Python 侧的统一接入

SDK 给 Agent 级请求一个入口：

下面的 `await ctx.request(...)` 是第一期兼容接口，依赖内存 Future。新脚本使用 §16.7 的 `ctx.ask`，不以这段等待代码作为长期等待用户的验收依据；接口兼容按 §10.3 处理。

```python
outcome = await ctx.request(
    title="登录 Kimi Code",
    display=[link(url, render="qr")],
    questions=[secret("callback", "粘贴浏览器最后跳转到的地址")],
    options=[option("ok", "完成"), option("cancel", "取消")],
)
```

- 会话里的权限请求和提问，由家族模块翻译成现有的 `PermissionRequest` 会话事件，再把回答翻译回去：

| 家族 | 原生交互 | 翻成 |
|---|---|---|
| `claude_stream` | `can_use_tool`、`AskUserQuestion`、计划确认 | `permission` / `question` / `planApproval` |
| `codex_appserver` | 命令执行审批、文件改动审批、「问用户」选择题 | `permission` / `question` |
| `acp` | `session/request_permission` | `permission` |
| `http_sse` | OpenCode 的权限事件 | `permission` |

这部分翻译今天写在各个 Rust 适配器里，迁移后搬进家族模块。新 Agent 有新的交互形态，只要在脚本里翻成同一个结构，
平台不用改。

- 平台自己的审批（Workflow 的 Human 审批、项目审批请求）已经能工作，这次不迁，也不为它预留字段。

### 7.5 伪终端驱动

L5 要求脚本能在伪终端里驱动 TUI，把里面出现的链接、代码和输入提示转成用户请求。
SDK 提供跨平台封装：Unix 用标准库的 `pty`；Windows 需要 ConPTY，标准库没有现成封装，SDK 用 `ctypes` 直接调用系统 API
（第 10.2 节），不依赖额外的二进制模块。这是 Windows 上的主要风险，首版要实测。

上一版曾设想过一个兜底原语：在工作台终端里预先填好登录命令，让用户自己在 TUI 里操作。它等于让用户执行 CLI，
和第 1 节的判据冲突，已经删除。

## 8. 安装与更新

### 8.1 平台不认识任何生命周期动词

安装、更新、登录、卸载、回滚，在平台眼里都只是脚本在状态里声明的动作。平台只做三件事：

- **显示**：版本号、说明文字，以及带 `primary` 标记的主动作按钮。
- **执行**：用户点了哪个动作，就调用 `action.run`。
- **进度**：用 `job.progress` 显示进度条和日志尾巴，关掉页面再打开还能接着看。

不提供批量更新。自动更新跟随 Live 生效（第 8.3 节），不需要手动批量操作。

为什么安装前的确认也交给脚本：脚本本来就以用户权限执行任意代码，平台再加一道确认，挡不住一个有问题的
脚本，只会增加一个平台概念。SDK 提供标准的确认请求（展示命令、来源、大小），内置脚本统一使用。
由 LLM 发起的安装，确认请求是 Agent 级的，只有人能回答（第 7.3 节），Agent 自己批准不了。

### 8.2 安装旅程

1. **列表。** 工作台的「Agent」页和模型选择器里的「更多 Agent」，列出两层目录里的全部 Agent。
   可用的在前；没装的显示清单里的简介和脚本给的主动作（「安装」）。
2. **点「安装」。** 内核对这个动作调用 `action.run`，拿到 job id。脚本先检查前置条件，比如 npm 方式需要 Node。平台和内置脚本都不代装 Node：
   没有 Node 时，脚本在状态里提示让用户已有的 Agent（如内置 Genet）把 Node 装好，装完回来再点「安装」，
   不用重启 GeneHub。脚本每次重新查找 Node：PATH、常见安装目录、用户登录 shell，所以 daemon 启动后才装的
   Node 也能找到。需要别的安装方式时，改脚本即可，内核不变。然后发一个用户请求，展示可选的安装方式、具体命令、来源和预计大小，等用户确认。
3. **过程。** 列表行显示 job 的阶段（下载、安装、校验）、百分比（有就显示）和最后几行日志。
   用户离开再回来，进度还在。
4. **完成。** 脚本重新探测，记下实际安装到的绝对路径（写进 `state/<id>`），不再依赖 daemon 的 `PATH`。
   以前「npm 全局 bin 不在 daemon PATH 里」那一类问题就此消失。然后推送新状态：
   - 需要登录：仍不可用，主动作变成「登录」，点了以后由脚本发起第 7 节的用户请求。
   - 不需要登录或已登录：`ready`，模型目录随状态出现。
5. **失败。** `job.progress` 带 `error`，行里显示原因，还有「重试」和「让内置 Agent 诊断」两个入口。
   后者会开一个内置 Agent 会话，带上 `genet agent logs <id>` 的输出。

默认装到用户目录，不用 sudo 或管理员权限。确实需要提权的方式，脚本要在确认请求里写明。

### 8.3 更新旅程：跟随 daemon Live 更新

Agent 不单设自动更新开关，而是和 daemon 的 Live 更新一起走：同一时机触发，同一套规则（后台进行、不需要确认、
过程可见、失败自动回退）。

1. **触发。** Live 更新生效时 guest 整体重新加载，所有 `serve` 跟着重启。脚本在启动时自己检查 CLI 有没有新版，
   要更新就在后台起一个 job。平台没有任何更新相关的代码。查最新版的频率由脚本自己节流和缓存。
   手动「更新」是脚本在详情里提供的普通动作。
2. **执行。** 进度显示方式和安装一样，列表行里看得到。
3. **正在跑的会话。** 由脚本处理：通常等当前一轮结束，重启 CLI 子进程，再按恢复句柄接回原会话。
4. **装完验收。** 脚本跑一遍自己的快速自检，确认新版 CLI 仍然兼容。不兼容就自动回到上一版本，比如
   `npm install <pkg>@<上一版>`，然后报不可用并写明原因，等脚本修好再试。
5. **不是 GeneHub 装的 CLI。** 用户在外部自己装、自己升级的，脚本第一次发现时发一个用户请求，
   问「是否交给 GeneHub 自动更新」，回答记进 `state/<id>`。这是脚本层的约定，平台不知道。

两种更新都跟随 daemon Live：

- **CLI 本身**：脚本在 `serve` 启动时检查并更新。
- **脚本**：内置脚本编在组件里，随 Live Release 一起更新；用户层脚本靠直接修改。两者都走第 4.3 节的受控重启。

### 8.4 体验改进：只做平台成本低的

| 改进 | 做不做 | 平台要做什么 |
|---|---|---|
| 在模型选择器里选中、或用它开新会话时，如果 Agent 不可用，当场显示原因和主动作按钮，点了就发起用户请求 | 做 | 选择器多一个状态行和按钮，复用列表行的组件 |
| 上面那种情况下，完成登录后自动把刚才那条消息发出去 | **不做** | 要在内核里新增一个「挂起的消息」状态机，成本不低；用户登录后重发一次即可 |
| 安装完自动接着发起登录请求，不用再点一次 | 做 | 无，SDK 的默认流程 |
| 登录默认优先设备码，其次粘贴跳转地址，最后才是本机浏览器 | 做 | 无，SDK 的默认顺序 |
| 自动更新不打扰：列表上不常驻「有更新」标记，只显示失败和回退；手动「更新」放进详情 | 做 | 负成本，少画一个标记 |
| 「让内置 Agent 修复」一键走完：开一个内置 Agent 会话，带上 `genet agent logs` 的输出；它在 `user/` 里改好，跑 `genet agent test`，最后 `genet agent reload` | 做 | 一个按钮，加一段固定的开场提示 |
| 修好后自动启用，显示「正在使用本地修改版本」和「恢复内置」按钮 | 做 | 无新机制：`reload` 触发受控重启（§4.3），坏了会自动退回内置；「恢复内置」就是 `reset` |

## 9. CLI

### 9.1 脚本侧

平台只调用 `agent.py serve`。SDK 约定了几个面向开发者和 Agent 的子命令，平台不依赖它们：

```
agent.py test [--live]     # 验收：协议格式、回放标准对话、真机冒烟
```

### 9.2 平台侧（面向 Agent 和开发者，不面向终端用户；全部支持 `--machine`）

```
genet agent list | show <id>
genet agent action <id> <action>      # 例如 install、login；交互仍然只出现在工作台；要 Settings 能力
genet agent reload <id>               # user/ 改完后启用
genet agent reset <id>                # 删掉 user/<id>，恢复内置；要 Settings 能力
genet agent test <id> [--live]        # 有 user/<id> 时测它，即使运行中的已退回内置版本
genet agent logs <id> [--lines 1-500]
```

去掉的子命令都有更简单的替代：

- 新建或复制一份：直接复制目录，比如 `cp -r builtin/codex user/codex`。
- 禁用：删掉 `user/` 下的目录，或改成不合规的清单。
- 诊断：看 `logs`。

会话中途切换设置沿用会话 CLI 现有的 `--model` / `--mode` / `--effort`；通用的 `--axis` 参数没有做，等有脚本
Agent 声明了这三者之外的设置项再加。

## 10. 运行时与 SDK

### 10.1 内置文件：沿用现有机制

内置的 `agents/`、SDK 和 Python 安装脚本，和内置 Skill 一样在构建期编进 `genehub_guest.wasm`，daemon 启动时物化到
渠道数据目录（`docs/builtin-skills.md`）。

- Live 包本来就同时带着 wasm 和这些文件，组件更新时一起换新，天然整组生效、整组回退。
- 不改发布清单，不改 host，不发 App Release。
- 物化出来的文件都不需要可执行权限：`.py` 由解释器读取，安装脚本由 `sh` 或 `powershell` 执行。
- 体积：这些文件是几百 KB 量级的文本，远低于 host 对组件 64 MiB 的上限（`apps/host/src/update.rs`）。

### 10.2 Python 运行时：安装程序交付，daemon 只读

交付方式、目录、脚本和失败处理见 [python-runtime.md](./python-runtime.md)。这里只留脚本 Agent 关心的几点：

- Python 由安装程序（`install.sh`、桌面安装器）和开发环境的 `devctl` 运行同一份脚本装好，写入
  `<渠道数据目录>/agents/runtime/python.json`；daemon 不下载、不安装、不预热，只读这份记录。
  找不到时，脚本 Agent 显示不可用，原因是「Python 运行时未安装」。
- 版本和各平台 sha256 只在 `scripts/python-runtime/python.pin` 一处；三个平台都用 python-build-standalone。
  换版本只随 App 版本升级，不支持 live 更新。官网不托管、也不重新打包任何 Python。
- 哈希保证下载内容，所以上游地址和镜像都不需要可信：对不上哈希就换下一个地址。

**Windows 的伪终端。** SDK 用标准库 `ctypes` 直接调用 ConPTY 的系统 API，不依赖额外的二进制模块（不需要 pywinpty）。

**隔离。** 由平台强制，脚本无法改变：

1. **只用绝对路径启动。** 读 `python.json` 里的绝对路径，永远不在 `PATH` 里查找，也就碰不到系统 Python、
   用户的 venv 或 conda、Windows 应用商店的 `python.exe` 别名。
   - 标准库目录里放有 `EXTERNALLY-MANAGED`（PEP 668）：往这份 Python 里全局 `pip install` 会直接失败，
     并提示先建虚拟环境；虚拟环境本身不受影响。
2. **用隔离模式启动**，命令是 `python -I -X utf8 <builtin>/sdk/boot.py <agent-dir>`。
   - `-I` 会忽略所有 `PYTHON*` 环境变量和用户自己的 site-packages，也不会把脚本所在目录加进搜索路径。
   - 搜索路径由 `boot.py` 精确指定，只有这四处：`<agent>/lib`、`<agent>`、SDK、运行时自带的标准库。
   - `.pyc` 缓存写到 `state/<id>/` 下。
3. **反方向也要隔离。** 运行时目录绝不加进 Agent CLI 子进程的 `PATH`。
   - Agent 在用户项目里执行 `python`，用的仍然是用户系统里的 Python 或他的 venv、conda。
   - 脚本拉起 CLI 时传的是用户原本的环境，只去掉 GeneHub 自己注入的变量。
4. **平台自带 Python 通过 `GENEHUB_PYTHON`（一个绝对路径）暴露给会话**，Skill 脚本和 Agent 都可以用它运行脚本、
   创建虚拟环境；它只读，不往里装包。
5. **启用前先自检。** 安装脚本运行 `python -I -c ...`，版本和 `python.pin` 对不上就报错，不写 `python.json`。

### 10.3 SDK `genehub_agent`

SDK 是内置文件的一部分，随 Live Release 更新，不跟着运行时走。脚本可以用 `lib/` 覆盖其中任何模块。

**兼容规则。** SDK 的主版本就是清单里的 `protocol`。同一个 `protocol` 内，SDK 只增不改。

- 删改接口必须升 `protocol`，旧 `protocol` 的脚本按第 4.3 节停用，退回内置版本。
- 不另设 SDK 版本范围字段。内核不跑 `test`（§4.3）；同一个 `protocol` 内若出了不兼容，表现为启动失败或崩溃，按崩溃退回内置版本，界面同时标出「基于旧内置版本」。
- 验收工具以录好的标准对话和 mock 后端为主，在 CI 里就能跑。需要真实登录的冒烟只在本机跑。

SDK 提供以下几样：

- **核心**：`serve` 主循环、JSON-RPC 分帧、事件构造器（类型从 `genehub_proto` 生成）、状态快照、job 封装、
  统一的 `ctx.request`（第 7.4 节）、日志遮罩。
- **进程工具**：按进程组启动、杀进程树、Windows 的 `PATHEXT` 查找、伪终端驱动（Unix 用 `pty`，Windows 用 `ctypes` 调 ConPTY）。
  其中前几样从 `apps/daemon/src/adapter/mod.rs` 迁出。
- **安装工具**：npm、官方安装脚本、GitHub release 二进制、brew、winget 等常见安装方式的封装，带进度解析。
- **按协议形态分的家族模块**，各自把原生交互翻成用户请求（第 7.4 节）：
  - `acp`：Cursor 的历史导入、Kimi Code、goose、gemini
  - `claude_stream`：Claude、TClaude、CodeBuddy
  - `codex_appserver`：Codex
  - `http_sse`：OpenCode
  - `cursor_print`：Cursor 的会话
- **历史导入**：各家历史目录的位置和路径编码规则全部放在脚本里，比如 CodeBuddy 的长路径摘要算法
  （`docs/third-party-agents.md` §3.3）。
- **验收工具**：回放 `tests/` 里的标准对话，校验事件结构，跑真机冒烟。

接入一个 ACP 系的新 Agent，主要工作是写安装、登录和登录态判断这几段，会话部分直接复用家族模块。

## 11. 覆盖检查

**第一期只支持 Codex 和 Cursor 两个第三方 Agent，并且一次清理干净。** 其余第三方 Agent 的 Rust 适配器在第一期直接删除，
之后按第 13.2 节逐个以脚本目录的形式重新接入。下表是全部 Agent 的目标形态。

## 12. 安全

- **脚本的信任级别等同于它驱动的 Agent。** 两者都以用户权限运行（`docs/third-party-agents.md` §1），
  平台不尝试沙箱化脚本。
- **用户层是一个持久的注入点。** 一份本地补丁能看到它所接 Agent 的全部对话。对策有三条：
  - `user/` 和 `state/` 只允许 owner 读写（用现有的 `fs-perms.restrict-to-owner`）。
  - Agent 选择器上标出来源（builtin / user / override）和脚本摘要，能查看相对内置版本的 diff。
  - 内置版本更新时，覆盖它的用户层版本要重新验收（第 4.3 节）。
- **不支持工作区里的 Agent 定义。**
- **不新增授权关系。** 跨机器操作复用现有的 `--machine` 机器授权；用户请求只给已认证的工作台客户端。
- **密钥和链接的规则见第 7.3 节。**
- **运行时的完整性由哈希保证**：上游地址和镜像都不需要可信，哈希写在签名的 wasm 里（第 10.2 节）。

P1 为优先完成的设计与可靠性改进，P2 为后续完善，P3 为体验整理。N1 是新交互机制符合产品理念的前置验收项，不能降为可选优化。每项独立提供验证证据，不以其他用例通过替代。

|---|---|---|---|
| N1 | P1 | 长期等待用户的持久交互机制 | 会话及 Agent 级请求都保存待答状态和恢复步骤；当前执行结束，长期无人回答不占着原执行；重启后可恢复或明确说明授权已过期 |
| N2 | P1 | 普通会话的输入框与选项入口 | 用户要求对话内输入或选择时显示原生卡片，回答只交给正确的恢复执行；不支持的 Agent 明确说明限制 |

| N4 | P1 | 测试资源生命周期 | 执行器异常终止后能安全回收失去所有者的目录和进程；不会误删、误杀仍在运行的任务 |

### 16.3 交互生命周期：保存、停止、回答、恢复

**用户可能长时间不回复，是正常场景。** 按架构 §3.4，停止的是当前执行，保留的是 Session、用户 round、待答问题和恢复义务。等待状态不依赖原 RPC、会话进程、WebSocket 或浏览器连接；回答后开启新执行。下一版统一遵守以下顺序：

1. **保存待答状态。** 持久记录请求 ID、作用域、原执行关联、非秘密的问题或模板标识、恢复步骤及修订信息。
   多设备看到的是同一请求；进程重启不应让同一决定变成一个新问题。
2. **停止当前执行。** 请求展示前确认会话执行和会话子进程已结束，释放执行占用。共享 `serve` 可以继续服务其他会话；
   Agent 级 job 应退到可恢复的待答状态，不能靠一直存活的协程、CLI 或未结束的 RPC 保存续执行位置。
   清理失败必须显示为停止失败，不能先声称已经安全等待用户。
3. **接收一次回答。** 按原有作用域和权限校验，将决定与请求修订绑定，持久记录是否已消费。重复提交、
   迟到回答、另一设备回答和已取消请求不得再次派发同一决定；提交成功表示已受理，不表示后续操作已经完成。
   外部变更使用稳定操作标识、receipt 和 revision 核对，结果未知时先检查事实，禁止盲目重放；不新增任意第三方副作用的 exactly-once 承诺。
4. **恢复新的执行。** 依据已保存的恢复步骤启动新执行，并带上用户答案；恢复失败保留可重试状态。
   普通问答不提升会话权限；审批继续走已有授权规则。恢复后不得重复询问已经决定的同一问题。
5. **取消与过期可解释。** 无回复本身不应作为用户拒绝或任务失败，不设置要求用户及时返回的答题倒计时。具有外部有效期的授权材料过期时，保留待处理事项，
   明确告知用户需要重新发起授权，不自动反复启动登录 CLI。主动取消或关闭会话结束恢复义务；daemon 正常退出保留它。

密钥与授权材料继续遵守 §7.3：**不进入 LLM、时间线、日志和反馈包，也不因持久恢复而写入普通任务状态。**
待答记录保存模板、操作关联和非秘密恢复信息；API Key 答案只送到执行保存操作的脚本，凭据仍由第三方 CLI 或现有凭据存储保存。
登录链接、OAuth 回调、设备码等临时展示材料过期或重启后应明确重新获取，不把整份请求含秘密地序列化保存。

设备码轮询和 OAuth 回调可能依赖第三方 CLI 保持运行。实施 N1 前必须逐家核查其停止与恢复能力，并把授权执行
与待用户状态分开：能恢复时保存符合凭据边界的恢复信息并释放进程；不能恢复时结束本次授权尝试，保留「需要重新登录」事项，
用户回来后再明确发起新授权。当前保留登录 CLI 等待 10 / 15 分钟的做法是待修差距，不保留为产品原则的例外。
上游协议无法满足这一合同的路径应明确报告能力限制，不能以有限超时、空闲协程或页面不卡作为已经停止的证据。

对第一期设计的调整范围：§7.3 的 Agent 级请求内存约定、§7.4 的等待式 SDK 入口、§6.3 的 job 状态表达需要同步评审。
模型目录快照仍可保留原有缓存策略。首批以 `request.suspend` / `action.resume` 和 `ctx.ask(job, step, ...)` 增量扩展 protocol 1；旧 `ctx.request` 保留兼容但不满足持久暂停合同。破坏性变更按 §10.3 升版。
具体 Agent 的授权方式和过期处理继续在脚本层，内核只管理通用的请求、操作记录和生命周期。

### 16.4 平台能力发现与局部健康

**能渲染原生请求，不等于 Agent 能主动调用。** N2 / N3 要核对真实工具注册、CLI 发现、模式限制和能力说明，
提供普通会话能稳定使用的结构化交互入口；复用已有停止与恢复机制，不通过强制切换第三方 Agent 模式绕过限制。
实际支持依各 Agent 的工具能力与协议确定，不能只凭 `permissions: true` 宣称所有交互形态都可主动发起。

平台指南应说明用户说「给我一个输入框和选择」时如何发起会话请求。预览用于用户明确需要的页面或阶段产物；
独立 HTML 页不能代替对话请求。能力不可用时说明限制，禁止编造命令或把未经接通的控件描述成真实会话功能。
Agent 脚本位置和诊断入口从 `agent show`、`logs`、`test`、`reload` 等实际接口发现，不要求用户先给出产品源码路径。

N5 保留 `ready` 作为是否允许选择、路由的标志，另表达健康信息：本地凭据、模型目录是否来自缓存、最近推理结果、
各工具服务状态及其验证时间。缓存目录或 `login status` 不能单独证明上游仍接受凭据。
模型目录的 401、工具的 403、推理鉴权失败要按实际操作归属处理；脚本根据凭据变化或真正影响该会话的错误决定恢复，
不能因为任意 stderr 中出现「401」就重启全部会话。

### 16.5 可靠性与集成验收

测试资源回收需要可验证的所有者记录和活动状态，覆盖正常收尾、执行器被终止及下一次启动时的回收。
清理前确认进程身份、目录归属和任务已经失去所有者，不能仅凭目录年龄、路径前缀或 PID 判断。
资源清点需保留便于定位的进程证据，并遮罩秘密；有界收尾等待仍必须抓住真正不退出的进程。

远程 reload/reset 优先采用通用操作记录：受理后返回可查询的操作标识，完成结果通过状态推送和查询返回。
这会调整现有同步返回语义，需一起评审 CLI、RPC 和工作台兼容；操作标识及重复请求处理不得假定已经存在。
日志权限过滤同时覆盖主动读取与推送，不能仅在 `agent.logs` 上检查授权。

验收分为可重复的确定性测试和真实 Agent 行为验收。前者覆盖协议、状态、错误和恢复；后者检查 Agent 是否会发现并正确调用能力。
不能只注入一条原生请求帧，就宣称用户的真实对话需求已经通过。

| 验收项 | 必须观察的结果 |
|---|---|
| 用用户原话测试输入框和选项 | 真实 CLI 和工作台显示原生提问；未生成替代 HTML；答案进入正确的恢复执行 |
| 长时间没有回答 | 停止当前执行后无模型持续生成、无会话 CLI 保活；待答状态仍存在；其他会话照常工作 |
| 停止与恢复边界 | 请求先落盘，进程停止后再展示；停止失败不误报等待；回答触发新执行并保留恢复关联 |
| daemon / 脚本重启、工作台重连 | 普通待答请求恢复，已回答或取消的不复活；登录授权过期有明确提示；无需保留原 socket 或协程 |
| 两台设备回答、重复提交 | 仅一个决定生效，同一决定不重复派发；晚答设备刷新到已处理状态；外部操作结果未知时不盲目重放 |
| 恢复后不重复提问 | 已回答的同一请求不再发起；非秘密答案完整保留，普通问答不提升权限 |
| Agent 级安装与 API Key 请求 | 等待确认或输入时 job 可持久恢复；未确认不启动安装；密钥不进入普通持久记录、模型和诊断 |
| 设备码 / OAuth 登录过期 | 有效期和资源释放行为清楚；回来后重新授权可成功；不无限轮询或后台反复重开登录 |
| 授权过程中需要人决定或输入 | 待答阶段无原登录 CLI 或回调监听器持续等待；用户很久后回来可恢复或明确重新授权，10 / 15 分钟超时不能代替停止 |
| 权限与日志 | Read / Session / Settings 设备分别得到允许的数据；密钥与授权材料不泄漏 |
| 局部故障与远程操作 | 目录鉴权、MCP 失败和推理故障分别呈现；远程超时、重复操作不造成第二次重启 |
| RTC、空会话与验证工作区 | 失败阶段和当前通道可定位；退避与暂停仍有效；正常无轮次不报故障；工作区用途可辨认 |
| 测试执行器异常终止 | 失去所有者的目录和进程可回收；并行任务、活跃 daemon 与用户目录均保留 |

继续保留已有的隔离安装、登录、换 Key、更新、历史导入、进程清理和内置脚本自测专项。
安装验收使用专用隔离目录，实际执行 Python 安装脚本、npm 安装 Codex 和 Cursor 官方安装器；尽可能只 mock LLM。
Codex 用真实 CLI 连接 mock Responses 服务；Cursor 真实推理仍需要真实 provider canary，不能把其私有后端替身称为只 mock LLM。
真实 Agent 对自然语言的能力发现另作 canary，LLM mock 强制工具调用只能证明机制连通。
Windows 安装、路径、编码和 ConPTY 保留明确的平台验收项，不能以 Linux 结果代替。
各 run 绑定固定候选和产物，失败、blocked、资源泄漏与运行期间源码变化单独报告，不解释成通过。

### 16.6 实施顺序与范围边界

1. 先确定 N1 的持久请求与停止 / 恢复合同，再实施 N2 / N3 的调用入口与能力说明；两者一起验收。
2. N4 的测试资源回收与 N5 的健康状态可独立推进，先提供各自定向证据。
3. N6 / N7 的接口与授权一致性改进随后完成；N8 / N9 为诊断和网络排障，N10 为体验整理。
4. 交付前完成受影响专项和适用完整门禁，走提交审查与发布交接。本文汇总不等于开发已完成或发布已获授权。

继续保持脚本化接入的分层，不把各家 Agent 的安装、登录或更新知识重新写回内核。
Node 仍由用户安排已有 Agent 安装；不增加平台代装或独立 Codex 下载兜底。
Claude 家族、OpenCode 等接回仍属于 §13.2 的后续适配范围，不以这次改进计划暗示已恢复支持。
8 个已暂停的旧 Rust 用例保留暂停原因和恢复条件，未执行不计为通过，对应能力重新接入时恢复。
本节不改变密钥隔离规则、平台审批授权规则，也不新增「登录完成后自动重发原消息」的承诺。

| 项目 | 已落地的行为 | 仍需保留的边界 |

**账号授权能力差距。** 当前 Codex/Cursor 账号授权依赖运行中的上游 CLI，没有可停止后续接的公共合同。此次选择显式报告「此版本不能在工作台完成账号登录」，持久保留需要登录的事项，提供取消和本地凭据检查；不保活 CLI，不伪造已完成登录，也不恢复已删除的终端登录兜底原语。Codex API Key 的输入与保存已走真实 CLI 和持久请求。手机内完成账号 OAuth / 设备码授权的目标尚未满足，须由脚本层补充具备持久恢复能力的官方授权接口后单独验收。Cursor 仍以已配置的外部凭据运行；其真实推理不能作为只 mock LLM 的测试。

SDK 的最小持久动作示例：

```python
async def run_action(self, ctx, action, job):
    outcome = await ctx.ask(job, "confirm", "确认操作",
                            options=[option("run", "执行"), option("cancel", "取消")])
    if outcome.canceled or outcome.option_id != "run":
        job.done("已取消")
        return
    # 只在已消费的回答进入新执行后做外部变更。
    await perform_operation()
```

多步骤动作必须实现 `resume_action(ctx, action, step, job)`，按保存的 step 跳转，不可把整条安装/登录链从头重放。

新增验收包括：真实浏览器点击、真实 SessionController CLI 提问、daemon 重启、两台 Settings 设备竞争同一持久答案、取消、外部结果未知、损坏记录保留与修复、执行器 SIGKILL 后恢复，以及只读列表/推送的日志权限。真实 Codex 安装旅程包含真正的原生提问与新执行恢复；另设真实模型的自然语言发现旅程。

N5、N6、N8 的其余部分、N9、N10 尚未在首批实现；它们的完成判据仍按 §16.2 保留。本批定向 run、失败证据和最终验证结论记录在同目录的 `agent-script-adapters-implementation.md`，只有经过固定候选验证的范围才标为完成。
