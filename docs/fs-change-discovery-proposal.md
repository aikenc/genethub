# 基于磁盘时间的状态变更发现与同步（提案）

- 状态：已评审（2026-11-09），dev-5 实现中，未合入主干、未发布
- 日期：2026-11-09
- 范围：daemon guest 内的会话目录、Space 发现、Timer 钩子登记三处磁盘扫描；团队 Timer 的本机与远程岗位
  同步；不改 WIT/host（第 3 期除外）
- 依据：dev-5 `09cc8a00`（父 `df1533ec` 远程岗位 `TEAM_MACHINE`，主干 `b951c49d`）；本机 Beta
  0.20.1-beta.6 日志 2026-11-08 21:53–23:08Z；wasmtime-wasi 48 源码

## 摘要

- **用户影响**：本机 Beta（445 个工作区、约 2350 个会话目录）上，页面重连、CLI 和跨机请求被持续拖慢；
  一次页面切回前台后用了 13 秒才恢复（fb_tfKT5yf74IN2）。Timer 调度本身是异步的，慢在 daemon 单线程上的
  周期性全量磁盘扫描。
- **解决**：所有基于文件的状态改为“磁盘指纹索引”——用 `(mtime, size, 创建时间)` 判断是否变化，用目录
  mtime 剪枝，热数据每轮核对、冷数据每 30s 覆盖一遍；对外提供不透明的变更游标，团队 Timer（含远程岗位）
  按游标增量同步，不再逐个查询。
- **防复发**：规模用例固定 450 工作区 / 2500 会话 / 5 个团队 Timer（含 Hub 远程岗位），稳态不得出现
  慢扫描告警，后台扫描占 guest 轮询时间 ≤2%，单次独占 ≤10ms。

## 现状与证据

daemon 是 Wasmtime 组件，全部会话、页面、CLI 和心跳共用一个执行线程（`blocking.rs`）。扫描虽有
`WorkBudget` 让出，但每段仍独占线程，且扫描几乎不停：

| 扫描 | 代码 | 频率 | 实测 |
| --- | --- | --- | --- |
| 会话目录全量核对 | `session/store.rs` `reconcile_catalog` → `scan_metadata(None)`；后台循环 `lib.rs` space_discovery 与任意会话读取都会触发 | 距上次 >5s 即触发，不分范围 | 74 分钟 400 次，每次约 4.7s，独占约 1.6s；每次 2350 个条目只有约 20 个真正变化 |
| Space 发现 | `workspace.rs` `scan_spaces` | 每 2s | 74 分钟 707 次超过 1s，单次 1–5s |
| Timer 钩子登记 | `hooks/mod.rs` `run_timer` → `tick_project` → `file::snapshot` | 每 1s，对 445 个工作区逐个 `is_dir`/`read_dir`/读文件，同步无让出 | 平均每 tick 独占 84.7ms |

慢扫描窗口内的 guest 轮询时间归因（`session_catalog_work`，120 个窗口共 708s）：后台发现循环 31.8%，
Timer 脚本发来的本机 CLI 请求 23.4% + 9.2%，钩子运行任务 11.3%，Timer 调度 8.5%，网页服务 8.3%。

每个会话条目的核对要 2–3 次文件系统调用（墓碑 `exists`、`meta.json` stat，另有每个 home 的
`establish_home` 多次 `exists`），按日志折算约 0.2ms/次（经 Wasmtime 的阻塞线程转发），这是 O(N)
扫描贵的原因。

团队侧：旧模板每轮读全机会话再按 Space 过滤（我 11-09 的临时分页补丁保留了这一语义）；当前模板已按
Space 分页，但远程岗位（`TEAM_MACHINE`）的会话只能由定义源机器的 Timer 每轮带 `--machine` 去目标机查，
目标机不跑 Timer（`remote-targets.md`）。每次远程查询又会让目标机做一次全机核对。

## 用哪个文件时间

结论：**用 mtime 做主信号，但与 size、文件身份一起组成指纹，只判断“和上次是否相同”，永不比较新旧，
永不跨机器比较。**

| 时间 | 取舍 |
| --- | --- |
| mtime（`data_modification_timestamp`） | 采用。内容写入必变；各平台都有。缺点：可被 `touch`/`cp -p`/`rsync -t`/`tar x` 改回旧值，粒度因文件系统而异（FAT 2s、HFS+ 1s、ext4/APFS 纳秒但内核用粗时钟） |
| 目录 mtime | 采用，用于剪枝。目录内**新增/删除/改名条目**才变；文件原地改写、深层变化不变 |
| ctime（inode 状态变更） | 不用。Wasmtime 48 把 WASI `status_change_timestamp` 填成 `created()`（创建时间），guest 拿不到真 ctime；Windows 也没有 ctime |
| atime | 不用。`noatime/relatime` 下不可靠，且读取本身会改它 |
| 创建时间（guest 里读作 `created()`） | 采用，充当文件身份。原子替换（临时文件改名）换了新文件，创建时间随之变化，即使 mtime 被还原也能发现；改内容不变，所以不能单独用 |
| 文件身份（Unix dev+inode） | 想用但拿不到：`std::os::wasi::fs::MetadataExt` 在稳定版 Rust 上不可用，WASI 的 `metadata_hash` 也不经 `std` 暴露；由创建时间代替 |

GeneHub 自己的写入都走“临时文件 + 改名”（`config::save_private`），因此每次重写 `meta.json`：文件身份变、
文件 mtime 变、**所在会话目录 mtime 也变**；新建会话改变 `sessions/` 目录 mtime；删除写墓碑改变
`tombstones/` 目录 mtime。这让两级目录剪枝成立。

**时间粒度竞争**（同 Git 的 racy-git）：记录指纹时若 `now - mtime < 2s`，标记为“未稳定”，下轮无条件
重查，直到稳定。这样同一秒内的两次写入不会因指纹相同被漏掉。

已知不可检测：同大小原地改写并还原 mtime 且不换 inode（如 `touch -r` 配合原地编辑）。只能靠显式
`--fresh` 读取或低频（例如 30 分钟）全量内容核对兜底，文档写明。

## 具体方案

### 1. 统一的磁盘指纹索引（guest 内新模块，三处复用）

```text
Stamp   = { mtime_ns, size, file_id }        // 相等比较；任一不同即“变了”
Entry   = { stamp, settled: bool, tier: hot|cold, revision, checked_at }
Index   = 目录树 → Entry；每处业务（会话、Space、钩子）一棵树
```

- **自己的写入直接更新索引**：`save_meta`、墓碑、Space 创建/打开、钩子由 daemon 写入时，写完立即记录新
  指纹和新 revision，不需要再被扫描发现。
- **扫描只做 stat，不读内容**：指纹没变就跳过；变了才读、解析那一个文件。
- **热/冷分层**：热 = 最近 10 分钟变过、自己刚写过、指纹未稳定；每轮（2s）核对。冷 = 其余；每条每 30s
  至少核对一次，首次核对时间按路径散列铺开，避免同一时刻集中到期。每段 4ms 让出。
- **冷层为什么是 30s**：平台的主动刷新（`catalog_wake`）只覆盖 daemon 自己的写入；别的进程写的文件只能靠
  扫描发现，所以全局视图的外部变化延迟就是冷层周期。带范围的读取不受此限。
- **平台动作让所在目录变热**：刚打开的项目、daemon 刚在其中建过或写过会话的 `sessions/` 目录，之后 1 分钟
  每轮核对一次列表，同一目录里别的进程新建的会话 2s 内出现在全局视图；已有会话被别的进程原地改写仍按冷层 ≤30s。
- **目录剪枝**：`sessions/` 指纹不变 → 没有新增/删除会话，不 `read_dir`；会话目录指纹不变 → 不 stat
  `meta.json`、不查墓碑。每个会话的常态成本从 2–3 次调用降到冷轮转时的 1 次。

### 2. 三处扫描的改法

| 处 | 现在 | 改为 |
| --- | --- | --- |
| 会话目录 | 任意读取或后台循环 >5s 就全机核对 | 后台按热/冷预算核对；`--workspace W` 读取只同步核对 W（有界，2s 内复用）；不带范围的读取直接用索引，不触发全机扫描，返回 `checkedAt` |
| Space 发现 | 每 2s 遍历整棵 `spaces` 树 | 根目录和集合目录每轮 stat；各 Space 内部 30s 冷周期（启动后新出现的 Space 先热 1 分钟，刚部署后的修改 2s 内生效）；指纹变了才读 `agent-space.genet.json`；发现结果未变时不重新登记；显式 `space open` 立即重读 |
| Timer 钩子登记 | 每秒对每个工作区 `read_dir` 并读钩子文件，同步不让出 | 缓存解析结果；每个工作区的钩子目录每 5s 核对一次指纹（新写入的钩子 5s 内生效），分摊到各 tick 并让出；钩子真正运行前仍重读自己的文件，触发语义不变 |
| 内置 Skill 物化 | 每条消息逐字节比对 104 个文件（约 1.4MB） | 首次全量比对并清理旧文件；之后 30s 内直接信任，过期后只 stat，指纹变了才比对内容；解析好的 Skill 目录一并缓存 |

### 3. 变更游标：本机与跨机同步

索引给每次变化分配本 daemon 内单调递增的序号（与浏览器目录的 dirty/removed 同一处记录）。合同
（新增 `session.changes` RPC，能力 `session.changes.v1`）：

```text
genet session list --workspace W1 --workspace W2 --since start|<cursor> [--include-archived] [--lean] [--machine M]
→ {"sessions":[...行...], "removed":[{"workspaceId","id"}], "cursor":"…", "complete":true, "reset":false}
```

- 每行与 `session get --summary` 相同（活跃会话用内存中的元数据）；`complete:false` 时带回 cursor 续读，
  每次最多 200 行，最多 100 个工作区。
- 游标是不透明字符串（daemon 实例令牌 + 序号，CLI 再绑定机器），不含任何文件时间，跨机器无时钟偏差。
- daemon 重启、游标太旧（删除记录只保留最近 4096 条）或来自别的机器 → `reset:true`，本次回复从头列出
  整个范围，调用方用它替换原快照。
- 只读索引，不触发扫描：自己的写入立即可见，其他进程的写入在后台核对到之后可见（≤30s）。
- 运行中会话的 `lastActivityAtMs` 每 5s 至多记一次变化，游标读者看到的活跃时间最多晚 5s；这不唤醒
  浏览器目录推送。

### 4. 团队 Timer（含远程岗位）

- **原则：只换数据来源，不跳过任何一轮。** 脚本可能做任何事，到点、超时、卡住等时间判定都在脚本里按
  当前时间每轮照常计算；平台不根据指纹替脚本决定“这轮不用跑”。
- 按机器分组：本机一组（团队自己的 Space）；每台远程机器一组（`members`/remote-targets 里绑定到该机器的
  岗位工作区，以及逐个查询中学到的工作区）。每轮每台机器**一次** `--since` 调用，游标与快照存
  `.genethub/team/state/sync.json`；本轮内自己改过会话（派单、发消息等）后，下次读取再增量同步一次。
- `sessions_of`/`session_summary` 由本轮快照提供；快照里没有的会话仍逐个查询（例如会话已不存在时要拿到
  `targetNotFound`）。
- 跨机调用复用已有 Hub 连接（`09cc8a00`），不再每轮一张票。目标机离线或未升级（没有 `session.changes.v1`）
  时，本轮回到逐个查询；保留上次快照但不用于判断，不当作空列表。
- 只同步岗位自己的工作区；目标机上同一 `~/.genehub-teams/<源 Team>` 下其他团队的数据不读。
- 旧团队升级到当前模板后撤掉临时分页补丁；升级前，第 2 节已让不带范围的读取不再触发全机扫描，旧模板
  也不再驱动磁盘扫描（只剩 CLI 本身的开销）。

## 取舍与替代

- **只调大间隔**（例如 30s 全量）：最小改动，但每次仍独占秒级，规模越大越卡，外部变化延迟变长。不采用。
- **文件系统监听**（inotify/FSEvents/ReadDirectoryChangesW）：最省，但必须在 host 实现并新增 WIT，属于 App
  发布；监听会溢出、在 NFS/部分 WSL 挂载上不可用。作为第 3 期的唤醒提示，指纹索引仍是唯一事实来源。
- **写者日志**（每次写入追加 `sessions/.journal`）：可精确拿到变化 ID，但要求所有写者（其他渠道、导入工具、
  人工）都遵守，否则仍需扫描；可在第 2 期评估是否值得作为热层加速。

## 验收

| 目标 | 输入 | 通过条件 |
| --- | --- | --- |
| 不再持续占用 | 450 工作区、2500 会话、5 个团队 Timer（2 个带 Hub 远程岗位），无变化运行 5 分钟 | 无 `session_catalog_slow`/`workspace_discovery_slow`；后台扫描 ≤2% guest 轮询时间；Timer/发现单次独占 ≤10ms |
| 自己写入即时 | daemon 更新会话 | 下一次读取立即可见，不依赖扫描 |
| 外部写入可见 | 另一进程原子替换某会话 `meta.json`；原地改写；新建/删除会话目录 | 带范围读取立即可见；全局视图 ≤30s |
| 粒度竞争 | 同一秒内连续两次同大小写入 | 第二次被发现 |
| 游标 | 无变化、有变化、daemon 重启、远端离线 | 无变化回复不触发远端扫描；重启后 `reset:true` 且完整读取后不丢变化；离线不清空快照 |
| 用户体验 | 上述负载下手机页面切回前台 | 3s 内恢复可用 |

旧代码基线必须让“不再持续占用”一项失败，证明用例有效。

## 分期

1. **guest 内索引与三处扫描改造**（仅 `genehub_guest.wasm`，可经 Beta Live 发布）。独立交付：不再卡，
   旧团队也受益。
2. **变更游标 + 团队模板按机器分组同步**，升级线上旧团队、撤补丁。依赖第 1 期的索引。
3. （可选，App 发布）host 原生文件监听作为唤醒提示。

## 未决

- guest 内单次 stat 的实际成本（日志折算约 0.2ms）；规模用例按 daemon 进程 CPU 时间验收，真实机器待 Beta 复测。
- 创建时间作文件身份：Linux/macOS/Windows 原生文件系统可用；个别文件系统不提供创建时间时退化为
  `(mtime, size)`，仍有未稳定窗口兜底。
- WSL `/mnt/*`、NFS 上 mtime 粒度和属性缓存行为，需要在 WSL-4090-1 上实测。
- 其他渠道 daemon 是否写同一个会话 home（决定外部写入的常见程度和冷层延迟是否可接受）。
