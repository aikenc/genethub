## 先回答三个问题

1. **现在的影响是什么。** 这几天的循环是：人跑测团队 → 发现问题 → 描述给 Agent → 让 Agent 修复 → 让 Agent 发 Beta → 人回到团队看有没有变好。人是瓶颈，人不在时问题会堆积：XWorld 反思岗位从 11-09 12:33 到 11-10 02:00 至少 6 次记录同一个 `SB010`，14 小时没人处理。beta.6 和 beta.7 的发布记录都写着"已有团队需要升级模板后才能用上"，发完以后有没有生效，也要人回去看。
2. **怎么解决。** 新增平台开发侧的观察者 Skill `genethub-team-observer`，在 dev-2 里形成一条闭环：用 Wait 机制在一个会话里持续在线 → 按文件读取所有机器上的团队信号 → 以用户身份下达目标、给授权、做产品判断 → 把问题分到平台内核、内置样板或反思流程 → 在 dev-2 修复并发布 dev 版本 → 确认本机、Mac 和团队都已采用 → 复验后关闭。闭环只在 dev-2 内完成，不合入主干，不发 Beta 和 Stable。
   - **已完成**：两份提案已提交；B-P0、初版观察工具、两队启动；公共反馈命令及SB010修复已发dev.3/dev.4，本机和Mac真实采用。
   - **待实施/闭环**：A-P1过程事件及两个参数、完整观察信号与后续质量模型；两队采用后的原场景复验和首轮结算仍须逐项确认。
   - **待验证**：B-P1 两队完整业务验收及 B-P2 长期观察；逐项状态见[实施对账](team-experiment-implementation-audit-20261110.md)。
3. **怎么防止问题复发。** 闭环自己记账：每个问题记录谁先发现、多久修好、团队是否采用、是否复发。人每次被迫介入都记为闭环本身的缺陷，下一轮改进观察者 Skill。每个修复附夹具或回归测试，并且要在团队采用之后用团队自己的信号确认好转才能关闭。

## 1. 摘要与建议

- **人只做三件事**：下达长期目标和预算；随时抽查、纠偏；做只有人能做的物理或授权操作（例如在 Mac 界面上点"允许"）。授权和产品判断由观察者模拟用户完成，人抽查时可以推翻。
- **观察者是平台开发者，不是团队组长**：它不管理团队，只通过平台改动影响团队。dev-2 渠道里它有全部权限：提交、构建、发布、更新、卸载。
- **持续在线靠 Wait**：沿用 openplay 组长的前台阻塞等待，不需要平台新增定时原语。
- **信号按文件读取**：平台完全基于文件系统，观察者用跨机器的 shell 和文件下载读取任何机器上的团队文件；团队对平台的反馈走评估提案第 5.7 节的反馈文件。
- **先让正式分可判定**：补过程事件、小时卡与反思读卡；已有反馈继续处理，按失分修复通用机制，并用非本项目夹具和团队采用后的卡验证。
- **两支新实验团队**：Beta 两队停止后，从主队推送的同一 team/项目起点建立 ds、hy。需要比较模型时保持目标、预算、工具、平台版本与起点一致；自然业务目标不同时只作观察，不作模型因果结论。

## 2. 角色与边界

### 2.1 两条轴

**角色层**回答谁做事：

| 角色层 | 包含谁 | 做什么 | 节奏 |
| --- | --- | --- | --- |
| 团队执行层 | 前台、Owner、成员、QA | 推进目标，产出业务成果 | 按任务，分钟级 |
| 团队自管理层 | 反思岗位、定时自评 | 改进本队的工作方式；自己改不了的反馈给平台 | 按反思周期，小时级 |
| 平台开发层 | 观察者与 dev-2 的开发 Agent | 观察多个团队与平台运行，改平台，发布 dev 版本并复验 | 按 Wait 周期与预算 |

执行层与自管理层的分界：只影响当前这一单的决定属于执行层；改变团队以后怎样工作的属于自管理层。

**制品层**回答改哪里：

| 制品层 | 内容 | 唯一写入方 |
| --- | --- | --- |
| 平台内核 | daemon、宿主、CLI、协议、定时 hook 机制 | 平台开发层 |
| 内置样板 | 公共工作流脚本 `genet_builtin`、公开扩展基类、默认评分模型、内置 Skill（含 `team-reflect`） | 平台开发层 |
| 团队定义 | 本队岗位、Skill、业务脚本、项目扩展类、设置、`open.env`、平台反馈文件 | 团队自管理层 |
| 业务产物 | 游戏源码、资产、构建 | 团队执行层 |

问题按"必须修改哪个制品层"归属，与谁先发现无关。团队打在样板内部的补丁不算修复，是"样板不够用"的信号。

### 2.2 人与模拟用户

- 人不在三层之内：人给团队下目标，给平台开发层授权与纠偏。
- 观察者以用户身份和团队对话时，是平台开发层借用了人的通道。它给出的授权和产品判断都记入运行记录，人可以随时推翻（第 5.4 节）。
- **团队准备是唯一的例外**：迁移和建队时，观察者以管理员身份写团队定义；目标一旦下达，团队定义只归团队。

## 4. 开工时现状与证据（历史快照）

### 4.1 dev-2 与 Live

- `devctl.sh status`：lane `parity`，supervisor running，`up to date: yes`，`live:` 为空。各槽位的 `.dev-runtime/live/artifacts` 都是空的，Live 从没用过。
- `devctl.sh live` 用 `publish-component.mjs --commit --channel dev`，要求双仓干净、已按 HEAD 构建；首版 `0.0.1-dev.1`，之后递增；经 RPC 让已安装 daemon 取走，最多等 60 秒。槽位里有一个未跟踪文件，会被"双仓干净"拦下，需要先提交或移走。
- 内置 Skill 和团队样板编在 guest 里（`apps/daemon/build_support.rs` 以 `include_bytes!` 嵌入，`apps/guest` 依赖 `genet-daemon`），所以样板修复能走 Live；宿主、CLI 的修复要重新 `build` 并 `serve`。

问题不在系统权限，而在版本跟随。权限按 `macos-pitfalls.md` 的 SOP 处理即可：先签名再启动、先停 daemon 再换文件、不在已授权的真实程序上做实验、不为编译在真机上装 Rust。

## 5. 具体方案

### 5.1 观察者 Skill

位置 `genethub-spaces/skills/lifecycle/genethub-team-observer/`，挂载到 `dev-2`。

```text
genethub-team-observer/
  SKILL.md               输入、闭环环节、护栏、恢复与交接
  references/
    readiness.md         开工核对清单
    routing.md           分流规则、自愈时限、典型案例
    simulated-user.md    模拟用户的授权与产品判断依据
    acceptance.md        触发自检与第 3 节各旅程的验收
  scripts/
    observer.py          ready / wait / mark / report / slot（槽位 CLI 包装）
    test_observer.py     用固定团队快照测试核对、唤醒判断和分流
```

运行记录 `team-observer.json` 放在任务目录，生命周期仍由 `workflowctl.py` 管理：目标与预算、团队、已发消息编号、模拟用户决定、问题与路线、dev 版本与采用、Wait 节奏。换会话时按它接续，不重发已发出的消息。

### 5.2 持续在线：Wait

沿用 openplay 组长的做法，观察者在一个会话里不结束回合：

- `observer.py wait <秒数>` 前台等待，内部按不超过 60 秒的片段检查，外部工具调用遵守当前运行时的等待上限；逻辑等待最长 540 秒，收到 Human 输入立即返回。不得用一次不可中断的长工具调用阻断用户纠偏。
- 等待期间约每 60 秒做一次只读检查，不调用模型。下列情况提前返回，并写明变化：
  - 团队新增或更新了平台反馈文件；
  - 团队在等用户回答（前台提问、授权请求）；
  - 团队会话失败、暂停或长时间无进展；
  - 某支团队的分数卡新触发红线（评估提案 A-P2 之前用原型代算）；
  - daemon 或 Hub 的错误突增，或定时任务连续失败；
  - 某台机器离线，或运行的 guest 与本槽版本不一致；
  - 到了简报时间或预算截止时间。
- 每次返回附一行节奏：近一小时等待占比、无变化醒来次数。
- `observer.py mark start|brief|stop|resume` 记录开工、简报、停止和恢复；到预算截止就停，不自行延长。
- 单个会话的上下文会随着持续运行增长。超过阈值时，按运行记录交接给新会话，由新会话接着 Wait。

这样就不需要平台新增会话级定时原语，第一轮提案里的这项平台需求撤销。

### 5.4 模拟用户：授权与产品判断

观察者不等人，直接以用户身份回答团队：

- **依据**：用户下达目标时的原话；团队已有的目标文档与产品标准（例如 XWorld 的 `docs/team-goals.md`）；人此前的明确决定（例如"hy 太浪费时间"、Mac 优先）。依据不足时选保守的一方，并在简报里标明。
- **授权**：实验环境内的动作可按目标和预算决定，例如切模型、加并发、清理已可回收的工作树、重启本队远端岗位。第 5.8 节已有 Human 明确授权的一次性 Beta 停队、主队成果整理与 push 属于启动准备；其他会影响 Beta/Stable、Mac 上真实安装或用户真实数据的请求不在实验自主范围内。
- **产品判断**：用浏览器打开团队的可见成果（预览、截图、可玩版本），按目标给出具体反馈，例如"山门切片的远景层次不够，玩家看不出宗门规模"。不替团队改成果，也不教团队怎么做。
- **记账**：每个模拟决定写入运行记录的 `simulatedDecisions`，含理由和依据；区分正常产品决定、纠正、催促与救援，在 M3 中与真人输入分开。不能用观察者持续救援换来的低人工占用证明团队自愈；修复复验包含不追加救援的同类任务。人推翻的决定转为 `simulated-user.md` 的修订。
- **不透露内部信息**：发给团队的任务与体验反馈只取用户视角，消息里不写后台日志、内部文件路径、函数名、CLI 参数或会话编号。开发者可独立获取信息、发 dev、更新机器和观察重启，不能把诊断答案喂给团队或替它实现业务。消息保留 Agent/脚本来源，不伪造 Human 身份或原生权限批准。

### 5.5 分流、修复与门禁

- **分流**按第 2.1 节的制品层：平台内核、内置样板脚本，或内置 Skill 与反思流程。团队自己的问题先给自愈时限（两次反思周期或 4 小时，先到者为准）；红线阻断目标时可以提前判定，但要记理由。
- **修复**在 dev-2 的成对产品仓里按 `genethub-role-development` 进行：先写让问题出现的夹具，确认修复前失败、修复后通过。引导类修复写一个触发场景，说明期望团队怎样做。
- **门禁**（dev 不走 GitHub CI）：
  1. 受影响范围的 testctl 门禁通过：明确范围用 `dev-feedback`，跨模块用 `dev`；
  2. 按 `genethub-modify-review` 取得封印并提交到槽位分支；
  3. `devctl.sh build` 与 `identity` 通过。
- **成批发布**：多个修复合成一个 dev 版本，两次发布之间至少隔一次复验。

### 5.6 发布、采用与回退（只在 dev-2）

| 改动所在 | 本机 | Mac | 团队 |
| --- | --- | --- | --- |
| 内置样板、内置 Skill、daemon 逻辑（guest） | `devctl.sh live`，确认 `daemonVersion` 等于新版本 | 沿既有已授权入口下载本槽签名guest（以接收方 `completed` 和sha256为准）；ABI匹配时原子替换，由现有watcher采用；核对原生版本、运行摘要、设备身份及原任务恢复，不因每次更新主动停宿主 | 反思岗位按升级提醒合入；用 `run.py describe`、`drift` 确认 |
| 宿主、CLI | 重新 `build`，在没有在途关键操作时重启 `serve` | Linux构建不能当Mac原生载体；需要时取得已核实的Mac原生配套产物，先签名、核对既有授权与管理者，再在隔离实例更新并验收；没有目标候选则保留未覆盖，不笼统声称无法维护Mac | 同上 |

- **Mac 首次推送前**核对实际现装宿主与候选guest的ABI，不沿用初稿旧版本号。需要更换原生宿主时先验证目标平台及稳定签名、复用既有App授权，不在Mac上为此安装编译工具。

- **回退**：本机用 `devctl.sh reset live` 回到安装包里的 guest；Mac 恢复推送前保留的上一版文件；团队样板由团队按升级流程回退。
- 先分清控制进程与更新目标；任一已授权渠道的OS shell可维护目标，不再要求Human准备SSH/重登录。只有尚无任何可用渠道才需要首次登录安装。涉及宿主重启时核对在途工作与恢复通路；同ABI guest优先沿现有watcher更新。开发维护、版本采用、任务恢复与团队自主自愈分别记账。

### 5.7 与 Beta/Stable 的隔离

闭环只发 dev 版本，不合入主干，不发 Beta 和 Stable。剩下的风险来自共用的东西：

| 共用 | 风险 | 对策 |
| --- | --- | --- |
| 签名根（所有渠道共用，种子写在 `apps/host/src/keys.rs`） | 签名只保证内容完整；若有人用 `--channel beta` 签名，Beta 宿主会接受 | 观察者和推送脚本只允许 `--channel dev`。dev 签出的组件信封渠道为 `dev`，Beta、Stable 宿主核对渠道后会拒绝 |
| 发布代码 `publish-component.mjs`、`publisher/*.mjs` | 为 dev 改它，可能改坏 Beta 发布 | 闭环不修改发布代码；确需修改时单独立项，合入前在 `release-beta` 用 `--plan` 复核 |
| Mac 上真实的 Beta/Stable | 推送或重启误伤 | 只操作 `com.genethub.dev2.multimachine` 和 `~/GeneHub/dev-2-multimachine` |
| Mac 的浏览器采集和 Blender（XWorld 约定浏览器并发每队不超过 2 路） | 多队岗位互相抢占 | 开始切换先停止 Beta 两队；新队各用自己的岗位安装与运行目录，并按机器总容量分配并发 |
| team 与项目共同 remote | 实验队写错主线、其他队引用或同名标签 | team 用 `exp_<name>`；项目用 `exp_<name>/integration` 与 `exp_<name>/<岗位>/<任务ID>`；推送明确引用，远程标签按队命名 |
| 本机 CPU 与磁盘（`/data` 已用 77%） | 拖慢 Beta 的发布与运行 | 迁移不复制工作树；构建避开 Beta 发布时段 |

**步骤与完成边界**：

5. **新建项目起点**：两个项目检出均从共同 remote 的同一 `projectBaseSha` 建 `exp_<name>/integration`。新任务从本队明确提交开 `exp_<name>/<岗位>/<任务ID>`；执行者负责自己的工位和提交。旧 Skill、宪章与脚本中写死 `main`、`int/map` 或裸岗位前缀的内容必须随新队约定更新，不能只改一份分支说明。
6. **初始化运行与资产**：不复制旧会话、任务账本、派单、回执、写锁、timer 或 Git worktree 元数据。只复制业务实际引用的非 Git 素材，记录来源和摘要；新队看板、评分、反馈和发布运行目录从新实例开始。可共享只读缓存，可变输出与入口分别归队。旧数据不作为新队改善证据。
7. **安装远端岗位**：按现有官方 `employee sync` 流程，为每队的 qa、map-integrator 分别绑定并安装自己的执行副本；Mac 目标从实际目录核对，旧候选为 `mch_ZPK9UJkCq-Q5`，不可仅凭历史 ID 操作。远端项目也用共同 remote、本队基线和约定提交分支，不 clone 可写的团队定义源替代安装。
8. **逐队验收**：每队可见、前台可对话、模型与实际安装身份正确；各跑本队的一条“派单 → 远端执行 → 如有代码则提交 push → 原任务回传 → 本队集成 → 实际产物/预览验收 → 结算释放”链路。QA 对固定提交或制品操作。迁移成功要同时满足两队验收及 Beta 两队仍停止。

准备和重试按任务记录核对已完成动作，已有引用或回执先比对，不重复 push、建队或安装。旧 `clone_exp.py` 的独立 bare remote、`push --mirror` 和 `rewind_exp.py` 强推旧 `int/map` 的路径不适用于本合同。重新实验在保留已有证据后按明确任务重开，不通过强推共享引用抹掉历史。
