# GeneHub 产品工程引导

> 角色：说明**方案该长什么形状**。在技术方案成形的过程中阅读，是落地前的门禁。<br>
> 配套规范：[《GeneHub 产品工程律法》](./engineering-laws.md)说明实现时不能做什么，是提交合并前的门禁。<br>
> 上游：下面第 0 节的四条边界判据；[architecture.md](./architecture.md) 的 B1–B5 是本文引用的技术边界。<br>
> 适用范围：本仓的产品代码、协议、部署与产品文档。测试工程另有细化，见下文 `G11`。<br>
> 执行要求：**动手写代码之前**完整阅读本文，并按「方案门清单」产出方案声明；范围变化时重新过一遍。

产品工程的价值不是把需求实现出来，而是让每一次实现都落在同一组边界内，使得下一次改动仍然便宜。

本文只回答"该往哪走"。禁止项与零容忍边界只写入配套律法，不在本文复制第二份。所有条目使用永久
ID `Gxx`。

## 0. 四条边界判据

这四条排在所有条目之前，因为它们是**否决权**：命中任意一条的方案不进入实现，无论其余条目答得多好。

| 判据 | 否决什么 |
| --- | --- |
| **资产不动** | 任何要求把用户作品或密钥搬离用户设备的方案 |
| **多机是常态** | 任何把本机当唯一一等目标、把远程当降级模式的方案 |
| **Agent 可替换** | 任何让内核认识具体 agent 的方案 |
| **会话跟着人** | 任何把会话绑在某个窗口、某条连接或某台客户端上的方案 |

第四条管的是**人离开、断网、换设备**这三件事。软件升级时打断正在进行的那一轮是可以接受的，只要用户
看得见发生了什么、状态可恢复；不要为它设计额外机制。

这四条是产品承诺在工程侧的同义投影，措辞与运营侧的产品愿景文档保持一致。本仓不引用那份文档——
外部贡献者只需要本文就能判断一个方案能不能做。

## 引导 Checklist

### G01. 边界先于功能

先写下这次不可让步的边界，再推导取舍。[architecture.md](./architecture.md) §2 的 B1–B5 是范本：
五条边界在前，后面所有设计都是它们的推论。

方案要指明本次触达哪些既有边界、为什么不违反；确实需要移动边界时，先改
[architecture.md](./architecture.md)，再谈实现。**不允许在实现里悄悄移动边界，然后回写文档。**

### G02. 抽象必须被第二个实现证伪

只有一个调用方时写出来的"抽象层"，形状必然就是那个调用方。方案里必须指出第二个形状是什么，以及
它什么时候接进来。

如果答案是"以后再说"，那这次就不要引入抽象层，直接写具体实现——两个具体实现比一个假抽象便宜。

### G03. 协议只有一处定义

新字段只能进 `packages/proto`，由它生成两端类型。方案若涉及跨仓副本（如 Relay 与 Cloud 共享的
Fabric wire），必须同时给出逐字比对 gate，不能靠"记得两边一起改"。

协议变更还要回答兼容窗口：新旧两端在同一时刻分别是什么版本，哪一侧先发。

### G04. 默认走高频通道

方案的默认假设是：这次变化只更新 `genehub_guest.wasm` 与官网。要动 WIT、host/Wasmtime、CLI 生命周期、
desktop OS 壳、安装器或签名根，必须在方案里显式声明进入完整模式并说明为什么——那条路径的目标占比
不超过 5%（[architecture.md](./architecture.md) B5）。

声明的模式会被交付分类器核对；漏标按 fail closed 处理。**声明发生在动手之前，不是事后从 diff 反推。**

### G05. 多机是默认假设

设计任何能力，先回答"用户有两台机器时它长什么样"。

三个必答问题：这个能力属于某一台机器还是属于用户？跨机时谁是事实来源？远端不可达时降级成什么？
把"本机"当成唯一一等目标、把远程当降级模式的方案，按第 0 节第二条判据否决。

### G06. 带宽优先

新能力要回答"人的输入输出动作减少了多少"，而不只是"多了什么功能"。

人机协作里有四类固定消耗：把体验翻译成文字、用语言描述屏幕上的位置、人不在场时的决定等待、人工调度。
模型再强一倍，这四类消耗一点都不会少。一个只增加功能面但不减少这四类消耗的方案，优先级默认低于减少
它们的方案。

### G07. 能力靠声明，不靠试错

先定义 `Capabilities` 位，再设计界面。前端要在按钮渲染之前就知道这个 agent 能不能切模型，而不是
点了才报错。

同理，模型、思考强度、模式、以及 agent 自报的额外运行轴是各自独立的轴，一条轴表达一件事，不要
合并进同一个字段或字符串。

### G08. 不可信输入在方案里定级

预览内容、第三方 agent 输出、用户提供的 HTML、外部文件——凡是要进入 Agent 上下文或产品渲染路径的
外来数据，方案必须回答三件事：

1. **来源标记**：它进入上下文时如何被标注为不可信，Agent 凭什么不把它当指令；
2. **形状约束**：是带 schema 的枚举事件，还是自由文本（默认应为前者）；
3. **限额**：速率、体积、并发上限，以及超限时的行为。

回答不了这三条的方案不能进实现。这一条是"作品即界面"这条产品曲线的安全前提：一旦预览内容能向
Agent 回话，不可信的 HTML 就获得了一条对 Agent 说话的通道。

### G09. 遥测与功能同批设计

可观测点和功能一起进方案，不留作后续任务。方案要指明本次新增哪些可测量事实，以及它们支撑哪条 SLO
或哪个产品指标。

"先做功能，观测以后补"的结果是永远没有观测——[roadmap.md](./roadmap.md) 里 SLO telemetry 长期为
"不存在"就是这条缺失的代价。

### G10. 不做清单是方案的一部分

方案必须写明本次明确不做什么。这一条比它看起来重要：它是后续讨论的锚点，也是验收范围的边界。

推翻既有决策时，记录**顺序与理由**，不只记结论。一份好的推翻记录会写清"最早的结论是什么、当时的理由
错在哪、现在的结论和理由分别是什么"——只记结论的话，同一个方案会被第三次提出来。

### G11. 测试形状在方案期定下

按 [testing.md](./testing.md) 声明本次的目标、oracle、真实组件边界与 mock 边界，以及新增或受影响的
case 层级与门禁。测试工程另有一份带永久 ID 的理念与律法（`P01–P13`），与测试基建同仓维护；写测试的
任务以那两份为准，本文只要求方案期把测试形状定下来。

缺少可观察边界时，先界定独立的产品接口任务：生产接口必须有明确 owner、稳定入口、真实产品消费者，
能独立 build/typecheck 并通过真实 artifact smoke。不要把测试内部 helper、相对源码 import 或类型投影
当成"已有接口"。

## 方案门清单

进入实现之前产出下列声明，它们同时是工作流 `plan-ready` 转换的证据：

| 声明 | 内容 |
| --- | --- |
| `guidance_digest` | 本文与配套律法的 Git blob digest |
| `promise_check` | 本次触达第 0 节哪几条判据，为什么不触发对应否决 |
| `boundary_impact` | 触达哪些 B1–B5 边界；是否需要移动边界 |
| `delivery_mode` | `guest-only` 或 `full`；选 `full` 要给理由（`G04`） |
| `second_shape` | 若引入抽象，第二个实现形状是什么（`G02`） |
| `untrusted_input` | 若有外来数据，`G08` 三问的答案 |
| `observability` | 本次新增的可测量事实（`G09`） |
| `not_doing` | 明确不做清单（`G10`） |
| `oracle` | 验证方式、真实组件与 mock 边界（`G11`） |

对 `G01–G11` 逐项标记 `适用` 或 `不适用`，`不适用` 要给理由。任何一项无法回答时，方案没有成形，
不能进入实现。

## 条目管理

- `Gxx` 永久稳定，不因排序或删除而重编号，也不复用已退役 ID；
- 一个条目只表达一个正向设计判据；禁止项移入[律法](./engineering-laws.md)；
- 新条目追加新 ID；被替代条目标记 `superseded by Gxx`，保留历史可追溯性；
- 修改本文使用独立治理提交，说明原因、受影响的方案门与 Skill；
- 本文与律法的组合 digest 是执行版本，任务记录保存该 digest；
- Skill、CI 与其他文档只引用 ID 与链接，不复制条目正文。
