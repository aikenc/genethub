## 目标与唯一验收

**改进平台与内置团队样板，使 XWorld-ds、XWorld-hy 两个团队的团队工作质量分都达到 80。**

这是本阶段唯一的验收。建队、构建成功、dev 发布、团队在线、项目成果都不是完成证据。

## 两种质量分开

| | 团队工作质量 | 项目成果质量 |
| --- | --- | --- |
| 衡量 | 团队协作接力得好不好 | 做出来的东西好不好 |
| 口径 | 本文“评分口径”一节，只有这一个分数 | 项目自己定义（XWorld 为 Demo / 切片 / 成品） |
| 负责 | 平台开发：改平台和内置样板 | 团队自己 |
| 地位 | 唯一验收 | 实验方向，不是死目标 |

项目需求是评分的负载：工作质量必须在真实、有难度的需求下达到 80。团队无事可做时红线自然为零，
那样的分数没有意义。

## 评分口径

- 模型：[tq/1 草案](team-work-quality-model-proposal.md)第 5.2～5.4 节的
  R1～R5 红线、M1～M6 主指标与锚点；分数 = 基础分 − 50 × 触发的红线类数，最低 0。
- 新增红线 **R6 并行不足**：团队有未完成的用户目标期间，有效在途工作项按时间加权，小时均值低于 2。
  - 只计有开工事件且最终有结论的工作项；硬拆或空派会在 M1 返工、M5 空转上反向扣分。
  - 等待用户回答、用户暂停期间不计。只剩串行工作不豁免：能否拆出可并行工作本身是团队能力。
- 只有一个团队工作质量分，项目成果不计入。
- **达到 80 的判定**：截止前，任意连续 3 张小时卡都是正式分（已知权重 ≥80%、R1～R6 全部可判、
  已闭环工作项 ≥20）且 ≥80。窗口可以跨越多个 dev 版本，每张卡记录当时采用的样板与平台版本。
- 同一账本重算结果逐字节一致；数据缺失记未知，不记 0。两队从新建后建立各自基线，不把旧账本
  未迁入造成的红线消失当作改善。

## 平台开发怎么推进

1. **先让分数可判定。** 现状只有只读原型，覆盖 30% 权重，R4、R5、M1、M2 算不出；Beta XWorld 24 小时
   原型触发 R1/R2/R3，为 0 分。先把评分器做进内置样板按小时出卡，补齐缺失的过程事件。
2. **再按失分修平台。** 按“离 80 分的差距 × 权重”看失分去向：团队能自己改的交给反思岗位；内核、
   样板或公共 Skill 的缺陷由平台修。
3. **随时发布 dev 迭代。** 发布频率不受限制，发布不重置评分窗口；新版本引入的红线如实计分。
   每项修复说明通用根因，附一个非本项目夹具（换掉 XWorld 仍成立），团队采用后在卡上看到效果。
4. **反思岗位读卡自主改进。** 样板让反思简报带上最新卡和失分账单；改 workflow 还是知识库、怎么改，
   由团队自己决定，平台不规定改进格式。

## 用户视角的需求

- 平台开发只以用户身份提业务需求和体验反馈，每队每滚动小时最多 3 条、流程类最多 1 条（`observer.py pace`）。
- 方向是团队按自己的定义把项目做到切片级别；达到后继续提更高复杂度的需求，没达到如实记差距。
- 不催办、不指定岗位分工、不给根因或修法，不写团队仓和项目仓。

## 现有机制与缺口

| 能力 | 样板已有 | 缺口 |
| --- | --- | --- |
| 评分 | 无（仅 `docs/evidence/team-work-quality-20261110/prototype_score.py`） | 评分器进样板、按小时出卡 |
| 过程事件 | 任务账本有派出、结束时间；`finish` 带自由文本证据 | 开工、送达、读入、停摆、资源归还事件；`--follows`、`--standing` |
| 并行 | `TEAM_MAX_ACTIVE_SESSIONS` 上限 | 在途工作项度量（R6 依赖开工事件） |
| 改进闭环 | `team-reflect` 二级记忆、自主改 Skill、`run.py feedback` 与复验 | 反思简报读不到质量卡和失分账单 |
| 成果展示 | 看板里程碑、可玩版本、QA 报告与截图 | 属于项目，平台不加阶段合同 |
