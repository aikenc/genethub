# GeneHub 产品工程律法

> 角色：说明实现时**不能做什么、必须做到什么**。在落地过程中阅读，提交合并前强制门禁化。<br>
> 配套规范：[《GeneHub 产品工程引导》](./engineering-guidance.md)说明方案该长什么形状，是落地前的门禁。<br>
> 上游：[engineering-guidance.md](./engineering-guidance.md) §0 的四条边界判据、
> [architecture.md](./architecture.md) 的 B1–B5。<br>
> 适用范围：本仓的产品代码、协议、部署与对外文案；Cloud 侧的部署与许可条款另有 overlay。
> 测试工程另有配套律法，见 `L09`。<br>
> 执行要求：实现期随时可查；提交或合并前逐条对照，任何一条不满足即**不得**形成提交候选。

律法与引导的区别是判定方式：律法能对着 diff、CI 结果或运行产物判定真假。**判定不了真假的条目不属于
本文**，它属于引导。

所有条目使用永久 ID `Lxx`。每条必须有执行点——**指不到执行点的条目还不成立为律法**，这条对本文
自身同样适用（见「执行点缺口」）。

## 律法 Checklist

### L01. 内核不得按具体 agent 名字分支

daemon 业务代码里不允许出现 `if agent == "genet"` 这类判断。具体 agent 的知识只能存在于它自己的
adapter 文件里。内置 Agent 不享受任何例外。

**执行点**：静态检查 + 变更审查清单。

### L02. 不得把某个 agent 的原始事件当作产品协议

daemon 不得直接转发某个 agent 的线格式。每个 adapter 负责翻译成 `packages/proto` 定义的归一化
`TimelineItem` / `SessionEvent`，前端只认这一套。

session 边界之后只保留 `Overview` 形状，裁剪规则见 [architecture.md](./architecture.md) §4。

**执行点**：变更审查清单 + 协议序列化测试。

### L03. relay 不得理解它搬运的东西

三条同时成立：`forward/` 只准 import `contract/` 与 `shared/`；数据路径上不得出现 `JSON.parse` /
`JSON.stringify`；`package.json` 不得有任何数据库依赖。

**执行点**：`apps/relay/test/boundaries.test.ts`（已存在）。

### L04. 不得丢事件

未见过的工具类型必须走 `Unknown` 兜底渲染，不白屏、不静默丢弃。新 agent 冒出没见过的形状时，产品
仍要能展示。

**执行点**：testctl specialty。

### L05. 不得静默失败

RPC 必须返回结构合法的响应，包括"不支持"也要显式回答。不允许挂起等对端超时。

错误必须可操作：连接未配对、设备离线、身份不一致、版本不兼容要用各自的错误，不得伪装成"文件不存在"
这类邻近错误。

**执行点**：testctl journey + 协议测试。

### L06. 不得声称未验证的属性

对外文案（README、官网、界面文字、发布说明）中每一句安全、性能、可用性声明，必须指向
[roadmap.md](./roadmap.md) 的一个状态项或一个 case ID。

具体到当前：Relay 单独不具备业务内容密钥、数据面不解析也不落库——这句可以说；平台技术上无法查看
或冒充端点——**不能说**，托管 Control 仍生成对称 peer secret。95%、分钟级、秒级在测量系统建立之前
一律称"目标"。

**执行点**：变更审查清单；建立文案-证据矩阵后可机械化。

### L08. 不得保留原生业务回退路径

产品运行时只有 WASM guest。缺 host、缺 `genehub_guest.wasm`、或二者 WIT 摘要对不上时，在 instantiate
之前失败；不得改跑原生业务二进制，也不得把原生路径当兼容层保留。

**执行点**：host/guest ABI 门（已存在）。

### L09. 不得把测试内部构造当成生产接口

测试内部 helper、相对源码 import、生成的类型投影都不是生产接口。生产接口必须有明确 owner、稳定入口、
被真实产品消费者使用，能独立 build/typecheck，并通过真实 artifact smoke。

细化条款见测试工程的理念 `P11` 与配套律法，它们与测试基建同仓维护。

**执行点**：测试工程律法门 + testctl layer lint。

### L10. 安装包不得分发 AGPL 与闭源的 combined work

官方安装包与开源安装包装的是同一份 `packages/workbench` 构建产物，差别只有构建期常量与 CSP。账号形状的
闭源页面不得编译进随包分发的 bundle。

**执行点**：打包脚本校验 + 变更审查清单。

### L11. 撤销必须本地即时生效

设备撤销由 daemon 本地判定并立即断连，不得依赖控制面推送成功、不得等待轮询周期。控制面宕机或被
攻破都不影响已授权设备的撤销。

**执行点**：自建全栈用例。

### L12. 不得把 blocked / unstable 解释成 passed

测试结果只按 runner 给出的状态解释。缺失证据、跳过、不稳定都不是通过；不得为了让门变绿而重写或
削弱 gate。

**执行点**：testctl gate。

## 提交前对照

提交或合并前对每个 `Lxx` 回答：

- `符合`：给出代码、case、run 或产物证据；
- `不适用`：说明为什么本次变更不触达该条；
- `阻断`：不得作为提交候选，回到实现阶段。

机器检查不替代这部分工程判断。任何 `阻断` 必须回到实现，不得以"后续任务处理"带过。

## 执行点缺口

本文要求每条律法都指到执行点。当前不满足这一要求的条目列在这里，它们同时是待建的机械门：

| 条目 | 缺口 | 补齐方式 |
| --- | --- | --- |
| `L06` | 只有人工审查，没有文案-证据矩阵 | 建立声明清单，每条绑定状态项或 case ID |
| `L01` | 只有审查清单，没有静态检查 | 对 daemon 业务模块加 agent 名字字面量检查 |

缺口存在期间，对应条目仍然有效并由审查执行；**缺口不是豁免**。

## 条目管理

- `Lxx` 永久稳定，不因排序或删除而重编号，也不复用已退役 ID；
- `L07`（活动 turn/PTY 连续性）在首次生效前撤回：升级或切换时打断进行中的一轮是可接受的，只要用户
  看得见且状态可恢复，按最低成本处理，不设律法也不设专项。ID 不复用；
- 一个条目只表达一个可判定的禁令或硬性要求；正向判据移入[引导](./engineering-guidance.md)；
- 新条目追加新 ID 并同时声明执行点；被替代条目标记 `superseded by Lxx`；
- 修改本文使用独立治理提交，说明原因、受影响的门禁与 Skill；
- 本文与引导的组合 digest 是执行版本，任务记录保存该 digest；
- Skill、CI 与其他文档只引用 ID 与链接，不复制条目正文。
