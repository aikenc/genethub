**1. 背景：用户想让多台机器共同工作，发现入口却让 Agent 判断“没有机器”。**

GeneHub 的目标使用方式是：用户向一个会话交代工作，由它找到持有代码、GPU 或其他资源的机器，把任务派过去，并把结果交回来。用户不需要先知道任务会经过哪种连接方式，也不应该因为不知道一个额外选项而被告知没有机器。

这里有四个需要区分的对象：机器是执行和保存数据的设备；workspace 是该机器上登记的工作目录或 Space；会话在其所属机器上运行和保存；团队是用户拥有的 Space 树及协作脚本。平台提供跨机原语，团队样板负责岗位选择、并发、待办和结果接力。平台能远程运行命令，不等于团队样板已经能可靠地跨机协作。

本次讨论中的两种连接来源是：本地直连配对库，以及本机 daemon 根据当前身份取得的 Hub 机器目录。现在的 `machine list` 默认只读前者，而日常机群主要由后者发现。底层执行却已经能够尝试直连或 Hub。这使发现入口和实际执行回答了不同的问题。

业务经过如下：用户要求排查开发机群中的协作摩擦，随后指定 dev-2 改进。上一轮在该槽位提交了跨机 `spawn/send`，同时给空机器列表增加提示。用户进一步指出：既然目的是找机器，为何默认命令仍然不查询完整目录？这暴露了先迁就局部实现、后补提示的设计问题。

| E4 | [team.py](../apps/daemon/builtin-skills/genehub/references/team-template/tools/team.py) 的 `remote_role_workspace` 只匹配名字或目录名，不核验团队；显式 workspace 直接返回 | 远端只有另一团队的 `qa` 时会选中它 |
| E5 | 同一脚本 `choose` 在跨机分支前应用本机模型覆盖；跨机默认分支未验证 `media` | 本机模型 ID 被发送到远端，视频任务可能选到不具备视频能力的模型 |
| E6 | 同一脚本 `reconcile` 遇到非 `targetNotFound` 错误直接抛出 | 一台远端连接失败，后续本地与远端记录都停止本轮对账 |
| E7 | 同一脚本借助本机 `os.path.realpath/basename` 解析远端根路径 | Linux 发起方不能正确提取 Windows 路径末尾的岗位名 |
| E8 | 同一脚本 `cmd_spawn` 跨机时跳过 `claim`，将 `lock` 留空 | 没有目标端写入互斥，重复派单可能同时修改同一目录 |
| E9 | 同一脚本 `notice` 在跨机 `unpause=True` 时去掉 `--system`；[inbox.rs](../apps/daemon/src/session/inbox.rs) 接收普通对话输入时清除暂停 | 普通跨机投递可能恢复用户主动停止的会话 |
| E10 | [query.rs](../apps/daemon/src/cli_front/query.rs) 的 capabilities 与 command schema 分别维护 `requiresDaemon` | Agent 发现到的前置条件互相矛盾 |

模拟输入举例：远端 workspace 列表只有 `/teams/other-team/spaces/qa` 时，`remote_role_workspace(machine, "qa")` 返回该 workspace；本机配置 `TEAM_MODEL_WORK=local-only-model` 时，跨机 `choose` 仍返回该模型；首条远端记录抛出 `relayUnavailable` 时，后面的本地记录没有被查询。

现有提交做对了远端选择器传递、按机器区分查询缓存、在待办中记录机器，以及从远端读取最终回复。这些可以保留。需要纠正的是把“每次调用都带了选择器”当成“整条团队工作流已经正确”。

**3. 用户场景与目标：每一项改动必须改善一段可观察的操作。**

| 场景 | 当前行为 | 目标行为 |
| --- | --- | --- |
| 用户说“看看有哪些机器可以安排工作” | Agent 查默认列表，得到空结果后停止或要求配对 | 默认一次查询发现当前身份可见的目录，并正确解释在线与连接权限 |
| 用户说“让另一台机器的 QA 检查本项目” | 按通用岗位名猜目标，可能命中别的项目 | 使用已登记的本项目目标；没有明确目标时给出候选，不创建会话 |
| 两个任务同时交给同一远端开发岗位 | 两个会话可能进入同一写目录 | 获得独占目录或隔离 worktree；没有可用执行目录则明确拒绝 |
| 用户停止远端任务，随后又到达后台通知 | 投递可能自动解除暂停 | 通知保留，用户停止继续有效；只有明确的继续执行操作才能恢复 |
| 一台机器掉线，其他任务已完成 | 对账遇到异常退出，已完成结果也可能延迟 | 该机器任务保留为待恢复，其余结果正常交付 |
| 派发成功后发起方在收到响应前断线 | 重试可能再次创建会话 | 通过任务 ID 和回执确认是否已接单，避免重复执行 |

本期不改变设备授权模型，不建设新的中央团队调度服务，不自动把项目复制到空闲机器，也不把在线机器视为已安装好岗位。首帧看门狗、事件泵丢事件和其他 daemon 性能问题另案处理。

**4. 平台修改：统一机器目录，并让失败说明真实原因。**

推荐把现有 `reachable` 的目录合并能力提升为默认，并抽出供列表和详情共用的目录解析器。连接建立继续复用既有选择流程，不在列目录时逐台探测或申请连接票据。

| 拟议命令 | 行为 | daemon 依赖 |
| --- | --- | --- |
| `machine list` | 本机、直连配对、当前身份 Hub 目录合并 | 需要本机 daemon；Hub 明确未加入时返回本机与直连记录 |
| `machine list --reachable` | 兼容旧命令，等同默认列表 | 同上 |
| `machine list --paired` | 只读直连库，空列表仅表示没有直连记录 | 不依赖 daemon |
| `machine show <ID>` | 用同一目录解析器查详情，不主动连接目标 | 需要本机 daemon |
| `machine show <ID> --paired` | 查看指定直连记录，供离线诊断 | 不依赖 daemon |

`--paired` 与 `--reachable` 同时提供时返回参数错误。选择器仍只接受机器精确 ID；同名机器保留为不同条目。

合并时按 ID 去重，Hub 显示名优先；保留 `sources` 多来源信息。已有 `source` 字段继续保留，表示主要展示来源，避免突然破坏读取它的脚本。`online` 为 `true/false/null`，仅表达在线报告；本机条目标记 `local: true`。保留旧 `scope: reachable` 以兼容消费者，文档明确它是历史名称，不代表逐台连接成功。

成功输出沿用 `genet.cli/v1` 的 envelope，增加明确的完整性与来源信息。以下为拟议数据形状：

```json
{
  "scope": "reachable",
  "complete": true,
  "machines": [
    {
      "machineId": "mch_example",
      "name": "workstation",
      "local": false,
      "online": true,
      "source": "hub",
      "sources": ["paired", "hub"]
    }
  ]
}
```

“目录可见”“机器在线”“实际连接及权限”分开解释。`machine list/show` 只处理前两者；实际连接由现有 `context --machine` 验证。目录发现使用既有只读能力；不放宽取票、执行、文件或设置权限。

Hub 故障、权限拒绝或状态未就绪时，默认查询返回标准错误 envelope 和非零退出码，错误详情携带 `complete: false`、已知目录条目、失败来源和原始错误码。没有成功响应中静默混入不完整列表；调用方可以展示已知条目，但不能据此断言目录完整。明确未加入 Hub 属于正常状态，不能与 Hub 暂时不可用混淆。

配对库只有 `NotFound` 视为空；其他读取错误保留具体原因。票据申请错误保留可识别的上游错误信息；只有确认的授权拒绝才归类为授权问题，不靠错误文本猜测。服务端若只返回通用失败，报告票据申请失败和阶段，不臆断“目标离线”或“没有配对”。

`machine forget` 保持只删除本地直连凭证的语义，输出明确提示 Hub 发现结果可能仍存在；它不表示撤销远端授权。帮助、schema、capabilities 和 Skill 同步说明默认目录及 `--paired` 的不同前置条件。

**5. 团队修改：用明确的执行目标，替代按名字猜另一台机器上的岗位。**

团队配置中增加可选的远端目标记录。下面是结构示意，最终文件位置应沿用团队现有的自有配置方式，不能写入生成的 `AGENTS.md` 或用户凭证文件：

```json
{
  "remoteTargets": {
    "qa": {
      "machineId": "mch_example",
      "workspaceId": "w_example",
      "expectedRole": "qa",
      "expectedTeamRoot": "/teams/project-a",
      "mode": "read-only"
    }
  }
}
```

该记录是调度目标声明，不是授权白名单。登记时读取目标 workspace，展示其所属机器、根目录、父空间及岗位供确认。运行前复核登记事实；仅有同名岗位不足以证明归属。显式 workspace 也要验证存在且符合声明，不能直接绕过检查。

远端未登记、岗位归属无法核验或同名候选冲突时，返回可操作的候选与缺项，不创建会话。跨团队协作允许显式登记目标，不能把另一团队的岗位自动解释为本团队。目录展示名变化不使绑定失效，机器或 workspace 被替换则需重新确认。

岗位路径使用目标端提供的结构化信息；必要的路径规范化在目标系统完成，不能在发起方对远端路径调用本机 `realpath`。

目标端模型选择只使用目标端可用路由。显式档位及媒体需求在目标端验证；未指定模型时使用目标端有效默认。显式模型必须在目标端存在且满足媒体需求。本机 `TEAM_AGENT`、`TEAM_MODEL_WORK/RESEARCH` 不再隐式控制远端；需要指定目标 Agent 时放在目标记录或显式请求中并验证。

读写类型必须明确。上例 `read-only` 不只是提示词标签：接单前检查目标执行方式能否落实只读边界，不能保证时拒绝以只读承诺启动。写任务则必须经过下一节的目标端互斥。

**6. 执行与恢复：总账在发起方，目录互斥和接单回执在执行方。**

发起方负责任务意图、父子关系和最终通知；执行方负责本机目录分配、锁、会话与执行回执。两者通过稳定 `taskId` 和任务内容摘要关联。已有 `--message-id` 继续用于相同会话中的消息去重；不能据此推定跨会话创建天然幂等。

拟议派发顺序：

1. 发起方先原子保存任务意图、目标、内容摘要及 `taskId`，再发起请求。
2. 目标端接单逻辑先登记回执，核验目标及能力，取得目录或 worktree；同一 ID、相同内容返回已有状态，不新建会话。同一 ID、不同内容明确拒绝。
3. 创建会话后记录其 ID；响应丢失时先按回执恢复。处于“可能已创建但未记下会话”的窗口，必须用稳定关联标识找回或停止重试，不能盲目重建。
4. 发起方记录接单回执后结束本轮，由现有定时对账继续推进。
5. 结果先持久化，再向发起会话投递带稳定 ID 的完成通知；取得投递回执后归档交付记录。

拟议任务阶段为 `prepared → accepted → running → result-ready → delivered`；`paused`、`failed`、`cancelled` 单独记录。连接不可达是“状态暂不可观测”，不能替代执行阶段或直接生成失败终态。

目标端复用现有写者锁、worktree 及原子文件写入机制。写任务取得独占目录；同一岗位的并发任务使用隔离 worktree，没有可用目录就拒绝。锁带任务与会话归属，恢复时先核验会话和执行状态；单纯心跳超时不足以证明可以释放锁，因为断网期间旧任务可能仍在运行。

对账对每条记录独立捕获连接错误，对异常机器退避并保留任务，其余记录继续处理；给远端查询设置预算，避免一个慢查询占满整次 hook。相同故障状态变化时报告，避免每五秒重复提醒。

消息默认仍走不解除暂停的系统通知；去掉跨机专有的自动恢复分支。恢复执行必须走明确的继续执行请求，并保留 Agent 来源。用户主动停止的任务不自动重派；执行失败可以报告或按任务策略恢复，但不可伪装成人的批准。

结果交接同时包含产物身份。代码结果包含仓库、分支、提交和验证摘要；文件结果包含所属机器、源路径及校验信息，复用现有文件下载能力取回。发起方只把真实存在的本地文件作为预览链接，不能把远端绝对路径当成本地链接。

目标端接单逻辑先在样板层设计，不新增平台中央团队服务。其调用路径必须验证能保留现有授权和来源归属；不能通过任意远端脚本改用目标机器的更高权限。若既有原语不能完成可靠接单关联，先给出最小平台合同补充及验证，再实施该阶段。

cloud 仓本轮不预设需要改动。若验证发现 Hub 响应缺少必要的故障类型，再单独提出最小接口变更；不得夹带既有脏改动。测试工程的具体文件选择遵守 dev-2 已选测试 Skill 和工程规则，不在本提案中复制门禁命令。

**8. 替代方案与代价：避免为了消除一个选项而建设整套新平台。**

| 方案 | 优点 | 代价或缺陷 | 建议 |
| --- | --- | --- | --- |
| 保留默认列表，仅加提示 | 改动最小 | 默认答案仍然不完整；直连库非空时甚至没有提示 | 不采用 |
| 简单让默认调用现有 `reachable` | 快速解决空列表主诉求 | 详情、读取错误、来源覆盖、合同与离线行为仍不一致 | 作为 A 的起点，补齐这些合同后交付 |
| 默认逐台连接探测 | 能获得当时的连接结果 | 目录延迟随机器数增长，且可能触发票据权限请求 | 不采用，连接核验继续显式执行 |
| 会话留在本机，仅用远端工具 | 可复用现有本机团队接力 | Agent 进程仍占本机，不能替代需要远端 Agent 环境的任务 | 保留为受限条件下的可用路径 |
| 直接保留候选里的跨机 `spawn/send` | 已有代码可用作原型 | 尚缺目标归属、写入互斥和恢复保证 | 修正 B/C 后再开放 |
| 新建平台中央团队调度器 | 可集中协调 | 与团队归用户的现有架构冲突，影响和迁移面显著扩大 | 本期不采用 |

默认目录需要本机 daemon，会改变原来可离线读配对库的操作；新增 `--paired` 明确保留这条排障路径。目标登记增加少量初始化工作，换来不误派项目。执行回执和目录隔离增加状态及磁盘管理成本，因此 C 必须有故障验证，不能靠一段提示词声称支持。

**9. 验收：观察真实目标和最终状态，不只检查命令参数。**

| 编号 | 输入或故障 | 必须观察的结果 |
| --- | --- | --- |
| T1 | 直连库为空，Hub 有机器 | 默认列表包含 Hub 条目；`show` 可查询同一 ID |
| T2 | 直连与 Hub 含同一 ID；另有同名不同 ID | 同 ID 合并且保留来源；同名不同 ID 不合并、不猜选择器 |
| T3 | 无 daemon、Hub 未加入、Hub 超时、直连库无权限，分别执行 | 结果正确区分；`--paired` 可独立工作；读取失败不伪装为空 |
| T4 | 取票授权拒绝与服务失败 | 错误阶段、原因与重试含义正确；不建议无关的重新配对 |
| T5 | 本项目未登记远端；仅另一项目有同名 `qa` | 不创建任何会话，列出候选或缺少的目标声明 |
| T6 | 远端 ID 无效、岗位改变或 Windows 路径 | 拒绝失效绑定；合法跨系统绑定可用，不依赖发起方路径解析 |
| T7 | 本机有模型覆盖；远端无该模型；任务需视频 | 不继承本机覆盖；能力不满足时不创建执行会话 |
| T8 | 同一远端目录同时派两个写任务 | 获得两个隔离目录，或第二个被拒；不存在两个写者共享目录 |
| T9 | 用户暂停远端后到达系统通知 | 暂停仍有效，通知不丢；明确继续执行后才恢复 |
| T10 | 一台远端不可达，另有本地及远端已完成任务 | 不可达任务保留且退避，其余结果本轮可交付 |
| T11 | 接单或创建后响应丢失；两端分别重启 | 同任务恢复同一执行关联；无法确认时不重复创建 |
| T12 | 结果已保存、完成通知回执丢失 | 同 ID 重投最终只交付一次，产物仍可取得 |

平台回归验证目录和错误合同；样板故障注入验证状态、锁和消息；真实双机验收在专用测试 Space 完成从派发到产物取回的闭环。真实任务采用无业务副作用的固定文件处理，核对工作目录、进程所在机器、会话数量、文件校验及最终投递。

另外，用自然语言任务“列出我当前能看到的机器”“让另一台机器的 QA 检查本项目”做 Agent 行为评估，观察其是否误报无机器、误选团队或把接收回执当作完成。允许不同正确工具路径；不把固定调用顺序作为唯一正确答案。记录最终结果、错误分类、耗时和工具调用数，避免只增加测试断言而没有改善使用体验。

机器目录随账户及在线情况变化，不把现场的 6 台写死为测试期望。没有通过真实双机验收时，交付声明只能是本地候选，不能宣称用户团队已具备跨机能力。

**10. 交付、迁移和回滚：先独立交付 A，再开放完成验证的团队能力。**

A 可独立评审及发布，不依赖用户团队升级。已有查询直连库的脚本迁移到 `--paired`；`--reachable` 长期兼容。输出保留既有核心字段，新增字段及错误细节由 schema 记录。若需要回退默认行为，可回退 A，直连库和 Hub 登记不做破坏性迁移。

B 修正候选行为并补充目标配置，C 完成执行保证；跨机团队入口在 B/C 验收完成前不作为正式能力发布。若需要先发布同一产品批次中的 A，应在该发布候选中禁用未完成的样板跨机入口，并同步说明能力范围。

用户团队是独立资产：模板发布不会自动让已建团队脚本生效。升级按既有三方合并流程保留用户修改，目标端和派发端检查兼容版本，新增记录标明格式版本。旧版本不识别的新记录不能被其直接消费。

回退团队版本前先停止新派单，核对正在运行的远端任务并保存其回执；不得删除锁或待办后直接回退。旧脚本不能消费的新记录保留，由兼容的新版本恢复完成或明确取消，再回退入口。产品发布、安装和 daemon 重启分别按对应发布流程执行，不由提案评审代替授权。

实施前的设计验证集中在 C：现有会话创建能否通过稳定关联标识覆盖崩溃窗口，以及远端接单调用能否保持原身份。必须用原型给出可验证答案；若不能，需要补充最小平台原语后再评审 C，不影响 A/B 的设计结论。当前没有经过原型的工期依据，不给出虚假的代码行数或完成日期。

**11. 提案写法与一手参考。**

Rust 官方 RFC 模板要求从用户问题及必要背景出发，使用具体场景解释变化，再写实现细节、代价、替代方案和未决问题。本提案据此把场景、代码证据和方案逐项关联，便于评审者判断是否值得改以及能否实现。[Rust RFC 模板](https://github.com/rust-lang/rfcs/blob/main/0000-template.md)。

Anthropic 的工具工程经验强调按 Agent 的任务设计工具、给出有意义的返回内容，并用现实任务评估。对应本案，机器目录的默认值与错误解释应帮助 Agent 做出正确下一步，而非让它学习内部存储差异。[Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)。

Anthropic 的 Agent 评估说明区分执行轨迹与环境中的最终结果，且建议用多次尝试观察可靠性。对应本案，参数是否传递只是过程证据；最终还要检查会话是否只创建一次、暂停是否保留、写入是否隔离、产物是否交回。[Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。

项目内架构以 [团队机制](./teams.md) 为当前事实来源。较早的 [跨机会话控制与下载提案](./cross-machine-control-and-download-proposal.md) 保留了来源归属及文件传输的历史决策；其中早期缺陷描述不等于当前缺陷，本提案不据此重新引入授权模型或重复开发下载能力。

**12. 已授权实施的 CLI 可用性修正。**

用户在扩展命令审查后明确指出，Agent 可以通过管道过滤结果，`--limit` 不是必须项，并授权其余确定问题先修复。
本批保留现有列表输出和默认范围，不引入分页、默认截断或 `--limit`。例如会话筛选可使用
`genet session list | jq -c '.data.sessions[] | select(.status == "running")'`；JSON 结构筛选无需改变产品列表合同。
该授权对应用户消息 `u_7175fd948efd43e78dcec809dfe175e9`。

具体背景是：Agent 已经正确选择了操作，但顶层解析器会吞掉子命令参数，帮助和机器合同又与实际命令不同。
这类问题不能靠管道过滤修复。例如 `genet shell --cwd <目录> -- python3 --version` 实际只返回 GeneHub 版本，
完全没有执行 Python；`session list --source-kind typo` 则成功返回空结果，把参数错误伪装成没有会话。

| 项目 | 本批修改及位置 | 可观察验收 |
| --- | --- | --- |
| 参数边界 | `apps/cli/src/main.rs` 只在完整顶层版本调用时处理 `--version/-V`，不扫描子命令与负载 | Python 版本命令真实执行；顶层版本仍可在不可用数据目录下工作 |
| 帮助发现 | `cli_front/mod.rs/query.rs` 从命令合同生成分组和命令帮助，识别无参数的 `--help/-h` 形式 | `session --help` 和 `agent run --help` 成功且不创建会话；负载中的帮助字样原样保留 |
| Space 发现 | 为已存在的 `space.open` 增加 schema 和 capabilities 条目 | 帮助、schema 与真实 `space open <root>` 输入一致，不新增打开目录副作用 |
| 输入校验 | `query.rs` 校验 source-kind 枚举；`file.rs` 拒绝未知选项及多余位置参数 | 拼错筛选和传输查询选项立即返回参数错误，不返回伪空列表或伪目标缺失 |
| 路由筛选 | `converse.rs` 根据 `--tag/--media` 自动启用路由视图 | 隐式和显式 `--routes` 返回相同筛选结果 |
| schema 一致 | `query.rs/target.rs` 修正 Agent/档位/续接三种运行输入、传输单条和列表输出、进程远程路由声明 | 合法档位请求不再缺少必填 Agent；两种传输响应均符合 schema；进程路由元数据与执行入口一致 |
| 权限分类 | `router.rs` 对已认证但缺少能力的请求返回 Forbidden，保留未认证错误 | 受限身份调用配置能力明确返回 forbidden；授予能力的语义和范围不变化 |
| 完成语义 | 使用说明明确 shell 的进程结果和文件下载等待超时结果 | 调用方可据 terminal record 判断真实结果；保持现有退出码兼容性 |

本批不改变 shell 的冻结退出码，不把“等待下载超时”改成“取消传输”，也不新增团队调度机制。
原有 A/B/C 仍按各自范围推进，本批不将它们标记为完成。

验证以现有公开 CLI 专项和 owning-package 回归为基础，新行为用 TypeScript 专项驱动隔离环境中的真实
CLI、daemon 和签名 guest，不 mock 内部函数；产品修正附同批公开入口回归，不夹带测试治理或基建改造。候选验证只证明指定
CLI 范围，不作为 Beta 发布或完整 dev 资格。回滚可回退本批提交，列表数据及用户配置无迁移。
