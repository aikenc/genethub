# GeneHub 安全模型

> 上位文档：[architecture.md](./architecture.md)　实现约束：[control-plane.md](./control-plane.md)  
> 本文回答三个问题：**谁能看到什么、什么东西泄露了怎么办、哪些事绝对不做。**

---

## 1. 信任边界

```
┌───────────┐   E2E 加密   ┌──────────────┐   E2E 加密   ┌────────┐
│ 用户客户端 │◄════════════►│ Hub forward/ │◄════════════►│ daemon │
└───────────┘              │ （哑管道）    │              └────────┘
      │                    └──────────────┘                   ▲
      │ 账号 / 机器目录 / 授权（TLS，可见元数据）                  │
      ▼                                                        │
┌────────────────────────────────────────────────────────────┴───┐
│ Hub control/ ── 执行通道（仅租用场景，可见 prompt 与输出，明文）    │
└────────────────────────────────────────────────────────────────┘
```

转发层与控制面同一部署但**信任级别不同**，这是 [architecture.md](./architecture.md) §6.4 要求模块隔离的安全侧理由：合并部署不等于合并权限。

| 组件 | 信任级别 | 能看到 | 看不到 |
|------|----------|--------|--------|
| Hub `forward/` | **按不可信设计** | IP、时序、包大小、通道 id | 任何内容——它不 parse payload |
| Hub `control/` | **半可信**（我们自己运营，但要限权） | 账号、机器目录、连接元数据、租用执行内容 | 自有机器的工作台内容 |
| daemon | 可信（用户自己的机器） | 全部 | — |
| 桌面壳 | 可信 | 本机 | — |

同一个进程里跑着两个信任级别，风险是有人图省事在转发路径上直接读控制面的数据结构。防线是依赖方向检查（[architecture.md](./architecture.md) §6.5）：不是靠自觉，是靠构建失败。

### 1.1 引入 Hub 之后，端到端加密的说法要改口径

纯粹的点对点方案可以说"中转不可信也没关系，因为公钥来自你手上的二维码"。GeneHub 为了让用户不必配对每一台设备，改由 Hub 分发机器公钥——**信任锚就从二维码转移到了 Hub**：一个被攻破的 Hub 可以把假公钥发给浏览器，做中间人。

不能只当没这回事，必须给出可核对的手段：

1. 桌面端「本机信息」里显示 daemon 公钥指纹（前 8 字节 base32，分组显示）。
2. Web 首次连接某台机器时显示指纹，用户可与桌面端核对；核对过的指纹记在设备会话里，之后变化要弹警告。
3. 指纹变化的原因只有两个：用户主动轮换密钥，或有人在中间。文案要直说。

对外表述统一为：**"中转服务器看不到你的内容；平台不主动读取你的内容，自有机器的会话平台在技术上也读不到；租用他人机器的会话经平台转发，平台在技术上可见。"** 不要写"平台绝对无法看到任何内容"。

## 2. 凭证清单

| 凭证 | 存放 | 生命周期 | 泄露后果 | 可否单独撤销 |
|------|------|----------|----------|--------------|
| 设备会话 refresh token | 客户端安全存储；Hub 存哈希 | 长期，可"信任 30 天" | 该设备身份被冒用 | ✓ |
| 设备转移链接 | 一次性 URL | ≤ 15 分钟，一次性 | 一个新设备会话 | ✓ |
| 恢复密钥（临时用户） | 桌面本地；Hub 存哈希 | 长期 | 临时身份被接管 | ✓ |
| 设备码 / enrollmentToken | 内存 | ≤ 10 分钟 | 可把机器登记到攻击者账号 | ✓（过期即失效） |
| daemon credential secret | daemon 本地；Hub 只存 sha256 | 长期 | 可冒充该机器接执行任务 | ✓ |
| **pairing offer** | 客户端；**不落 Hub 库** | 长期 | **该机器完整控制权** | **✗ 只能整机轮换** |
| relay 邀请码 | 用户手上 | 可配 | 白嫖中转 | ✓ |

一句话：**除了 offer，其他都能单独收回。所以 offer 的下发面要压到最小。**

## 3. 分享与扫码：把"账号接管链接"改掉

上一版设计里"分享链接 = 登录同一账号"。在这个产品里，账号名下挂的是能执行任意代码的电脑，所以一条转发到群里的链接就等于交出机器。规则改为：

| 规则 | 要求 |
|------|------|
| 授予对象 | 一个**设备会话**，不是账号本身 |
| 有效期 | ≤ 15 分钟 |
| 使用次数 | 1 次，核销即废 |
| 可见性 | 原设备上能看到"已在某 IP / 某浏览器被使用"，可一键撤销 |
| 二次确认 | 公开机器、发起租用、升级账号、删除机器、下发 offer 到新设备 —— 必须在已信任设备上确认 |
| 异常处置 | 同一链接短时间内多 IP 尝试 → 自动作废并告警 |

**扫码登录同理**：新设备展示二维码，由**已登录的设备**扫码并在自己屏幕上确认"是否允许 <设备名 / IP / 位置> 登录"。不能做成"扫一下就进"，那等价于把二维码截图发出去就能登录。

## 4. offer 的处置规则（硬规则）

1. offer **不出现在任何分享给人类的链接、二维码、聊天消息、日志、终端输出**里。
2. offer 只在 Hub 与"已认证且属于机主本人"的设备会话之间传递，每次下发写审计。
3. 租用场景**绝不**下发 offer。
4. 文档、脚本、演示里如果打印了 offer，视同泄露，按 §6 处理。
5. 桌面端提供「轮换本机身份」按钮，并明确提示：**会让我已有的所有设备重新配对**。

## 5. 转发层准入：身份即准入

旧的独立中转 `relay.genethub.com` 对任何人开放，没有鉴权、限速和配额，谁知道域名谁就能白嫖。原计划补一套邀请码来堵这个洞。

转发折进 Hub 之后**这套邀请码不需要了**：能开通道的前提是已登记的机器 + 已授权的设备，身份系统本来就有。

```
daemon / 客户端开通道时携带 Hub 签发的短期票据（含机器 id，私钥签名，短 TTL）
        │
        ▼
forward/ 只验签，不查库 —— 保证控制面抖动时既有连接不受影响
        │
        ▼
control/ 可随时作废票据来源；撤销经 contract 的 onRevoked 推给 forward/
```

要点：

- 票据只做**准入**，不参与端到端加密，不改变转发层按不可信设计的定位。
- 坚持**无状态验签**：转发层一旦要查库，就等于把控制面的可用性变成会话的可用性，也等于给将来的拆分埋了一根线。
- 基础限额仍要有：单连接速率、单机器并发连接数、单 IP 新建连接频率。
- 迁移期内老的独立中转保持可用，新客户端一律走新端点，旧域名在 MVP 后下线。

## 6. 事故响应预案

| 事故 | 处置 |
|------|------|
| offer 泄露 | 桌面端「轮换本机身份」（删除 `server-id` 与 `daemon-keypair.json` 后重启）→ 重新配对全部设备 → 审计标记 |
| 转移链接泄露 | 撤销链接 + 撤销由它创建的设备会话 |
| Hub 库泄露 | 库里只有哈希（credential verifier、token hash），仍需：强制全体设备会话下线、轮换 Hub 签名密钥（等于作废全部在途票据）；机器凭证本身不需要重建 |
| 某台机器被入侵 | Hub 侧 `DELETE /api/machines/{id}` 断开关系，从租用池摘除，通知机主本地轮换 |
| 转发层被滥用 | 收紧限额；必要时轮换签名密钥强制全体重新取票 |

## 7. 部署基线（已在自有环境落实）

| 规则 | 原因 |
|------|------|
| **托管 Web UI 的机器上不跑 daemon** | daemon 会把 agent 执行能力开在这台机器上；Web UI 是纯静态产物，用 Caddy 托管即可 |
| 静态站点上 `/api/*`、`/ws` 直接返回 404 | 避免 SPA 兜底把探测请求答成 200，也避免误导客户端 |
| 应用服务只监听 `127.0.0.1`，由 Caddy 终止 TLS | 不暴露明文端口 |
| 任何常驻服务都要有重启策略 | 容器用 `unless-stopped`；非容器进程用 systemd，不用 `nohup` |
| 生产机上的 daemon（如果将来确实需要）必须独立低权限用户 + 限定 workspace + 不装 provider 凭证 | 限制被攻破后的爆炸半径 |

过渡期的工作台域名已改为 Caddy 静态托管，服务器上的守护进程已停止并轮换了身份密钥。自研工作台上线后该域名下线。
