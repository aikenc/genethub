# 安全模型

> 上位文档：[architecture.md](./architecture.md)  
> 本文回答三个问题：**谁能看到什么、什么东西泄露了怎么办、哪些事绝对不做。**

---

## 1. 信任边界

```
┌───────────┐    TLS     ┌────────────┐    TLS     ┌────────┐
│ 浏览器/手机 │◄══════════►│   relay    │◄══════════►│ daemon │
└───────────┘            │ 只搬字节    │            └───┬────┘
      │                  └────────────┘                 │ 准入在这里判：
      │ 账号（仅托管部署时）                              │ 本地已授权设备列表
      ▼                                                  │
┌────────────────────────────────────────────────────────┐
│ 控制面 ── 本仓之外的服务。只做身份，不做准入决策            │
└────────────────────────────────────────────────────────┘
```

| 组件 | 信任级别 | 能看到 | 看不到 |
|------|----------|--------|--------|
| relay | **按不可信设计** | IP、时序、包大小、通道 id | 它不解析 payload，也不落库 |
| 控制面 | **半可信** | 账号、连接元数据 | 会话内容不经过它；它也决定不了谁能连你的机器 |
| daemon | 可信（你自己的机器） | 全部 | — |
| 桌面壳 | 可信 | 本机 | — |

**自建部署里根本没有控制面**：relay + 静态工作台两个东西就够，授权全靠配对（[self-hosting.md](./self-hosting.md)）。控制面只在托管部署里出现，而且它拿到的权力比看上去小——准入判断永远在 daemon 手里（§4）。

relay 与控制面是两个进程、两个仓库，这不是部署细节而是安全边界：合并部署就等于合并权限。依赖方向由 CI 检查守着（[architecture.md](./architecture.md) §6.4），靠的是构建失败而不是自觉。

### 1.1 现在的加密到什么程度，说清楚

**当前实现是传输层加密**：本机走 loopback，局域网与转发走 TLS。relay 处理的是 TLS 解密之后的应用层字节，它在代码上不解析、不存储，但**技术上具备读取能力**。

**这不是端到端加密。** 真正的 E2EE 要求 daemon 与客户端基于对方公钥直接协商，relay 只见密文。它在路线图上（[roadmap.md](./roadmap.md) M4），尚未实现。

因此对外表述统一为：

> relay 不解析、不存储你的流量，代码开源并且可以自己部署。会话内容不经过控制面。当前为传输层加密，端到端加密尚未实现。

不要写"平台无法看到你的内容"。等 E2EE 落地了再改这句话。

### 1.2 公钥指纹要能核对

引入控制面分发机器信息之后，信任锚从"你手上的二维码"转移到了控制面：一个被攻破的控制面可以把假地址、假指纹发给浏览器。给用户可核对的手段：

1. 设置页「这台机器」显示 daemon 公钥指纹（分组显示），桌面端与浏览器是同一段代码、同一个位置——用户要核对，两边就得长一样。
2. 桌面壳另有一条独立来源：它自己起的 daemon 在启动时就把指纹打给了它。两个来源不一致意味着中间有人，这种情况前端自己就会告警，不指望用户逐位比对。
3. 浏览器没有独立来源，只能靠人核对——所以文案要说清楚「跟你在那台电脑上看到的对一遍」。
4. 指纹变化只有两个原因：用户主动轮换密钥，或有人在中间。文案要直说。

**尚未落地**：把核对过的指纹记进设备会话，之后变化自动弹警告。目前浏览器每次都要人自己看。

## 2. 凭证清单

| 凭证 | 存放 | 生命周期 | 泄露后果 | 可否单独撤销 |
|------|------|----------|----------|--------------|
| **设备凭证**（daemon 签发） | 客户端本地；daemon 本地（明文，权限 600） | 长期 | 该设备身份被冒用，可远程连这台机器 | ✓（机器上删一行） |
| **配对邀请码** | 只在一次性链接/二维码里 | ≤ 15 分钟，一次性 | 一台设备被加进授权列表 | ✓（过期或用掉即失效） |
| 设备会话 token | 客户端安全存储；控制面存哈希 | 长期，可「信任 30 天」 | 该设备身份被冒用 | ✓ |
| 设备转移链接 | 一次性 URL | ≤ 15 分钟，一次性 | 一个新设备会话 | ✓ |
| 恢复密钥 | 桌面本地；控制面存哈希 | 长期 | 临时身份被接管 | ✓ |
| 设备码 / enrollmentToken | 内存 | ≤ 10 分钟 | 可把机器登记到攻击者账号 | ✓（过期即失效） |
| daemon uplink secret | daemon 本地；控制面只存 sha256 | 长期 | 可冒充该机器挂上转发 | ✓ |
| 通道票据 | URL 查询串 | ≤ 2 分钟，一次性 | 一次接入机会 | ✓（用即作废） |
| 本机 token | daemon 启动时生成，写在 stdout | 进程生命周期 | 本机进程可连本机 daemon | 重启即换 |

通道票据走查询串是不得已：浏览器发起 WebSocket 握手时无法设置请求头。代价用两条约束抵消——一次性、有效期以秒计，并且核销与校验在同一条 SQL 里完成，两个并发接入不可能都成功。

## 3. 分享与扫码

账号名下挂的是**能执行任意代码的电脑**，所以"分享链接 = 登录同一账号"这种做法在这里等于交出机器。规则：

| 规则 | 要求 |
|------|------|
| 授予对象 | 一个**设备会话**，不是账号本身 |
| 有效期 | ≤ 15 分钟 |
| 使用次数 | 1 次，核销即废 |
| 可见性 | 原设备能看到「已在某 IP / 某浏览器被使用」，可一键撤销 |
| 二次确认 | 删除机器、升级账号、把机器设为可被他人访问 —— 必须在已信任设备上确认 |
| 异常处置 | 同一链接短时间内多 IP 尝试 → 自动作废并告警 |

**扫码同理**：新设备展示二维码，由**已登录的设备**扫码并在自己屏幕上确认「是否允许 <设备名 / IP / 位置> 登录」。不能做成"扫一下就进"，那等价于把二维码截图发出去就能登录。

## 4. 转发准入：由机器自己判

**准入的判断者永远是 daemon，不是 relay，也不是任何服务端。** 这是一条设计约束而不是实现细节：控制面宕机或被攻破都不该让别人连上你的电脑。

daemon 本地维护一份已授权设备列表，形态就是 `authorized_keys`——设备名、首次接入时间、最后活跃时间。撤销就是删一行并断开那条连接，立即生效，不依赖任何推送到达。

```
客户端连 relay 的某个 rendezvous 槽位
        │
        ▼
relay 把两条 socket 接起来（它只做这一件事）
        │
        ▼
daemon 检查这个设备在不在自己的已授权列表里 → 放行或断开
```

### 4.1 配对：链接是一次机会，不是钥匙

机器出示一个一次性、≤15 分钟的配对链接（附二维码）。客户端打开后换到一份**长期设备凭证**存在本地。链接用掉即废，所以它泄露的上限是"一台设备被加进列表"，而不是"永久访问权"——§3 那几条规则在它身上继续成立。

这跟"分享链接 = 登录同一账号"是两回事，后者等于交出机器。

### 4.2 双向证明，凭证不过线

rendezvous 槽位可能被抢占：谁知道那个 id，谁就能抢先挂上去冒充这台机器。所以连接建立后双方必须各证明一次，用配对时的共享秘密，**秘密本身不发送**：

```
客户端 → 机器：设备 id、随机数 n、H("client:" + n + ":" + 秘密)
机器  → 客户端：H("server:" + n + ":" + 秘密)
```

抢占者两个方向都答不出来。随机数不允许重复使用，所以截获一次也没法重放。

这里不需要 TOFU：客户端在配对时就已经持有这台机器的秘密，之后每次都是拿已知秘密做强认证，不存在"首次信任"这个环节。指纹告警只对"机器目录由服务端下发、客户端从未直接配对过"的场景有意义。

### 4.3 托管部署上叠加的东西

走官方流程时多一条：daemon 本地记一条"我信任账号 A"。之后账号 A 在新设备上登录，控制面顺着 daemon 已有的那条出站连接转达一句"这个设备属于账号 A"，daemon 按本地记录**自己**签发一份设备凭证。

那条连接本身已经双向认证过，所以不需要额外的签名断言机制，也不需要 daemon 保存控制面公钥并处理轮换。准入实现仍然只有一套，控制面只是个身份声明的转达者。

### 4.4 其余要点

- 限额是必需品：单连接缓冲、单机并发客户端数、单帧大小、在线机器总数（[relay.md](./relay.md) §6）。
- 自建 relay 的 join token 只约束机器挂上行连接。客户端只能连到已存在的槽位，白吃流量得先占一个槽位。
- 配对时新签发的凭证会经过 relay。自建场景下 relay 是你自己的；托管场景下这是当前传输层加密的已知限制，随 E2EE（M4）一起解决。

## 5. 事故响应

| 事故 | 处置 |
|------|------|
| 配对链接泄露 | 它一次性且 ≤15 分钟；若已被用掉，在机器的设备列表里撤销那台设备 |
| 某台设备丢了 | 在机器上撤销那一行，连接立即断开。不需要联系任何服务端 |
| 转移链接泄露 | 撤销链接 + 撤销由它创建的设备会话 |
| 控制面数据库泄露 | 库里只有哈希（credential verifier、token hash）。仍需强制全体设备会话下线；设备凭证是 daemon 签发的，控制面没有，不必重建 |
| 某台机器被入侵 | 机主在那台机器上清空授权列表并轮换身份；无法登录该机器时，在控制面撤销登记以断掉上行 |
| daemon 本机 token 泄露 | 重启 daemon 即更换；同时检查是谁能读到该进程的 stdout |
| relay 被滥用 | 收紧限额；必要时轮换控制面与 relay 之间的 token |

## 6. 部署基线

| 规则 | 原因 |
|------|------|
| **托管工作台静态文件的机器上不跑 daemon** | daemon 会把执行能力开在这台机器上；工作台是纯静态产物 |
| 纯静态托管时，`/api/*`、`/ws` 直接返回 404 | 避免 SPA 兜底把探测请求答成 200。同域部署（工作台与控制面同一个 origin）不适用这条，那里 `/api` 本来就是控制面 |
| 应用服务只监听 `127.0.0.1`，由反向代理终止 TLS | 不暴露明文端口 |
| 任何常驻服务都要有重启策略 | 容器用 `unless-stopped`；非容器进程用 systemd |
| 服务器上如果确实要跑 daemon：独立低权限用户 + 限定 workspace + 不放 provider 凭证 | 限制被攻破后的爆炸半径 |
