## 角色与改动归属

向团队发送业务目标、可见体验、验收与预算；原生消息保留 Agent/脚本来源。开发侧独立观察、归因、修平台和发 dev，分析按必须改变的制品归属：

| 制品 | 写入方 | 验收 |
| --- | --- | --- |
| 平台内核（daemon、CLI、协议、hook） | 平台开发 | 原公共入口复现，修复/回归、dev 采用与业务续工 |
| 内置样板、公共脚本与 Skill、默认评分 | 平台开发 | 共性夹具、扩展兼容、团队合入采用后的原任务复验 |
| 本队岗位、经验、业务工具与设置 | 本队反思 | 反思自行调整、构建、远端同步与业务复验 |
| 游戏代码、资产、构建 | 团队执行 | 固定制品的实际预览、QA 与交付 |

目标发出后，开发者不能继续改本队定义或替团队实现游戏。开发操作 Skill 的改进解决观察者自身摩擦，不能替代团队机制的平台修复。

## 评分与对照不能漏掉的规则

- 统计单位是一张支持单，从派出、确认创建、开工、结论、送达、读入到采用/返工/废弃；不是会话数或工具次数。
- R1派单悬空、R2未结算义务、R3未达/错投/重复、R4无因停摆、R5资源未归还，均需对应夹具。正确暂停、等待用户、常驻和如实 QA 不通过应可豁免或作为有效结论。
- M1采用/返工、M2流转、M3人的占用、M4单位采用成本、M5空转、M6失败/恢复。正式过程事件由已有动作点产生，不能让 Agent 填表，也不让调度依赖诊断事件日志。
- 工作质量与游戏成果质量两张卡分别展示；核心分只用样板口径，项目分才叠加项目扩展。阈值、权重和噪声要版本化，缺数据不伪造正式分。
- 原型只有约30%主指标权重覆盖；正式分要求的覆盖、五红线可判定及样本门槛未达，不能出模型排名。第一派单时间只作诊断，不单独入分。
- 两队起点、目标、预算、平台和工具约束已对齐；这轮 HY 接受额外催促，必须列出干预差异，因此本轮不能单独证明模型因果优劣。
- 真人纠偏、模拟用户产品决定、催促/纠正和开发救援分别记账。新队没有旧运行账本不等于红线修复，接受救援后的成功不等于自主恢复；需同类无追加救援复验。
