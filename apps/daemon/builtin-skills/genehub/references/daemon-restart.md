# 配置生效与 daemon 重启 SOP

适用于本机或远端 GeneHub daemon 配置生效、重启和恢复。
沿用机器已有启动方式，不要求 Linux 安装 systemd，不在本 SOP 中迁移托管方式。
只读诊断不授权重启；已有维护授权无需重复索取，但恢复条件必须满足。

## 1. 区分配置写入与生效

确认目标机器 ID、运行用户、渠道绑定 GENEHUB_CLI 和真实启动来源。仅核对必要环境项，
记录原配置、原 CLI/制品路径及恢复步骤，保留身份和数据目录，避免启动成另一用户/渠道。
具体配置项及其必配规则由相关功能说明定义，本 SOP 不引入通用必配环境变量。
按原启动方式持久化该变量；environment.d、服务管理器环境或终端 export 不会追溯修改已有进程。
写入后如果新远程 shell 未读到该变量，报告“已写入，待生效”，停止依赖该变量的取证/发布。
不能为通过配置门禁自动重启唯一的远程入口，也不能临时向取证命令注入变量冒充生效。

## 2. 重启前验证独立恢复连接

实际验证 SSH、云控制台或现场终端至少一个能够以正确用户执行恢复命令，并在重启期间保留。
另一个同样依赖目标 daemon 的 GeneHub 会话，不算独立恢复连接。
只有该 daemon 的远程 shell 时，可以准备配置和操作说明，但必须停止重启动作，
明确请用户先建立独立连接；等待时间或已有发布授权不能替代这个条件。

## 3. 从独立连接沿用原管理者执行

- 已有服务管理器：核实当前 PID 对应的服务与配置加载方式，使用该管理器的重启入口。
  不另行执行 CLI start/restart，不擅自新建服务或改变重启策略。
- 原来手动启动：在独立 SSH/控制台中显式加载已核实的配置，以相同用户、数据目录、渠道和
  原启动方式执行。确认没有并行启动者；使用目标 GENEHUB_CLI 绑定，不猜可执行名。

不要把 daemon start/restart 包进临时任务作为可靠重启方案。nohup/setsid 脱离终端或进程组，
不能证明脱离服务控制组；systemd-run 独立于旧 daemon，也不能保证新后台 daemon 在任务退出后存活。
临时发布 runner 只管理发布任务；本 SOP 不通过 KillMode=none 等手段绕开生命周期管理。
执行前核对实际安装脚本的重启副作用，同样遵守本节，不因换了安装命令而绕过。

## 4. 分层验收

记录有界等待时限。先从独立连接检查进程、本地 daemon 健康和启动日志；已有管理器时再检查服务状态。
远程使用场景再从另一台已授权机器确认原机器 ID 上线，重新打开 shell，仅检查所需变量，
运行该功能的只读配置检查。本机未配对 Hub 的使用场景验收本地连接，不为验收强制配对。
退出独立启动命令后仍可连接，且所需配置解析成功，才能报告“已生效”。单次 CLI 返回 0、出现 PID、
配置文件存在或 Hub 短暂在线都不足以验收；进程健康也不能代替 Hub 和远程 shell 验收。

## 5. 超时与恢复

使用保留的独立连接读取退出状态和完整日志，判断旧进程未停、新进程启动失败，还是启动后退出。
从原配置/制品恢复并按原方式启动；如果旧配置缺目标变量，可以先恢复远程可达，仍标配置待生效。
恢复失败就停止进一步变更并报告现场证据，不盲目重复 restart，不删锁、不批量杀进程。
没有退出日志和实际服务配置时，不能把锁冲突、启动失败或控制组清理中的任一种当成已确认根因。
