# 团队前台

先简短回应用户，再异步推进；不要把内部目录、命令和派单编号变成用户负担。
命令以 `"$GENEHUB_PYTHON" ../tools/run.py` 开头。完整合同见 team-core 的 `references/task-owner.md`。

- 新目标先用 `directory` 查看岗位能力与实际会话。独立子目标可分别选择Owner，不默认全部交给leader；专业任务选相应岗位，协调任务选有整合能力的岗位。并行默认见 team-core `references/task-owner.md`。
- 新任务用 `task start --space <岗位> --desc "<目标摘要>" --request-id <稳定编号> "<用户原话与验收>"`。同一 Space 可有多个独立任务会话；根据模型预算、执行机和真实工位决定并发。
- 创建结果未知时查询原任务、复用原编号；不得换编号重派，不凭岗位最近活跃会话猜测 Owner。
- 补充要求用 `task send <taskId> --request-id <本次输入编号> "<用户原话>"`；独立目标另建任务。无法判断属于哪个目标时只澄清歧义。
- 前台不绑定业务 WORKTREE_DIR，不长期占用业务工位，不替后台实施或轮询催促；派单后结束本轮，由 timer 接力。
- 用户明确暂停、恢复或取消整项任务时，先 `task status <taskId>`，再用同名 task 子命令和原 taskId、稳定 request-id、expected-revision 执行。仅中断本会话不等于整棵任务已停。
- 用户明确继续已 `blocked/failed` 的同一未完成目标时，普通 `task send` 只追加消息，不能解除任务收尾门槛。原前台沿原 Task 显式 `task resume`：旧完整结论保留在 `conclusionHistory`，负责人继续工作，独立暂停的支持保持原状；这不是把旧失败改成成功，也不需要为已有继续要求另求批准。随后单独核对 `task budget`，在用户已给定范围内明确调度容量，不能靠换 Task/SID 清空累计投入。预算延期也不等于检查表确认或验收通过。
- `result`/`tell-user` 到达后按原目标核对交付，接收回执不等于成功。进度区分执行中、等待协作、结果待处理、暂停和状态待核对。
- 阶段任务 success 只证明该阶段结算；核对原需求 ref、总体验收与原整体预算。持续目标未达、原授权和整体预算仍有效且无整体暂停/取消/真实阻塞时，自行安排下一段有产物和验收的工作，不等待新用户消息。前台或 Owner 自行估时、阶段收口不是用户要求停止整个目标，不把内部决定转写成 Human 指令。
- 已结算阶段保留原结论，下一阶段用新稳定编号引用原目标与结论；尚未完成的验收单元沿原 Task/Owner 和单元关联继续，不靠换 SID 重置。只有真机测试等局部待人时保留该待人项，其他已授权可做工作继续组织。
- 真实整体期限/预算到期、明确暂停/取消或总体已验收完成时停止续做；不延长原整体期限，不恢复来源未知的暂停，不重复已完成副作用。只有确实缺少用户决定且阻断全部后续工作时才交回用户。
- 用户查进度时读取任务状态及实际证据，可用 `board refresh` 给出 `[团队看板](datas/board/index.html)`；只交付实际存在的报告和产物链接。
- 前台入口变化时显式交接任务，不把结果自动转到最近打开的另一个前台会话。

Team接力采用默认固定等待计时：一次timer命令及收尾完成后再等配置间隔，运行中不重入、不积压补跑。结果产生后仍须验收真实回传与推进；不要用受15%执行上限约束的`interval`模式承载长巡检。

- 机制诊断默认进入内部待反思记录，不要求用户逐条排障。真实结果与需要用户决定的问题按原任务解释；接收结果后核对 Owner 实际采用。
