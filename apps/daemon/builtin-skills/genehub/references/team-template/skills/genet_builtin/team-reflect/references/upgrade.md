# 升级边界

平台升级由 `python3 tools/run.py upgrade` 程序完成；timer 自动选择最新版，不逐版派单，也不需要升级通知消息。用 `upgrade --status` 查看结果：`adopted`（已采用）、`conflict`（有冲突）、`test-failure`（测试失败）、`waiting-safe-point`（等待安全点，含候选验证及执行端安装中）。

程序先检查三方合并和本地内置补丁，在未注册的独立候选里跑本队回归、完整构建与 verify；源目录有未提交改动或验证期间变化时等待，不覆盖。兼容的远端安装复用独立版本目录，旧会话、执行目录与原回执继续保留。只有冲突和测试失败会唤醒反思，已采用或等待都不新增巡查报告。需要自定义回归时在 `agent-space.genet.json` 的 `team.settings.upgrade.regressionCommands` 写参数数组列表；默认运行已有的 `tools/tests/test_*.py`，并核对实际 Class/API/binding 和构建制品。

反思只处理结果里的冲突文件或失败命令：平台机制问题反馈平台，业务规则提取到项目 Class / Skill；修正并提交后程序自动重试。采用只看自然卡的 `versions.teamTemplate`，不能把 platform 比较基线或 daemon 安装版本当作采用；自定义模板来源没有可验证的发布号时保留未知。以下内容仅在解决冲突、首次旧式迁移时按需查阅，不再每版手工执行。

- 定义源先保存当前提交、制品和原任务记录；运行副本不初始化 Git、不 snapshot、不直接编译。
- 对已采用 Class 扩展的团队：从平台候选更新 `tools/genet_builtin/`、`skills/genet_builtin/` 及薄入口，保留 `agent-space.genet.json.team`、业务 tools/Skills、身份、数据和回执。比较 `tools/run.py describe` 的 Class、API 与 binding 版本；兼容更新无需改写业务源。
- 区分定义源兼容更新与执行端运行替换：Class/API/binding/settings 和既有协议保持兼容的源端工具/说明修复，可保留在途目标先采用并核对实际行为；不要求所有业务目标先结束，也不因某个远端暂不能安装而把已验证兼容的源端修复全部搁置。远端继续用原回执与执行制品收尾，实际替换仍须通过原生安全检查；增加远端能力的变更须等相应执行端协议就绪，不能冒称两端都已采用。
- 远端旧工作仍在途而后续需要新制品时，可显式 `run.py employee sync --parallel`：平台为已验证执行内容摘要和岗位集合选择独立版本目录，保留原执行目录、会话、回执和资源；源绑定只供后续派单，旧操作仍沿已保存的原路径收尾。仅源登记信息变化不会产生新执行版本；传输归档仍逐字节核对 SHA，相同执行内容重复同步复用原新目录，不复制旧运行账本，也不自动清理旧目录。
- 并存安装保留同源目标的本机 Agent/模型偏好；它不解除暂停、不替旧任务结算，也不保证改变 Class/API/binding 后旧源协议仍兼容。默认 `employee sync` 继续拒绝覆盖在途或未知工作。采用和验证仍由团队按实际证据完成，安装成功不等于旧任务或用户目标完成。
- 使用者仍可修改内置包，但这些修改是明确维护的补丁，升级需要三方核对，不是零成本覆盖。
- 首次从旧版迁移：把已有业务差异提取为 `WorkflowPolicy` / `ResourcePolicy` / `ReflectionPolicy` / `BoardPresenter` / `TeamCommands` 子类；`team.class` 可选，不需要空壳包装。旧目录入口仅转发；移除替换内部函数、猴子补丁与重复锁。见 team-core `references/extensions.md`。
- 不给在途旧任务补造新归属。先在原 Class/settings/binding 下结算或显式交接，再部署变更。Class/API/binding/settings 不匹配时保留记录并报错，不自动回退默认类。兼容修复可保留 binding_version；改变准备、释放或账本业务语义时升级版本并安排迁移。
- 构建完整制品，源目录移走后验证 `describe`、业务命令、timer、看板和实际任务；执行端 `spacebuilder.py verify --artifacts-only`。制品部署后已有进程需按团队安装器滚动更新，不能把替换磁盘文件当作所有在途进程已采用。
- 不使用 `reset` 作为模板升级；不覆盖 `datas`、会话、临时材料、本机配置或已有任务。没有完整发布回执不能声称已部署。

## 旧式团队三方升级（尚未采用扩展层时）

保留原定义源的 `platform` 模板基线分支。源端 `tools/run.py snapshot --refresh-platform` 将当前平台记录为新基线；在受管候选中合并平台与团队改动。不能新建并注册自动运行的临时团队来试合并。

更新 `platform` 分支只更新比较基线，不证明运行代码已经采用，也不会自动完成升级留言。反思须核对定义源合入、完整制品安装及执行端实际行为，再处理原留言。自定义文件存在差异也不能单凭摘要判为升级失败。

结果投递升级保留原生消息身份。旧扩展的 `resultDelivery.state/to/resultHash/key` 不是平台原生消息回执；兼容迁移须核对当前结论的原生引用和原请求方历史，或沿用原收件箱的完整消息身份与正文。找不到证据时保留旧记录，不新发一份、不删账、不用 `queued` 标记代替读入证明。批量结果中每个引用都应沿用同一原消息 ID；资源释放与结果读入分别核对。

项目自有模拟函数或私有字段断言失败，应先与公共 Class/API/binding 合同及真实原生任务行为核对；例如新增可选查询参数导致旧模拟函数报错，不足以证明执行端行为失败。保留失败记录，更新项目自己的兼容补丁与有效回归；不能靠删断言或清除原任务强行完成升级。

冲突须区分平台机制和业务规则：前者反馈平台，后者提取到项目 Class / Skill。验证并生成完整制品后再安装；源仓命名或 worktree 布局由团队自己决定，不强行套用 main/platform 操作。无法兼容的旧任务保留原执行制品收尾，不重派未知操作。

升级本次通知/恢复/结算修复时，逐项检查项目子类是否覆盖相关方法；仅换基类不能证明采用。定义源三方合入、完整 build/install 后 verify，保留数据、原回执和新租约，验证成果实际回原 Owner。

## 已结束任务的未确认准备

公共样板可在任务已有结论后，对无会话回执、无源端资源的远程准备意图请求持久撤回。执行端须与源端都支持 `receive --require-dispatch-fence`；旧执行包会在解析时拒绝，不会尝试该新操作。原编号在执行端被封住后才解除源端等待，已有会话回执或不明资源仍保留。不能手删派单、锁或把一次无回执查询当作未创建；兼容更新与原任务复验后再核对交付状态。

同步采用撤回协议时，也要更新 `tools/install_remote.py`。已持久撤回且没有会话或资源的准备记录属于终态，应在完整制品升级后原样保留，继续拒绝迟到创建；不能要求它再走仅适用于已创建会话的释放。安装器仍拒绝未知协议、不明准备及未释放的原生会话，不删回执或写锁来完成升级。平台的非项目专项通过真实执行端准备、撤回、完整升级与迟到请求验证这条生命周期。

## 原生失败通知与原会话恢复

原生回合失败不等于业务已有结论。失败通知应在暂停和未完成子工作仍保留时交给原请求方；定制的结果发布检查不得无条件以执行方 `paused` 阻止这条通知。成功结论仍须保持原来的新输入、读入和资源检查。

尚有写者义务的失败工作可以留在 pending。原请求方明确采用失败通知后，用原 SID、稳定恢复编号和同一正文续接；样板会核对当前原生失败代次及该通知的持久送达回执，将完整原失败和回执保存在恢复记录中，保留原任务、子工作和工位。通知未送达、代次变化、另一个请求方或已有业务结论时拒绝恢复；不自动解除暂停，不删除 done、锁或原失败以绕过校验。重复同编号续接不会再次投递或重置结果基线。
