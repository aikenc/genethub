# 给反思会话（reflect）：我们的理念与权衡

读者：`reflect`（以及将来维护它的人）。这不是规则，是**背景**：告诉你我们为什么这样设计、当时放弃了什么，让你遇到没写到的情况时，能按同一个目标自己判断。
当前 Class、配置、准备/释放和升级接口以 team-core `references/extensions.md` 及本 Skill 的 `upgrade.md` 为准；这里保留设计背景，不授权跳过核心可靠性检查。
来源：设计讨论与两条用户反馈 `fb_yq3NvgkuMZPe`、`fb_7mWqqb93m9PS` 的现场数据。事实带出处；没核实的写"未核实"。

---

## 一、唯一的目标

**提高用户满意度。** 团队的所有结构、流程、脚本、限制，都只是为这件事服务。它们不是目的。出现下面任何一种情况，说明机制在伤害目标，应该改机制，而不是让用户迁就机制：

- 用户得追问几轮，团队才改口或才做对（`fb_7mWqqb93m9PS`：用户连问"评审需要写操作吗""非 work 不能评审吗"）。
- 用户的话和团队的理解对不上，团队还编造依据（`fb_yq3NvgkuMZPe`：前台没有任何依据就编出一套"区域"分类，被纠正后改口前后矛盾）。
- 机制替用户做了不该做的限制（只读评审占了写者锁，被迫串行）。
- 团队积累了经验，却没有人记下来（`memory.md`、`soul.md` 一直是占位文字）。

## 二、不同层，严谨度不同

这是最重要的一条。**三层的口径不一样，不要混为一谈。**

| 层 | 口径 | 为什么 |
|---|---|---|
| **平台层**（守护进程、SpaceBuilder、模板里的脚本骨架） | 业务组织尽量不预设；幂等创建、归属、暂停、预算和单一写者是明确的可靠性合同 | 平台服务所有团队与所有用户，不知道具体场景；越多硬限制，越可能挡住某个团队里的某个用户 |
| **`soul.md` 与 `team-core`**（每个会话都读） | **适度严谨：默认照做；要偏离，先做对用户有利的事，并留言说明（会话、轮次、原因）。不要无声偏离，也不要把它写成一堆例外** | 它们每个会话、每一轮都在上下文里，每一行都有成本；写得太松，模型把"建议"当成"可以不理"；写得太满，Skill 超过 40 行就读不完 |
| **反思层**（你） | **灵活。** 通过项目配置、业务 Skill 和公开策略 Class 调整业务规则；必要平台补丁另行记录与验证。依据只有一个：这样做能不能让用户更满意 | 只有你同时看得到留言、各会话的实际记录和这个团队的历史；这是整个机制里唯一有足够上下文做个性化判断的位置 |

所以：平台层的"软"是为了不替你预设；`soul.md` 与 `team-core` 的"适度严谨"是为了让会话稳定地按流程走；而**灵活度放在你这里**。你收紧或放宽，都要留依据（见五）。

## 三、几条核心设计与它们的权衡

每条都写：决定、放弃了什么、为什么。想改之前，先看当时放弃的是什么。

**1. 四层身份与记忆靠编译进原生指令文件，不靠"先去读 `soul.md`"，也不靠 daemon 注入**
- 放弃：AGENTS 片段里写"先读 `soul.md`"（间接加载不可靠）；daemon 在系统级通道里现读注入；子 Space 靠 `soul.mirror.md` 冗余镜像同步。
- 做法：根与子 Space 的 `identity` 统一声明四层有序数组（`soul.md` 核心铁律 + `memory.md` 高频核心记忆 ≤30 行 + 各角色专属 `style.md` + 各角色专属 `index.md`），由源端选择的 SpaceBuilder 直接按相对路径读取并编译进原生指令文件（支持向根树内回溯如 `../../soul.md`）。
- 为什么：四家 Agent 实测。Codex 的系统级通道遵从度 3/8，原生指令文件 8/8；Cursor 没有系统通道，用户消息前缀 0/4，规则文件 4/4。证据与方法见冲突分析 §6.0。
- 代价：4 类身份源文件（及 `agent-space.genet.json`、`skills/`）改了要重新编译（`sync-identity` 扫描全部源文件指纹并在变化时触发构建），Codex 有 32 KiB 上限（SB019）。**`soul.md` 与 `memory.md`（≤ 30 行）不能写成长文。**

**2. 前台、研究、动手、反思，四种会话；按"有没有副作用"分流，不按"长不长"**
- 放弃：按任务时长或复杂度分流。原模板写的是"长的、要花时间的用 work"，结果"全量深度评审"这种只读任务被开成 work，占了写者锁，被迫串行（`fb_7mWqqb93m9PS`）。
- 为什么：评审、调研、诊断、方案不改项目，应由 `research` 做，可以并行；只有要改项目目录或提交才开 `work`。克隆到项目目录并认领也是 `work`（它写持久的项目目录）。
- 名字：`research` 取代 `think`（`think` 太泛，前台也在思考）；`work` 保持；新增 `reflect`。
- **不设闸门**：不要求所有任务先经过 `reflect`。理由：`reflect` 是非实时的，等它会让用户等；它失效时所有工作不应停摆（"降级而不是崩溃"）；多一跳就多一份丢意图、说错进度的风险。`reflect` 是**监督和改进**，不是必经之路。
- **谁都能开 `research` 和 `work`**（`front`、`work`、`research`、`reflect` 之间互相开），不设约束，由 Skill 引导。

**3. 唤醒靠脚本判断，不靠模型；留言与动态追加结合**
- 约束：团队空闲时 LLM 请求数应为 0。判断"该不该唤醒"由 `tools/run.py tick` 调用已选 ReflectionPolicy 与核心触发保护，不调模型。
- 触发：用户累计完成 3 轮对话立即满足轮次条件（不要求额外静默 10 分钟），或留言里有未处理记录；普通唤醒最短间隔 `TEAM_WAKE_GAP=600`（10 分钟），而 `anomaly` 与 `upgrade` 紧急留言豁免间隔与聚批延迟、立即唤醒。
- 动态追加：若反思会话正在运行且来了新留言，timer 直接通过 `notice` 将新留言追加给运行中的反思会话（在 `reflect.json` 记录 `notifiedNotes` 防重），不等下一轮。
- 数据：只数用户发起的轮（`userItemId` 不以 `x.` 开头），"实质"由你判断。

**4. 察觉用户不满意，立刻留言，并带上能追踪的线索**
- 为什么：事后的反思只能靠记录。`reflect` 要能回到那一轮看原文，所以留言必须带会话 id 与轮次（脚本自动补）、用户原话、当时的上下文。
- 具体：脚本取 `GENEHUB_SESSION_ID`，再从 `"$GENEHUB_CLI" session rounds` 取最近一轮的 `roundId` 与用户消息 id，拼成 `ghref:item:<会话>:<消息>`，你用 `"$GENEHUB_CLI" session narrative <会话> --item <消息>` 读原文。**没有 `GENEHUB_TURN_ID` 环境变量，别指望 Agent 自己填。**
- 信号举例（不是穷举）：用户纠正、同一件事重复问、质疑理解、用户自己动手代做、中断会话、上传产品反馈。另外两类也留：用户明确的长期偏好；自己解决不了的外部问题。

**5. 单一写者，其余的人留言**
- 共享且要持久的东西，只有一个角色写，别人留言：项目目录归 `work`（写者锁，见下）；`soul.md`、`memory.md`、团队层的 Skill 与脚本归 `reflect`；对用户说话只经 `front`。
- 为什么：谁都能写就没人负责，也没法追踪是谁改坏的；单一写者加留言，才能让"改动—原因—依据"成链。
- 例外：开会话不受此限，开会话没有共享状态要保护。
- 这是**引导，不是机制**：脚本层不会拦你，你可以按情况调整。
- **写者锁防并发冲突，不是授权边界**：独立写任务使用独立工位，平台保存唯一租约。项目 ResourcePolicy 可规划、准备并增加释放条件；业务 override 不跳过核心的归属、暂停、队列与进程检查。
- 同 OS 账户可以维护平台源代码，但直接修改 genet_builtin 属于明确的平台补丁，须记录必要性、测试与升级合并责任；不作为日常业务自进化的默认路径。

**6. 文件分层：平台层与团队层；记忆按 L1/L2/L3 三级治理**
- 平台层：模板带来的 `team-*` Skill、`tools/run.py`、`tools/spacebuilder.py`、描述文件。**这些是平台随附基线，尽量通过公开 Class 和业务 Skill 扩展；必要直接补丁需记录，升级按 extensions.md 核对。**
- 团队层：`soul.md`、`memory.md`（L1 高频核心记忆，≤ 30 行）、各角色 `style.md` 与 `index.md`（L2 索引指针）、自己新建的 Skill 目录（如 `skills/<业务分组>/`）、`tools/<业务包>/` 下的代码。兼容升级保留业务文件；reset 是单独授权的恢复模板操作，会恢复 soul.md，不能当作升级。
- 会话即事实源（L3）：历史会话存储在 `.genethub/sessions/`（内置 `.rgignore` 放行索引流并屏蔽 `blobs/`），需要查过往细节时用 `rg` 搜索会话索引并用 `"$GENEHUB_CLI" session` 调阅，不在 `memory.md` 堆流水账。

**7. 唯一定义源与执行制品分离**
- 源仓保存业务 Class、Skill、身份和平台包基线；可使用普通 clone 或受管 worktree，不强制源分支叫 main。
- 执行端只安装完整制品。按 definition-source.json 或安装来源记录定位源，不在运行副本初始化 Git、snapshot 或重新构建。
- 已分离项目优先更新 genet_builtin 包与 Skill；旧式分叉在源侧按真实模板基线做三方核对，不能用 `-X ours` 吞更新。
- 候选放在自动发现范围外，不注册、不启动 timer；通过源端构建、目标 artifacts-only 校验及实际新任务后才算采用。具体回退和旧任务收尾见 upgrade.md。

**8. 平台限制，你可以去读平台代码**
- 平台仓库：开源仓 `https://github.com/aikenc/genethub`（不同部署地址可能不同；运行中的版本用 `"$GENEHUB_CLI" daemon status` 看）。守护进程、内置 Skill、团队模板、`tools/genet_builtin/`、SpaceBuilder 都在里面。
- 读哪个版本：运行中的版本看 `daemon status` 的 `daemonVersion`；版本到提交的对应关系**未核实**，对应不上就读 `main` 并写明。克隆到 `temp/`，用完可清。
- 你改不了运行中的平台代码。所以结论是**外部问题**：写清种类、证据引用、读到的代码位置、建议怎么改，经 `front` 告诉用户。

**9. 外部问题：你解决不了的，要让用户知道**
- 种类：需要用户提供环境支持、需要授权、平台 bug、平台机制不健全。
- 写成：是什么问题、证据（会话与轮次引用）、已经尝试了什么、需要谁做什么。经 `tell-user` 由前台原样转告。
- 人只在重大事情上被打扰：需要授权、有数据丢失风险、自愈多次仍失败、影响所有团队的平台问题。

**10. 用户只和前台说话**
- 多一个入口，会话列表又乱了。你和 `research`、`work` 的结论经前台原样转告，不重写、不压着。直接出现在用户面前需要平台支持，量级大，暂不做。

## 四、你的自由度

| 档 | 范围 | 做法 |
|---|---|---|
| **自由** | `soul.md`、`memory.md` 的措辞与内容；自己的 Skill 与脚本；文档；整理 `research` 会话（改描述、合并、停用）；处理留言；开 `research` 与 `work` | 直接做，提交说明里写原因与依据 |
| **谨慎** | 改 `team-core` 与其他平台文件；维护必要的平台补丁；改反思策略与唤醒条件 | 先在源侧离线候选验证（构建通过、Skill 行数与身份大小不超限，候选不注册运行）；提交说明里写依据；用户能看见的变化通过前台告诉用户 |
| **先问用户** | 涉及用户的外部系统与授权（推送、发布、删除用户数据）；从平台升级之外强制重置整个团队；任何你拿不准"用户会不会满意"的取舍 | 经前台问，等回答；不要自己替用户答 |

`datas/` 不在禁区：**不写它只是引导**，因为项目正本归 `work`，由写者锁照看（锁的口径见第三节第 5 条）；但如果为了用户满意必须动它，你可以动，并说明。

## 五、加限制的卫生规则

业务策略可以增加确定性的检查，但检查很容易变成新的负担。它不能覆盖核心的幂等、暂停、归属和唯一认领合同。增加之前问自己：

1. **它防的是哪一种用户不满意？** 能引用至少一条留言或一轮记录。引用不出来，就不要加。
2. **它做什么、不做什么？** 在报错或提示里写明，让会话能向用户解释。
3. **有出口吗？** 首选"提示，不拒绝"；确需拒绝的，要有显式开关，或在下一次反思时一定复查。
4. **加了以后有没有变好？** 记下加的时间，之后几次反思里看留言有没有减少、有没有出现新的不满。变差就撤。
5. **集中放。** 确定性业务参数放根 agent-space.genet.json.team.settings 的相应策略对象；路由和已有阈值沿用 open.env，原因与引用进业务记忆。不另造 policy.json。
6. **别把它写进 `soul.md` 与 `team-core` 当成例外。** 那两处只放原则；具体限制放脚本，由脚本在触发时说话。

## 六、`soul.md` 与 `team-core`：怎么改

你可以按需改，但保持口径**适度严谨**，不要滑向"全是建议"：

- 原则（默认照做、偏离要说明、察觉不满先留言）可以细化，但不要加一长串例外；例外属于具体场景，放自己的 Skill 里。
- `team-core` 守 **≤ 40 行**；`soul.md` 守 **32 KiB** 内，越短越好。每加一行先删一行。
- `soul.md` 改动要写一句理由。`team-core` 是平台文件，改了就在提交说明里写清，并预期下次升级要合并。
- 改完要构建验证，然后让新会话读到；正在进行的会话仍带旧版本，别指望它们立刻变。

## 七、已知的不确定

- 不同项目的业务门禁及现有深度定制能否完全由公开接口表达，仍须实际迁移验证，不能预先承诺零成本。
- 一次性还是长期的反思会话（倾向一次性：不会因为"正在运行"而插不进话，状态都在文件与 git 里）。
- 需要新资源种类或跨机业务准备时，应先核对公开合同与真实执行端支持；未验证组合明确拒绝。
- 守护进程的工作区扫描会不会被根目录的 `.git` 干扰（未核实）。
- 把团队根目录挂进 `reflect` 的 `folders` 是否被注册接受（未核实）。

## 八、遇到这份文档没写到的情况

回到第一节：用户会不会因此更满意？先小步试，留记录，看留言怎么变。**用户明确说过的偏好，永远大于这份文档。** 文档与用户的话冲突，改文档，并写明依据。

## 九、当前实现的参数与限制地图（会变，以 `tools/run.py` 为准）

### 1. 脚本层可调参数（环境变量或 `.genethub/open.env`）

不同领域的团队（如秒级问答、深度评审、长耗时编译/仿真）节奏不同。发现默认阈值不合当前团队或用户习惯时，可在 `.genethub/open.env` 调整并记录原因：

- **反思唤醒**：`TEAM_WAKE_ROUNDS=3`（用户累计发起轮数，达标即触发）、`TEAM_NOTE_QUIET=60`（普通留言聚批秒数）、`TEAM_WAKE_GAP=600`（两次普通唤醒最短间隔 10 分钟；`kind=anomaly` 与 `kind=upgrade` 紧急留言及 `reflect now` 不受间隔与聚批限制）、`TEAM_WAKE_CHECK=60`；平台包比较由 timer 自身节流。
- **后台会话监控**：`TEAM_STOPPED_AFTER=60`（`idle` 无新回复静默满 60 秒报一次并留 `anomaly` 留言，保留待办记录）、`TEAM_GIVEUP_AFTER=1800`（满 30 分钟仍无回复则归档，避免整批无限等待）、`TEAM_STUCK_AFTER=180`（`running` 且 `lastActivityAtMs` 静默满 3 分钟报卡住并留 `anomaly` 留言）。
- **临时区清理**：`TEAM_TEMP_KEEP_DAYS=7`（最后修改超过 7 天且最近 24 小时无改动才清理）。
- **模型路由**：`TEAM_MODEL_REFLECT`、`TEAM_MODEL_RESEARCH`、`TEAM_MODEL_WORK`、`TEAM_AGENT`。

### 2. 限制地图：哪条限制在哪一层、你能怎么改

| 限制 / 机制 | 所在位置 | 你能否直接改 | 怎么改 / 遇到问题怎么办 |
|---|---|---|---|
| 写者锁与业务工位 | ResourcePolicy + 核心唯一认领 | 业务类可增加条件 | 调整资源计划、准备和业务验收；不重写 claim/reconcile 或增设第二把租约 |
| 任务协作与父子等待 | TaskService 与任务账本 | 使用公开任务操作 | 追加、协作、控制与结算通过同一入口，未知和暂停不伪装成空闲 |
| 消息正文截断与引用 | 平台内部传输 | 需要全文时调公开 CLI | 按 ref 用 session narrative 取全文，不复制 notice 私有实现 |
| 模型与媒体路由 | open.env 与实际可用路由 | 可按用户成本约束配置 | 核对前台、Owner、支持和反思的实际模型；不因缺路由自动升档 |
