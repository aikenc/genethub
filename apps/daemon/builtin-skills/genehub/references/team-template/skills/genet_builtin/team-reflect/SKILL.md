# 团队反思与进化

首要提升用户满意度，其次提升团队工作质量，并对自身工作质量负责。按本轮信号读消息里的简报（≤5,000字符），再沿卡、留言编号或 ghref 取相关证据，不扫描全队历史。背景见 references/rationale.md。

团队根用 `run.py path root` 核对；带 `.spacebuilder/output-lock.json` 的是执行制品，在唯一定义源维护、构建和部署，执行端验证。业务文件、身份、原任务和回执保留。

1. **按优先级核对信号**：先用户不满、纠偏和真实拒收，再红线/警告与失分，同时检查自身重复唤醒。沿原 ref 读原文和原生状态；用户明确暂停/取消和来源未知的暂停不自动解除，客观局部阻塞与“未收到用户意见”分开。
2. **把工作还给负责方**：交付本身由 Owner 修；目标未达、整体授权与预算有效且没有可执行工作时，沿原需求把具体差距直接交给长期目标 Owner 组织下一轮，不让前台再次派目标。阶段已结算、无新用户消息或 activeGoalMs=0 都不证明原需求消失。
3. **只改能改变行为的原因**：本队工作方式用公开扩展合同维护，见 team-core references/extensions.md；不复制调度器或增加处置台账。平台原因写入本队平台归因通道，尽量绕行并继续其它可做项，不假设有人接手或等待回应。
4. **同一事实只处理一次**：同一指纹不变不再唤醒，严重度或事实实质变化再处理；自己的报告、记忆和提交不成为新信号。没有新信号就等待，不因整点、回合数或迭代结算例行巡查。
5. **有改动就验证效果**：说明针对哪个信号、预期哪个变化、在哪次同类交付或自然卡复验；无效就撤回或换方案。身份运行 `run.py sync-identity`，运行包由源端构建、执行端 `verify --artifacts-only`，实际采用另核；只提交本轮已验证改动，保留他人未提交成果。Skill≤40行、编译指令≤32KiB。
6. **记忆只按复发沉淀**：同一教训至少两次独立发生且有 ghref 才更新岗位 index.md；跨角色高频教训再进根 memory.md（≤30行）。不重复已有规则，细节留原会话。
7. **无动作就结束原信号**：只 `run.py notes done <编号> --result "<依据与原因>"`，不写报告、不 snapshot、不更新记忆、不发“已巡查”。有动作也在原项留改动和验收；不把可继续的升级维护核销给下一次反思。

质量卡只读；正式、暂定与未知分开，原始证据和历史卡保留。红线按本小时事实自动归档，失格与连续计数归零，不人工解除、不另开测量窗口，用户验收另判，见 team-core references/quality.md。

团队原因由 Owner/反思处理；平台归因仅写本队记录，不是产品内接手岗位。归因错误才沿原实例用 quality triage 更正，保留旧依据；不增加审批或解除步骤。

升级自动选最新版，已采用或等待不唤醒；只处理实际冲突和测试失败。复用原维护项和已完成回执，继续审阅、合并、构建与验证，见 references/upgrade.md；确需等外部事实时记录原承接，不重做已完成阶段。
